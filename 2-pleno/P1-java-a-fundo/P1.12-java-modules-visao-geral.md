# P1.12 — Java Modules (visão geral)

> ⏱️ ~1h30 · 🔵 Pleno · Pré-requisitos: P1.01 (classloading), J1.16 (pacotes e modificadores de acesso), J0.02 (JDK, `pom.xml`)

É **visão geral**, como pede a trilha: o PayFlow **não** usa `module-info.java` (veja a decisão na seção "Trade-offs"). Nenhum conteúdo do PayFlow foi compilado.

## 🎯 Objetivos
Ao final desta aula você consegue:
- **Explicar** o que o **sistema de módulos (JPMS, Java 9)** resolve: **encapsulamento forte** e **dependências explícitas**.
- **Ler** um `module-info.java` (`requires`, `exports`, `opens`, `uses`/`provides`) e **prever** o que compila e o que quebra.
- **Distinguir** *classpath* (módulo sem nome) de *module path*, e **entender** por que `--add-opens` aparece ao atualizar o JDK.
- **Usar** `jdeps` e `jlink` para descobrir as dependências e gerar um *runtime* enxuto.
- **Decidir** se um projeto precisa de módulos (e por que o PayFlow não).

## 🤔 Por que isso importa
Você **não vai escrever** `module-info.java` no dia a dia de um serviço Spring. Mas **vai esbarrar** em módulos: o JDK é modular; `java.lang.reflect.InaccessibleObjectException: … does not "opens java.lang"` aparece ao subir de versão com uma biblioteca antiga; imagens de contêiner enxutas usam `jlink`; e a pergunta "o que são módulos do Java e por que existem?" é recorrente em entrevistas de pleno.

## 💡 Intuição (explicação simples)
Até o Java 8, um `.jar` era uma **caixa aberta**: qualquer classe **pública** de qualquer jar era acessível por todos (inclusive as **partes internas** que o autor nunca quis expor), e as dependências eram só "o que estiver no classpath". Um **módulo** é um **prédio com portaria**: ele declara **o que oferece** (`exports`: as salas abertas ao público), **de quem depende** (`requires`: com quem tem contrato) e **o que mantém trancado** (todo o resto, **mesmo as classes `public`**). Quem tenta entrar por uma porta que não foi declarada **leva um erro** (em compilação ou em execução), em vez de depender, sem saber, de um detalhe interno.

## 🔬 Como funciona por dentro
- **`module-info.java`**, na raiz do código-fonte do módulo, descreve o módulo:
```java
module payflow.ledger {
    exports com.payflow.ledger;          // API pública; o pacote .internal NÃO é exportado
}
module payflow.app {
    requires payflow.ledger;             // dependência explícita
    requires payflow.fee.spi;
    uses com.payflow.fee.FeePolicy;      // vai procurar implementações (ServiceLoader)
}
module payflow.fee.flat {
    requires payflow.fee.spi;
    provides com.payflow.fee.FeePolicy with com.payflow.fee.flat.FlatFee;   // oferece uma implementação
}
```
| Diretiva | Significado |
|---|---|
| `requires m` | depende do módulo `m` (a JVM **resolve o grafo** na partida e falha se faltar) |
| `requires transitive m` | quem requer **este** módulo também **enxerga** `m` |
| `exports p` / `exports p to m` | **pacote** `p` acessível a todos / só ao módulo `m` (*qualified export*) |
| `opens p` | permite **reflexão profunda** (`setAccessible`) em `p` em tempo de execução (frameworks: Spring, Hibernate, Jackson) |
| `uses S` / `provides S with I` | **serviços**: acoplamento fraco por interface, resolvido por `ServiceLoader` |
- **Encapsulamento forte:** classes `public` de pacotes **não exportados** são **inacessíveis** fora do módulo, **inclusive por reflexão** (a menos que `opens`). Antes dos módulos, `public` era "público para todo o classpath".
- **Classpath × module path:** no **classpath** (o que o `java -jar` e o Spring Boot usam), tudo vai para um **módulo sem nome** (*unnamed module*) que **enxerga e é enxergado por tudo**; os JARs **não** têm encapsulamento nem dependências verificadas. No **module path**, cada módulo é **nomeado**, com `module-info`, e as regras acima valem. Um JAR **sem** `module-info` no module path vira **módulo automático** (exporta tudo, requer tudo): ponte para migrar.
- **O próprio JDK é modular** (`java --list-modules` mostra **69** módulos nesta instalação): `java.base` (`String`, `List`, `java.time`…), `java.sql`, `java.net.http` (o `HttpClient` **não** está em `java.base`: a P1.11 mostrou o erro). **A partir do Java 16/17 o encapsulamento das **partes internas do JDK** é forte por padrão** (JEP 396, 403, conferidos): reflexão em `String.value`, `sun.misc.*` etc. **falha**, e é o motivo dos `--add-opens` quando uma biblioteca antiga é executada num JDK novo.
- **Ferramentas:** `jdeps` (analisa **dependências** de módulos/JARs), `jlink` (monta um **runtime personalizado** só com os módulos necessários), `jmod`, `java --describe-module m`, `java --list-modules`.

## 🛠️ Exemplo prático
> Em `lab/jvm-lab/modules-lab/src/` há quatro módulos: **`payflow.ledger`** (exporta `com.payflow.ledger`; esconde `com.payflow.ledger.internal`), **`payflow.fee.spi`** (a interface `FeePolicy`), **`payflow.fee.flat`** (uma implementação) e **`payflow.app`** (a `Main`). Todos os comandos da pasta `lab/jvm-lab/`.

### A. Compilar e rodar
```bash
O=$(mktemp -d)
javac -d $O --module-source-path modules-lab/src --module payflow.app,payflow.fee.flat
java -p $O --add-modules payflow.fee.flat -m payflow.app/com.payflow.app.Main
```
```text
fee(100.00) = 1.50
módulo desta classe: module payflow.app | nomeado? true
implementações de FeePolicy encontradas: 1
  flat -> 2.00
```
`Ledger.fee` usa a classe interna `Rounding` (arredondamento `HALF_EVEN`, decisão 4): `100.00 × 0,015 = 1,50`. A `Main` descobre a `FeePolicy` por `ServiceLoader`. **Sem** `--add-modules payflow.fee.flat`, o módulo provedor **não entra no grafo** (ninguém o `requires`): o resultado é **0** implementações (executado):
```text
implementações de FeePolicy encontradas: 0
```
**Aviso:** é exatamente o tipo de "funciona aqui, falha lá" que serviços causam; módulos de **plugin** são adicionados com `--add-modules` (ou por `jlink --bind-services`).

### B. O encapsulamento forte em ação
Em `payflow.app`, tentando usar a classe **interna** do `payflow.ledger`:
```java
public class Bad { Object x = new com.payflow.ledger.internal.Rounding(); }
```
```text
modules-lab/src/payflow.app/com/payflow/app/Bad.java:2: error: package com.payflow.ledger.internal is not visible
public class Bad { Object x = new com.payflow.ledger.internal.Rounding(); }
                                                    ^
  (package com.payflow.ledger.internal is declared in module payflow.ledger, which does not export it)
```
Erro **em compilação**, apesar de `Rounding` ser `public`. E por **reflexão** (`Main` com argumento):
```text
classe achada: class com.payflow.ledger.internal.Rounding
Exception in thread "main" java.lang.IllegalAccessException: class com.payflow.app.Main (in module payflow.app) cannot access class com.payflow.ledger.internal.Rounding (in module payflow.ledger) because module payflow.ledger does not export com.payflow.ledger.internal to module payflow.app
```
`Class.forName` **acha** a classe, mas **usá-la** falha em execução com a mensagem **exata** do que corrigir (`exports`/`opens`).

### C. O mesmo no JDK: o `--add-opens`
```java
Field f = String.class.getDeclaredField("value");
f.setAccessible(true);          // tenta violar o encapsulamento do java.base
```
```text
$ java ReflectJdk.java
java.lang.reflect.InaccessibleObjectException: Unable to make field private final byte[] java.lang.String.value accessible: module java.base does not "opens java.lang" to unnamed module @15d9bc04

$ java --add-opens java.base/java.lang=ALL-UNNAMED ReflectJdk.java
acessou String.value: 3 bytes
```
Esta é a mensagem que você vai ver ao **subir de JDK** com uma biblioteca que usa reflexão em classes do JDK. A saída de curto prazo é `--add-opens` (no `JAVA_TOOL_OPTIONS` do contêiner, J9); a de longo prazo é **atualizar a biblioteca**. Trate cada `--add-opens` como **dívida técnica** (S7).

### D. `jdeps`: o que o meu código realmente usa
```bash
jdeps -s --module-path $O --module payflow.app
```
```text
payflow.app -> java.base
payflow.app -> payflow.fee.spi
payflow.app -> payflow.ledger
```
Para um *JAR* do PayFlow (J10) o comando `jdeps --print-module-deps app.jar` lista os módulos do JDK necessários (útil para o `jlink`, abaixo). **Não executado** no PayFlow: o Spring Boot empacota em *fat JAR* aninhado; para o `jdeps` use o JAR **extraído** (J9: `extract --layers`).

### E. `jlink`: um *runtime* só com o que preciso
```bash
jlink --module-path $O --add-modules payflow.app,payflow.fee.flat --output rt --strip-debug --no-header-files --no-man-pages
rt/bin/java --list-modules
rt/bin/java -m payflow.app/com.payflow.app.Main
```
```text
java.base@25.0.5.0.3
payflow.app
payflow.fee.flat
payflow.fee.spi
payflow.ledger
fee(100.00) = 1.50 ...
  flat -> 2.00
```
O *runtime* personalizado tem **5 módulos** (só `java.base` do JDK, contra os **69** da instalação completa) e ocupou **55 MiB** (somando tudo, **sem os arquivos `.debuginfo`** de símbolos de depuração que a distribuição Ubuntu inclui e que somam centenas de MiB: ignore-os nesta comparação; a parte principal, `lib/modules`, tem **25 MiB**). A instalação completa do mesmo JDK, também sem `.debuginfo`, tem ~**583 MiB**. Para **um** serviço Spring Boot, o `jlink` exige que **todas** as dependências (inclusive transitivas e *automatic modules*) sejam resolvíveis; é **mais trabalho** e raramente compensa frente a `eclipse-temurin:25-jre-alpine` (J9) ou a camadas bem feitas. Recurso útil em ferramentas de linha de comando, aplicativos desktop e imagens mínimas.

## 🧠 Pausa para lógica
**Enunciado:** o módulo `payflow.ledger` exporta `com.payflow.ledger` e esconde `com.payflow.ledger.internal`. Um colega quer usar `Rounding.money(...)` em `payflow.app`. (a) Dê **duas** soluções **sem** exportar o pacote interno para todo o mundo. (b) Qual delas é a **melhor** do ponto de vista de design?

<details><summary>Dica</summary>Exportar para **um** módulo específico; ou **promover** a funcionalidade à API pública.</details>
<details><summary>Solução</summary>

(a) 1) *Qualified export*: `exports com.payflow.ledger.internal to payflow.app;` (só `payflow.app` enxerga). 2) **Expor** a operação na API pública (`Ledger.round(BigDecimal)` em `com.payflow.ledger`, delegando ao `Rounding`). (b) A **2ª**: o **pacote interno continua livre para mudar** sem quebrar ninguém; a 1ª cria um **acoplamento** entre módulos que o encapsulamento existe justamente para evitar. Regra: **exporte contratos, não implementações.**
</details>

**Variação:** o que acontece se `payflow.app` fizer `requires payflow.ledger;` mas o `Ledger` devolver um tipo de `payflow.fee.spi` na assinatura pública e o `payflow.app` **não** fizer `requires payflow.fee.spi`? (Dica: `requires transitive`.)

## ⚖️ Trade-offs e quando NÃO usar
- **O PayFlow roda no *classpath* e **não** terá `module-info.java`.** Motivos: o Spring Boot, o Hibernate, o Jackson e o Flyway fazem **reflexão e carregamento dinâmico** intensos (precisariam de `opens`/`--add-opens` em tudo); o **fat JAR** do Spring Boot é aninhado e **não** é um módulo; e o ganho (encapsulamento) vem, no nível da aplicação, de **outro** mecanismo mais adequado: **Spring Modulith e ArchUnit** (P4), que verificam as **fronteiras entre módulos de domínio** dentro do mesmo JAR.
- **Quando vale usar JPMS:** **bibliotecas** reutilizáveis (para garantir que o código interno não vaze), **ferramentas** de linha de comando/desktop distribuídas com `jlink`, e plataformas de *plugins*. **Quando não vale:** aplicações Spring/Jakarta EE típicas.
- **Dois níveis de "módulo" que não se confundem:** *módulo Java* (JPMS, **tempo de compilação/linkagem**, na JVM) × *módulo de domínio* (P4: pacotes e regras de dependência verificadas por teste). Você **pode** ter o segundo sem o primeiro.
- **Módulos automáticos e dependências "não modulares"** (a maioria do ecossistema) tornam a migração dolorosa: é um **custo real**.

## ⚠️ Erros comuns e boas práticas de produção
- **`InaccessibleObjectException: … does not "opens …"` ao atualizar o JDK:** biblioteca antiga com reflexão em classes do JDK. **Atualize a biblioteca** primeiro; `--add-opens` é **paliativo** (registre como dívida).
- **`--illegal-access`:** a opção que **liberava** o acesso no Java 9–15 foi **removida** no 17: não adianta procurá-la em guias antigos.
- **`NoClassDefFoundError`/`module not found` ao rodar um módulo sozinho:** o grafo de módulos não incluiu uma dependência (`requires` faltando) ou um **provedor** de serviço (seção A: `--add-modules`).
- **Pacote dividido entre módulos** (*split package*: o mesmo pacote em dois módulos): **proibido** no module path (erro de resolução).
- **Esperar que `public` signifique "acessível a todos":** em módulo, só se o pacote for **exportado**.
- **Gerar imagem com `jlink` e esquecer os módulos usados por reflexão** (o `jdeps` **não vê** `Class.forName("...")`): a aplicação quebra em execução. Teste a imagem **de verdade** (P7/P8).
- **Misturar** `--add-opens` espalhados em vários scripts: **centralize** em um lugar documentado (`JAVA_TOOL_OPTIONS`, `compose.yaml`) com o **motivo**.

## 🎤 Na entrevista
- **O que são módulos do Java (JPMS) e que problema resolvem?** Agrupam pacotes com um `module-info.java` que declara **dependências** (`requires`) e **API pública** (`exports`); o que não é exportado é **inacessível**, mesmo sendo `public` (encapsulamento forte), e o grafo é verificado na partida (*reliable configuration*).
- **Qual a diferença entre classpath e module path?** O classpath junta tudo em um **módulo sem nome** sem encapsulamento nem verificação de dependências; o module path usa módulos **nomeados**, com regras de visibilidade e grafo resolvido.
- **Por que aparece `--add-opens` ao atualizar o JDK?** O JDK passou a **encapsular fortemente** seus pacotes internos (a partir do Java 16/17); bibliotecas que usam reflexão neles precisam que o módulo seja *aberto*.
- **O Spring Boot usa módulos Java?** Aplicações Spring Boot em geral rodam no **classpath** (módulo sem nome); o ecossistema depende de reflexão, e o *fat JAR* não é modular.
- **Para que servem `jdeps` e `jlink`?** `jdeps` analisa dependências; `jlink` monta um *runtime* mínimo com apenas os módulos necessários.
