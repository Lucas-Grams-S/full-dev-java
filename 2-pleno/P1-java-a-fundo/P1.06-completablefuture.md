# P1.06 — `CompletableFuture`

> ⏱️ ~1h30 · 🔵 Pleno · Pré-requisitos: P1.05, J1.13 (lambdas), J1.14 (`Optional`), J6.08 (`RestClient` e *timeouts*)

> ⚠️ **Verificação:** executado de verdade em `lab/jvm-lab/Futures.java` (JDK 25.0.5). O "câmbio" é **simulado** com `Thread.sleep` (não há chamada de rede). Saídas reais abaixo; os tempos oscilam ±10 ms. O PayFlow não foi compilado.

## 🎯 Objetivos
Ao final desta aula você consegue:
- **Compor** operações assíncronas (`supplyAsync`, `thenApply`, `thenCompose`, `thenCombine`, `allOf`, `anyOf`) sem bloquear a thread chamadora.
- **Tratar** erros (`exceptionally`, `handle`) sabendo **quando** a exceção vem embrulhada em `CompletionException`.
- **Impor** prazos (`orTimeout`, `completeOnTimeout`) e **explicar** por que `cancel()` **não** interrompe o trabalho.
- **Escolher** o *executor* certo e **evitar** esgotar o `ForkJoinPool.commonPool()` com tarefas bloqueantes.

## 🤔 Por que isso importa
O endpoint de **saldo convertido** (J6.08) chama um provedor de câmbio externo. Se amanhã o PayFlow precisar **consultar 3 provedores** e usar o mais rápido (ou a média), chamá-los **um após o outro** triplica a latência. `CompletableFuture` é a ferramenta clássica do Java para **disparar vários trabalhos independentes e combinar os resultados** — e é onde a maioria dos bugs de concorrência "de aplicação" nasce: erro engolido, pool errado, *timeout* ausente.

## 💡 Intuição (explicação simples)
Você pede **três orçamentos** a três lojas. Em vez de ir a uma, esperar, depois ir à outra (sequencial), você **liga para as três ao mesmo tempo** e anota num caderno: "quando o orçamento da loja A chegar, multiplique por 830; quando os três chegarem, tire a média". O **caderno** é o `CompletableFuture`: uma **promessa com instruções pendentes** (`thenApply`, `thenCombine`) que disparam sozinhas quando o valor chega. Você só "para e espera" (`join`) no último instante, ou nunca (se entregar o caderno a outro).

## 🔬 Como funciona por dentro
- `CompletableFuture<T>` é um `Future` **que você pode completar** (`complete`, `completeExceptionally`) e que aceita **etapas dependentes** (`CompletionStage`): cada `thenXxx` cria **outro** futuro que depende do anterior (uma árvore/lista de callbacks), sem bloquear.
- **Família de métodos** (decore o padrão: *o que faz* + `Async` opcional):

| Método | Equivale a | Quando |
|---|---|---|
| `supplyAsync(() -> v, ex)` / `runAsync(r, ex)` | `submit` | iniciar o trabalho |
| `thenApply(f)` | `map` | transformar o resultado (síncrono) |
| `thenCompose(f)` | `flatMap` | `f` devolve **outro** `CompletableFuture` (evita `CF<CF<T>>`) |
| `thenCombine(outro, f)` | "e" | juntar **dois** independentes |
| `thenAccept(c)` / `thenRun(r)` | `forEach` | consumir sem devolver valor |
| `allOf(...)` / `anyOf(...)` | "todos" / "o primeiro" | juntar **N** (`allOf` devolve `Void`) |
| `exceptionally(f)` / `handle(f)` / `whenComplete(c)` | `catch` / `catch+finally` | erros |
| `orTimeout(t)` / `completeOnTimeout(v, t)` | prazo | Java 9+ |

- **Em que thread cada etapa roda?** `thenApply` roda **na thread que completou** o estágio anterior (ou, se já estava completo, **na thread que chamou `thenApply`**: provado abaixo). As variantes `…Async` **agendam** a etapa no executor (por padrão `ForkJoinPool.commonPool()`, ou o que você passar).
- **O pool padrão é o `commonPool`:** `supplyAsync(supplier)` **sem** executor usa o `ForkJoinPool.commonPool()`, de tamanho ≈ **núcleos − 1** (11 nesta máquina). Foi desenhado para **CPU-bound**; tarefas **bloqueantes** (I/O, `sleep`) o **esgotam** e travam **toda** a JVM que o compartilha (inclusive *streams* paralelos).
- **Erros:** uma exceção numa etapa **completa o futuro excepcionalmente** e **pula** as etapas dependentes até um `exceptionally`/`handle`. `join()` lança `CompletionException`; `get()` lança `ExecutionException`; ambos com a **causa** real em `getCause()`.

## 🛠️ Exemplo prático
> `lab/jvm-lab/Futures.java`: `java Futures.java <chain|fanout|errors|timeout|pitfall|median>`. O "provedor de câmbio" é `rate(provider, millis, fail)`: dorme, e devolve `5.10 + 0.0N` (N = tamanho do nome) ou lança `IllegalStateException("<provedor> fora do ar")`.

```java
static final ExecutorService IO = Executors.newFixedThreadPool(8, r -> { Thread t = new Thread(r, "io-" + System.nanoTime() % 1000); t.setDaemon(true); return t; });
```

### A. Encadear
```java
CompletableFuture<String> cf = CompletableFuture
        .supplyAsync(() -> rate("ecb", 100, false), IO)                       // 1) assíncrono
        .thenApply(r -> new BigDecimal("830.00").multiply(r))                   // 2) transforma (map)
        .thenCompose(v -> CompletableFuture.supplyAsync(() -> v.setScale(2, RoundingMode.HALF_EVEN), IO))   // 3) outro futuro (flatMap)
        .thenApply(v -> "saldo convertido = " + v);
System.out.println("(main não bloqueou: isDone=" + cf.isDone() + ")");
System.out.println(cf.join());
```
```text
(main não bloqueou: isDone=false)
saldo convertido = 4257.90
```
`isDone=false` **imediatamente**: a cadeia foi montada e a thread seguiu. Só o `join()` bloqueia. (Dinheiro continua em `BigDecimal` com `HALF_EVEN`, decisão 4: `830.00 × 5.13 = 4257.90`.)

### B. Disparar vários e combinar (*fan-out/fan-in*)
```java
var a = CompletableFuture.supplyAsync(() -> rate("ecb", 300, false), IO);
var b = CompletableFuture.supplyAsync(() -> rate("bcb", 500, false), IO);
var c = CompletableFuture.supplyAsync(() -> rate("xe",  400, false), IO);
CompletableFuture.allOf(a, b, c).join();                                       // espera as três (em paralelo)
```
```text
allOf: ecb=5.13 bcb=5.13 xe=5.12 em 505 ms (sequencial seria ~1200 ms)
anyOf: 5.16 em 202 ms
thenCombine: média=5.1300 em 502 ms
```
`allOf` leva o tempo da **mais lenta** (500 ms), não da soma (1 200 ms). `anyOf` devolve a **primeira** a completar (200 ms: a rápida) — mas as **outras continuam rodando** (veja `cancel` adiante). `thenCombine` junta **duas** e faz a média com `divide(TWO, 4, HALF_EVEN)`.

### C. Erros: onde "aparecem" e como tratá-los
```text
join():  CompletionException -> causa java.lang.IllegalStateException: bcb fora do ar
get():   ExecutionException -> causa java.lang.IllegalStateException: bcb fora do ar
exceptionally: 5.00
handle:        falhou: CompletionException/bcb fora do ar
cadeia:        tratado no fim
allOf falhou: bcb fora do ar; o outro já terminou? true (o allOf só completa quando TODOS completam)
```
Pontos:
1. A **mesma** falha chega como `CompletionException` (`join`) ou `ExecutionException` (`get`): **sempre desembrulhe `getCause()`**.
2. No `handle((v, ex) -> …)` o `ex` pode vir **embrulhado** em `CompletionException` (como acima): `ex.getCause().getMessage()`. Em `exceptionally`, idem. **Não compare `ex instanceof IllegalStateException`** sem desembrulhar.
3. **O erro atravessa a cadeia:** o `thenApply` do meio **não rodou** (nem imprimiu); o `handle` final tratou. Por isso um erro **no começo** não precisa de `try/catch` em cada etapa.
4. `allOf` **espera todos**, mesmo quando um falha cedo; só então completa excepcionalmente. Para "falhar rápido" use `anyOf` com cuidado, ou a *structured concurrency* (P1.10), que cancela os irmãos.
5. `exceptionally(ex -> valorPadrão)` **transforma** o erro em dado: para câmbio pode ser ok (cache da última cotação); para **dinheiro** é perigoso — **nunca** devolva um "valor padrão" que parece verdadeiro e vire um saldo ou uma cobrança.

### D. Prazos e cancelamento
```java
var slow = CompletableFuture.supplyAsync(() -> rate("lento", 2000, false), IO).orTimeout(300, TimeUnit.MILLISECONDS);
var withFallback = CompletableFuture.supplyAsync(() -> rate("lento", 2000, false), IO).completeOnTimeout(new BigDecimal("5.00"), 300, TimeUnit.MILLISECONDS);
```
```text
orTimeout: TimeoutException após 303 ms
completeOnTimeout: 5.00
cancel(true) -> true, isCancelled=true
  a tarefa cancelada continuou até o fim
```
`orTimeout` **completa o futuro** com `TimeoutException` em ~300 ms, **sem** esperar os 2 000 ms. **Mas**: `cancel(true)` num `CompletableFuture` **não interrompe** a thread que está executando a tarefa (diferente do `FutureTask`): ela **continua até o fim** ("a tarefa cancelada continuou até o fim"), consumindo CPU/conexão. O prazo vale para **quem espera**; **o trabalho** só acaba se a tarefa **cooperar** (consultar `Thread.interrupted()` ou usar um *timeout* de rede, `readTimeout`, J6.08). Em outras palavras: *timeout* no `CompletableFuture` **não substitui** *timeout* na chamada HTTP.

### E. A armadilha do `commonPool` e quem executa cada etapa
```bash
java Futures.java pitfall
```
```text
commonPool parallelism = 11, núcleos = 12
22 tarefas bloqueantes de 500 ms no commonPool: 1006 ms
as mesmas com um pool próprio de 22 threads: 503 ms
thenApply rodou em: io-N
sobre futuro já completo, rodou em: main
```
O `commonPool` tem 11 threads: 22 tarefas de 500 ms levaram **2 ondas (≈ 1 s)**; com pool próprio de 22 threads, **1 onda (≈ 0,5 s)**. Em produção, o `commonPool` é **compartilhado com todos os *streams* paralelos e outros `CompletableFuture`** da JVM: uma tarefa **bloqueante** lá pode **derrubar partes não relacionadas** do sistema. **Regra: sempre passe um `Executor` explícito em tarefas que bloqueiam.** (E a última linha: `thenApply` sobre um futuro **já completo** roda na **thread chamadora**, `main`: não presuma onde a etapa executa.)

## 🧠 Pausa para lógica
**Enunciado:** escreva `convertedBalance(BigDecimal balance)` que consulta **três provedores em paralelo**, descarta os que **falham ou passam de 400 ms**, e devolve a **mediana** das cotações que sobraram (ou lança `IllegalStateException` se sobrarem menos de 2).

<details><summary>Dica</summary>Para cada provedor: `supplyAsync(..., IO).orTimeout(400ms).handle((v, ex) -> ex == null ? Optional.of(v) : Optional.empty())`. Depois `allOf` e filtre os presentes.</details>
<details><summary>Solução</summary>

```java
static BigDecimal median(List<BigDecimal> xs) {
    var s = xs.stream().sorted().toList();
    int n = s.size();
    return n % 2 == 1 ? s.get(n / 2) : s.get(n / 2 - 1).add(s.get(n / 2)).divide(BigDecimal.TWO, 4, RoundingMode.HALF_EVEN);
}

BigDecimal convertedBalance(BigDecimal balance, List<Supplier<BigDecimal>> providers) {
    List<CompletableFuture<Optional<BigDecimal>>> fs = providers.stream()
        .map(p -> CompletableFuture.supplyAsync(p, IO)
                 .orTimeout(400, TimeUnit.MILLISECONDS)
                 .handle((v, ex) -> ex == null ? Optional.of(v) : Optional.<BigDecimal>empty()))   // falha ou prazo: sem voto
        .toList();
    CompletableFuture.allOf(fs.toArray(CompletableFuture[]::new)).join();          // nunca lança: handle trata tudo
    List<BigDecimal> ok = fs.stream().map(CompletableFuture::join).flatMap(Optional::stream).toList();
    if (ok.size() < 2) throw new IllegalStateException("poucas cotações: " + ok.size());
    return balance.multiply(median(ok)).setScale(2, RoundingMode.HALF_EVEN);
}
```
Executado (`java Futures.java median`, 4 provedores simulados):
```text
3 respondem:            4257.90 em 216 ms
1 falha, 1 estoura (2 ok de 4): 4257.90 em 402 ms
só 1 ok:               IllegalStateException(poucas cotações: 1) em 401 ms
```
`handle` **nunca propaga**, então `allOf(...).join()` não lança. O pior caso é ~400 ms (o `orTimeout`), não a soma. Cuidado: os provedores que estouraram **ainda rodam** (seção D): dê a eles um *timeout* de rede.
</details>

**Variação:** troque a mediana por "a **primeira** cotação que responder" com `anyOf` e discuta o que se **perde** (validação cruzada).

## ⚖️ Trade-offs e quando NÃO usar
- **`CompletableFuture` × virtual threads (P1.10):** com threads virtuais, escrever **código sequencial bloqueante** em uma thread por tarefa é **mais simples** e igualmente escalável; o `CompletableFuture` ainda vale para **compor/combinar** resultados e para o *timeout* declarativo. Para **só** "chamar 3 serviços em paralelo e juntar", *structured concurrency* (P1.10) é mais segura (cancela os irmãos, não vaza tarefas).
- **`CompletableFuture` × programação reativa (P3, WebFlux/Reactor):** o CF é **um** valor futuro; reativo trata **fluxos** com *backpressure*. Para um pedido→resposta, CF basta.
- **Encadeamento longo:** 8 `thenCompose` aninhados é **pior** que 8 linhas bloqueantes em thread virtual. Se a cadeia ficou ilegível, o design é o problema.
- **Não use** `CompletableFuture` para **tirar** trabalho da thread da requisição "para ser mais rápido" se você vai dar `join()` logo em seguida: é custo sem ganho (a menos que haja **paralelismo real** entre etapas independentes).

## ⚠️ Erros comuns e boas práticas de produção
- **`supplyAsync` sem executor** com chamada de rede (seção E): esgota o `commonPool`.
- **Erro engolido:** um `CompletableFuture` cujo resultado ninguém consome **perde** a exceção (como o `submit`, P1.05). Termine toda cadeia com `.exceptionally`/`.handle`/`.whenComplete` que **registre** (`WARN`/`ERROR`, sem dado pessoal) ou **propague** a quem espera.
- **Misturar `join()` dentro de outra etapa** (bloquear a thread do pool que ia completar a etapa seguinte): causa **deadlock de pool** quando todas as threads esperam trabalho que está na fila.
- **`get()`/`join()` sem prazo** (a thread chamadora espera para sempre). Use `orTimeout` **e** `get(timeout)`.
- **Dependência de `ThreadLocal`/`SecurityContext`/MDC** (J8, J5.11 `requestId`): a etapa pode rodar em **outra thread**; o contexto **não** vai junto. Capture o que precisa **antes** (ids como argumento) ou use um *executor* que propague contexto.
- **Esperar que `cancel()` pare o trabalho** (seção D).
- **Exceção dentro de `thenApply`** vira `CompletionException`: quem faz `catch (IllegalStateException e)` em volta do `join()` **não pega**.

## 🎤 Na entrevista
- **Diferença entre `thenApply` e `thenCompose`?** `thenApply` aplica uma função **síncrona** (`T → U`); `thenCompose` aplica uma função que **retorna outro** `CompletionStage` (`T → CF<U>`) e o "achata", como `map` × `flatMap`.
- **Em que thread executa `thenApply`?** Na thread que completou o estágio anterior, ou na chamadora se já estava completo; só `thenApplyAsync` agenda no executor. Por isso não se deve confiar em *thread locals* nas etapas.
- **Qual o risco do `ForkJoinPool.commonPool()` como executor padrão?** Pool pequeno (≈ núcleos − 1), compartilhado pela JVM; tarefas bloqueantes o esgotam e afetam outras partes (streams paralelos). Passe um executor próprio para I/O.
- **`cancel()` interrompe a tarefa?** Não, no `CompletableFuture`: apenas completa o futuro com `CancellationException`; a tarefa em execução continua.
- **Como você impõe *timeout* nessa composição?** `orTimeout` / `completeOnTimeout` (Java 9+) no futuro, **mais** *timeouts* de rede na chamada para liberar a thread de fato.
