## 🎯 Objetivos
Ao final desta aula você consegue:
- **Distinguir** *data race* (P1.08) de ***race condition*** (erro de lógica de tempo) e **reconhecer** os dois padrões clássicos: ***read-modify-write*** e ***check-then-act***.
- **Provocar** uma corrida **de verdade** com um *harness* (largada sincronizada, repetição, **invariantes** verificáveis) e **medir** a falha.
- **Corrigir** com lock, CAS e **verificação atômica**, e **provar** a correção com o mesmo *harness*.
- **Explicar** *deadlock* (condições de Coffman), **detectá-lo** (`jcmd Thread.print`, `ThreadMXBean`) e **preveni-lo** (ordem global de locks, `tryLock` com *backoff*).

## 🤔 Por que isso importa
A regra 1 do PayFlow ("saldo nunca fica negativo") e a regra 3 ("saldo = soma dos lançamentos") são **invariantes**. **Condições de corrida são a maneira mais fácil de violá-las** sem uma única linha "errada" olhando isoladamente. Dinheiro **criado do nada** ou **destruído** por uma corrida é um incidente de **perda financeira**, e o teste de unidade passa. Esta aula é o **laboratório da perda de dinheiro**.

## 💡 Intuição (explicação simples)
- **Corrida *check-then-act*:** duas pessoas olham o **mesmo saldo** de R$ 100 no extrato do app, **ambas** veem "dá para sacar R$ 100" e **ambas** sacam. Cada uma agiu certo **com o que viu**; o erro está no **intervalo** entre olhar e agir.
- **Perda de atualização (*lost update*):** duas pessoas **copiam** o mesmo caderno, cada uma soma R$ 10 na **sua** cópia e devolve; a segunda devolução **apaga** a primeira.
- ***Deadlock*:** duas pessoas passam por uma **porta estreita** de lados opostos, cada uma **segurando a sua metade** e esperando a outra recuar. Ninguém recua; **ficam ali para sempre**.

## 🔬 Como funciona por dentro

### 1. O vocabulário certo
| Termo | O que é | Conserta com |
|---|---|---|
| ***Data race*** | acesso concorrente ao mesmo dado, ao menos uma escrita, **sem HB** (P1.08) | sincronização (HB) |
| ***Race condition*** | o **resultado depende da ordem/tempo** de execução (pode haver HB em cada passo e **ainda** assim estar errado) | tornar a **sequência** atômica |
| ***Read-modify-write*** | ler, calcular, escrever (`balance = balance + v`) | lock, CAS, operação atômica |
| ***Check-then-act*** | verificar uma condição e agir **supondo que ela continua valendo** (`if (saldo >= v) debita`) | tornar **verificar+agir** atômico |

Repare: **cada passo isolado pode ser *thread-safe*** (`ConcurrentHashMap.get`, `put`) e a **sequência** não ser (P1.07). Por isso "uso uma coleção concorrente" **não** basta.

### 2. Como tornar a sequência atômica
- **Exclusão mútua** (`synchronized`, `ReentrantLock`): só uma thread **por vez** na seção crítica. Simples; custo de espera.
- **Otimista com CAS** (`AtomicReference.updateAndGet`/`compareAndSet`): lê, calcula, **tenta trocar só se ninguém mudou**; senão **repete**. Sem fila; a função precisa ser **pura** (pode rodar mais de uma vez).
- **Delegar ao banco** (P2, e o `@Version` da J5): `UPDATE accounts SET balance = balance - ? WHERE id = ? AND balance >= ?` é **verificar+agir em uma operação** atômica **do banco**.
- **Regra de ouro:** a atomicidade tem de abranger **todo o invariante**. Se o invariante envolve **duas contas** (transferência), proteger **cada conta separadamente** ainda deixa "dinheiro no ar" entre as duas operações (veja a seção B3).

### 3. *Deadlock*: as quatro condições (Coffman)
Só ocorre se **todas** valerem ao mesmo tempo:
1. **Exclusão mútua:** o recurso só serve uma thread por vez.
2. **Segura-e-espera:** quem tem um recurso **espera** por outro.
3. **Sem preempção:** ninguém tira o recurso à força.
4. **Espera circular:** A espera B, B espera A (ou um ciclo maior).
**Prevenir = quebrar uma delas.** O jeito mais barato: quebrar a **4ª** com uma **ordem global** de aquisição ("sempre trava a conta de **menor id** primeiro"). Quebrar a **3ª**: `tryLock` com *timeout* e **soltar** o que já tem. Outras falhas de vivacidade: ***livelock*** (todos recuam e tentam de novo **em sincronia**, sem avançar) e ***starvation*** (alguém nunca é atendido).

## 🛠️ Exemplo prático
> `lab/jvm-lab/Races.java`: `java Races.java <lost-update|overdraft|conservation|deadlock|deadlock-fix|deadlock-trylock|throttle|throttle-fix>`.

As contas ingênuas (formato do PayFlow, **sem nenhuma proteção**):
```java
static class NaiveAccount {
    final UUID id; BigDecimal balance;
    void deposit(BigDecimal v) { balance = balance.add(v); }                              // ler → somar → escrever
    boolean withdraw(BigDecimal v) {
        if (balance.compareTo(v) >= 0) { balance = balance.subtract(v); return true; }     // verificar → agir
        return false;
    }
}
```

### A. Perda de atualização (*read-modify-write*)
8 threads × 20 000 depósitos de `1.00` (esperado `160000.00`):
```text
ingênua:      45434.00  (esperado 160000.00)
synchronized: 160000.00
CAS (AtomicReference): 160000.00
```
A conta ingênua **perdeu 72% do dinheiro** (114 566 de 160 000). As duas correções acertam. O CAS:
```java
void deposit(BigDecimal v) { balance.updateAndGet(b -> b.add(v)); }      // função pura: pode ser reexecutada
boolean withdraw(BigDecimal v) {
    while (true) {
        BigDecimal cur = balance.get();
        if (cur.compareTo(v) < 0) return false;
        if (balance.compareAndSet(cur, cur.subtract(v))) return true;       // só troca se ninguém mudou
    }
}
```

### B. *Check-then-act*: o saque que passa duas vezes
Uma conta de `100.00` e **16 threads** tentando sacar `100.00` ao mesmo tempo. **Só um** saque pode passar. Repetido em 2 000 contas novas:
```text
ingênua:      em 136 de 2000 rodadas mais de um saque passou (até 9 saques; saldo final até -100.00)
synchronized: em 0 de 2000 rodadas passou mais (ou menos) de um saque
```
Em **6,8%** das rodadas a regra 1 foi violada; em uma delas **9 saques de R$ 100 passaram** de uma conta de R$ 100 (o saldo final chegou a `-100.00`, violando a regra 1: dois `subtract` em sequência sobre uma verificação já velha). Com `synchronized` em `withdraw` (verificar + agir **sob o mesmo lock**): **0 falhas em 2 000**. Note a **raridade**: 93% das rodadas **passaram** sem erro: um teste que roda uma vez **não pega**.

### B3. Transferência: o dinheiro que aparece e some
Duas contas com `1000.00` (total `2000.00`); 8 threads transferem `10.00` de uma para a outra, `withdraw` + `deposit`:
```text
ingênua:      total = 48830.00 (começou com 2000.00)  x=23780.00 y=25050.00
cada método synchronized: total = 2000.00  <- ainda pode ter dinheiro "no ar" (sacou de um, ainda não depositou no outro), mas ao final fecha
```
A versão ingênua **criou R$ 46 830** do nada (o total passou de 2 000 para 48 830) porque os `deposit` se sobrescrevem e os `withdraw` leem valores velhos. **Esse é o "saldo que não bate"**; P1.13 o estuda a fundo. Com `synchronized` em cada método o **total fecha ao final**, **mas** durante a transferência há um instante em que o dinheiro saiu de uma conta e **ainda não entrou na outra**: quem somar as duas **nesse instante** vê `1990.00`. Se isso importa (relatório, auditoria), a transferência **inteira** precisa ser **uma** seção atômica (um lock que cobre as duas contas, ou uma **transação do banco**: J3.10, J5.11, P2).

### C. *Deadlock* (e como enxergá-lo)
Transferência com **um lock por conta**, na ordem dos argumentos; Ana→Bia e Bia→Ana ao mesmo tempo:
```java
static void transferNaive(LockedAccount from, LockedAccount to, BigDecimal v) {
    from.lock.lock();
    try {
        pause();                                   // alarga a janela (num sistema real: o tempo de uma consulta)
        to.lock.lock();
        try { …débito e crédito… } finally { to.lock.unlock(); }
    } finally { from.lock.unlock(); }
}
```
```text
$ java Races.java deadlock
t1 viva? true  t2 viva? true
DEADLOCK detectado em 2 threads:
  ana-para-bia espera o lock de bia-para-ana (java.util.concurrent.locks.ReentrantLock$NonfairSync)
  bia-para-ana espera o lock de ana-para-bia (java.util.concurrent.locks.ReentrantLock$NonfairSync)
```
Duas threads **vivas** (não terminaram), cada uma esperando a outra: **espera circular**. Dois jeitos de enxergar:
1. **Por código:** `ManagementFactory.getThreadMXBean().findDeadlockedThreads()` devolve os ids (ou `null`); é o que o laboratório usa (pode alimentar um *health check*, P6).
2. **Por fora, na JVM viva:** `jcmd <PID> Thread.print` (ou `kill -3`/`docker kill --signal=QUIT`) **detecta e imprime sozinho**:
```text
Found one Java-level deadlock:
=============================
"ana-para-bia":
  waiting for ownable synchronizer 0x00000006e3839248, (a java.util.concurrent.locks.ReentrantLock$NonfairSync),
  which is held by "bia-para-ana"

"bia-para-ana":
  waiting for ownable synchronizer 0x00000006e38225b0, (a java.util.concurrent.locks.ReentrantLock$NonfairSync),
  which is held by "ana-para-bia"

Java stack information for the threads listed above:
===================================================
"ana-para-bia":
	at jdk.internal.misc.Unsafe.park(java.base@25.0.5.0.3/Native Method)
	- parking to wait for  <0x00000006e3839248> (a java.util.concurrent.locks.ReentrantLock$NonfairSync)
	...
	at Races.transferNaive(Races.java:64)
```
Leia: **quem espera o quê** e **quem o segura** (a seta fecha em círculo), e a **linha do seu código** (`Races.transferNaive(Races.java:64)`, o segundo `lock()`).

### D. Correção 1: ordem global de aquisição
```java
static void transferOrdered(LockedAccount from, LockedAccount to, BigDecimal v) {
    LockedAccount first = from.id.compareTo(to.id) < 0 ? from : to, second = first == from ? to : from;
    first.lock.lock();
    try { second.lock.lock(); try { …débito e crédito… } finally { second.lock.unlock(); } } finally { first.lock.unlock(); }
}
```
```text
t1 viva? false  t2 viva? false  (tempo 4060 ms)
findDeadlockedThreads() = null (sem deadlock); saldos a=500.00 b=500.00
```
Terminou em **4 060 ms** (200 transferências × 20 ms, **serializadas**, pois todas disputam as mesmas duas contas): **todos** travam na **mesma ordem** (menor `id` primeiro), então **não existe ciclo**. Saldos `500.00/500.00` (100 transferências de ida e 100 de volta). É a correção **preferida**: determinística, sem retentativas. **No banco é a mesma ideia:** `UPDATE`/`SELECT … FOR UPDATE` nas duas contas **sempre em ordem de `id`** (P2, locking pessimista).

### E. Correção 2: `tryLock` com *backoff* aleatório
```java
if (from.lock.tryLock()) { try { pause();
    if (to.lock.tryLock()) { try { …débito e crédito…; return; } finally { to.lock.unlock(); } }
} finally { from.lock.unlock(); } }
Thread.sleep(ThreadLocalRandom.current().nextLong(1, 15));       // jitter: evita livelock
```
```text
tryLock + jitter: t1 viva? false  t2 viva? false  saldos a=500.00 b=500.00  retentativas=510  tempo=9233 ms  deadlock? false
```
**Sem deadlock** e saldos certos, mas **510 retentativas** e **9,2 s** (contra **4,06 s** da ordem global): **~2,3× mais lento** neste cenário, porque as duas threads **colidem repetidamente** (quase um *livelock*) e o *backoff* aleatório só desfaz aos poucos. Sem o *jitter* aleatório, as duas **recuariam e voltariam em sincronia para sempre**. Use quando **não dá para impor uma ordem** (locks vindos de bibliotecas diferentes), **não** como primeira escolha.

### F. O defeito real do `LoginThrottle` (J8.06): verificar-e-agir **entre chamadas**
O `ThrottledAuthenticationProvider` faz (J8.06): `if (throttle.isLocked(key)) recusa; … delegate.authenticate(…) [BCrypt, ~dezenas de ms]; … throttle.failure(key)`. **Cada método é `synchronized`**, mas a **sequência** "verifica → gasta BCrypt → registra" **não é atômica**. Simulação (limite de **5** erros; **60** tentativas de senha errada **simultâneas** para o mesmo e-mail; a senha leva 20 ms para ser testada):
```text
ingênuo   : limite = 5 erros; 60 tentativas simultâneas; senhas realmente testadas = 60
corrigido : limite = 5 erros; 60 tentativas simultâneas; senhas realmente testadas = 5
```
O bloqueio por 5 erros **não limitou nada**: **as 60** passaram pela verificação **antes** de qualquer uma registrar o erro, e **60 senhas** foram testadas. Um atacante que dispara tentativas **em paralelo** contorna o limite (cada uma custa um BCrypt, ainda por cima: CPU). A correção é **reservar** a tentativa **antes** do trabalho caro, na **mesma região crítica** da verificação:
```java
synchronized boolean tryBegin()  { if (failures + inFlight >= max) return false; inFlight++; return true; }   // verifica E reserva
synchronized void endFailure()   { inFlight--; failures++; }                                                  // ao terminar com erro
// sucesso: inFlight-- e zera as falhas
```
Com isso: **5** senhas testadas em vez de 60. (Isto é um **defeito de projeto da J8.06** encontrado nesta aula: está registrado em "Correções pendentes" do `progresso.md` e **não** reescrevi a J8; a correção entra como **exercício do PayFlow** abaixo.)

## ⚖️ Trade-offs e quando NÃO usar
- **Locks em memória só protegem UMA instância da aplicação.** Duas instâncias do PayFlow (P7, Kubernetes: várias réplicas) **não compartilham** `synchronized`/`ReentrantLock`. Para invariantes **entre instâncias** o árbitro é o **banco** (`UNIQUE`, `WHERE balance >= ?`, `@Version`, `SELECT … FOR UPDATE`: P2) ou um serviço de coordenação. **Não use um lock Java para proteger dinheiro em produção multi-instância.**
- **Lock grosso × fino:** um lock **global** de transferências é correto e **serializa tudo** (vazão ruim); um lock **por conta** com ordem global é o meio-termo; o banco com **bloqueio por linha** é o que escala.
- **Otimista (CAS/`@Version`) × pessimista (lock):** otimista é ótimo com **pouca disputa** (quase nunca repete); com **muita disputa** na **mesma** conta vira tempestade de repetições (P1.13 mede). Pessimista serializa e **não** repete, mas **bloqueia** (e pode gerar *deadlock*).
- **Não "resolva" com `Thread.sleep`** nem com "executar poucas threads nos testes": esconde, não corrige.

## ⚠️ Erros comuns e boas práticas de produção
- **"Proteger" só um dos lados:** sincronizar o `deposit` e esquecer o `withdraw`, ou travar a escrita e ler **sem** lock (P1.08).
- **Lock ordering inconsistente** entre partes do código escritas por pessoas diferentes: documente a **ordem global** ("sempre pelo `id` crescente") e teste.
- **Chamar código externo com lock** (callback, `RestClient`, log que faz I/O): segura o lock por tempo imprevisível e cria *deadlocks* escondidos.
- **`synchronized` em método que chama outro `synchronized` de objeto diferente** em ordem variável: o mesmo *deadlock* da seção C, escondido atrás de métodos.
- **Teste que roda uma vez:** a corrida da seção B falha em **6,8%** das rodadas. Um teste de concorrência precisa de **repetição** (milhares), **largada sincronizada** (`CountDownLatch`), **invariantes verificáveis** (total, não-negativo) e, de preferência, **rodar muito tempo** no CI noturno.
- **Transação do banco não é lock da JVM:** `@Transactional` (J5.11) **não** impede duas threads de lerem o mesmo saldo; o isolamento `READ COMMITTED` (padrão do PostgreSQL) deixa passar o *check-then-act* (P2: níveis de isolamento, `@Version`, `FOR UPDATE`).
- **Detectar tarde:** um *deadlock* só aparece sob carga. Tenha `jcmd Thread.print`/`kill -3` no *runbook* e um *health check* com `findDeadlockedThreads()` (P6).

## 🎤 Na entrevista
- **Diferença entre *data race* e *race condition*?** *Data race*: acesso concorrente sem HB (violação do JMM). *Race condition*: o resultado depende do **tempo/ordem**; pode existir mesmo com acessos sincronizados (ex.: `if (map.get(k)==null) map.put(...)`). Um não implica o outro.
- **O que é *check-then-act* e como evitar?** Verificar uma condição e agir **supondo** que continua verdadeira. Evite tornando **verificar + agir** atômico: lock, CAS, `putIfAbsent`/`compute`, ou restrição/`UPDATE` condicional no banco.
- **Como acontece um *deadlock* e como preveni-lo?** Quando quatro condições coexistem (exclusão mútua, segura-e-espera, sem preempção, espera circular). Prevenir quebrando uma: ordem global de locks, `tryLock` com *timeout* e liberação, travar tudo de uma vez.
- **Como você diagnosticaria um *deadlock* em produção?** `jcmd <PID> Thread.print` (ou `kill -3`): a JVM imprime "Found one Java-level deadlock" com quem espera quem; ou `ThreadMXBean.findDeadlockedThreads()` em um *health check*.
- **Por que `@Transactional` não resolve duas requisições sacando ao mesmo tempo?** Transação isola **escritas** conforme o nível de isolamento; no `READ COMMITTED` ambas leem o mesmo saldo. É preciso `@Version` (otimista), `SELECT … FOR UPDATE` (pessimista) ou `UPDATE … WHERE balance >= ?` (P2).
