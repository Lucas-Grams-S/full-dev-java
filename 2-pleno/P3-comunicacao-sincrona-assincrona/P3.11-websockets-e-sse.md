> ⏱️ ~1h30 · 🔵 Pleno · Pré-requisitos: J2 (HTTP, cookies), J4.05 (`fetch` e assincronia no navegador), J8 (autenticação, CSRF/CORS, origem), P3.01, P3.04/P3.05 (consumo de eventos)

PayFlow: **por leitura**.

## 🎯 Objetivos
Ao final desta aula você consegue:
- **Comparar** *polling*, ***Server-Sent Events* (SSE)** e **WebSocket** e **escolher** pelo requisito (direção, protocolo, reconexão).
- **Implementar** um stream SSE com `SseEmitter` (`id`, `event`, `data`, comentário de *heartbeat*) e **retomar** após queda com `Last-Event-ID`.
- **Implementar** um *handler* WebSocket com `TextWebSocketHandler` e **restringir a origem** (`setAllowedOrigins`), provando a recusa.
- **Listar** os problemas de produção: **autenticação, *proxies*/*timeouts*, limite de conexões e escala** (o estado vive **numa** instância).

## 🤔 Por que isso importa
O painel do PayFlow hoje só mostra o saldo **quando você recarrega**. Para "**seu pagamento QR foi confirmado**" aparecer **na hora** na tela do lojista (P3.10), o servidor precisa **empurrar** o evento. As duas ferramentas padrão são SSE e WebSocket; escolher a errada custa **infraestrutura** (conexões longas, *proxies*) e **complexidade**.

## 💡 Intuição (explicação simples)
- ***Polling*:** você liga na pizzaria a cada minuto: "saiu?". Gasta ligações e demora.
- **SSE:** a pizzaria **liga para você e fala**, e você **só escuta** (**uma via: servidor → cliente**). Se a linha cai, o telefone **religa sozinho** e diz "parei no aviso nº 7".
- **WebSocket:** uma **ligação telefônica** em que **ambos falam** quando quiserem (**duas vias**), mas **você** cuida de religar e de lembrar onde parou.

## 🔬 Como funciona por dentro

| | *Polling* | **SSE** | **WebSocket** |
|---|---|---|---|
| Direção | cliente → servidor (repetido) | **servidor → cliente** | **bidirecional** |
| Protocolo | HTTP normal | **HTTP** (`Content-Type: text/event-stream`, conexão longa) | HTTP *upgrade* → protocolo próprio ([RFC 6455](https://www.rfc-editor.org/rfc/rfc6455)) |
| Reconexão | n/a | **automática** no navegador (`EventSource`), com `Last-Event-ID` | **manual** (você implementa) |
| Formato | qualquer | **texto** (`id:`, `event:`, `data:`, `:comentário`) | texto **ou** binário |
| Atravessa *proxies* | sim | em geral sim (é HTTP; cuidado com *buffering*) | às vezes precisa configurar `Upgrade` |
| Melhor para | atualização rara | **notificações**, progresso, painéis | chat, jogos, colaboração, **cliente também envia muito** |
- **SSE** ([especificação WHATWG](https://html.spec.whatwg.org/multipage/server-sent-events.html), [MDN](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)): linhas de texto; um evento termina com **linha em branco**; `id:` permite o cliente reconectar enviando `Last-Event-ID`; uma linha começando por `:` é **comentário** (serve de *heartbeat* para manter a conexão viva através de *proxies*).
- **WebSocket:** o cliente faz um `GET` com `Upgrade: websocket`; se o servidor aceita (`101`), a mesma conexão TCP passa a carregar **mensagens** nos dois sentidos. **Não** há reconexão, *ack* nem garantia de entrega: se a conexão cai, **mensagens se perdem** a menos que **você** projete (números de sequência, reenvio).
- **Cada cliente = uma conexão longa aberta** no servidor (memória, descritor de arquivo, *thread*/estrutura): `W` é **minutos ou horas** (Little, P3.01): `L = λ × W` explode. Com *threads* virtuais ou servidores não bloqueantes isso é viável; com 200 *threads* de plataforma, **não**.
- **Escala horizontal:** o emissor (`SseEmitter`) vive **na memória de UMA instância**. Se o evento é produzido em **outra** instância, ele **não encontra** o cliente. Solução: **todas** as instâncias consomem o evento (um **grupo de consumidores por instância** no Kafka, ou *pub/sub* do Redis) e empurram aos **seus** clientes conectados.

## 🛠️ Exemplo prático

### A. SSE e WebSocket no Spring MVC
```java
package com.payflow.lab;

import java.io.IOException;
import java.util.List;
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.CopyOnWriteArrayList;
import java.util.concurrent.atomic.AtomicLong;
import org.springframework.context.annotation.Configuration;
import org.springframework.http.MediaType;
import org.springframework.web.bind.annotation.*;
import org.springframework.web.servlet.mvc.method.annotation.SseEmitter;
import org.springframework.web.socket.*;
import org.springframework.web.socket.config.annotation.*;
import org.springframework.web.socket.handler.TextWebSocketHandler;

/** P3.11: SSE (servidor → cliente, sobre HTTP) e WebSocket (bidirecional). */
@Configuration
@EnableWebSocket
class RealtimeConfig implements WebSocketConfigurer {
    @Override
    public void registerWebSocketHandlers(WebSocketHandlerRegistry registry) {
        registry.addHandler(new EchoHandler(), "/ws/echo").setAllowedOrigins("http://localhost");
    }

    static class EchoHandler extends TextWebSocketHandler {
        @Override protected void handleTextMessage(WebSocketSession s, TextMessage m) throws IOException {
            s.sendMessage(new TextMessage("eco:" + m.getPayload()));
        }
    }
}

@RestController
class SseController {
    record Event(long id, String data) {}
    private final Map<String, List<SseEmitter>> emitters = new ConcurrentHashMap<>();
    private final Map<String, List<Event>> history = new ConcurrentHashMap<>();
    private final AtomicLong seq = new AtomicLong();

    @GetMapping(value = "/sse/wallets/{id}", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    SseEmitter subscribe(@PathVariable String id, @RequestHeader(value = "Last-Event-ID", required = false) String lastId) throws IOException {
        var emitter = new SseEmitter(60_000L);
        emitters.computeIfAbsent(id, k -> new CopyOnWriteArrayList<>()).add(emitter);
        Runnable cleanup = () -> emitters.get(id).remove(emitter);
        emitter.onCompletion(cleanup); emitter.onTimeout(cleanup); emitter.onError(e -> cleanup.run());
        if (lastId != null) {                                   // reconexão: reenvia o que o cliente perdeu
            long last = Long.parseLong(lastId);
            for (Event e : history.getOrDefault(id, List.of())) if (e.id() > last) send(emitter, e);
        }
        emitter.send(SseEmitter.event().comment("conectado"));
        return emitter;
    }

    @PostMapping("/sse/wallets/{id}/publish")
    void publish(@PathVariable String id, @RequestBody String data) {
        var e = new Event(seq.incrementAndGet(), data);
        history.computeIfAbsent(id, k -> new CopyOnWriteArrayList<>()).add(e);
        for (var em : emitters.getOrDefault(id, List.of())) {
            try { send(em, e); } catch (IOException ex) { em.completeWithError(ex); }
        }
    }

    private void send(SseEmitter em, Event e) throws IOException {
        em.send(SseEmitter.event().id(String.valueOf(e.id())).name("balance").data(e.data()));
    }
}
```
Pontos do SSE: `SseEmitter(60_000L)` (*timeout*); registro **limpo** em `onCompletion/onTimeout/onError` (senão vaza emissores); `history` em memória para o **replay** com `Last-Event-ID` (no PayFlow, o replay viria do **banco/Outbox**, não da memória); `comment("conectado")` envia uma linha `:conectado` (útil como *heartbeat*). Pontos do WebSocket: `@EnableWebSocket`, `WebSocketConfigurer`, `setAllowedOrigins`.

### B. Provas
```java
package com.payflow.lab;

import static org.assertj.core.api.Assertions.assertThat;
import static org.awaitility.Awaitility.await;

import java.net.URI;
import java.net.http.*;
import java.time.Duration;
import java.util.List;
import java.util.concurrent.*;
import org.junit.jupiter.api.Test;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.boot.test.web.server.LocalServerPort;

@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
class RealtimeIT {
    @LocalServerPort int port;
    final HttpClient http = HttpClient.newHttpClient();

    void publish(String wallet, String data) throws Exception {
        http.send(HttpRequest.newBuilder(URI.create("http://localhost:" + port + "/sse/wallets/" + wallet + "/publish"))
                .POST(HttpRequest.BodyPublishers.ofString(data)).header("Content-Type", "text/plain").build(), HttpResponse.BodyHandlers.discarding());
    }

    List<String> subscribe(String wallet, String lastId, CompletableFuture<?>[] holder) {
        List<String> lines = new CopyOnWriteArrayList<>();
        var b = HttpRequest.newBuilder(URI.create("http://localhost:" + port + "/sse/wallets/" + wallet)).header("Accept", "text/event-stream");
        if (lastId != null) b.header("Last-Event-ID", lastId);
        holder[0] = http.sendAsync(b.build(), HttpResponse.BodyHandlers.ofLines()).thenAccept(r -> {
            System.out.println("SSE content-type=" + r.headers().firstValue("Content-Type").orElse("?"));
            r.body().forEach(lines::add);
        });
        return lines;
    }

    @Test
    void sseStreamsEventsAndReplaysAfterReconnect() throws Exception {
        var holder = new CompletableFuture<?>[1];
        var lines = subscribe("w1", null, holder);
        await().atMost(Duration.ofSeconds(5)).until(() -> lines.contains(":conectado"));
        publish("w1", "{\"balance\":\"90.00\"}");
        publish("w1", "{\"balance\":\"80.00\"}");
        await().atMost(Duration.ofSeconds(5)).until(() -> lines.stream().filter(l -> l.startsWith("data:")).count() == 2);
        System.out.println("SSE linhas=" + lines);
        assertThat(lines).contains("event:balance");
        holder[0].cancel(true);                                   // o cliente cai
        publish("w1", "{\"balance\":\"70.00\"}");                // evento perdido pelo cliente
        String lastSeen = lines.stream().filter(l -> l.startsWith("id:")).reduce((a, b) -> b).get().substring(3);
        var holder2 = new CompletableFuture<?>[1];
        var lines2 = subscribe("w1", lastSeen, holder2);        // reconecta dizendo até onde viu
        await().atMost(Duration.ofSeconds(5)).until(() -> lines2.stream().anyMatch(l -> l.contains("70.00")));
        System.out.println("SSE reconexao Last-Event-ID=" + lastSeen + " recebeu=" + lines2);
        holder2[0].cancel(true);
    }

    @Test
    void webSocketEchoesBothWays() throws Exception {
        List<String> got = new CopyOnWriteArrayList<>();
        WebSocket ws = http.newWebSocketBuilder().header("Origin", "http://localhost")
                .buildAsync(URI.create("ws://localhost:" + port + "/ws/echo"), new WebSocket.Listener() {
                    @Override public CompletionStage<?> onText(WebSocket w, CharSequence data, boolean last) {
                        got.add(data.toString()); w.request(1); return null;
                    }
                }).get(5, TimeUnit.SECONDS);
        ws.sendText("ola", true).get(5, TimeUnit.SECONDS);
        ws.sendText("saldo?", true).get(5, TimeUnit.SECONDS);
        await().atMost(Duration.ofSeconds(5)).until(() -> got.size() == 2);
        System.out.println("WS recebeu=" + got);
        assertThat(got).containsExactly("eco:ola", "eco:saldo?");
        ws.sendClose(WebSocket.NORMAL_CLOSURE, "fim").get(5, TimeUnit.SECONDS);
        // origem não permitida é recusada no handshake
        var bad = http.newWebSocketBuilder().header("Origin", "http://evil.example")
                .buildAsync(URI.create("ws://localhost:" + port + "/ws/echo"), new WebSocket.Listener() {});
        try { bad.get(5, TimeUnit.SECONDS); System.out.println("WS origem hostil: ACEITA (!)"); }
        catch (ExecutionException e) { System.out.println("WS origem hostil recusada: " + e.getCause().getClass().getSimpleName() + " " + e.getCause().getMessage()); }
    }
}
```
```text
SSE content-type=text/event-stream
SSE linhas=[:conectado, , id:1, event:balance, data:{"balance":"90.00"}, , id:2, event:balance, data:{"balance":"80.00"}, ]
SSE content-type=text/event-stream
SSE reconexao Last-Event-ID=2 recebeu=[id:3, event:balance, data:{"balance":"70.00"}, , :conectado, ]
WS recebeu=[eco:ola, eco:saldo?]
WS origem hostil recusada: WebSocketHandshakeException null
```
- **SSE:** `content-type=text/event-stream`; as linhas chegaram como `id:1 / event:balance / data:{...}` e **linha em branco**; o cliente "caiu" (cancelamos), um **terceiro evento** foi publicado, e ao **reconectar** com `Last-Event-ID: 2` o servidor **reenviou só o `id:3`**, sem repetir os dois primeiros (a linha `:conectado` do `comment` vem **depois** do *replay* no log).
- **WebSocket:** `eco:ola` e `eco:saldo?` voltaram (mensagens nos **dois** sentidos); com `Origin: http://evil.example` o *handshake* **foi recusado** (`WebSocketHandshakeException`): sem `setAllowedOrigins`, **qualquer página** abriria um socket autenticado pelo cookie da vítima (*Cross-Site WebSocket Hijacking*; relacione a J8.04, CSRF).

### C. O PayFlow (por leitura)
- **Escolha: SSE** para "pagamento confirmado" e "saldo atualizado": o fluxo é **só servidor → cliente**, o navegador **reconecta sozinho**, usa **HTTP** (cookie/sessão da J8, passa por *proxies*) e é **mais simples** de proteger. **WebSocket** só se houvesse **chat/colaboração** (não há).
- Endpoint `GET /api/v1/accounts/{id}/events` (SSE): **autenticado** (a **mesma** cadeia de segurança, J8) e **autorizado por conta** (IDOR, J8.05: conta de outro usuário → 404). **`EventSource` não envia cabeçalho `Authorization`** (a API do navegador só aceita URL e `withCredentials`): no painel (sessão por **cookie**) funciona; para um cliente com JWT use **`fetch` com leitura de *stream***. ⚠️ **Não coloque o JWT na URL** (vai para *logs* e histórico).
- **Origem do evento:** o consumidor Kafka do grupo **`panel-<instância>`** (um grupo **por instância**, para que **todas** recebam) transforma `PaymentConfirmed` num `SseEmitter.send` aos clientes **daquela** instância.
- **Operação:** *heartbeat* a cada 15–30 s (comentário); *timeout* de *proxy* **maior** que o *heartbeat* (⚠️ o limite varia por *proxy*; confira o seu); **limite de conexões por usuário**; encerramento gracioso no *deploy* (`SseEmitter.complete()`; o navegador reconecta).

## 🧠 Pausa para lógica
**Enunciado.** O painel tem **20 000 usuários simultâneos** com SSE, cada conexão fica aberta em média **30 min**, e cada usuário abre/fecha uma conexão a cada 30 min. (a) Quantas conexões abertas em média? (b) Com Tomcat de 200 *threads* de plataforma e `SseEmitter` (servlet assíncrono), o que importa: *threads* ou memória? (c) Se uma instância cai, quantas reconexões por segundo (distribuídas em 30 s)? (d) O que evita o *thundering herd*?

<details><summary>Dica</summary>

Little: `L = λ × W`; no servlet assíncrono a *thread* é **liberada** entre envios.
</details>

<details><summary>Solução</summary>

(a) **20 000** conexões abertas (cada usuário mantém uma). (b) Com servlet **assíncrono** a *thread* não fica presa por conexão: o limite vira **memória/descritores de arquivo** (e o limite de conexões do Tomcat/SO, ⚠️ **não medido aqui**), não as 200 *threads*; com `Thread` por conexão bloqueante, **200 *threads* seria o teto**. (c) Se a queda é de **uma instância de 4** (5 000 clientes): 5 000 ÷ 30 s ≈ **167 reconexões/s** (o navegador espera o tempo configurado em `retry:`). (d) **Jitter** no `retry:` do SSE e **limites de taxa** de conexão; o *balanceador* distribui; o servidor pode enviar `retry: <ms aleatório>` ao encerrar.
**Variação:** 100 000 usuários. O que muda na arquitetura? (Mais instâncias **e** um barramento (Kafka/Redis) para **fan-out**; considerar um serviço de *push* dedicado.)
</details>

## ⚖️ Trade-offs e quando NÃO usar
- **SSE:** simples, reconecta sozinho, HTTP; **só servidor→cliente**, texto, limite de conexões HTTP/1.1 por domínio no navegador (≈ 6; com HTTP/2 o limite sobe: ⚠️ confira a MDN), sem binário.
- **WebSocket:** bidirecional e binário; **mais difícil** (reconexão, backpressure, autenticação, *proxies*, escala) e **sem *ack***.
- **Quando NÃO usar nenhum dos dois:** a atualização é rara (>30 s) ou o cliente é um *backend* (use **webhook**, P3.10, ou fila); *polling* com cache de 5–10 s costuma bastar e **escala melhor** que 20 000 conexões longas.

## ⚠️ Erros comuns e boas práticas de produção
- **`setAllowedOrigins("*")`** com autenticação por cookie: *hijacking* entre sites.
- **Emissor vazando:** esquecer de remover o `SseEmitter` em `onTimeout/onError` ⇒ memória.
- **Sem *heartbeat***: o *proxy* ou o ALB fecha a conexão ociosa (e o cliente fica "sem receber" sem aviso).
- ***Buffering* do *proxy*:** nginx pode **acumular** a resposta e o cliente só vê os eventos em bloco (⚠️ não testado; a documentação do seu *proxy* diz como desligar).
- **Estado só em memória** (`history`, mapa de emissores): **perde tudo** num *deploy*; o *replay* real vem de uma fonte durável.
- **Enviar dado pessoal** no stream sem autorização por conta (IDOR).
- **JWT na URL**.
- **Bloquear a *thread* do evento** enviando para um cliente lento: use filas por cliente e **descarte** os lentos.

## 🎤 Na entrevista
**1. "SSE ou WebSocket?"** *Resposta-modelo:* SSE para **empurrar do servidor** (notificações, progresso): HTTP, reconexão automática com `Last-Event-ID`, simples de proteger. WebSocket quando o **cliente também envia** com frequência (chat, colaboração) ou precisa de binário; custo: reconexão, *ack* e escala por conta própria.
**2. "Como escalar conexões de tempo real em várias instâncias?"** *Resposta-modelo:* a conexão vive **numa** instância; o evento precisa chegar a **todas** (grupo de consumidores por instância no Kafka, ou *pub/sub* Redis), e cada uma entrega aos seus clientes; o *replay* vem de uma fonte durável; balanceador com *timeouts* maiores que o *heartbeat*.
**3. "Quais os riscos de segurança de WebSocket?"** *Resposta-modelo:* *Cross-Site WebSocket Hijacking* (validar `Origin`), autenticação do canal (não confiar só no cookie sem checar a origem; não usar token em URL), autorização por recurso (IDOR), limites de tamanho/taxa de mensagem.
