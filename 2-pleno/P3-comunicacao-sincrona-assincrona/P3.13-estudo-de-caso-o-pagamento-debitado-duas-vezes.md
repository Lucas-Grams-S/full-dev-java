# P3.13 — Estudo de caso: o pagamento debitado duas vezes

> ⏱️ ~1h30 · 🔵 Pleno · Pré-requisitos: P3.04 a P3.10 (Kafka, garantias, idempotência, retry/DLQ, Outbox, webhooks), P2.02 (travas), P1.13 (estudo de caso anterior)

> ✅ **Validação final (2026-11-24):** módulo executado no PayFlow reconstruído; resultado e o que continua não executado no [README do módulo](README.md). Os avisos "não executado" / "por leitura" abaixo descrevem a escrita original.

> ⚠️ **Verificação:** o **mecanismo** do incidente foi **reproduzido de verdade** em `lab/messaging-lab` (`DoubleDebitCaseIT`, 3 testes: Kafka 4.3.1, PostgreSQL 18, `kafka-clients` 4.2.2, JDK 25.0.5): um consumidor Kafka **expulso do grupo** por lentidão reprocessa a mensagem e o **débito duplica**; com idempotência, não. **A narrativa do incidente (cliente, valores, horários, prazos de *deploy*) é fictícia**, criada para ensinar. Os números do laboratório (2 débitos × 1) são medidos; **nenhuma estatística de mercado** é afirmada. Estornos, reconciliação em volume e o PayFlow do aluno: **por leitura**.

## 🎯 Objetivos
Ao final desta aula você consegue:
- **Investigar** um incidente de duplicidade com **evidência** (consulta de reconciliação, linha do tempo, log do consumidor) em vez de palpite.
- **Reproduzir** a causa raiz em laboratório e **provar** a correção.
- **Corrigir em camadas** (consumidor idempotente, tempo de *poll*, Outbox, observabilidade) e **remediar** os clientes afetados respeitando a **regra 5** (lançamentos nunca alterados).
- **Registrar** a decisão como ADR (**0015**) com opções, trade-offs e consequências.

## 🤔 Por que isso importa
É o **pior tipo de bug** em pagamentos: **silencioso**, intermitente, raro nos testes e **caro** (dinheiro do cliente, reputação, regulação). Ele reúne tudo o que o módulo ensinou: *at-least-once*, *rebalance*, idempotência, Outbox. O Pleno é quem **investiga e fecha** essa classe de problema.

## 💡 Intuição (explicação simples)
Um **caixa** cobra a compra, mas o **chefe o chama** para outra tarefa no meio do atendimento e ele demora. O gerente acha que ele **sumiu** e **passa a cliente para outro caixa**, que **cobra de novo**. Quando o primeiro volta, a cliente **já pagou duas vezes**. O problema **não** foi um caixa ruim: foi **não existir um recibo numerado** que o segundo caixa pudesse consultar.

## 🔬 A investigação (formato ADR: contexto → diagnóstico → opções → decisão)

### 1. Contexto (fictício)
O PayFlow processa **pagamentos de cobrança** (`PaymentRequested`) a partir de um tópico Kafka; um consumidor (`PaymentConsumer`) **debita** a conta do cliente e grava em `payments`. Em uma semana de pico, o suporte recebe **tickets**: *"fui cobrado duas vezes pela mesma compra"*. O saldo total **bate** com os lançamentos (a regra 3 não acusa nada): **cada débito** tem seu lançamento; o erro é **dois débitos para um pedido**.

### 2. Linha do tempo (como a evidência foi lida)
1. **Reconciliação:** `payments` com o mesmo `request_id` mais de uma vez.
```sql
select request_id, count(*) c, sum(amount) total
from payments
where request_id is not null
group by request_id
having count(*) > 1;
```
No laboratório: `[{request_id=pay-777, c=2, total=200.00}]` (um pedido de 100,00 debitado **200,00**).
2. **Padrão:** os duplicados ocorrem **em lotes**, em horários de **pico**, com intervalo de **vários segundos** entre os dois débitos.
3. **Log do consumidor** no pico: `Offset commit cannot be completed since the consumer is not part of an active group for auto partition assignment; it is likely that the consumer was kicked out of the group` (**erro real** do laboratório: `CommitFailedException`) e o *rebalance* logo antes.
4. **Hipótese:** o processamento passou de `max.poll.interval.ms`; o Kafka deu o consumidor como morto, **reatribuiu** a partição e a mensagem foi **reentregue** (*at-least-once*, P3.06); como o consumidor **não era idempotente**, debitou outra vez.

### 3. Reprodução (o "teste que falha")
```java
/** Um consumidor com max.poll.interval.ms=3000 cujo processamento da 1a entrega leva 5 s. */
void runScenario(Consumer<String> handler) throws Exception {
    String topic = KafkaBasicsIT.newTopic(1);
    try (var p = KafkaBasicsIT.producer()) { p.send(new ProducerRecord<>(topic, "cliente", "pay-777")).get(); }
    var cfg = new HashMap<String, Object>(Map.of("bootstrap.servers", KafkaBasicsIT.BOOT, "group.id", "g-case-" + topic,
            "auto.offset.reset", "earliest", "enable.auto.commit", "false", "max.poll.interval.ms", "3000",
            "key.deserializer", org.apache.kafka.common.serialization.StringDeserializer.class.getName(),
            "value.deserializer", org.apache.kafka.common.serialization.StringDeserializer.class.getName()));
    try (var c = new KafkaConsumer<String, String>(cfg)) {
        c.subscribe(List.of(topic));
        boolean first = true;
        long end = System.currentTimeMillis() + 25_000;
        int committed = 0;
        while (committed == 0 && System.currentTimeMillis() < end) {
            for (var r : c.poll(Duration.ofMillis(500))) {
                handler.accept(r.value());                              // 1) efeito (debito)
                if (first) { Thread.sleep(5000); first = false; }       // 2) lento: passa do max.poll.interval.ms
                try { c.commitSync(); committed++; }                    // 3) commit
                catch (CommitFailedException e) { System.out.println("CASO commit falhou (consumidor expulso do grupo); a mensagem sera reentregue"); }
            }
        }
    }
}

@Test
void withoutIdempotencyTheCustomerIsDebitedTwice() throws Exception {
    runScenario(id -> consumer.handleUnprotected("cliente", new BigDecimal("100.00")));
    var saldo = jdbc.sql("select balance from wallets where id='cliente'").query(BigDecimal.class).single();
    int n = jdbc.sql("select count(*) from payments").query(Integer.class).single();
    System.out.println("CASO_SEM_IDEMPOTENCIA pagamento unico pay-777 de 100.00 -> debitos=" + n + " saldo=" + saldo);
    assertThat(n).isEqualTo(2);
}

@Test
void withIdempotencyTheCustomerIsDebitedOnce() throws Exception {
    runScenario(id -> consumer.handleIdempotent(id, "cliente", new BigDecimal("100.00")));
    var saldo = jdbc.sql("select balance from wallets where id='cliente'").query(BigDecimal.class).single();
    int n = jdbc.sql("select count(*) from payments").query(Integer.class).single();
    System.out.println("CASO_COM_IDEMPOTENCIA pagamento unico pay-777 de 100.00 -> debitos=" + n + " saldo=" + saldo);
    assertThat(n).isEqualTo(1);
}

@Test
void reconciliationQueryFindsDuplicates() throws Exception {
    runScenario(id -> {
        consumer.handleUnprotected("cliente", new BigDecimal("100.00"));
        jdbc.sql("update payments set request_id = :r where request_id is null").param("r", id).update();
    });
    var dups = jdbc.sql("select request_id, count(*) c, sum(amount) total from payments where request_id is not null group by request_id having count(*) > 1")
            .query().listOfRows();
    System.out.println("CASO_CONCILIACAO duplicados=" + dups);
    assertThat(dups).hasSize(1);
}
```
```text
CASO commit falhou (consumidor expulso do grupo); a mensagem sera reentregue
CASO_CONCILIACAO duplicados=[{request_id=pay-777, c=2, total=200.00}]
CASO commit falhou (consumidor expulso do grupo); a mensagem sera reentregue
CASO_SEM_IDEMPOTENCIA pagamento unico pay-777 de 100.00 -> debitos=2 saldo=800.00
CASO commit falhou (consumidor expulso do grupo); a mensagem sera reentregue
CASO_COM_IDEMPOTENCIA pagamento unico pay-777 de 100.00 -> debitos=1 saldo=900.00
```
- **Sem idempotência:** **1** pagamento (`pay-777`, R$ 100) ⇒ **2 débitos**, saldo **800,00** (devia ser 900,00). A 1ª entrega debitou, "processou" por 5 s (limite 3 s), o `commitSync` **falhou** e o grupo reentregou.
- **Com idempotência (P3.07):** **1 débito**, saldo **900,00**, mesmo cenário (a 2ª entrega bate na restrição única e é ignorada).
- **Conciliação:** a consulta acima encontra o duplicado.

### 4. Causa raiz e fatores contribuintes (sem culpa)
| Camada | Fator |
|---|---|
| **Causa raiz** | consumidor **não idempotente** consumindo de um canal **at-least-once** |
| **Gatilho** | processamento **lento** (chamada externa dentro do laço do consumidor) excedeu `max.poll.interval.ms` ⇒ *rebalance* |
| **Agravante** | `max.poll.records=500` (padrão): 500 mensagens por `poll` ⇒ o tempo total do lote **estoura** o intervalo |
| **Por que passou nos testes** | o ambiente de teste **nunca** reentrega (consumidor único, rápido); **nenhum teste** reentregava a mesma mensagem |
| **Por que demorou a ser notado** | o saldo **bate** com os lançamentos (a conciliação da regra 3 **não** detecta duplicidade de *pedido*), sem alerta de *lag* nem de `request_id` repetido |

## 🛠️ A correção, em camadas (defesa em profundidade)

| # | Medida | Evita | Referência |
|---|---|---|---|
| 1 | **Consumidor idempotente:** `INSERT processed_messages … ON CONFLICT DO NOTHING` **+** débito na **mesma transação**, chave = `paymentRequestId`/`eventId` do **produtor** | o dano, **mesmo se** a mensagem repetir | P3.07 |
| 2 | **Restrição única no próprio efeito:** `UNIQUE (request_id)` em `payments` | segunda barreira (a do banco, que não depende do código) | P3.07 |
| 3 | **Tempo de *poll*:** reduzir `max.poll.records` (ex.: 10) e tirar chamadas lentas do laço; `max.poll.interval.ms` só **depois** de medir | a **causa** da reentrega | P3.04 |
| 4 | **Outbox** no produtor com `eventId` estável | evento perdido/duplicado por **escrita dupla** | P3.09 |
| 5 | **Conciliação de pedido** (consulta acima) **diária** + alerta se `count > 0` | **detectar** o que as outras camadas deixarem passar | P3.13 |
| 6 | **Alertas** de *lag*, de `CommitFailedException` e de *rebalances* | enxergar **antes** do cliente | P6 |
| 7 | **Teste que reentrega** a mesma mensagem 3× (e concorrente) | regressão | P3.07 |

A medida 1 resolve o **dano**; a 3 resolve a **frequência**; a 5 resolve a **detecção**. **Nenhuma sozinha basta.**

### Remediação dos clientes afetados (regra 5: lançamentos imutáveis)
**Não** se apaga nem edita o lançamento duplicado: **estorna-se** com **novo** lançamento de compensação, **idempotente** (a chave do estorno é `reversal:<paymentId>`):
```sql
-- (por leitura; ajuste aos nomes reais da J3/P2)
insert into ledger_entries (account_id, type, amount, ...)
select account_id, 'CREDIT', amount, ...
from payments p
where p.id in (/* os duplicados "segundos" identificados pela conciliação, aprovados por um humano */);
```
Passos: (1) **congelar** a lista de duplicados com a consulta de reconciliação; (2) **aprovação humana** (quatro olhos); (3) estorno por **lançamento de crédito** com `reversal_of` (rastreável) **e** evento no Outbox para **avisar o cliente**; (4) **verificar** que saldo = Σ lançamentos (regra 3) **depois**; (5) **comunicar** os clientes (jurídico/suporte: fora do escopo técnico).

## 🧠 Pausa para lógica
**Enunciado.** Em um dia, o consumidor processou **10 000** pagamentos e **12** foram duplicados. (a) A taxa de duplicidade? (b) O saldo total dos clientes bate com os lançamentos? (c) Se cada pedido é de R$ 80 em média, quanto foi **debitado a mais**? (d) Por que um **teste de carga** comum **não** acharia isso?

<details><summary>Solução</summary>

(a) 12 ÷ 10 000 = **0,12%**. (b) **Sim**: cada débito duplicado tem **seu** lançamento; a regra 3 compara saldo com lançamentos, não **pedido × débitos** (conciliação **de pedido** é outra consulta). (c) 12 × R$ 80 = **R$ 960**. (d) Teste de carga mede vazão/latência com consumidor **saudável**; a duplicidade exige **reentrega** (lentidão, *rebalance*, queda), que o teste não provoca: é preciso **injetar a falha** (caos, S4) ou **testar a reentrega** diretamente.
**Variação:** `max.poll.records=500` e cada mensagem leva 700 ms. Quanto leva um `poll` completo, e passa de 300 s? (500 × 0,7 s = **350 s** > 300 s: **expulsão garantida**. Com `max.poll.records=100`: 70 s, ok.)
</details>

## ⚖️ Trade-offs e quando NÃO usar (a decisão)
| Opção | Prós | Contras | Veredito |
|---|---|---|---|
| **A) Aumentar `max.poll.interval.ms`** | 1 linha | **esconde** o problema; um consumidor travado de verdade demora para ser detectado; **não** evita duplicata por queda | só como **ajuste**, depois de medir |
| **B) Trocar para *at-most-once*** (confirmar antes) | sem duplicata | **perde** pagamentos | **rejeitada** (dinheiro) |
| **C) Transações do Kafka (EOS)** | atômico Kafka→Kafka | **não** cobre o banco (P3.06) | **não resolve** este caso |
| **D) Consumidor idempotente + restrição única** | **resolve o dano**, funciona também em RabbitMQ/webhook | uma tabela e retenção a gerir | **escolhida** |
| **E) Trava distribuída por pedido** (Redis) | tenta "um por vez" | mais uma peça, **expira** (mesmo problema de lease), complexidade | rejeitada (o banco já dá a unicidade) |
**Decisão:** D + medidas 3–7. **Quando NÃO** confiar só em idempotência: efeitos **fora** do banco (e-mail, PSP): lá a chave de idempotência do **provedor** e a **conciliação** são a rede de proteção.

## ⚠️ Erros comuns e boas práticas de produção
- **"Aumentar o timeout resolve."** Troca a frequência, não o risco.
- **Estornar editando/apagando o lançamento** (viola a regra 5 e **destrói** a trilha).
- **Corrigir em produção antes de reproduzir** (você não sabe se corrigiu).
- **Culpar a pessoa** que escreveu o consumidor: a causa é **o sistema** ter permitido (sem teste de reentrega, sem alerta). Postmortem **sem culpa** (S4).
- **Reprocessar a DLQ gerando novo `eventId`** (duplica de novo).
- **Idempotência só na API** (`Idempotency-Key`) **e não** no consumidor: são **duas** fronteiras.

## 🎤 Na entrevista
**1. "Um cliente foi cobrado duas vezes. Como você investiga?"** *Resposta-modelo:* começo pela **evidência**: consulta de reconciliação (pedido × débitos), linha do tempo, logs do consumidor (*rebalance*/`CommitFailedException`), formulo a hipótese (reentrega *at-least-once* + efeito não idempotente), **reproduzo** em teste, corrijo com idempotência (chave do produtor + restrição única na mesma transação), reduzo a causa (`max.poll.records`), adiciono **detecção** (conciliação diária, alertas) e **estorno** com lançamento compensatório.
**2. "Por que não resolveram com exactly-once do Kafka?"** *Resposta-modelo:* a transação do Kafka só é atômica **dentro do Kafka**; o débito está no PostgreSQL e **fora** dela (P3.06). A saída é idempotência no efeito.
**3. "Como reverter o dano respeitando a imutabilidade do livro-razão?"** *Resposta-modelo:* **lançamento de compensação** (estorno) rastreável (`reversal_of`), com aprovação humana e idempotência da própria correção; nunca `UPDATE/DELETE` em lançamento.
