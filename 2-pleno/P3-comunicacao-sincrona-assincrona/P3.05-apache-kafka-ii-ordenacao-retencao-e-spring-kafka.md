## 🤔 Por que isso importa
Na P3.04 você usou o cliente puro. No dia a dia você usa o **Spring Kafka**: ele esconde o laço `poll()` e o commit, e **por isso** erros de configuração (`ack`, concorrência, serialização) viram **perda ou duplicata** sem aviso. E duas decisões de operação aparecem em toda revisão: *"por quanto tempo guardamos?"* (**retenção**) e *"o log guarda o histórico ou só o último estado?"* (**compactação**).

## 💡 Intuição (explicação simples)
O diário (P3.04) não pode crescer para sempre. **Retenção por tempo** é o arquivista que **joga fora os cadernos com mais de 7 dias**, mesmo que ninguém os tenha lido. **Compactação** é o arquivista que, para cada **etiqueta** (conta), mantém **só a última anotação** ("saldo atual") e descarta as anteriores: o diário vira um **cadastro de estados**. O **Spring Kafka** é a **secretária** que lê o diário por você, chama o seu método a cada anotação e marca a página lida **quando você manda**.

## 🔬 Como funciona por dentro

### 1. Ordem: o que preserva e o que quebra
**Preserva:** mesma **chave** (mesma partição) + um **único produtor lógico** + `enable.idempotence=true` (**padrão**, P3.04: mantém a ordem mesmo com `max.in.flight.requests.per.connection=5`) + **um consumidor** por partição processando **em sequência**.
**Quebra:**
| Causa | Por quê |
|---|---|
| **Aumentar o nº de partições** | `hash(chave) % N` muda; a mesma conta passa a cair em outra partição, **depois** das mensagens antigas na antiga |
| **Chave nula/trocada** | mensagens da mesma entidade em partições diferentes |
| **Consumo paralelo dentro da partição** | `@KafkaListener` com `@Async`/*pool* interno processa fora de ordem |
| **Retentativa em tópico separado** (`@RetryableTopic`, P3.08) | a mensagem 1 vai para o tópico de retry e a 2 passa **na frente** |
| **Dois produtores** para a mesma chave (ou *retry* de aplicação que reenvia depois) | a ordem de **chegada** manda |
| **Sem idempotência** em clientes antigos + `max.in.flight > 1` | *retry* de lote reordena |
Para o PayFlow, "ordem por conta" basta; **ordem global não existe** e ninguém deveria depender dela.

### 2. Retenção e compactação
- **`cleanup.policy=delete`** (padrão): o *broker* apaga **segmentos inteiros** velhos conforme `retention.ms` (**7 dias = 604 800 000 ms**, **medido**) e/ou `retention.bytes` (padrão **−1 = sem limite**). Só apaga **segmentos fechados**; o **segmento ativo** não é apagado, e a verificação roda a cada `log.retention.check.interval.ms` (padrão **5 min** na documentação do *broker*; **2 s** no laboratório). **Consumidor lento demais perde dados**: se o *offset* dele for apagado, ele recebe `OffsetOutOfRangeException` (medido) e o `auto.offset.reset` decide o que fazer.
- **`cleanup.policy=compact`:** mantém **a última mensagem de cada chave** (em segmentos **já fechados e "sujos"**); uma mensagem com **valor nulo** (*tombstone*) sinaliza **apagar** a chave. Serve a **tabelas de estado** (cadastro, saldo atual, configuração) reconstruídas relendo o tópico; **não** serve a **eventos** que importam por si (cada transferência é um fato, não "o último valor").
- O **offset nunca é reaproveitado**: apagar o começo **não** renumera; o *log start offset* sobe (medido: 20, com *end offset* 25).

### 3. Spring Kafka em 5 pontos
1. **`KafkaTemplate<K,V>.send(...)`** devolve `CompletableFuture<SendResult>`; **espere/trate** o resultado (o envio é **assíncrono**: sem tratar, "enviei" não prova nada). 
2. **`@KafkaListener`** cria um **contêiner** que faz o `poll()`; seu método roda **na *thread* do contêiner**, **uma mensagem por vez por partição**. `concurrency` = nº de *threads* (≤ partições).
3. **`AckMode`:** padrão **`BATCH`** (confirma **depois** de processar todos os registros do `poll()`, [documentação](https://docs.spring.io/spring-kafka/reference/kafka/receiving-messages/message-listener-container.html)); `RECORD` (a cada registro, mais lento e mais seguro), `MANUAL`/`MANUAL_IMMEDIATE` (você chama `Acknowledgment.acknowledge()`). O Spring Kafka define `enable.auto.commit=false`.
4. **Exceção no listener** → `CommonErrorHandler` (padrão: `DefaultErrorHandler`, repete e, **esgotado, registra e pula** a mensagem!). **Sem configurar DLT, uma mensagem venenosa é descartada com um log** (P3.08).
5. **Serialização:** `String`/`byte[]` simples; JSON com `JacksonJsonSerializer`/`JacksonJsonDeserializer` (Jackson 3, existem no JAR 4.1.2; os `JsonSerializer` antigos são do Jackson 2). **Desserializador JSON confiando em qualquer tipo** (`trusted.packages=*`) é **vulnerabilidade**: confie em pacotes **explícitos**, ou use *record*/DTO fixo.

void onMessage(ConsumerRecord<String, String> rec) {
    int n = attempts.computeIfAbsent(rec.value(), k -> new AtomicInteger()).incrementAndGet();

### C. Retenção: o começo do log some
```java
@Test
void retentionDeletesOldSegmentsButOffsetsKeepGrowing() throws Exception {
    String t = "lab.ret." + UUID.randomUUID().toString().substring(0, 8);
    try (var admin = AdminClient.create(Map.of("bootstrap.servers", KafkaBasicsIT.BOOT))) {
        admin.createTopics(List.of(new NewTopic(t, 1, (short) 1).configs(Map.of("retention.ms", "3000", "segment.ms", "1000", "segment.bytes", "1048576")))).all().get();
        try (var p = KafkaBasicsIT.producer()) {
            for (int i = 0; i < 20; i++) p.send(new ProducerRecord<>(t, "k", "old-" + i)).get();
            Thread.sleep(2500);
            for (int i = 0; i < 5; i++) p.send(new ProducerRecord<>(t, "k", "new-" + i)).get();   // força rolar o segmento
        }
        var tp = new TopicPartition(t, 0);
        long start = 0, end = 0;
        for (int i = 0; i < 40; i++) {
            start = admin.listOffsets(Map.of(tp, OffsetSpec.earliest())).all().get().get(tp).offset();
            end = admin.listOffsets(Map.of(tp, OffsetSpec.latest())).all().get().get(tp).offset();
            if (start > 0) break;
            Thread.sleep(1000);
        }
        System.out.println("RETENCAO log_start_offset=" + start + " log_end_offset=" + end + " (20 antigas escritas, retention.ms=3000)");
        assertThat(start).isGreaterThan(0);
        // quem pede um offset que já foi apagado:
        var cfg = new HashMap<String, Object>(Map.of("bootstrap.servers", KafkaBasicsIT.BOOT, "group.id", "g-ret-" + t, "enable.auto.commit", "false",
                "auto.offset.reset", "none",
                "key.deserializer", org.apache.kafka.common.serialization.StringDeserializer.class.getName(),
                "value.deserializer", org.apache.kafka.common.serialization.StringDeserializer.class.getName()));
        try (var c = new org.apache.kafka.clients.consumer.KafkaConsumer<String, String>(cfg)) {
            c.assign(List.of(tp)); c.seek(tp, 0);
            try { c.poll(Duration.ofSeconds(3)); System.out.println("RETENCAO seek(0) não falhou?"); }
            catch (org.apache.kafka.clients.consumer.OffsetOutOfRangeException e) { System.out.println("RETENCAO seek(0) -> OffsetOutOfRangeException: " + e.offsetOutOfRangePartitions()); }
        }
    }
}
```
```text
RETENCAO log_start_offset=20 log_end_offset=25 (20 antigas escritas, retention.ms=3000)
RETENCAO seek(0) -> OffsetOutOfRangeException: {lab.ret.e6b47147-0=0}
COMPACTACAO 18 mensagens escritas (3 chaves × 6 versões); depois da compactação restam 6: [saldo-v5, saldo-v5, saldo-v5, saldo-v6, saldo-v6, saldo-v6]
```
Escrevemos **20** mensagens "antigas", esperamos mais que `retention.ms=3000`, escrevemos **5** novas (isso **fecha o segmento antigo**) e o *broker* apagou as 20 primeiras: **`log_start_offset=20`, `log_end_offset=25`**. Quem pediu `seek(0)` recebeu **`OffsetOutOfRangeException`** (com `auto.offset.reset=none`; com `earliest` pularia para o 20 **em silêncio**, e você perderia 20 eventos sem erro).

### D. Compactação: a última de cada chave (com uma surpresa)
```java
@Test
void compactionKeepsTheLatestValuePerKey() throws Exception {
    String t = "lab.compact." + UUID.randomUUID().toString().substring(0, 8);
    try (var admin = AdminClient.create(Map.of("bootstrap.servers", KafkaBasicsIT.BOOT))) {
        admin.createTopics(List.of(new NewTopic(t, 1, (short) 1).configs(Map.of("cleanup.policy", "compact", "segment.ms", "1000",
                "min.cleanable.dirty.ratio", "0.01", "min.compaction.lag.ms", "0", "delete.retention.ms", "100")))).all().get();
        try (var p = KafkaBasicsIT.producer()) {
            for (int round = 1; round <= 5; round++) for (String k : List.of("ana", "bruno", "carla")) p.send(new ProducerRecord<>(t, k, "saldo-v" + round)).get();
            Thread.sleep(2500);
            for (String k : List.of("ana", "bruno", "carla")) p.send(new ProducerRecord<>(t, k, "saldo-v6")).get();   // rola o segmento
        }
        List<String> seen = List.of();
        for (int i = 0; i < 40; i++) {
            seen = DeliveryAndIdempotencyIT.readAll(t, "read_uncommitted");
            if (seen.size() <= 6) break;
            Thread.sleep(1000);
        }
        System.out.println("COMPACTACAO 18 mensagens escritas (3 chaves × 6 versões); depois da compactação restam " + seen.size() + ": " + seen);
        assertThat(seen.size()).isLessThan(18);
    }
}
```
Escrevemos 18 mensagens (3 chaves × 6 versões). Depois da compactação sobraram **6**: `[saldo-v5 ×3, saldo-v6 ×3]`. **Não** sobrou 3: a v5 de cada chave ficou no segmento **fechado** (compactado), mas a v6 estava no segmento **ativo**, que **não é compactado**. **Compactação não é "uma por chave, sempre"**: é "**no máximo** a última **dos segmentos antigos**"; o leitor tem de **tolerar** versões repetidas (e a última que ele vê é a verdadeira).

## 🧠 Pausa para lógica
**Enunciado.** Um tópico recebe **2 000 eventos/s** de **500 bytes**. (a) Quantos GiB/dia (sem replicação)? (b) Com retenção de 14 dias e fator de replicação 3, quanto disco no total? (c) O *lag* de um consumidor chegou a **3 dias**; ele perde dados com retenção de 7 dias? E se ele ficar parado **8 dias**?

<details><summary>Dica</summary>

1 GiB = 2³⁰ bytes. Replicação multiplica o disco.
</details>

<details><summary>Solução</summary>

(a) 2 000 × 500 = 1 000 000 B/s = ~0,93 MiB/s; × 86 400 s = 86 400 000 000 B ≈ **80,5 GiB/dia**. (b) 80,5 × 14 × 3 ≈ **3 380 GiB (≈ 3,3 TiB)**. (c) Com **3 dias** de *lag* e 7 de retenção: **não** perde (está dentro da janela); parado **8 dias**: **perde** o dia mais antigo (o *offset* dele já foi apagado ⇒ `OffsetOutOfRangeException`/salto conforme `auto.offset.reset`). Por isso: **alerta de lag** muito antes de chegar perto da retenção (P6).
**Variação:** o evento cai para 200 bytes com compressão 3:1 (`compression.type=lz4`)? Refaça (a): ≈ 80,5 × 200/500 ÷ 3 ≈ **10,7 GiB/dia** (compressão **depende** do conteúdo: meça).
</details>

## ⚖️ Trade-offs e quando NÃO usar
- **Retenção longa** = reprocessar o passado fácil, **mais disco** e mais **dado pessoal guardado** (LGPD, J8.07: o evento tem **ids**, não dados pessoais, para poder **expirar** sem drama). **Curta** = barato, **risco** para consumidores lentos.
- **Compactação:** ótima para **estado**, **errada** para **fatos**. E **apagar um dado pessoal** por compactação exige *tombstone* + esperar a limpeza: não é imediato.
- **`AckMode.RECORD`** (mais seguro, mais *commits*) × **`BATCH`** (rápido, mais **repetição** depois de uma queda: até um `poll()` inteiro, até `max.poll.records=500`).
- **Muitas partições** = paralelismo, **mais arquivos abertos, mais *rebalance* lento, mais latência de eleição** (⚠️ não medido aqui).
**Quando NÃO usar o Kafka como banco:** ele **não** consulta por chave com eficiência, **não** tem transação com o seu banco, e o histórico é **limitado pela retenção**. A fonte da verdade do saldo é o PostgreSQL.

## ⚠️ Erros comuns e boas práticas de produção
- **`DefaultErrorHandler` sem DLT:** a mensagem que falha de vez é **registrada e descartada** (P3.08 corrige).
- **Listener chamando `@Async`** para "ir mais rápido": **quebra a ordem** e o commit acontece **antes** do trabalho acabar.
- **`auto-offset-reset: earliest` em produção** num grupo **novo** reprocessa **todo** o histórico (milhões de e-mails!). Defina por grupo e proteja efeitos externos com idempotência (P3.07).
- **JSON com `trusted.packages=*`.**
- **Mudar o formato do evento sem versão:** consumidores antigos **quebram** (P5: compatibilidade; por ora `schemaVersion` no evento).
- **Esquecer `.get()`/callback no `send`:** falhas de produção ficam **invisíveis**.
- **Medir a retenção em minutos** e esquecer o **segmento ativo**: o teste mostrou que é preciso **rolar** o segmento para o *broker* apagar.

## 🎤 Na entrevista
**1. "Retenção × compactação?"** *Resposta-modelo:* retenção apaga por **idade/tamanho** (bom para fluxo de eventos); compactação mantém **a última por chave** nos segmentos antigos (bom para estado; o segmento ativo não é compactado; *tombstone* apaga a chave).
**2. "Como preservar a ordem de uma conta?"** *Resposta-modelo:* chave = id da conta, um produtor lógico, idempotência (padrão), consumo sequencial por partição, **sem** `@Async` no listener, e **não** aumentar partições sem plano de migração.
**3. "O consumidor ficou 10 dias fora e a retenção é de 7. E agora?"** *Resposta-modelo:* o *offset* foi apagado: `OffsetOutOfRangeException` ou salto silencioso (conforme `auto.offset.reset`); reconstruir a partir da **fonte da verdade** (o banco) ou de um *snapshot*; prevenir com alerta de *lag* e retenção compatível com o tempo de recuperação.
