## 🎯 Objetivos
Ao final desta aula você consegue:
- **Subir** um Keycloak com Docker, **importar um realm** e **esperar** que ele esteja pronto sem adivinhar.
- **Configurar** clientes (público × confidencial), escopos (padrão × opcional), **audiência**, papéis e usuários **como código**, e **explicar** o que cada ajuste muda no token.
- **Mover** para o realm as defesas que o PayFlow implementava à mão (bloqueio por tentativas, política de senha) e **provar** que funcionam.
- **Listar** o que um Keycloak **de produção** exige que o de desenvolvimento esconde.
- **Comparar** Keycloak, Spring Authorization Server e os serviços gerenciados (Cognito, Entra ID, Identity Platform).

## 🤔 Por que isso importa
Na J8 o PayFlow carregava três responsabilidades que **não são da API**: **guardar senhas** (BCrypt), **limitar tentativas** (`LoginThrottle`, em memória, que só protege **uma** instância) e **aplicar política de senha** (`PasswordPolicy`). Cada uma virou código, testes e risco. Um servidor de identidade as entrega **prontas, revisadas por milhares de instalações e com interface de administração**.

No dia a dia de um pleno, "subir o Keycloak" não é o difícil (são 20 segundos). O difícil é **tratá-lo como o que ele é**: o **cofre das identidades**, uma peça que, se cair, **derruba o login de tudo**, e cuja configuração precisa estar **no Git**, não em cliques que ninguém lembra.

## 💡 Intuição (explicação simples)
Se o PayFlow é um **prédio**, o Keycloak é a **portaria**: um balcão com porteiro, cadastro de moradores, crachás com prazo e uma regra para quem erra a senha demais. Antes, cada apartamento (a API) tinha o **próprio porteiro** improvisado. Agora o prédio tem **uma portaria só**, e os apartamentos só conferem o **crachá** (o token), sem precisar conhecer o morador.

## 🔬 Como funciona por dentro

### Os conceitos do Keycloak (o vocabulário mínimo)
| Conceito | O que é | Neste laboratório |
|---|---|---|
| **Realm** | um "universo" isolado: usuários, clientes, papéis, políticas, **chaves próprias** | `payflow` (o `master` é só da administração) |
| **Client** | um aplicativo/serviço que pede tokens | `payflow-web` (público), `payflow-notifications` e `payflow-reporting` (confidenciais), `payflow-lab-direct` (só testes) |
| **Client scope** | um **pacote** de *claims*/permissões que o cliente pode pedir | `transfers:read`, `transfers:write`, `internal:notify`, `payflow-api-audience` |
| **Protocol mapper** | regra que **escreve uma claim** no token | o *audience mapper* que escreve `aud=payflow-api` |
| **Realm role** | papel do **usuário** | `USER`, `ADMIN` |
| **Service account** | o "usuário" de um cliente confidencial (client credentials) | um por cliente de serviço |
| **Default × optional scope** | o padrão vem **sempre**; o opcional só se o cliente o **pedir** (e tiver o direito) | `transfers:*` e `internal:notify` são **opcionais** |

### Cliente público × confidencial
- **Público** (`payflow-web`): **não consegue guardar segredo** (app móvel, SPA, binário que o usuário baixa). Autentica-se **só por PKCE**.
- **Confidencial** (`payflow-notifications`): roda **no servidor**, guarda um `client_secret` e o usa para provar quem é **no *endpoint* de token**.

## 🛠️ Exemplo prático

### 1. Subir e **esperar** (executado)
```bash
docker run -d --name lab-p10-keycloak -p 127.0.0.1:8180:8080 \
  -e KC_BOOTSTRAP_ADMIN_USERNAME=admin -e KC_BOOTSTRAP_ADMIN_PASSWORD=lab-admin-only \
  -v "$PWD/payflow-realm.json:/opt/keycloak/data/import/payflow-realm.json:ro" \
  quay.io/keycloak/keycloak:26.8.2 start-dev --import-realm
until curl -fs http://127.0.0.1:8180/realms/payflow/.well-known/openid-configuration >/dev/null; do sleep 2; done
```
```
keycloak ready after ~18s
```
- `-p 127.0.0.1:8180:8080`: **só no laptop** (a regra da J9: o Docker contorna o firewall, então publique em `127.0.0.1`).
- `KC_BOOTSTRAP_ADMIN_*`: o administrador **temporário** do realm `master`. **Só do laboratório**: em produção, crie um administrador de verdade e **remova** o temporário.
- **Esperar pela URL do realm** (e não por `sleep 20`): é ela que a API vai consultar.
- `start-dev` **não é produção** (seção "Em produção").

### 2. O JSON do realm (trechos)
```json
{ "realm": "payflow", "sslRequired": "external",
  "bruteForceProtected": true, "failureFactor": 5,
  "accessTokenLifespan": 300, "ssoSessionIdleTimeout": 1800,
  "revokeRefreshToken": true, "refreshTokenMaxReuse": 0,
  "passwordPolicy": "length(12) and notUsername",
  "roles": { "realm": [ {"name":"USER"}, {"name":"ADMIN"} ] },
  "clients": [
    { "clientId": "payflow-web", "publicClient": true, "standardFlowEnabled": true,
      "directAccessGrantsEnabled": false,
      "redirectUris": ["http://127.0.0.1:8099/callback", "http://localhost:8080/login/oauth2/code/keycloak"],
      "attributes": { "pkce.code.challenge.method": "S256" } },
    { "clientId": "payflow-notifications", "publicClient": false, "serviceAccountsEnabled": true,
      "standardFlowEnabled": false, "secret": "lab-only-notifications-secret-change-me" } ],
  "users": [ { "id": "11111111-1111-4111-8111-111111111111", "username": "alice@example.com",
               "realmRoles": ["USER"], "credentials": [{"type":"password","value":"alice-lab-pass-1","temporary":false}] } ] }
```
| Ajuste | Efeito medido |
|---|---|
| `sslRequired: external` | HTTP só em endereços locais (por isso funciona em `127.0.0.1`); fora dele, o Keycloak exige HTTPS |
| `accessTokenLifespan: 300` | `exp − iat = 300` (testado: `KeycloakRealmIT`) |
| `pkce.code.challenge.method: S256` | sem `code_challenge`, o fluxo **não começa** (`Missing parameter: code_challenge_method`) |
| `directAccessGrantsEnabled: false` em `payflow-web` | o app **não pode** receber a senha (P10.01) |
| `redirectUris` **exatos** | `http://evil.example/callback` → `400`, sem tela de login |
| `"id"` do usuário | **o `sub` do token é exatamente esse UUID** (medido: `sub=11111111-1111-4111-8111-111111111111`) |
| `bruteForceProtected` + `failureFactor: 5` | 5 falhas seguidas bloqueiam (seção 4) |

> 💸 **Os segredos acima são do laboratório** (`lab-only-…-change-me`) e **estão num arquivo versionado de propósito**. Em qualquer ambiente real o `secret` **não** vai no JSON do realm: entra por variável/arquivo do cofre (P10.05).

### 3. Uma armadilha medida: o JSON que **apagou `sub` e as permissões**
Minha primeira versão do JSON declarava **os escopos próprios** dentro do realm (`"clientScopes": [ … ]`). O Keycloak subiu, o login funcionou e **o token veio assim**:
```
{"iss":"http://127.0.0.1:8180/realms/payflow","aud":"payflow-api","typ":"Bearer",
 "azp":"payflow-lab-direct","sid":"…","scope":"openid transfers:read"}
```
**Sem `sub`. Sem `realm_access`. Sem e-mail.** A causa: ao importar um realm que **declara** `clientScopes`, o Keycloak **não cria** os escopos embutidos (`basic`, `roles`, `profile`, `email`) — e são eles que carregam os *mappers* de `sub` e dos papéis. O cliente os listava, mas eles **não existiam**. Uma API que dependesse de `sub` (o dono, IDOR) teria **quebrado em silêncio**, ou pior: tratado todo mundo como o mesmo usuário.

**Correção:** o JSON declara só realm, clientes, papéis e usuários; **os escopos próprios nascem pela Admin REST API** (`kc-setup.py`), **depois** que o Keycloak criou os embutidos. Depois da correção, o mesmo pedido devolveu:
```
claims={"iss":"http://127.0.0.1:8180/realms/payflow","aud":"payflow-api","sub":"11111111-1111-4111-8111-111111111111",
        "typ":"Bearer","azp":"payflow-lab-direct","realm_access":{"roles":["USER"]},
        "scope":"openid profile transfers:read email","name":"Alice Silva","email":"alice@example.com", …}
```
**Lição:** **teste o token que o servidor emite**, não o JSON que você escreveu (`KeycloakRealmIT.userAccessToken_hasTheClaimsTheApiReads`).

### 4. Escopos e audiência pela Admin REST API (`kc-setup.py`, executado)
```python
SCOPES = {
    "payflow-api-audience": {"mapper": True, "type": "default"},   # escreve aud=payflow-api
    "transfers:read": {"type": "optional"},
    "transfers:write": {"type": "optional"},
    "internal:notify": {"type": "optional"},
}
# … cria o que faltar (idempotente) e liga cada escopo ao cliente certo:
PLAN = {
    "payflow-web":           {"default": ["payflow-api-audience"], "optional": ["transfers:read", "transfers:write"]},
    "payflow-notifications": {"default": ["payflow-api-audience"], "optional": ["internal:notify"]},
    "payflow-reporting":     {"default": ["payflow-api-audience"], "optional": []},   # NÃO tem internal:notify
}
```
Saída da subida (`out-setup.txt`): `create scope transfers:read 201`, … `payflow-notifications: optional scope internal:notify -> 204`. Duas consequências **medidas**:
- Pedir **só** `openid` a um cliente com escopo **opcional** devolve `scope=openid profile email`: **sem** `transfers:*`. O escopo **não vem de graça**.
- O cliente **sem o direito** que pede o escopo **é recusado**: `payflow-reporting` pedindo `internal:notify` → **`400 {"error":"invalid_scope","error_description":"Invalid scopes: internal:notify"}`**.

### 5. O que o Keycloak emite para uma **máquina** (executado)
```
service claims={"exp":…,"iat":…,"jti":"trrtcc:…","iss":"http://127.0.0.1:8180/realms/payflow","aud":"payflow-api",
  "sub":"f4ca3ca0-d53e-4410-ad9f-1317b7424f2c","typ":"Bearer","azp":"payflow-notifications","scope":"internal:notify",
  "clientHost":"172.17.0.1","clientAddress":"172.17.0.1","client_id":"payflow-notifications"}
service has refresh_token=false
wrong secret -> 401 {"error":"unauthorized_client","error_description":"Invalid client or Invalid client credentials"}
```
Sem `email`, sem papéis de usuário, **sem *refresh token*** (a máquina simplesmente pede outro). O `sub` é o da **conta de serviço**, não de uma pessoa. E o Keycloak acrescenta `clientHost`/`clientAddress`/`client_id` (**não** os use para autorizar: o endereço depende da rede por onde o pedido passou).

### 6. As defesas que saíram do código do PayFlow (executado: `RealmPolicyIT`)
```
failure #1 -> 400 Invalid user credentials
…
failure #5 -> 400 Invalid user credentials
right password after 5 failures -> 400 {"error":"invalid_grant","error_description":"Invalid user credentials"}
reset 'short' -> 400; reset equal to username -> 400; reset ok -> 204
```
- **Bloqueio por tentativas (substitui o `LoginThrottle` da decisão 64):** depois de 5 erros, **até a senha certa é recusada** — e com a **mesma mensagem** (`Invalid user credentials`): quem ataca **não descobre** que a conta está bloqueada (nem o Keycloak ajuda a enumerar). A decisão 64 registrava o custo do `LoginThrottle` (trancar a conta alheia); o do realm **tem o mesmo custo** e a vantagem de **valer para todas as instâncias** e ter **tempos de espera configuráveis** (⚠️ os parâmetros de espera **não** foram testados: só o bloqueio em 5 falhas).
- **Política de senha** (`length(12) and notUsername`): a redefinição administrativa de `short` e de `carol@example.com` (igual ao *username*) falhou com `400` (`Invalid password: minimum length 12.` e `…must not be equal to the username.`). Isso **substitui** a regra de tamanho da `PasswordPolicy` da J8.06. ⚠️ O Keycloak tem outras políticas (dicionário/`passwordBlacklist`, histórico, validade): **não testei**; a verificação contra senhas vazadas (HIBP) da J8.07 **não** tem equivalente automático que eu tenha conferido.

### 7. O PayFlow depois do Keycloak: o que **sai** do código (por leitura)
| Sai (J8) | Para onde vai |
|---|---|
| `PayflowUserDetailsService`, `DaoAuthenticationProvider`, `PasswordEncoder` **da API** | Keycloak |
| `TokenService` + `POST /api/v1/auth/token` + `JwtConfig` (HS256) | Keycloak + `issuer-uri` (P10.03) |
| `LoginThrottle` / `ThrottledAuthenticationProvider` (decisão 64) | `bruteForceProtected` |
| `PasswordPolicy` (tamanho) | `passwordPolicy` |
| `users.password_hash` | **removida** em duas etapas (P10.03: *expand/contract*) |
| `PAYFLOW_SECURITY_JWT_SECRET` | **deixa de existir** (a API só tem chaves públicas) |

## 🏗️ Estudo de caso: o realm que só existia nos cliques
**Situação.** O time sobe o Keycloak de *staging*, configura **tudo pela interface** e funciona. Na produção, alguém refaz "de cabeça" e esquece o *audience mapper* do `payflow-notifications`; o serviço de notificações recebe tokens **sem `aud=payflow-api`** e a API passa a recusá-los (`The aud claim is not valid`). Ninguém sabe o que difere entre os dois ambientes.

**Diagnóstico.** Não há **fonte da verdade**: a configuração do IdP vive **dentro** do IdP.

**Opções.** (A) documentar os passos num wiki (envelhece); (B) **exportar o realm** (`kc.sh export`/a interface) e versionar o JSON (é uma **fotografia**; mistura segredos e dados); (C) **configuração como código aplicada de forma idempotente** (o JSON de **estrutura** + um *script* sobre a Admin API, como `kc-setup.py`; ou o *provider* de Terraform do Keycloak — ⚠️ **não verificado** aqui) com **um teste que pede um token e confere as *claims***.

**Decisão (ADR 0022).** **C**, mais o **teste do token emitido** (`KeycloakRealmIT`) no pipeline. O JSON no Git tem **estrutura e usuários de laboratório**; segredos e usuários reais **não** entram.

## ⚖️ Trade-offs e quando NÃO usar
| | **Keycloak** (autohospedado) | **Spring Authorization Server** | **Gerenciado** (Cognito, Entra ID, Identity Platform) |
|---|---|---|---|
| Esforço inicial | baixo (configuração) | **alto**: você escreve login, consentimento, MFA, administração | mais baixo |
| Operação | **sua**: atualizações, banco, HA, *backup* | sua, **e** o código é seu | **do provedor** |
| Padrões | OIDC/OAuth completo, SAML, federação, MFA | OAuth/OIDC (o que você construir) | variam; recursos próprios |
| Controle e portabilidade | **alto** | máximo | **menor** (claims e fluxos do provedor) |
| Custo | infraestrutura + tempo de quem opera | tempo de desenvolvimento | **por usuário ativo** |
- O **Spring Authorization Server** passou a ser publicado **junto com o Spring Security 7** (o artefato `spring-security-oauth2-authorization-server` existe na versão **7.1.2**, a mesma do Boot 4.1.2; ⚠️ **não o usei**: só conferi o artefato no repositório Maven). **Vale** quando você precisa de um *token endpoint* **muito customizado** e tem quem o mantenha; **não vale** para "ter login".
- **Gerenciado vale** quando **ninguém** do time quer operar identidade (e o custo por usuário cabe). **Atenção:** as *claims* mudam de provedor para provedor (nome do papel, presença de `aud`…): **o conversor de autoridades da API é o adaptador** (P10.03); trocar de provedor **não é** só trocar a URL. ⚠️ Não testei a API contra outro provedor.
- **Keycloak sozinho não é segurança:** sem HTTPS, *backup*, atualização e *monitoramento*, ele é **um alvo único** com todas as identidades.

### Em produção (o que o `start-dev` esconde) — ⚠️ **não executado**
Conferir na [documentação de produção](https://www.keycloak.org/server/configuration-production) e na [de contêineres](https://www.keycloak.org/server/containers):
- **HTTPS** e **nome de host** configurados; **atrás de proxy**: cabeçalhos `X-Forwarded-*` **só** de um proxy confiável.
- **Banco externo** (PostgreSQL): o H2 do modo de desenvolvimento **não** serve; **o banco do Keycloak é separado do banco do PayFlow**.
- Imagem **otimizada** (`start --optimized` depois de `build`), **sem** o administrador temporário, com *backup* do banco e **teste de restauração**.
- **Alta disponibilidade** (várias réplicas coordenadas) e **atualização de versão** como rotina (os *releases* são frequentes: a 26.8.2 saiu em novembro de 2026).
- **Na AWS (P9):** um serviço ECS/Fargate próprio + um RDS próprio + ALB; **cada serviço novo** que o Keycloak chame (SMTP, por exemplo) exige **caminho de saída** (P9.01).
- O que o aluno **precisa decidir** antes: quem **opera** o Keycloak e quem é **acordado** quando ele cai.

## ⚠️ Erros comuns e boas práticas de produção
- **Declarar `clientScopes` no JSON do realm** e ficar sem `sub`/papéis (seção 3). **Sempre** peça um token e leia as *claims*.
- **`redirectUris` com `*`**: redirecionamento aberto (P10.01).
- **`directAccessGrantsEnabled: true` num cliente de produção:** o app volta a receber a senha.
- **Segredo de cliente no repositório** ou no *log*: `client_secret` vazado = qualquer um **vira** aquele serviço (P10.05).
- **Esquecer o `aud`**: o token vale em **qualquer** API do mesmo realm. O *audience mapper* é obrigatório.
- **Misturar o realm `master` com a aplicação**: o `master` administra o Keycloak; a aplicação usa **o seu realm**.
- Mensagem real (senha errada no fluxo de senha): `{"error":"invalid_grant","error_description":"Invalid user credentials"}` — e **a mesma** com a conta bloqueada.

## 🎤 Na entrevista
- **"Cliente público ou confidencial?"** — Depende de **conseguir guardar um segredo**: servidor = confidencial (autentica no *endpoint* de token); navegador/móvel = público (**PKCE**, sem segredo). Segredo dentro de um app distribuído **não é segredo**.
- **"O que é um realm no Keycloak?"** — Um espaço **isolado** de usuários, clientes, papéis, políticas **e chaves de assinatura**. A API confia num realm específico (`issuer`).
- **"Como você versiona a configuração do Keycloak?"** — A **estrutura** (clientes, escopos, papéis, políticas) como código **idempotente** no Git; **segredos** e usuários reais **fora**; e **um teste que pede um token e confere as *claims*** — porque a configuração pode estar "certa" e emitir o token errado (medi: sem `sub`).
- **"Por que não escrever o próprio servidor de autorização?"** — Login, MFA, recuperação de senha, bloqueio, consentimento, administração e **segurança de protocolo** são enormes e cheios de armadilhas (**RFC 9700**). O **custo de manter** supera o de **operar** um pronto — salvo requisito muito específico.

### Equivalência AWS ↔ Azure ↔ GCP (identidade de usuários)

- [ ] Subo o Keycloak com Docker e **espero** o realm responder (sem `sleep` cego).

- [ ] Diferencio cliente **público** × **confidencial** e escopo **padrão** × **opcional**.
