Os números percentuais vêm de **uma** execução com *hash* determinístico: **repetíveis**, mas dependentes dos IDs usados (`user-0…user-99999`).

## 🎯 Objetivos
Ao final desta aula você consegue:
- **Separar** *deploy* (o código chegou ao servidor) de *release* (o usuário vê a mudança) e **dizer** que problema isso resolve.
- **Classificar** *flags* (de *release*, de experimento, operacionais/*kill switch*, de permissão) por **tempo de vida e dono**.
- **Implementar** um avaliador com **precedência de regras**, ***rollout* percentual estável**, **sal por *flag*** e **atualização atômica**, e **provar** cada propriedade com um teste.
- **Controlar** a **dívida de *flags*** (vencimento, dono, remoção) e **testar os dois ramos**.
- **Decidir** entre *flag* próprio, OpenFeature e serviço gerenciado.

## 🤔 Por que isso importa
Na P8.03, o *canary* limitou o risco **no deploy**. O *feature flag* limita o risco **depois do deploy**: o código novo **está em produção, desligado**; liga-se para 1% dos usuários, depois 10%, e **desliga-se em segundos, sem deploy**, se algo der errado. É a ferramenta que permite **integrar código incompleto na `main` todo dia** (CI de verdade, P8.01) sem expô-lo. Também é uma **fonte clássica de incidentes**: *flag* esquecido, *flag* lido de forma inconsistente, *flag* que ninguém sabe se pode ser removido. O PayFlow lida com dinheiro: um *flag* **nunca** pode contornar uma invariante do *ledger*.

## 💡 Intuição (explicação simples)
O **disjuntor** de cada cômodo do painel elétrico (e não só o geral): a fiação nova já está instalada na parede (o **deploy**), mas a corrente só passa quando você **liga o disjuntor** (o **release**). Você liga o do quarto de hóspedes primeiro; se o fusível queimar, **desliga** sem mexer na fiação. E há uma regra de casa: um **disjuntor sem etiqueta** (sem dono nem data) é perigoso: **ninguém sabe** se pode ser removido.

## 🔬 Como funciona por dentro

### Quatro tipos de *flag* (a classificação de Fowler)
| Tipo | Para quê | Vida | Exemplo no PayFlow |
|---|---|---|---|
| **Release** | esconder funcionalidade incompleta até estar pronta | **dias/semanas**; **remova** depois | `transfer.new-limit-rules` |
| **Experimento** | comparar variantes (A/B) | semanas; remova ao decidir | `checkout.fee-layout-b` |
| **Operacional** (*kill switch*) | desligar uma dependência/feature sob estresse | **longa**; é parte da operação | `webhook.dispatch` (liga/desliga o envio, P3.10) |
| **Permissão** | recursos por plano/cliente | **longa**; é regra de negócio | `limits.premium` |

A classificação importa porque **a vida útil define a disciplina**: *flag* de release que **fica para sempre** vira **dívida** (caminho de código morto, dois ramos para testar); *flag* de permissão **é** o produto. Veja o [artigo de Fowler](https://martinfowler.com/articles/feature-toggles.html) para a taxonomia completa.

### O avaliador (código **executado**)
Ordem de decisão em `FeatureFlags.isEnabled(chave, contexto, valorPadrão)`:
```java
boolean decide(Map<String, Flag> flags, String key, Context ctx, boolean defaultValue) {
    Flag f = flags.get(key);
    if (f == null) return defaultValue;                          // 0. flag desconhecido: o PADRÃO é de quem chama
    if (!f.enabled()) return false;                              // 1. kill switch vence tudo
    if (f.allowUsers().contains(ctx.userId())) return true;      // 2. testadores internos
    for (var e : f.requiredAttributes().entrySet())              // 3. regra de segmentação (país, plano)
        if (!e.getValue().equals(ctx.attributes().get(e.getKey()))) return false;
    return bucket(f.key(), ctx.userId()) < f.basisPoints();      // 4. percentual
}

/** Balde estável 0..9999 a partir do SHA-256 de "flag:usuario" (a chave do flag é o SAL). */
int bucket(String flagKey, String userId) {
    byte[] h = MessageDigest.getInstance("SHA-256").digest((flagKey + ":" + userId).getBytes(UTF_8));
    long v = ((h[0] & 0xFFL) << 24) | ((h[1] & 0xFFL) << 16) | ((h[2] & 0xFFL) << 8) | (h[3] & 0xFFL);
    return (int) (v % 10_000);
}
```
Cada linha tem um **motivo** e um **teste**:

**1. Precedência (executado):**
```
PASS allowlisted user sees pix-v2 even at 0%
PASS kill switch beats the allowlist
PASS unknown flag returns the CALLER's default
```
O *kill switch* **vence até a lista de testadores**: quando você desliga, **desliga para todos**. O **padrão vem de quem chama**: para uma funcionalidade **nova**, `false` (falha fechada); para um **kill switch operacional** de algo que já funciona, o padrão **é `true`** (se o serviço de *flags* cair, **o sistema continua como antes**).

**2. *Rollout* percentual (executado):** o usuário cai num **balde** (0–9999, *basis points*) calculado por *hash*; `balde < percentual × 100` liga.
```
enabled for 10057 of 100000 users = 10.06% (target 10%)
```
O desvio esperado de um sorteio é ~95 usuários (desvio padrão binomial de n=100.000, p=0,1); o resultado ficou a **57** do alvo. **Sem estado**: o usuário **não** é guardado em lugar nenhum.

**3. *Stickiness* e rampa (executado):**
```
PASS same user, same answer, every time (no state stored)
at 25%: 25191 users enabled; 10057 of the 10057 users from the 10% step are still in
```
O mesmo usuário recebe **sempre** a mesma resposta (senão a tela "pisca" entre versões) e, ao subir de 10% para 25%, **ninguém perde** a funcionalidade: o grupo de 10% está **contido** no de 25% (`balde < 1000` ⊂ `balde < 2500`). Um sorteio **aleatório por requisição** (`Math.random() < 0.1`) **não** tem nenhuma das duas propriedades.

**4. O sal: *flags* independentes (executado):**
```
salt=true  two 50% flags: both on for 25.0% of users (independent = 25%, bug = 50%)
salt=false two 50% flags: both on for 50.2% of users
```
Se o *hash* usa **só o usuário** (sem a chave do *flag* como sal), **os mesmos 50%** dos usuários recebem **todos** os *flags*: vira um "grupo cobaia" que sofre **todas** as mudanças ao mesmo tempo, e qualquer **experimento** fica **confundido** (os efeitos de dois *flags* se misturam). Com o sal (`"flag:usuario"`), os grupos são **independentes** (25,0% = 50% × 50%).

**5. Atualização atômica e leitura consistente (executado):** o conjunto de *flags* é um **mapa imutável** dentro de um `AtomicReference`; atualizar é **trocar a referência** (P1: publicação segura, sem *lock* nas leituras). Mas **duas leituras** seguidas podem pegar **versões diferentes**:
```
two separate isEnabled() calls:    10,547,449 paired reads, 5,979,241 inconsistent (56.7%)
ONE snapshot per decision (view):  13,593,224 paired reads, 0 inconsistent (0.0%)
```
O cenário é **extremo** (um *thread* trocando os dois *flags* em laço fechado, sem pausa) e **por isso** o 56,7%: em produção, uma troca a cada minuto produziria **um** par torto a cada **muitas** milhões de leituras; mas **dinheiro** e **UI** tolerariam um par torto? **Regra do PayFlow:** uma **decisão** lê **um** *flag* ou usa **um** `view()` (um *snapshot* para o pedido inteiro). A atomicidade da **troca** não dá consistência entre **duas leituras**: é a mesma lição de visibilidade e atomicidade da P1.

**6. Dívida de *flags* (executado):**
```
expired flags: [old-experiment]
PASS the expiry check finds exactly the forgotten flag
```
Todo *flag* tem **dono** e **data de vencimento**; um teste de CI (`expired(hoje)` vazio) **reprova** o *build* quando um *flag* de *release* passa da data: **a dívida cobra sozinha**.

## 🛠️ Exemplo prático

### O desenho no PayFlow (por leitura; **não executado** no repositório do aluno)
```java
// com.payflow.shared.features: API pública do módulo shared (P4); o resto é package-private
public interface FeatureFlags {
    boolean isEnabled(String key, FlagContext ctx, boolean defaultValue);
    View view();                       // um snapshot para a DECISÃO inteira
    interface View { boolean isEnabled(String key, FlagContext ctx, boolean defaultValue); }
}

// com.payflow.transfer: o uso (uma decisão, um view)
var flags = featureFlags.view();
LimitRule rule = flags.isEnabled("transfer.new-limit-rules", FlagContext.of(userId), false)
        ? newRules : currentRules;
```
Três regras que o PayFlow (decisão 159) **escreve no código e no ArchUnit** (P4.10):
1. **Um *flag* nunca contorna uma invariante do *ledger*** (saldo não negativo, partidas dobradas, lançamentos imutáveis, regra 5): ele só **escolhe entre duas implementações válidas**. Um teste de propriedade roda **os dois ramos** contra as mesmas invariantes.
2. **`isEnabled` fora do `domain`**: o domínio recebe o **resultado** (um `LimitRule`), não o *flag* (o domínio não conhece o mecanismo).
3. **Nada de dado pessoal** no contexto do *flag* além do **identificador estável** (decisão 38 e LGPD): o `userId` já basta; **não** envie e-mail ou CPF a um serviço externo.

**Testar os dois ramos** (JUnit, por leitura; o avaliador em si já foi testado no laboratório):
```java
@ParameterizedTest
@ValueSource(booleans = {false, true})
void transferKeepsTheLedgerInvariantsWithEitherRule(boolean newRules) {
    flags.set("transfer.new-limit-rules", newRules);
    var result = transferService.execute(transferOf("100.00"));
    assertThat(ledger.sumAllEntries()).isEqualByComparingTo("0.00");   // partidas dobradas
    assertThat(accountRepository.findById(from).orElseThrow().balance()).isGreaterThanOrEqualTo(ZERO);
}
```

### De onde vêm os valores (as três opções)
| Opção | Como muda um *flag* | Prós | Contras |
|---|---|---|---|
| **A. Configuração estática** (`application.yml`/ConfigMap, P7.04) | edita e **reinicia** (um *rolling*) | zero infraestrutura; versionado no Git | mudar leva **minutos**; **não** é um *kill switch* de verdade |
| **B. Tabela no PostgreSQL** + cache de ~10 s | `UPDATE`; vale em segundos | simples, auditável, sem novo componente | cria tabela (migração; V12 está livre) e **uma tela/endpoint** administrativo; **você** mantém o avaliador |
| **C. OpenFeature** + provedor (flagd, Unleash, LaunchDarkly...) | pelo painel do provedor | padrão aberto; **troca de provedor sem mudar o código**; segmentação rica | mais um componente (disponibilidade, custo, **dados** no terceiro) |

O [OpenFeature](https://openfeature.dev/) é uma **API padrão** (não um serviço): o código chama `client.getBooleanValue("flag", false)` e o **provedor** é plugável. A [SDK Java](https://github.com/open-feature/java-sdk) está em `dev.openfeature:sdk` **1.23.0** (conferido no Maven Central); o README mostra `OpenFeatureAPI.getInstance()`, `setProviderAndWait(...)`, `getClient()` e `getBooleanValue(chave, padrão)`. ⚠️ Não executei o SDK; o que está acima é **a API como o README a mostra**.

**Decisão do PayFlow (ADR 0020, decisão 159):** **A hoje** (um *kill switch* por **variável** reiniciando o *rolling*), com a **interface `FeatureFlags`** pronta; **migrar para B** quando o primeiro *flag* exigir "desligar em segundos" (candidato: `webhook.dispatch`); **C** só se surgir **segmentação** ou **experimentos** que justifiquem o componente. A interface é o que torna a troca **barata**: nenhum chamador muda.

## 🏗️ Estudo de caso: o *flag* que cobrou taxa em dobro
> **Cenário fictício.** O time liga o `fee.new-calculation` para 10% dos usuários numa **quinta**. Na segunda alguém descobre que **2% dos pagamentos** desses usuários **cobraram a taxa duas vezes**.

**Diagnóstico.** (1) *Quem* estava no grupo? O avaliador é **determinístico**: `bucket("fee.new-calculation", userId) < 1000` **reconstrói** a lista **sem** guardar nada. (2) *Quando* o *flag* mudou? Sem auditoria do valor do *flag*, **não se sabe**: o time **não** tinha log da decisão. (3) *Por que* a taxa dobrou? Um ramo do código aplicava a taxa e **o outro chamava o mesmo método de novo** por cima.

**Opções:** (A) desligar o *flag* e estornar manualmente; (B) desligar, **estornar por compensação** (P3.13: o *ledger* é imutável) e **escrever** o teste dos dois ramos; (C) só consertar e reimplantar.
**Decisão (resumida):** **B**, na ordem: **desligar primeiro** (segundos, sem deploy; é o benefício do *flag*), depois **estornar por compensação** (nunca `UPDATE` em lançamento), depois o teste que prova a invariante nos **dois** ramos, **auditando** o valor do *flag* em cada decisão de dinheiro (`flag.decision` no log estruturado, P6.01, **sem** dado pessoal). *Lição:* o *flag* **limitou o dano** (10% × 2%), mas **não o impediu**; a proteção real é o **teste das invariantes nos dois ramos**.

## ⚖️ Trade-offs e quando NÃO usar
- **Cada *flag* dobra os caminhos de código a testar** (2 *flags* = 4 combinações). Mantenha **poucos**, **curtos** e **independentes**.
- ***Flag* de release que não é removido** vira **dívida** e **código morto** que ninguém ousa apagar: **vencimento + dono + teste de CI**.
- **Não use *flag* para o que o *canary* já resolve** (P8.03): se a mudança é só "versão nova do código", *canary* basta; *flag* vale quando o **código novo precisa estar desligado** (trabalho incompleto) ou quando você quer **desligar sem deploy**.
- **Não use *flag* para mudar o esquema do banco:** a migração **já aconteceu** (*expand/contract*, P8.03); o *flag* só controla **qual caminho** a aplicação usa.
- **Não use *flag* para segurança:** "autorização desligada por *flag*" é uma vulnerabilidade esperando um valor errado.
- **Serviço gerenciado:** adiciona **latência** e **ponto de falha**; **avalie localmente** (em memória, com atualização em segundo plano) e defina o padrão **para quando ele cair**.

## ⚠️ Erros comuns e boas práticas de produção
- **Sorteio por requisição** em vez de *hash* do usuário: a tela "pisca" e a medição fica sem sentido (seção 3).
- **Sem sal:** os mesmos usuários recebem todos os *flags* (seção 4).
- **Ler o *flag* duas vezes na mesma decisão** (seção 5): um `view()` por pedido.
- **Padrão errado:** `defaultValue = true` para funcionalidade **nova** liga o código incompleto **se o serviço cair**. Um *typo* na chave (`"transfer.new-limit-rule"`) **também** retorna o padrão sem aviso: **logue uma vez** (`WARN`) as chaves desconhecidas e **valide no CI** que toda chave usada no código existe na definição.
- **Dado pessoal no contexto:** vai parar em log e em terceiros (LGPD).
- **Sem auditoria:** quando algo dá errado, ninguém sabe **quem** tinha o *flag* ligado **naquele minuto**.
- **Teste que liga o *flag* e esquece de desligar:** estado compartilhado entre testes; use *fixtures* que restauram.

## 🎤 Na entrevista
- **"Qual a diferença entre *deploy* e *release*?"** — *Deploy* é o código estar rodando em produção; *release* é o usuário **poder usá-lo**. O *flag* separa os dois: o código vai desligado e liga-se aos poucos, desligando-se **sem novo deploy**.
- **"Como você faz um *rollout* percentual estável?"** — *Hash* determinístico de (chave do *flag* + usuário) em baldes; mesmo usuário, mesma resposta; subir o percentual só **acrescenta** usuários; o **sal** por *flag* evita correlação entre *flags*.
- **"Quais os riscos de *feature flags*?"** — Dívida (código morto, combinações a testar), leitura inconsistente, padrão errado quando o serviço cai, dado pessoal no contexto, e *flag* usado para o que deveria ser deploy/segurança.
- **"Flag próprio ou OpenFeature/serviço?"** — Começar simples atrás de **uma interface**; adotar OpenFeature quando precisar de **trocar de provedor** ou segmentação rica; o serviço só quando o **custo de operar** o seu supera o do terceiro.
