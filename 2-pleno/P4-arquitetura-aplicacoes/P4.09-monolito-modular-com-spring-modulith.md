## 🎯 Objetivos
Ao final desta aula você consegue:
- **Explicar** o que é um **monólito modular** e por que ele é um **ponto de partida** melhor que microsserviços.
- **Usar** o Spring Modulith: **módulos por convenção de pacote**, `verify()`, interface pública **×** interna.
- **Testar** um módulo **isolado** (`@ApplicationModuleTest`, `Scenario`) e **documentar** as dependências.
- **Planejar** a migração do PayFlow (pacote por camada → módulos) **em passos pequenos**.
- **Reconhecer** as **armadilhas** que o laboratório achou.

## 🤔 Por que isso importa
Até aqui a arquitetura é **convenção**: "o `notification` não deve usar a tabela do `account`". Convenção **não aguenta** prazo apertado, rotatividade e *code review* cansado. O **monólito modular** transforma a convenção em **regra verificada no build**: **um** deployável (simples de operar: J9/J10), com **fronteiras internas** que o compilador/CI **defendem**. É o **passo prévio** ao microsserviço (P5): se você **não** consegue manter fronteiras **dentro** de um processo, separá-las em rede **piora** tudo.

## 💡 Intuição (explicação simples)
Um **prédio de apartamentos**: **um** terreno e **uma** conta de luz (um deployável), mas **cada apartamento tem porta e chave** (módulo), e o que passa entre eles é **pela portaria** (API pública ou evento). O Modulith é o **síndico automático**: reprova a obra que abre um buraco na parede do vizinho.

## 🔬 Como funciona por dentro

### 1. A convenção (e só isso)
> Cada **subpacote direto** do pacote da aplicação (`com.payflow.lab.account`) é um **módulo**. O **pacote raiz do módulo** é a **API pública**; **qualquer subpacote** (`account.application`, `account.adapter...`) é **interno**.

```text
com.payflow.lab                ← @SpringBootApplication (Application)
├── shared/                    ← módulo ABERTO (value objects): package-info com @ApplicationModule(type = OPEN)
├── account/                   ← AccountApi (pública) + internos: domain/, application/, adapter/
├── transfer/                  ← TransferCompleted (evento público) + internos
├── notification/              ← tudo interno (só ouve eventos)
└── antifraud/                 ← AntifraudApi (pública) + interno
```
Isso casa **com a hexagonal da P4.02**: o que o mundo vê (`AccountApi`, `TransferCompleted`) fica no **raiz**; portas, casos de uso e adaptadores ficam **abaixo**, e o compilador (`package-private`) mais o `verify()` protegem.

### 3. `verify()`: o síndico automático
```java
// src/test/java/com/payflow/lab/ModularityTests.java
class ModularityTests {

    static final ApplicationModules MODULES = ApplicationModules.of(Application.class);

    @Test
    void listsTheModules() {
        var names = MODULES.stream().map(m -> m.getIdentifier().toString()).collect(Collectors.toSet());
        System.out.println("MODULES = " + MODULES.stream().map(m -> m.getIdentifier().toString()).sorted().toList());
        assertThat(names).containsExactlyInAnyOrder("account", "transfer", "notification", "antifraud", "shared");
    }

    @Test
    void printsTheModuleModel() {
        MODULES.forEach(System.out::println);   // base package, beans, dependências de cada módulo
    }

    @Test
    void verifiesTheStructure() {
        MODULES.verify();   // falha com Violations se houver ciclo ou acesso a tipo interno
    }

    @Test
    void writesDocumentation() {
        new Documenter(MODULES).writeModulesAsPlantUml().writeIndividualModulesAsPlantUml().writeModuleCanvases();
    }

    @Test
    void badFixtureIsRejected() {
        var bad = ApplicationModules.of("com.payflow.fixtures.badmod", location -> true);  // o padrão EXCLUI classes de teste
```

### 4. Quem **pode** depender de quem: `allowedDependencies` e `@NamedInterface`
- `@ApplicationModule(allowedDependencies = {"account", "shared"})` num `package-info.java` do módulo: **lista branca** de dependências; **qualquer outra** reprova.
- **`@NamedInterface("api")`** num **subpacote** o **expõe** como parte da API (por padrão só o pacote raiz é público) e `allowedDependencies = "core::api"` permite depender **só desse** subpacote.
- `type = OPEN` (módulo **aberto**): todos os tipos são acessíveis, **não** é verificado por dentro. Serve para `shared` (value objects), **nunca** para módulos de negócio.

Experimento **executado** (`fixtures/modok` passa; `fixtures/modbad` reprova):

```text
MODBAD VERIFY ->
- Module 'extras' depends on non-exposed type com.payflow.fixtures.modbad.core.internal.CoreInternal within module 'core'!
Field <com.payflow.fixtures.modbad.extras.ExtraService.internal> has type <com.payflow.fixtures.modbad.core.internal.CoreInternal> in (ExtraService.java:0)
- Module 'reports' depends on module 'extras' via com.payflow.fixtures.modbad.reports.ReportService -> com.payflow.fixtures.modbad.extras.ExtraService. Allowed targets: core :: api.
```

### 5. Testar **um módulo** isolado: `@ApplicationModuleTest`
```java
// src/test/java/com/payflow/lab/transfer/TransferModuleTest.java
package com.payflow.lab.transfer;

import static org.mockito.Mockito.verify;

import com.payflow.lab.account.AccountApi;
import com.payflow.lab.shared.Money;
import com.payflow.lab.transfer.application.port.in.TransferUseCase;
import java.util.UUID;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.modulith.test.ApplicationModuleTest;
import org.springframework.modulith.test.Scenario;
import org.springframework.test.context.bean.override.mockito.MockitoBean;

/** Sobe SÓ o módulo transfer; o account vira um mock (a fronteira é a interface AccountApi). */
@ApplicationModuleTest
class TransferModuleTest {

    @Autowired TransferUseCase useCase;
    @MockitoBean AccountApi accounts;

    @Test
    void publishesEventAndMovesMoneyThroughThePort(Scenario scenario) {
        var from = UUID.randomUUID();
        var to = UUID.randomUUID();
        scenario.stimulate(() -> useCase.transfer(from, to, Money.of("25.00")))
                .andWaitForEventOfType(TransferCompleted.class)
                .matching(e -> e.sourceAccountId().equals(from))
                .toArrive();
        verify(accounts).withdraw(from, Money.of("25.00"));
        verify(accounts).deposit(to, Money.of("25.00"));
    }
}
```

- O teste **sobe só o módulo `transfer`** (modo **padrão** `STANDALONE`, conferido no código-fonte da anotação) e **não** carrega `notification`/`antifraud`/`account`; o que `transfer` precisa de `account` (`AccountApi`) vira **mock** (`@MockitoBean`, do Spring Framework). Teste de módulo = **rápido** e **prova que a fronteira basta**.
- **`Scenario`** estimula e **espera o evento** (`andWaitForEventOfType(...).matching(...).toArrive()`) sem `Thread.sleep` (P4.07).
- ⚠️ **Surpresa 3:** o **teste precisa estar no pacote do módulo** (`com.payflow.lab.transfer`). Colocado em `com.payflow.lab` (a raiz), nenhum módulo é carregado e o teste falha com `No qualifying bean of type '...TransferUseCase'`.
- `mode = ALL_DEPENDENCIES` (ou `DIRECT_DEPENDENCIES`) carrega também os módulos de que ele depende, para um teste **de integração entre módulos**; o `EndToEndTest` (`@SpringBootTest`) cobre o **todo**.

## 🛠️ Exemplo prático

### O mapa de módulos do PayFlow (proposta, por leitura) e a **ordem de migração**
```text
com.payflow
├── shared/          Money, ids                               (aberto; só value objects imutáveis)
├── identity/        User, login, JWT, SecurityConfig         (genérico)
├── account/         Account, LedgerEntry, AccountApi, BalanceView, cache
├── transfer/        Transfer, TransferService, políticas, TransferCompleted
├── payment/         PaymentRequest, webhook, simulador do PSP
├── notification/    ouvintes + RabbitMQ
├── antifraud/       ouvintes + Kafka
├── reporting/       resumo mensal (visão materializada)
└── outbox/          OutboxEvent, OutboxRelay, IdempotentHandler (infra)
```
**Estratégia: "estrangular por dentro"** (decisão 125), **sem mudar** contrato HTTP nem esquema:
1. **PR 0:** acrescente as dependências do Modulith e **um teste **temporário** que **imprime** a mensagem de `verify()` **sem falhar** (`try/catch`): a lista é a **dívida** de hoje.
2. **PR 1:** crie `shared` (`Money`, ids) e mova.
3. **PR 2–n**, **um módulo por vez**, nesta ordem: `account` → `transfer` → `outbox` → `notification`/`antifraud` → `payment` → `reporting` → `identity`. Em cada PR: mover classes, **esconder** o que não for API (`package-private`), trocar chamadas diretas por **API do módulo** ou **evento**; **os testes de J5–P3 continuam verdes**.
4. **PR final:** reabilite `verify()`; ele passa a **barrar** regressões no CI (J10).
5. **Nunca** misture "mover pacote" com "mudar comportamento" no mesmo PR (revisão e *bisect* ficam impossíveis).

### Regras do PayFlow (decisão 122)
- **Um módulo = um subpacote direto de `com.payflow`**; o **raiz** do módulo contém **só** interfaces de API, eventos e DTOs públicos; o resto é `package-private`.
- **Dependência entre módulos** só por **API** (interface no raiz) ou **evento**; **nunca** por classe interna, **nunca** por tabela do outro (P4.11).
- `allowedDependencies` **declarado** em todo módulo (lista branca): o diagrama gerado **é** o desenho aprovado.
- `ModularityTests.verify()` e as regras do ArchUnit (P4.10) **rodam no CI**; **falha no build = PR não entra**.
- Cada módulo tem **seus** testes (`@ApplicationModuleTest`) além do `@SpringBootTest` geral.

## 🏗️ Estudo de caso curto: `reporting` quer o saldo
O `reporting` precisa do saldo de cada conta para o resumo. Opções: (a) chamar `AccountApi.balanceOf` por conta; (b) ler `accounts` direto por SQL; (c) manter **cópia própria** alimentada por `TransferCompleted`.

<details><summary>Dica e solução</summary>

**Dica:** quantas contas por relatório? Aceita dado **atrasado**? Quem é o **dono** de `accounts`?

**Solução:** (b) **nunca** (o Modulith **não vê** SQL: P4.11). (a) é o caminho **simples** quando são poucas contas e o dado precisa estar **fresco** (cada chamada é uma consulta: cuidado com **N+1**, P2.07). (c) é o caminho para **muitos dados e leitura pesada**: o `reporting` mantém **sua** visão (`ledger_monthly`, já existe desde P2.11) **alimentada por evento**; aceita atraso. No PayFlow: o resumo **já é** (c); o **saldo atual** na tela vem de `AccountApi` (a).
</details>

## ⚖️ Trade-offs e quando NÃO usar
- **Monólito modular × microsserviços:** o modular **mantém** *deploy* único, uma transação, **sem rede** entre módulos; **não** dá escala/*deploy* **independentes** nem isolamento de falha. Ganha **simplicidade**; perde **autonomia**. (P5 discute quando dividir.)
- **O Modulith verifica **estrutura Java**, não **dados**:** SQL numa `String` **passa** no `verify()` (P4.11, executado). Precisa de **regra de ArchUnit** e de **convenção** de dono da tabela.
- **Convenção de pacote** como **única** definição de módulo: renomear um pacote **muda** a arquitetura; refatorações grandes pedem cuidado.
- **Custo de adoção** num repositório **grande**: muitas violações de início; migre em passos (acima).
- **Eventos internos** trocam acoplamento de código por **fluxo implícito** (P4.07): documente e teste.
- **Maturidade:** o projeto é jovem e muda entre versões **maiores** (a 2.x acompanha o Boot 4); **fixe** a versão (BOM) e leia as notas de versão **antes** de subir.

## ⚠️ Erros comuns e boas práticas de produção
- **Módulo "util"/"common"** gigante: tudo depende dele; é um ciclo disfarçado. `shared` **só** com value objects.
- **API pública enorme** no pacote raiz (todas as classes `public`): sem fronteira. Raiz **pequeno**; resto `package-private`.
- **`@ApplicationModuleListener` sem tratar falha** (P4.07): erro **invisível**; precisa de retentativa/registro de publicações.
- **Teste de módulo no pacote errado** (surpresa 3) ou **`of(String)` sem incluir testes** (surpresa 2).
- **Esquecer a dependência `events-api`** (surpresa 1).
- **`verify()` só local:** precisa estar no **CI** para barrar a regressão.
- **Mensagem típica** quando alguém abre um buraco:
  `Module 'billing' depends on non-exposed type ...orders.internal.Secret within module 'orders'!`

## 🎤 Na entrevista
1. **"O que é um monólito modular?"** Um único deployável com **módulos de domínio** de fronteiras **verificadas** (API pública × interno, sem ciclos); pega os benefícios de organização dos microsserviços **sem** o custo de rede/operação.
2. **"Por que não começar com microsserviços?"** Porque **fronteiras erradas** em rede custam **muito** mais que dentro de um processo; começar modular **valida o recorte** antes de pagar a distribuição.
3. **"O que o Spring Modulith faz?"** Detecta módulos por convenção de pacote, **verifica** regras (ciclos, tipos internos, dependências permitidas), **testa módulos isolados**, **documenta** as dependências e oferece **eventos** entre módulos.
4. **"Como evitar que o acoplamento volte?"** `verify()` + ArchUnit **no CI**, `allowedDependencies` declarado, revisão de PR com a pergunta "de quem é essa tabela?".
