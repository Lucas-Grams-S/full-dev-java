# P4.07 — DDD tático II: repositórios e eventos de domínio

> ⏱️ ~1h30 · 🔵 Pleno · Pré-requisitos: P4.02 (portas), P4.05 (Observer), P4.06 (agregados), P3.09 (Outbox), P3.07 (idempotência), J5.11 (`@Transactional`)

> ⚠️ **Verificação:** **executado de verdade** em `lab/architecture-lab` (Spring Boot **4.1.2**, Spring Modulith **2.1.2**, H2 em memória só para ter uma transação real, JDK 25.0.5; 37 testes verdes): dois adaptadores da mesma porta (`InMemoryAccountStore` e `JdbcAccountStore`) passando no **mesmo contrato**; evento publicado **só se a transação confirma**; **ouvinte síncrono que falha desfaz a transferência**; **ouvinte assíncrono que falha é invisível ao publicador**. **Não executado:** o `PayFlow` real, o **registro de publicações** do Spring Modulith (`spring-modulith-events-jdbc`), `@Externalized`, `AbstractAggregateRoot`/`@DomainEvents` do Spring Data.

## 🎯 Objetivos
Ao final desta aula você consegue:
- **Definir** o **repositório** do DDD (porta de saída por **raiz de agregado**) e **distinguir** do "DAO" e do Spring Data.
- **Trocar** o adaptador de persistência **sem mexer** no domínio, provando com um **teste de contrato**.
- **Modelar** um **evento de domínio** (fato no passado, imutável) e **publicá-lo** dentro da transação.
- **Escolher** entre ouvinte **síncrono**, `@TransactionalEventListener` e `@ApplicationModuleListener` e **dizer o que cada um faz com falhas**.
- **Separar** **evento de domínio** (em memória, entre módulos) de **evento de integração** (Kafka, via Outbox).

## 🤔 Por que isso importa
Dois problemas aparecem quando o PayFlow vira modular: (1) **como o domínio lê e grava** sem conhecer SQL? (repositório); (2) **como `notification` e `antifraud` reagem** a uma transferência **sem o `transfer` conhecê-los**? (eventos). Errar o segundo é perigoso: **um ouvinte que falha pode desfazer o dinheiro** (síncrono) ou **ninguém perceber que falhou** (assíncrono). A diferença é uma **anotação**.

## 💡 Intuição (explicação simples)
- **Repositório:** o **arquivo do cartório**: você pede "me traga a conta 42" e **devolve** quando terminar; não pergunta **em que armário** ela está. Trocar o arquivo físico por digital não muda o **balcão**.
- **Evento de domínio:** o **aviso no quadro** "Transferência 7 concluída". Quem passa e se interessa age; quem escreve o aviso **não sabe quem lê**.

## 🔬 Como funciona por dentro

### 1. Repositório: **coleção de raízes de agregado**, não "DAO de tabela"
| | Repositório (DDD) | DAO / `JpaRepository` "puro" |
|---|---|---|
| Unidade | **raiz de agregado** (`Account`) | **tabela** |
| Linguagem | do **domínio** (`findById`, `save`) | do **banco** (`findByXAndYOrderBy...`) |
| Quem define a interface | o **núcleo** (porta de saída) | o framework |
| Expõe `EntityManager`/`Pageable`? | **não** | sim |

A **porta** (já vista na P4.02) e **dois adaptadores** que a implementam:

```java
// src/main/java/com/payflow/lab/account/application/port/out/AccountStore.java
package com.payflow.lab.account.application.port.out;

import com.payflow.lab.account.domain.Account;
import java.util.Optional;
import java.util.UUID;

/** Porta de SAÍDA: o domínio diz o que precisa; quem implementa é um adaptador. */
public interface AccountStore {
    Account save(Account account);
    Optional<Account> findById(UUID id);
}
```

```java
// src/test/java/com/payflow/lab/account/adapter/out/JdbcAccountStore.java
package com.payflow.lab.account.adapter.out;

import com.payflow.lab.account.application.port.out.AccountStore;
import com.payflow.lab.account.domain.Account;
import com.payflow.lab.shared.Money;
import java.util.Optional;
import java.util.UUID;
import org.springframework.jdbc.core.simple.JdbcClient;

/** SEGUNDO adaptador da mesma porta (só nos testes): prova que a troca não toca o domínio nem o caso de uso. */
public class JdbcAccountStore implements AccountStore {

    private final JdbcClient jdbc;

    public JdbcAccountStore(JdbcClient jdbc) {
        this.jdbc = jdbc;
    }

    @Override
    public Account save(Account account) {
        int updated = jdbc.sql("update accounts set owner = ?, balance = ? where id = ?")
                .params(account.owner(), account.balance().amount(), account.id()).update();
        if (updated == 0) {
            jdbc.sql("insert into accounts (id, owner, balance) values (?, ?, ?)")
                    .params(account.id(), account.owner(), account.balance().amount()).update();
        }
        return account;
    }

    @Override
    public Optional<Account> findById(UUID id) {
        return jdbc.sql("select id, owner, balance from accounts where id = ?").param(id)
                .query((rs, n) -> new Account(rs.getObject("id", UUID.class), rs.getString("owner"),
                        new Money(rs.getBigDecimal("balance"))))
                .optional();
    }
}
```

O **teste de contrato** (P4.03) roda **contra os dois** e **ambos passam** (`InMemoryAccountStoreContractTest` e `JdbcAccountStoreContractTest`): o caso de uso **não distingue** um do outro. No PayFlow o adaptador de verdade é um `AccountStoreJpa` **por trás** do `AccountRepository` do Spring Data: **o Spring Data é um detalhe de implementação** do adaptador, não a porta.

> 🧠 **Regra:** um repositório por **raiz de agregado**; consultas **de leitura** para telas (extrato paginado, resumo mensal) **não** são repositório de domínio: são **portas de consulta** (`StatementQuery`) com projeções (P2.07/P2.11).

### 2. Evento de domínio: um **fato** que aconteceu
Regras de um bom evento:
- **Nome no passado** (`TransferCompleted`, não `CompleteTransfer`): é um **fato**, não um pedido.
- **Imutável** (`record`), com **ids e valores**, **nunca** entidades (o ouvinte assíncrono receberia objeto **fora da sessão**: `LazyInitializationException`).
- **Autocontido:** leva o que os ouvintes **normalmente** precisam (evita que consultem o banco do publicador: P4.11).
- **Pertence ao módulo que o publica** (parte da **API pública** dele).

```java
// src/main/java/com/payflow/lab/transfer/TransferCompleted.java
package com.payflow.lab.transfer;

import com.payflow.lab.shared.Money;
import java.util.UUID;

/** Evento publicado pelo módulo transfer (parte da API pública dele). Imutável, no passado, sem lógica. */
public record TransferCompleted(UUID transferId, UUID sourceAccountId, UUID targetAccountId, Money amount) {
}
```

O caso de uso o publica **dentro** da transação, por uma **porta** (`DomainEvents`), e o adaptador usa o `ApplicationEventPublisher` do Spring:

```java
// src/main/java/com/payflow/lab/transfer/adapter/out/SpringDomainEvents.java
package com.payflow.lab.transfer.adapter.out;

import com.payflow.lab.transfer.TransferCompleted;
import com.payflow.lab.transfer.application.port.out.DomainEvents;
import org.springframework.context.ApplicationEventPublisher;
import org.springframework.stereotype.Component;

@Component
class SpringDomainEvents implements DomainEvents {

    private final ApplicationEventPublisher publisher;

    SpringDomainEvents(ApplicationEventPublisher publisher) {
        this.publisher = publisher;
    }

    @Override
    public void publish(TransferCompleted event) {
        publisher.publishEvent(event);
    }
}
```

### 3. Quem escuta, e **o que acontece quando falha** (o experimento)
Três mecanismos, três comportamentos:
| Mecanismo | Quando roda | Se o ouvinte lança exceção | Perde evento se a JVM cai? |
|---|---|---|---|
| `@EventListener` | **síncrono**, na **mesma *thread* e transação** | **sobe para o publicador** e **desfaz a transação** | não existe "depois": desfez tudo |
| `@TransactionalEventListener(AFTER_COMMIT)` | síncrono, **depois do *commit*** | o *commit* já ocorreu: o dado **fica** (o que o Spring faz com a exceção é detalhe de versão: ⚠️ **não executado**) | **sim**, se cair entre o *commit* e o ouvinte |
| `@ApplicationModuleListener` (Modulith) | **assíncrono**, depois do *commit*, **transação própria** (`REQUIRES_NEW`) | **invisível ao publicador**; só log | **sim** (a menos do registro de publicações do Modulith) |

Os dois primeiros **extremos** foram **executados** (com um adaptador JDBC/H2 para que houvesse transação de verdade):

```java
// src/test/java/com/payflow/lab/SyncListenerFailureTest.java
```

```java
// src/test/java/com/payflow/lab/AsyncListenerFailureTest.java
    static final AtomicInteger CALLS = new AtomicInteger();

    @TestConfiguration
    static class Boom {
        @Bean
        Object asyncBoom() {
            return new Object() {
                @ApplicationModuleListener
                void on(TransferCompleted event) {
                    CALLS.incrementAndGet();
                    throw new IllegalStateException("async listener failed");
                }
            };
        }
    }

    @Autowired AccountApi accounts;
    @Autowired TransferUseCase transfers;

    @Test
    void failureInAnAsyncListenerIsInvisibleToThePublisher() {
        var a = accounts.open("gus", Money.of("100.00"));
        var b = accounts.open("hana", Money.of("0.00"));

        transfers.transfer(a, b, Money.of("40.00"));                 // NÃO lança

        assertThat(accounts.balanceOf(b)).isEqualTo(Money.of("40.00"));
        await().atMost(Duration.ofSeconds(3)).untilAsserted(() -> assertThat(CALLS.get()).isEqualTo(1));
        System.out.println("ASYNC LISTENER FAILED -> transfer ok, saldo b=" + accounts.balanceOf(b) + ", ouvinte chamado " + CALLS.get() + "x (erro só no log)");
    }
}
```

Saída **real**:

```text
ASYNC LISTENER FAILED -> transfer ok, saldo b=40.00, ouvinte chamado 1x (erro só no log)
SYNC LISTENER FAILED -> saldo a=100.00 b=0.00
```

- **Síncrono:** o ouvinte falhou ⇒ `a=100.00`, `b=0.00`: **a transferência inteira foi desfeita** por causa de um erro **no ouvinte**. Isso é **desejável** se a reação é parte da regra; é **péssimo** se for só notificação (o e-mail fora do ar **cancela** a transferência).
- **Assíncrono:** o ouvinte falhou ⇒ a transferência **ficou** (`b=40.00`) e o publicador **nunca soube**; só o log registra. É o que queremos para **notificação** e **antifraude**; mas **o que falhou não tem retry automático**: é preciso **tratar** (próxima seção).

> ✅ O `EndToEndTest` também prova o outro lado do *commit*: uma transferência **rejeitada** (saldo insuficiente) **não** produz notificação (esperando 500 ms antes de concluir "nada chegou", porque num ouvinte **assíncrono** "nada ainda" **não** prova nada).

### 4. Evento de **domínio** ≠ evento de **integração**
```mermaid
flowchart LR
    T[transfer] -- "TransferCompleted (em memória, mesma JVM)" --> N[notification]
    T -- "TransferCompleted" --> AF[antifraud]
    T -- "TransferCompleted" --> OB[outbox<br/>@ApplicationModuleListener?]
    OB -- "grava outbox_events (P3.09)" --> DB[(PostgreSQL)]
    DB -- relé --> K[[Kafka payflow.transfers.v1]]
```
- **Domínio** (esta aula): fala **entre módulos da mesma JVM**, em memória, **pode se perder** se a JVM cair no meio.
- **Integração** (P3): sai **do sistema** (Kafka/RabbitMQ), **precisa ser durável**: por isso o **Outbox** (`outbox_events`, **mesma transação**, decisão 109).
- **Regra do PayFlow (decisão 120):** o que **não pode ser perdido** (notificar o cliente de um dinheiro recebido, antifraude) vai pelo **Outbox** (garantia *at-least-once*, P3.06); o evento **em memória** serve para **reações perdíveis ou reconstruíveis** (invalidar cache local, atualizar métrica) e para **desacoplar módulos** quando o ouvinte é o **adaptador de Outbox** (gravar a linha **na mesma transação**, com um ouvinte **síncrono**: `@EventListener`, **não** o assíncrono).
- **Armadilha de desenho:** o ouvinte do Outbox **precisa participar da transação** do publicador. Se usar `@ApplicationModuleListener` (nova transação, depois do *commit*), a linha do Outbox **perde a atomicidade** com a transferência: o problema da **escrita dupla** (P3.09) **volta**.
- **Spring Modulith** oferece o **registro de publicações de eventos** (`spring-modulith-events-*`, ex.: JDBC): grava os eventos **na transação** e **reenvia** os que não foram processados. É uma **alternativa** ao Outbox próprio para eventos **internos** (⚠️ **não executado** aqui) e `@Externalized` para publicar no Kafka (⚠️ idem). O PayFlow **mantém o Outbox próprio** (P3), medido e testado.

### 5. Detalhe do Spring: onde gerar o evento
- **Pelo caso de uso** (o do laboratório: `events.publish(...)` no `TransferService`): explícito, fácil de testar.
- **Pelo agregado**: o Spring Data permite `AbstractAggregateRoot.registerEvent(...)` / `@DomainEvents`: os eventos são publicados **quando o repositório chama `save`** ([docs](https://docs.spring.io/spring-data/commons/reference/repositories/core-domain-events.html)). Mais "DDD de livro", **menos explícito** (o evento depende de alguém chamar `save`). ⚠️ **não executado**; o PayFlow usa a forma **explícita**.

## 🛠️ Exemplo prático

### Regras de projeto do PayFlow para eventos (decisão 120)
1. **Nome no passado**, em inglês, no pacote **raiz** do módulo publicador (`com.payflow.transfer.TransferCompleted`).
2. `record` com `eventId` (UUIDv7), `occurredAt` (`Instant`), **ids** e valores (**`String` com 2 casas** para dinheiro **se** o evento for para fora: decisão 11; dentro da JVM pode ser `Money`).
3. **Um fato por evento**; **não** reutilize `TransferCompleted` para "estorno" (P3.13: tem o seu próprio).
4. Quem **precisa de atomicidade** com o dinheiro (Outbox) → **ouvinte síncrono**; quem só **reage** → **`@ApplicationModuleListener`**.
5. **Todo ouvinte é idempotente** (P3.07): uma reentrega **não** pode duplicar notificação/efeito.
6. **Teste obrigatório:** (a) com `Scenario`/`Awaitility`, o evento **chega**; (b) numa operação que dá *rollback*, **nada** chega (**esperando** o suficiente).

### Teste de módulo com `Scenario` (executado)
O `TransferModuleTest` (P4.09) **estimula** o caso de uso e **espera o evento** (`andWaitForEventOfType(TransferCompleted.class)`), sem `Thread.sleep`.

## 🏗️ Pausa de design: "notificação por ouvinte síncrono ou assíncrono?"
Se o serviço de e-mail ficar fora do ar por 30 min, o que **deve** acontecer com as transferências?

<details><summary>Dica e solução</summary>

**Dica:** a notificação faz parte da **regra de dinheiro**?

**Solução:** **não**: transferências **continuam**; e-mails **atrasam** e são enviados quando o serviço volta. Logo, **assíncrono** (`@ApplicationModuleListener`) **com retentativa e DLQ** (P3.08) e **idempotência** (P3.07): o `NotifyOnTransfer` **não** pode estar no **mesmo** caminho transacional do dinheiro. E **perder** a notificação por queda da JVM é inaceitável ⇒ ela vem do **Outbox → RabbitMQ** (P3), e o evento em memória só **dispara** a gravação no Outbox (síncrono, **mesma transação**).
</details>

## ⚖️ Trade-offs e quando NÃO usar
- **Eventos de domínio** trocam **acoplamento de código** por **acoplamento por contrato** (o evento) e **fluxo implícito**: "quem reage a `TransferCompleted`?" exige **ferramenta** (`Documenter`, P4.09) e testes.
- **Síncrono** = consistência e **acoplamento de falha**; **assíncrono** = isolamento e **consistência eventual** (e erro invisível).
- **Registro de publicações do Modulith** vs **Outbox próprio**: o primeiro **cobre** só o que passa pelo `ApplicationEventPublisher` e **reenvia ao reiniciar**; o segundo **sai do processo** (Kafka) com relé e métricas. Escolha **um** fluxo por evento: **dois mecanismos de reentrega** para o mesmo evento **duplicam**.
- **Repositório por porta** custa um mapeamento a mais; num CRUD sem regra, `JpaRepository` direto no serviço é aceitável (P4.01).
- **Evento anêmico** ("`AccountChanged`" sem dizer o quê) obriga o ouvinte a **consultar** o publicador: o acoplamento volta (P4.11).

## ⚠️ Erros comuns e boas práticas de produção
- **`@TransactionalEventListener` sem transação ativa** não dispara (a menos de `fallbackExecution = true`); e `@Transactional` com `REQUIRES_NEW` no ouvinte de `AFTER_COMMIT` é **necessário** para gravar no banco ([docs](https://docs.spring.io/spring-framework/reference/data-access/transaction/event.html)).
- **Ouvinte assíncrono que depende de dado que só existe depois do *commit*** funciona; um **síncrono** lendo o dado **antes do *commit*** em **outra conexão** não o vê.
- **Entidade no evento:** `LazyInitializationException`/dado mutável. Use `record` com ids.
- **Ordem entre eventos:** **não há** garantia entre ouvintes assíncronos nem entre eventos de agregados diferentes. Para ordem por conta, é Kafka com chave (P3.04).
- **Engolir exceção no ouvinte** para "não afetar o publicador": você **perde o erro**. Deixe lançar e **trate** com retentativa/DLQ.
- **Teste que prova "nada aconteceu" sem esperar** (ouvinte assíncrono): passa **sempre**. Use `await().during(...)`.

## 🎤 Na entrevista
1. **"O que é um repositório no DDD e como difere do DAO?"** Coleção de **raízes de agregado** com a linguagem do domínio e **interface definida pelo núcleo**; o DAO é por **tabela** e expõe a persistência.
2. **"Evento de domínio × evento de integração?"** Domínio: fato interno, em memória, entre módulos; integração: contrato **entre sistemas**, durável (Outbox/Kafka), versionado (P5).
3. **"`@TransactionalEventListener` perde eventos?"** Pode: roda **depois do *commit***; se o processo cair antes, o evento some (sem registro/Outbox).
4. **"Como garantir que o evento sai se a transação confirma?"** **Outbox**: gravar o evento **na mesma transação** e publicar depois (relé), aceitando *at-least-once* + consumidor idempotente.
