## 🎯 Objetivos
Ao final desta aula você consegue:
- **Definir** compatibilidade **para trás** e **para frente** e **classificar** uma mudança (campo novo, remoção, renomeação, tipo, enum).
- **Escrever** um **leitor tolerante** e **provar** o que acontece com campo desconhecido, ausente e enum novo.
- **Escolher** uma estratégia de **versionamento** para REST e para eventos.
- **Planejar** uma mudança **incompatível** pelo método **expandir → migrar → contrair**.
- **Decidir** quando um **registro de schemas** se paga.

## 🤔 Por que isso importa
No monólito, o compilador reclama quando você muda um campo. **Entre serviços não há compilador**: o consumidor foi implantado **ontem**, o produtor **hoje**, e o erro aparece **em produção**, às vezes **em silêncio** (o dado simplesmente some). Eventos são piores que APIs: **ficam gravados** (retenção de 14 dias no Kafka, decisão 105) e **vários** consumidores, que você talvez **nem conheça**, os leem.

## 💡 Intuição (explicação simples)
Você **reimprime o formulário** da empresa. Se **acrescenta** um campo **opcional** ao final, quem tem o formulário antigo ainda preenche e entrega. Se **troca a ordem** das perguntas ou **muda o significado** de um campo, os formulários antigos **são lidos errado**, e ninguém avisa. A **Lei de Hyrum** ([hyrumslaw.com](https://www.hyrumslaw.com/)) resume: com usuários suficientes, **todo comportamento observável** vira dependência de alguém.

## 🔬 Como funciona por dentro

### 1. Duas direções de compatibilidade
| Termo | Significa | Quem é protegido |
|---|---|---|
| **Compatível para trás** (*backward*) | o leitor **novo** lê dado **antigo** | consumidor atualizado **antes** do produtor |
| **Compatível para frente** (*forward*) | o leitor **antigo** lê dado **novo** | consumidor **atrasado** (o mais comum!) |
| **Total** (*full*) | as duas | quando a ordem de implantação é **incontrolável** |

Em eventos você **não controla** a ordem nem os consumidores: busque **as duas**.

### 2. Matriz de mudanças (executada)
```
T6 campo novo opcional: mapper do Boot le normalmente -> TransferCompletedV1[eventId=e1, transferId=t1, ...]
T6 FAIL_ON_UNKNOWN_PROPERTIES: Boot=false, Jackson 3 de fabrica=false (no Jackson 2 o padrao era true)
T6 mapper ESTRITO (FAIL_ON_UNKNOWN_PROPERTIES ligado) diante do campo novo: UnrecognizedPropertyException: Unrecognized property "channel" ...
T6 campo renomeado (transferId -> transfer_id): le SEM erro, transferId=null <- null silencioso
T6 valor novo de enum (PARTIALLY_REVERSED): InvalidFormatException: Cannot deserialize value of type `...Status` from String "PARTIALLY_REVERSED": not one of the values accepted ...
T6 com EnumFeature.READ_UNKNOWN_ENUM_VALUES_AS_NULL: status=null (o consumidor decide o que fazer com null)
T6 amount como numero JSON 100.10 -> BigDecimal 100.10 (ok aqui, mas ...)
T6 amount 12345678901234567.89 como numero via JsonNode/double: 1.2345678901234568E16 (perdeu precisao)
```
| Mudança do **produtor** | JSON (executado) | Protobuf (executado, P5.03) | Veredito |
|---|---|---|---|
| **Campo novo opcional** | leitor **tolerante** lê; **estrito** (`FAIL_ON_UNKNOWN_PROPERTIES`) **falha** | leitor antigo **ignora** | **seguro** se os leitores são **tolerantes** |
| **Remover** campo | leitor novo vê `null`/padrão | idem (valor padrão) | **quebra** se o consumidor **depende** dele |
| **Renomear** campo | `null` **silencioso** | **ok** (usa o número) | **quebra** (JSON); trate como **remover + acrescentar** |
| **Mudar o tipo** | erro de conversão ou dado errado | **perda silenciosa** (número reutilizado) | **quebra** |
| **Valor novo de enum** | **exceção** (padrão) | `UNRECOGNIZED` | **quebra**, a menos que o consumidor **se defenda** |
| **Mudar o significado** (ex.: `amount` com/sem taxa) | nada detecta | nada detecta | **a pior**: só **contrato + revisão** pegam |

**Duas surpresas do laboratório** que a leitura não mostraria:
1. **O padrão do Jackson 3 mudou:** `FAIL_ON_UNKNOWN_PROPERTIES` está **desligado de fábrica** (`false`) **e** no mapper do Boot. Eu havia escrito o teste achando o contrário (valia para o Jackson 2); o teste **provou** o erro. Consequência: **campo novo não quebra** o consumidor por padrão, e **campo removido/renomeado vira `null` sem aviso**, então **valide os obrigatórios** (Bean Validation ou checagem no listener) e mande para a DLT (P3.08).
2. **Enum novo quebra por padrão** mesmo com o resto tolerante: é o caso **mais esquecido**.

### 3. Leitor tolerante (*Tolerant Reader*)
O consumidor **lê só o que usa** e **ignora o resto** ([Fowler](https://martinfowler.com/bliki/TolerantReader.html)). Na prática, para o PayFlow:
```java
// Consumidor (serviço de notificações): só o que usa, validado
public record TransferCompletedV1(
        @NotBlank String eventId,
        @NotBlank String transferId,
        @NotBlank String sourceAccountId,
        @NotNull BigDecimal amount,   // JSON string "100.00" (decisão 11)
        Status status) { }            // enum com valor "desconhecido" tratado

enum Status { COMPLETED, REVERSED, UNKNOWN } // UNKNOWN recebe o que o consumidor não conhece
```
Regras do consumidor: **(1)** ignore campos desconhecidos; **(2)** **valide** os obrigatórios **na entrada** (campo ausente **não** pode virar `null` silencioso); **(3)** trate **enum desconhecido** (mapeie para `UNKNOWN` e **registre**, ou envie para a DLT); **(4)** **nunca** dependa de **ordem** de campos; **(5)** o dinheiro chega como **string** e é convertido para `BigDecimal` (decisão 11).

### 4. Versionar: REST e eventos
| Alvo | Estratégia | Quando |
|---|---|---|
| **REST** | **aditiva dentro de `/api/v1`** (campo novo opcional); **`/api/v2`** só para mudança **incompatível** (ADR 0008) | sempre aditiva primeiro |
| **Evento** | **envelope** com `eventId`, `eventType`, `schemaVersion`, `occurredAt`; **aditivo** na mesma versão; **tópico `…v2`** para quebra | evento é **contrato público** |
| **gRPC/Protobuf** | pacote `…v1`; regras de números/`reserved` | (P5.03) |

**Mudança incompatível: expandir → migrar → contrair** (o mesmo princípio de migração de banco, S3):
1. **Expandir:** o produtor passa a publicar **as duas formas** (campo antigo **e** novo; ou tópico `v1` **e** `v2`).
2. **Migrar:** cada consumidor muda para o novo **no seu ritmo**; **meça** quem ainda lê o antigo (consumer groups no `v1`, *lag*).
3. **Contrair:** só depois que **ninguém** lê o antigo (e o prazo de retenção passou) o produtor **para** de publicá-lo.

### 5. Registro de *schemas* (quando se paga)
Um **registro** guarda o *schema* de cada tópico e **recusa** uma publicação **incompatível** com a regra configurada (ex.: `BACKWARD`, `FORWARD`, `FULL`; ver a [documentação do Confluent](https://docs.confluent.io/platform/current/schema-registry/fundamentals/schema-evolution.html) e a [especificação do Avro](https://avro.apache.org/docs/current/specification/)).

| | Sem registro (hoje) | Com registro |
|---|---|---|
| **Quem barra a quebra** | **teste de contrato** + revisão | o **registro**, na publicação |
| **Custo** | só disciplina | **mais um serviço** para operar; formato (Avro/Protobuf) |
| **Vale quando** | **poucos** consumidores conhecidos | **muitos** consumidores, **times** diferentes |

**Decisão (129):** o PayFlow **não** adota registro agora (um produtor, um consumidor extra); **adota** o envelope, as regras acima e **testes de compatibilidade no CI** ([P5.09](P5.09-testes-de-contrato-spring-cloud-contract-ou-pact.md)). Reavalie quando houver **3+ consumidores** de um mesmo tópico.

## 🛠️ Exemplo prático: acrescentar `channelHint` ao `payflow.transfers.v1`
1. **Produtor (monólito):** acrescenta `channelHint` (**opcional**, `"EMAIL"|"PUSH"`) ao evento. Versão do esquema: **continua `v1`** (mudança **aditiva**).
2. **Teste de compatibilidade (CI do produtor):** o evento **novo** deve ser lido pelo `TransferCompletedV1` **atual** do consumidor (guardado como **fixture** no repositório do produtor): **campo desconhecido** ignorado.
3. **Teste do consumidor:** um evento **sem** `channelHint` (antigo, ainda na retenção) continua válido.
4. **Depois:** o consumidor passa a **usar** `channelHint` quando existir.

E uma mudança **incompatível**, ex.: `amount` de *string* para objeto `{value, currency}`: publique `payflow.transfers.v2` **junto** do `v1` (**expandir**); migre o serviço de notificações; **meça** o *lag* do grupo no `v1`; só então **contraia**.

## 🧠 Pausa para lógica: classifique a mudança
Para cada mudança, diga se é **compatível para trás** (B), **para frente** (F), ambas ou nenhuma, com leitor **tolerante**: (a) acrescentar `occurredAt` opcional; (b) remover `sourceAccountId` (que o consumidor usa); (c) acrescentar o valor `PARTIALLY_REVERSED` ao enum; (d) trocar `amount` de `"100.00"` para `100.00` (número).

<details><summary>Dica e solução</summary>

**Dica:** "para trás" = leitor **novo**, dado **antigo**; "para frente" = leitor **antigo**, dado **novo**.

**Solução:** (a) **ambas** (o antigo ignora; o novo tem padrão para a ausência). (b) **nenhuma** para quem usa o campo (o dado novo não o tem → `null` silencioso). (c) **para trás** sim; **para frente não**, a menos que o leitor antigo trate enum desconhecido (executado: exceção por padrão). (d) **depende do parser**: o Jackson aceitou o número (`100.10`), mas qualquer caminho que passe por `double` **perde precisão** (executado: `12345678901234567.89 → 1.2345678901234568E16`); **trate como quebra** e mantenha *string* (decisão 11). **Variação:** o que muda se o consumidor usar `JsonNode` em vez de *record*?
</details>

## ⚖️ Trade-offs e quando NÃO usar
- **Tolerância total** (aceita qualquer coisa) **esconde erros**: combine com **validação dos obrigatórios**.
- **Versão por tópico** (`v2`) **duplica** tráfego e operação durante a migração; só use para **quebra real**.
- **Registro de *schemas*** dá segurança **e** acopla o ciclo de implantação ao registro; para **um** par produtor-consumidor é **exagero**.
- **Eventos "gordos"** (com muitos dados) reduzem chamadas, mas **ampliam** o contrato; eventos "magros" (só ids) forçam o consumidor a **chamar de volta** (acoplamento síncrono!). O PayFlow manda **ids e valores** (decisão 120).

## ⚠️ Erros comuns e boas práticas de produção
- **Renomear campo "por organização":** vira `null` silencioso (executado).
- **Reaproveitar nome com outro significado** (`amount` passa a incluir taxa): nada detecta; **crie campo novo**.
- **Não validar obrigatórios** no consumidor (mensagem inválida segue para o banco).
- **Enum fechado no consumidor:** o primeiro valor novo derruba o consumo; a mensagem **volta** e **trava a partição** (P3.08). Use `UNKNOWN` ou DLT.
- **Mudar o evento sem avisar ninguém:** liste os consumidores (grupos do tópico) **antes**.
- **Fixture de evento só "do dia"**: guarde amostras de **cada versão** para o teste de leitura.

## 🎤 Na entrevista
1. **"O que é compatibilidade para trás e para frente?"** *Para trás*: leitor **novo** lê dado **antigo**. *Para frente*: leitor **antigo** lê dado **novo**. Em eventos busco **as duas** porque não controlo a ordem de implantação.
2. **"Como evoluir um evento sem quebrar consumidores?"** Mudanças **aditivas** e opcionais; leitores **tolerantes** com validação dos obrigatórios; mudança **incompatível** por **expandir → migrar → contrair** (tópico/versão nova em paralelo).
3. **"Para que serve um *schema registry*?"** Guardar os *schemas* e **recusar** publicação incompatível com a regra do tópico; compensa com **muitos** consumidores/times.
4. **"Qual a mudança mais perigosa?"** **Mudar o significado** de um campo (ou reutilizar o nome): **nenhum** parser ou registro percebe; só **contrato**, revisão e **testes de comportamento**.
