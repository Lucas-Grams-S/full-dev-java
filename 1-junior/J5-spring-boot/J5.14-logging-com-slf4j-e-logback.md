# J5.14 — Logging com SLF4J e Logback

> ⏱️ ~1h30 · 🟢 Júnior · Pré-requisitos: J5.05 (`application.yml`, perfis), J5.06 (filtros e interceptors, `WebErrors`), J5.11 (serviços), J0.06 (ler *stack traces*)

## 🎯 Objetivos
Ao final desta aula você consegue:
- Explicar a relação entre **SLF4J** (a interface) e **Logback** (a implementação) e ler uma linha de log do Spring Boot.
- Escrever logs com **níveis** corretos (`ERROR`, `WARN`, `INFO`, `DEBUG`, `TRACE`) e **mensagens parametrizadas** (`{}`), e explicar **por que** não se concatena.
- Configurar níveis e padrão em `application.yml` (por pacote e por perfil) e **trocar o nível em execução** (preview: Actuator, J5.15).
- Usar o **MDC** para colocar um **`requestId`** em todo log de uma requisição, e ver o formato **estruturado (JSON)**.
- Evitar o que **não** deve ir para o log: dados pessoais, segredos e **stack traces** de erros de negócio esperados.

## 🤔 Por que isso importa
Em produção você **não tem o debugger**. O log é o seu **gravador de voo**: quando um cliente diz "meu depósito sumiu às 14h32", ele é a única testemunha. Mas log demais é ruído (e custo, e risco de vazamento), log de menos deixa você cego. Em entrevista: "qual a diferença entre `WARN` e `ERROR`?", "por que usar `{}` em vez de `+`?" e "como acompanhar uma requisição entre vários logs?" são perguntas comuns. O módulo P6 leva isso adiante (logs estruturados, correlação entre serviços, tracing); aqui estão as bases.

## 💡 Intuição (explicação simples)
O **diário de bordo de um navio**. O capitão escreve **o que importa, no nível certo**: rotina ("passamos pelo farol", `INFO`), uma **atenção** ("mar mais agitado que o previsto", `WARN`), um **problema que exige reação** ("casco com rachadura", `ERROR`), e, só quando se investiga, **detalhes minuciosos** ("leitura do sonar a cada minuto", `DEBUG`/`TRACE`). Cada anotação tem **hora, quem escreveu e o número do turno** (o `requestId`: todas as anotações de um mesmo turno se leem juntas). E o diário **nunca** guarda a senha do cofre nem o CPF de um passageiro.

## 🔬 Como funciona por dentro

### 1. SLF4J e Logback
- **SLF4J** (*Simple Logging Facade for Java*) é só uma **fachada**: a interface `org.slf4j.Logger` que o **seu código** usa. Ela não escreve nada sozinha.
- **Logback** é a **implementação** padrão do Spring Boot (vem no `spring-boot-starter`, J5.02: `logback-classic`). Ele recebe as chamadas do SLF4J, decide **se** escreve (nível) e **como** (padrão, destino).
- Por que a fachada? Seu código e as **bibliotecas** (Hibernate, Spring, Tomcat) escrevem no **mesmo** sistema de log, e você pode trocar a implementação sem tocar no código.
- Cada `Logger` tem um **nome**, normalmente o da classe (`LoggerFactory.getLogger(AccountService.class)` → `com.payflow.service.AccountService`). Os nomes formam uma **hierarquia por pacote**, e o nível se configura por ela (`com.payflow` vale para tudo abaixo).

### 2. Os níveis
Do mais grave ao mais detalhado: **`ERROR` > `WARN` > `INFO` > `DEBUG` > `TRACE`**. Configurar um nível liga **ele e os mais graves**. O padrão do Spring Boot é `INFO`.
| Nível | Use para | Exemplo no PayFlow |
|---|---|---|
| **`ERROR`** | Algo **falhou** e precisa de **atenção humana**: bug, falha de infraestrutura | O `WebErrors` para uma exceção **inesperada** (com *stack trace*) |
| **`WARN`** | Situação **anormal mas tratada**; erro de **negócio** esperado; algo que merece olhar | `Deposit refused` (conta bloqueada) |
| **`INFO`** | **Marcos** do negócio e do ciclo de vida: o que aconteceu de importante | `Deposit accepted`, `Transfer completed`, `Started PayflowApplication` |
| **`DEBUG`** | Detalhe para **diagnóstico** (desligado em produção) | O SQL do Hibernate (`org.hibernate.SQL`) |
| **`TRACE`** | Detalhe **extremo** | O log de transações da J5.11 |
**Regra de ouro:** um erro de **negócio esperado** (saldo insuficiente, conta bloqueada) **não** é `ERROR`: o sistema fez exatamente o que devia. `ERROR` que dispara alarme toda hora deixa de ser olhado. **Quem trata a exceção loga uma vez:** não logue e relance em cada camada (o mesmo erro aparece cinco vezes).

### 3. Mensagens parametrizadas: `{}` em vez de `+`
```java
log.info("Deposit accepted: account={} amount={}", accountId, amount);     // ✅ parametrizado
log.info("Deposit accepted: account=" + accountId + " amount=" + amount);  // ❌ concatenado
```
Com `+`, a `String` é **montada antes** de o logger saber se vai descartá-la (nível desligado). Com `{}`, o logger só formata **se for escrever**. A diferença, **medida** (nível `DEBUG` desligado; objeto com um `toString()` que conta as chamadas):
```
concatenado:   toString chamado 1 vez(es)
parametrizado: toString chamado 0 vez(es)
com guard:     argumento calculado 0 vez(es)
```
Quando o **argumento em si** é caro de calcular (não apenas de formatar), proteja com `if (log.isDebugEnabled()) { ... }`. Uma exceção como **último** argumento imprime o *stack trace*: `log.error("Transfer failed: transfer={}", id, exception);` (sem `{}` para ela).

### 4. Anatomia de uma linha do Spring Boot
```
INFO [req-test-1] 1911179 --- [payflow] [o-auto-1-exec-2] com.payflow.service.AccountService       : Deposit accepted: account=20000000-...-01 amount=25.90
 │      │            │            │            │                       │                                  └─ a mensagem
 │      │            │            │            │                       └─ o logger (a classe), abreviado/alinhado
 │      │            │            │            └─ a thread (quem atendeu a requisição)
 │      │            │            └─ o nome da aplicação (spring.application.name)
 │      │            └─ o PID do processo
 │      └─ o requestId (MDC): é o que vamos configurar abaixo
 └─ o nível
```
(O início da linha, a data e hora, foi removido nos exemplos desta aula.)

### 5. MDC: o "número do turno" de cada requisição
O **MDC** (*Mapped Diagnostic Context*) é um **mapa por *thread*** em que você coloca dados de contexto (`MDC.put("requestId", id)`); o Logback os imprime com `%X{requestId}` em **toda** linha escrita por aquela thread. Em um servidor web, **uma thread atende uma requisição por vez**, então "meu `requestId`" vale para tudo que acontece nela: controller, serviço, SQL. **Regra:** `MDC.remove(...)` num `finally`, porque a thread **volta para o pool** e atenderia a próxima requisição com o id da anterior.

## 🛠️ Exemplo prático
> Testado com **JDK 25.0.5**, **Spring Boot 4.1.2** (Logback 1.5.38, SLF4J 2.0.20), PostgreSQL 18.6.

### 1. Configuração
`application.yml` (base = o que vale em produção):
```yaml
logging:
  level:
    root: INFO
    com.payflow: INFO
  pattern:
    level: "%5p [%X{requestId:-}]"          # o nível e o requestId (vazio fora de uma requisição)
```
- `%X{requestId:-}`: o `:-` é o valor **padrão** quando o MDC não tem a chave (por exemplo, no log de inicialização).
- `logging.pattern.level` troca **só a parte do nível** do padrão do Boot (os demais campos continuam).

`application-dev.yml` (acrescente):
```yaml
logging:
  level:
    com.payflow: DEBUG                     # no desenvolvimento, os logs do PayFlow em detalhe
    org.hibernate.SQL: DEBUG               # e o SQL que o Hibernate gera (J5.07)
```
Assim o `application-dev.yml` substitui o `logging.level.org.hibernate.SQL=DEBUG` que você colocava nas propriedades dos testes. **Em produção, `DEBUG` de `org.hibernate.SQL` fica desligado**: custa desempenho e pode vazar dados.

### 2. O filtro do `requestId`
`src/main/java/com/payflow/web/RequestIdFilter.java`
```java
package com.payflow.web;

import jakarta.servlet.FilterChain;
import jakarta.servlet.ServletException;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import java.io.IOException;
import java.util.Optional;
import java.util.UUID;
import org.slf4j.MDC;
import org.springframework.stereotype.Component;
import org.springframework.web.filter.OncePerRequestFilter;

/**
 * Dá um identificador a cada requisição e o coloca no MDC (um "mapa de contexto" por thread):
 * todo log escrito durante a requisição pode mostrá-lo (%X{requestId}), o que permite seguir UMA requisição.
 */
@Component
public class RequestIdFilter extends OncePerRequestFilter {

    public static final String HEADER = "X-Request-Id";
    public static final String MDC_KEY = "requestId";

    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response, FilterChain chain)
            throws ServletException, IOException {
        String id = Optional.ofNullable(request.getHeader(HEADER))
                .filter(value -> value.matches("[A-Za-z0-9-]{1,64}"))     // nunca confie no cabeçalho: evita "log injection"
                .orElseGet(() -> UUID.randomUUID().toString());
        MDC.put(MDC_KEY, id);
        response.setHeader(HEADER, id);
        try {
            chain.doFilter(request, response);
        } finally {
            MDC.remove(MDC_KEY);                                           // a thread volta ao pool: limpe sempre
        }
    }
}
```
- É um **filtro de servlet** (`OncePerRequestFilter`), não um *interceptor* do Spring MVC (J5.06): ele roda **antes** do `DispatcherServlet`, então o `requestId` já existe quando o interceptor de autenticação, o controller e o Hibernate escrevem.
- **Aceita o `X-Request-Id` do cliente** (útil quando um *gateway* já gerou um) **somente se** casar com `[A-Za-z0-9-]{1,64}`; senão gera um UUID. Nunca confie em um cabeçalho: um valor com quebra de linha (`\\n`) poderia **forjar linhas de log** (*log injection*; o teste `aMaliciousRequestIdIsReplaced` prova a troca).
- Devolve o id no cabeçalho da resposta (`X-Request-Id`), para o cliente citá-lo em um suporte.

import static org.assertj.core.api.Assertions.assertThat;

import java.util.concurrent.atomic.AtomicInteger;
import org.junit.jupiter.api.Test;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

/** Laboratório da J5.14: concatenar × parametrizar. O nível DEBUG está desligado (o padrão é INFO). */
class LoggingCostLabTest {

    private static final Logger log = LoggerFactory.getLogger(LoggingCostLabTest.class);

    /** Um objeto cujo toString é "caro" (pense em uma entidade grande ou numa lista): contamos as chamadas. */
    static class Expensive {
        final AtomicInteger calls = new AtomicInteger();

        @Override
        public String toString() {
            calls.incrementAndGet();
            return "expensive-state";
        }
    }

    @Test
    void concatenationPaysEvenWhenTheLevelIsOff() {
        Expensive value = new Expensive();
        log.debug("state = " + value);                 // a String é montada ANTES de o logger decidir descartar
        System.out.println("concatenado:   toString chamado " + value.calls.get() + " vez(es)");

    @Test
    void parameterizedMessagesAreFreeWhenTheLevelIsOff() {
        Expensive value = new Expensive();
        log.debug("state = {}", value);                // o logger só chama toString se o nível estiver ligado
        System.out.println("parametrizado: toString chamado " + value.calls.get() + " vez(es)");
        assertThat(value.calls.get()).isZero();
    }

    @Test
    void anArgumentThatItselfIsExpensiveNeedsAGuard() {
        AtomicInteger computed = new AtomicInteger();
        if (log.isDebugEnabled()) {                    // o guard evita CALCULAR o argumento
            log.debug("sum = {}", computed.incrementAndGet());
        }
        System.out.println("com guard:     argumento calculado " + computed.get() + " vez(es)");

### 6. Formato estruturado (JSON), uma prévia do P6
O Spring Boot sabe escrever logs em JSON, que ferramentas de agregação (Elasticsearch, Loki, CloudWatch) leem **sem expressões regulares**. Com `--logging.structured.format.console=logstash` (testado), a mesma linha vira:
```json
{"@timestamp":"2026-11-13T12:09:56.067585169-03:00","@version":"1","message":"Deposit accepted: account=20000000-0000-0000-0000-000000000001 amount=10.00","logger_name":"com.payflow.service.AccountService","thread_name":"http-nio-8080-exec-3","level":"INFO","level_value":20000,"requestId":"demo-123"}
```
O `requestId` do MDC vira um **campo** do JSON. Outros formatos disponíveis: `ecs`, `gelf` (consulte a [documentação](https://docs.spring.io/spring-boot/reference/features/logging.html)). Em produção, logs estruturados no *stdout* (o container captura) são o padrão; o P6 aprofunda.

## 🧠 Pausa para lógica
**Enunciado:** implemente um **logger de brinquedo** com: (a) **níveis** e um limite (`threshold`): mensagens abaixo dele são descartadas **antes** de formatar; (b) substituição de `{}` pelos argumentos, **na ordem**; (c) **exceção como último argumento** (não ocupa um `{}`); (d) um **MDC por thread** (`ThreadLocal<Map>`) cujo `requestId` aparece em cada linha.

<details><summary>Dica</summary>Compare níveis com o <code>compareTo</code> do <code>enum</code> (a ordem de declaração é a gravidade). Para os <code>{}</code>: <code>indexOf("{}", from)</code> em laço, anexando o trecho entre o último <code>from</code> e a posição achada. Verifique se o <b>último</b> argumento <code>instanceof Throwable</code> e, se for, use <code>args.length - 1</code> argumentos para os <code>{}</code>. Para provar que descartou "antes de formatar", passe um argumento cujo <code>toString()</code> lança um erro.</details>
<details><summary>Solução (testada com JDK 25.0.5)</summary>

```java
import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Map;

/** Um logger de brinquedo: níveis, mensagem parametrizada com {}, exceção no último argumento e um MDC por thread. */
public class MiniLogger {

    enum Level { TRACE, DEBUG, INFO, WARN, ERROR }

    private static final ThreadLocal<Map<String, String>> MDC = ThreadLocal.withInitial(HashMap::new);
    private final String name;
    private final Level threshold;
    final List<String> output = new ArrayList<>();

    MiniLogger(String name, Level threshold) {
        this.name = name;
        this.threshold = threshold;
    }

    static void put(String key, String value) { MDC.get().put(key, value); }

    static void clear() { MDC.remove(); }

    boolean isEnabled(Level level) { return level.compareTo(threshold) >= 0; }

    void log(Level level, String template, Object... args) {
        if (!isEnabled(level)) {
            return;                                           // descartado ANTES de formatar: nenhum toString chamado
        }
        Throwable error = args.length > 0 && args[args.length - 1] instanceof Throwable t ? t : null;
        int usable = error == null ? args.length : args.length - 1;   // o último Throwable não consome um {}
        StringBuilder sb = new StringBuilder();
        int from = 0;
        for (int i = 0; i < usable; i++) {
            int at = template.indexOf("{}", from);
            if (at < 0) break;                                // mais argumentos que {}: sobram (o SLF4J também ignora)
            sb.append(template, from, at).append(args[i]);
            from = at + 2;
        }
        sb.append(template.substring(from));
        String line = String.format("%-5s [%s] %s : %s", level, MDC.get().getOrDefault("requestId", ""), name, sb);
        output.add(line);
        if (error != null) {
            output.add("    " + error.getClass().getSimpleName() + ": " + error.getMessage());
        }
    }

    public static void main(String[] args) {
        MiniLogger log = new MiniLogger("AccountService", Level.INFO);
        MiniLogger.put("requestId", "req-42");

        log.log(Level.DEBUG, "state = {}", new Object() { public String toString() { throw new AssertionError("toString chamado!"); } });
        log.log(Level.INFO, "Deposit accepted: account={} amount={}", "A1", "25.90");
        log.log(Level.WARN, "Deposit refused: account={} reason={}", "A3", "blocked");
        log.log(Level.ERROR, "Transfer failed: transfer={}", "T9", new IllegalStateException("db down"));
        log.log(Level.INFO, "sem placeholders");
        log.log(Level.INFO, "só um {} para dois args", "a", "b");
        MiniLogger.clear();
        log.log(Level.INFO, "fora da requisição");
        log.output.forEach(System.out::println);
    }
}
```

## ⚠️ Erros comuns e boas práticas de produção
- **`System.out.println` / `e.printStackTrace()`** em código de produção: sem nível, sem logger, sem requestId, sem formato. Sempre `log.xxx(...)`. (O `BeanTour` e o `StartupBanner` das J5.02–J5.05 usavam `System.out` **só como laboratório**: apague-os agora.)
- **Segredos e dados pessoais no log:** senhas, tokens, números de cartão, **CPF, e-mail, telefone, endereço**. (LGPD, J8.) Registre **ids** (UUID), não pessoas. Cuidado com `log.info("user {}", user)`: o `toString()` da entidade pode incluir tudo (e disparar cargas preguiçosas, J5.08).
- **Logar e relançar em cada camada:** o mesmo erro vira cinco linhas. Log no ponto em que o erro é **tratado** (a borda).
- **`ERROR` para erro de negócio** (saldo insuficiente): vira ruído e mascara os erros de verdade. `WARN` ou `INFO`.
- **`log.error(e.getMessage())`:** perde o *stack trace*. Use `log.error("contexto", e)` (exceção como **último** argumento).
- **Concatenar strings** (`"a" + b`) em `log.debug`: paga mesmo com o nível desligado (medido acima).
- **`DEBUG`/`TRACE` ligado em produção:** volume e custo enormes; o SQL logado pode conter **dados** (com `TRACE` dos *binds*). Ligue só por um tempo e por pacote (via Actuator, J5.15).
- **Esquecer o `MDC.remove`:** vaza o `requestId` de uma requisição para outra.
- **Log como "banco de dados":** não dependa de log para regra de negócio ou auditoria legal; auditoria vai para uma **tabela** própria (S5).
- **Mensagens sem contexto:** `"Erro ao salvar"` não diz nada. Diga **o quê**, **com quais ids**, **qual regra**.
- **Cabeçalho do cliente direto no log** sem validar (*log injection*): valide, como o filtro faz.

## 🎤 Na entrevista
- **Qual a diferença entre SLF4J, Logback e Log4j?** SLF4J é uma fachada; Logback e Log4j2 são implementações. O Spring Boot usa SLF4J + Logback por padrão e adapta outras bibliotecas (o log4j-api cai em SLF4J).
- **Quais os níveis de log e quando usar cada um?** `ERROR` falha que exige ação; `WARN` anormal/tratado; `INFO` marcos do negócio; `DEBUG` diagnóstico; `TRACE` detalhe extremo. Produção em `INFO`.
- **Por que usar `{}` e não concatenar?** Evita montar a mensagem quando o nível está desligado e é mais legível; para argumentos caros, `isDebugEnabled()`.
- **O que é MDC e correlation id?** Mapa de contexto por thread impresso nos logs; o *correlation/request id* permite seguir uma requisição entre linhas (e, propagado em cabeçalhos, entre serviços).
- **O que não logar?** Segredos (senhas, tokens, chaves) e dados pessoais (LGPD); stack traces de erros de negócio esperados.
- **Como mudar o nível de log em produção sem reiniciar?** Pelo Actuator (`/actuator/loggers`), por pacote (J5.15), ou por configuração externa recarregável.
