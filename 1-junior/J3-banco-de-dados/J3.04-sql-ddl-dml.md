# J3.04 — SQL I: DDL e DML

> ⏱️ ~1h30 · 🟢 Júnior · Pré-requisitos: J3.01, J3.02, J3.03

## 🎯 Objetivos
Ao final desta aula você consegue:
- Criar tabelas com os **tipos** certos e as **constraints** nomeadas (`CREATE TABLE`), e alterá-las (`ALTER TABLE`).
- Inserir, atualizar e apagar linhas (`INSERT`, `UPDATE`, `DELETE`) usando `RETURNING` e `ON CONFLICT`.
- Carregar o **esquema** e os **dados de exemplo** do PayFlow no PostgreSQL.
- Interpretar as mensagens de erro de cada constraint violada.
- Dizer a diferença entre `DELETE`, `TRUNCATE` e `DROP`.

## 🤔 Por que isso importa
Todo sistema começa (e evolui) por `CREATE TABLE` e `ALTER TABLE`. Um `UPDATE` sem `WHERE` em produção é um dos acidentes mais clássicos da profissão, e a maioria dos erros de dado que você vai investigar vem de um `INSERT` que o banco aceitou porque faltava uma constraint. Aprender o DDL e o DML **com as mensagens de erro reais** faz você reconhecer o problema em segundos depois.

## 💡 Intuição (explicação simples)
- **DDL** (*Data Definition Language*) é a **planta do prédio**: cria, altera e demole **estruturas** (tabelas, colunas, constraints).
- **DML** (*Data Manipulation Language*) é a **mudança de móveis**: coloca, troca e retira **dados** dentro das estruturas.
- O SQL é **declarativo**: você diz **o quê** quer ("uma linha com estes valores"), não **como** o banco deve fazer. O banco escolhe o caminho.

## 🔬 Como funciona por dentro

### Famílias de comandos SQL
| Sigla | Para quê | Comandos |
|---|---|---|
| **DDL** | Estrutura | `CREATE`, `ALTER`, `DROP`, `TRUNCATE` |
| **DML** | Dados | `INSERT`, `UPDATE`, `DELETE` |
| **DQL** | Consulta | `SELECT` (J3.05 em diante) |
| **TCL** | Transação | `BEGIN`, `COMMIT`, `ROLLBACK` (J3.10) |
| **DCL** | Permissões | `GRANT`, `REVOKE` (visão em J8) |

### Tipos do PostgreSQL que o PayFlow usa
| Tipo | Para quê | Por quê |
|---|---|---|
| `UUID` | Identificadores | Decisão do projeto (J3.02); `uuidv7()` é novo no PostgreSQL 18 |
| `NUMERIC(19, 2)` | Dinheiro | Exato: até 19 dígitos, 2 depois da vírgula. **Nunca** `FLOAT`/`DOUBLE PRECISION` (aproximados) |
| `VARCHAR(n)` | Texto com limite | Documenta o limite e o banco o impõe |
| `TIMESTAMPTZ` | Data e hora | Guarda o **instante** (UTC internamente); decisão do projeto |
| `BIGINT` | Contadores (`version`) | 64 bits |
| `BOOLEAN`, `DATE`, `TEXT` | Verdadeiro/falso, data sem hora, texto sem limite | Uso geral |

`TIMESTAMPTZ` não guarda "o fuso": guarda o instante e **converte** para o fuso da sessão ao exibir. Um `TIMESTAMP` (sem fuso) guarda apenas "o relógio da parede", sem dizer em que lugar. Para um sistema que atende vários fusos, use `TIMESTAMPTZ` (e `Instant`/`OffsetDateTime` em Java, J1.15).

Armadilhas dos literais numéricos (verificadas com `pg_typeof`):
```sql
SELECT pg_typeof(1) a, pg_typeof(1.5) b, pg_typeof(1.5::float8) c;   -- integer | numeric | double precision
SELECT 10 / 4 AS int_div, 10 / 4.0 AS num_div, 10 % 4 AS mod;        -- 2 | 2.5000000000000000 | 2
SELECT (0.1::float8 + 0.2::float8) = 0.3::float8 AS float_eq,
       (0.1::numeric + 0.2::numeric) = 0.3::numeric AS num_eq;       -- f | t
```
O literal `1.5` já é `numeric` (exato). A divisão de dois inteiros é **inteira** (`10 / 4 = 2`, como em Java, J1.01). E `0.1 + 0.2` só dá `0.3` em `numeric`.

E o **arredondamento do banco não é o do Java** (decisão 4 do projeto: `HALF_EVEN`):
```sql
SELECT 123.456::numeric(5,2) AS cast_numeric, round(2.5) AS numeric_25, round(3.5) AS numeric_35, round(2.5::float8) AS float_25;
```
```
 cast_numeric | numeric_25 | numeric_35 | float_25 
--------------+------------+------------+----------
       123.46 |          3 |          4 |        2
```
`round(2.5)` em `numeric` dá **3** (arredonda a metade "para longe do zero"), enquanto em `double precision` dá **2**; e gravar `10.005` em `NUMERIC(19,2)` guarda `10.01` (J3.11), ao passo que `HALF_EVEN` em Java daria `10.00`. Por isso o PayFlow **arredonda na aplicação** e o banco só armazena (`projeto/adrs/0004-dinheiro-arredondado-na-aplicacao.md`).

### `CREATE TABLE`
```sql
CREATE TABLE nome (
    coluna  TIPO [NOT NULL] [DEFAULT valor],
    ...,
    CONSTRAINT nome_da_constraint  PRIMARY KEY (...) | UNIQUE (...) | CHECK (...) | FOREIGN KEY (...) REFERENCES outra (...)
);
```
Cada constraint recebe um **nome** (convenção da J3.02). Assim, `ck_accounts_balance` aparece na mensagem de erro, e não um nome gerado.

### `ALTER`, `DROP`, `TRUNCATE`
| Comando | Faz | Cuidado |
|---|---|---|
| `ALTER TABLE t ADD COLUMN c TIPO` | Nova coluna | `NOT NULL` sem `DEFAULT` falha se já há linhas |
| `ALTER TABLE t DROP COLUMN c` | Remove coluna e seus dados | Irreversível |
| `ALTER TABLE t RENAME COLUMN a TO b` | Renomeia | Quebra o código que usa o nome antigo |
| `ALTER TABLE t ADD CONSTRAINT ...` | Nova regra | Falha se os dados atuais já a violam |
| `DROP TABLE t` | Apaga a tabela inteira | Falha se outras tabelas a referenciam (use `CASCADE` com extremo cuidado) |
| `TRUNCATE t` | Apaga **todas** as linhas, rápido | Não aceita `WHERE`; falha se referenciada por FK |
| `DELETE FROM t WHERE ...` | Apaga linhas escolhidas | Sem `WHERE`, apaga todas |

### `INSERT`, `UPDATE`, `DELETE`
- `INSERT INTO t (cols) VALUES (...), (...)`: várias linhas de uma vez. Colunas omitidas recebem o `DEFAULT`.
- **`RETURNING`** devolve as colunas da linha inserida/alterada/apagada: é como o Java descobre o `id` gerado pelo banco (J3.11).
- **`ON CONFLICT`** (*upsert*): `DO NOTHING` ignora a linha que violaria a chave; `DO UPDATE SET ...` atualiza a existente. Será o mecanismo da **idempotência** (regra 4) e do *seed* repetível (J3.12).
- `UPDATE t SET c = v WHERE ...` e `DELETE FROM t WHERE ...`: **sempre com `WHERE`**. O banco só avisa quantas linhas afetou (`UPDATE 3`).

### 1. O esquema do PayFlow
No repositório `payflow`, crie `db/scratch/schema.sql` (arquivo **provisório**: na J3.12 ele vira as migrações do Flyway).

```sql
-- PayFlow: esquema do módulo J3 (PostgreSQL 18)
-- Convenção de nomes de constraints: pk_, uk_, ck_, fk_ + tabela + coluna(s)

CREATE TABLE users (
    id            UUID         NOT NULL DEFAULT uuidv7(),
    email         VARCHAR(255) NOT NULL,
    full_name     VARCHAR(120) NOT NULL,
    password_hash VARCHAR(100) NOT NULL,
    role          VARCHAR(20)  NOT NULL DEFAULT 'USER',
    created_at    TIMESTAMPTZ  NOT NULL DEFAULT now(),
    CONSTRAINT pk_users PRIMARY KEY (id),
    CONSTRAINT uk_users_email UNIQUE (email),
    CONSTRAINT ck_users_role CHECK (role IN ('USER', 'ADMIN'))
);

CREATE TABLE accounts (
    id         UUID           NOT NULL DEFAULT uuidv7(),
    owner_id   UUID           NOT NULL,
    balance    NUMERIC(19, 2) NOT NULL DEFAULT 0,
    status     VARCHAR(20)    NOT NULL DEFAULT 'ACTIVE',
    version    BIGINT         NOT NULL DEFAULT 0,
    created_at TIMESTAMPTZ    NOT NULL DEFAULT now(),
    CONSTRAINT pk_accounts PRIMARY KEY (id),
    CONSTRAINT fk_accounts_owner FOREIGN KEY (owner_id) REFERENCES users (id),
    CONSTRAINT ck_accounts_balance CHECK (balance >= 0),
    CONSTRAINT ck_accounts_status CHECK (status IN ('ACTIVE', 'BLOCKED', 'CLOSED'))
);

CREATE TABLE transfers (
    id                UUID           NOT NULL DEFAULT uuidv7(),
    source_account_id UUID           NOT NULL,
    target_account_id UUID           NOT NULL,
    amount            NUMERIC(19, 2) NOT NULL,
    status            VARCHAR(20)    NOT NULL DEFAULT 'PENDING',
    idempotency_key   VARCHAR(100)   NOT NULL,
    created_at        TIMESTAMPTZ    NOT NULL DEFAULT now(),
    CONSTRAINT pk_transfers PRIMARY KEY (id),
    CONSTRAINT fk_transfers_source FOREIGN KEY (source_account_id) REFERENCES accounts (id),
    CONSTRAINT fk_transfers_target FOREIGN KEY (target_account_id) REFERENCES accounts (id),
    CONSTRAINT uk_transfers_idempotency_key UNIQUE (idempotency_key),
    CONSTRAINT ck_transfers_amount CHECK (amount > 0),
    CONSTRAINT ck_transfers_status CHECK (status IN ('PENDING', 'COMPLETED', 'FAILED')),
    CONSTRAINT ck_transfers_different_accounts CHECK (source_account_id <> target_account_id)
);

CREATE TABLE ledger_entries (
    id          UUID           NOT NULL DEFAULT uuidv7(),
    account_id  UUID           NOT NULL,
    transfer_id UUID,
    type        VARCHAR(10)    NOT NULL,
    amount      NUMERIC(19, 2) NOT NULL,
    created_at  TIMESTAMPTZ    NOT NULL DEFAULT now(),
    CONSTRAINT pk_ledger_entries PRIMARY KEY (id),
    CONSTRAINT fk_ledger_entries_account FOREIGN KEY (account_id) REFERENCES accounts (id),
    CONSTRAINT fk_ledger_entries_transfer FOREIGN KEY (transfer_id) REFERENCES transfers (id),
    CONSTRAINT ck_ledger_entries_type CHECK (type IN ('DEBIT', 'CREDIT')),
    CONSTRAINT ck_ledger_entries_amount CHECK (amount > 0)
);
```
Comentários sobre as escolhas:
- `owner_id` e os demais campos de relacionamento são `NOT NULL`, **exceto** `ledger_entries.transfer_id`: um depósito é um lançamento **sem** transferência (`projeto/adrs/0001-ledger-transfer-id-nulo.md`).
- `accounts.version` existe desde já porque o `projeto-central.md` o define (será usado para *locking* otimista em P2); por enquanto vale 0.
- `CHECK (source_account_id <> target_account_id)` impede transferir para si mesma.
- Apenas o essencial para as regras de negócio 1 a 5; índices vêm na J3.09.

### 5. `ON CONFLICT` (*upsert*)
```sql
-- ignora a linha duplicada
INSERT INTO users (email, full_name, password_hash) VALUES ('ana@payflow.dev', 'Outra', 'x')
ON CONFLICT (email) DO NOTHING;                                  -- INSERT 0 0 (nada inserido, sem erro)

-- atualiza se já existir
INSERT INTO users (email, full_name, password_hash) VALUES ('ana@payflow.dev', 'Ana S. Silva', 'x')
ON CONFLICT (email) DO UPDATE SET full_name = EXCLUDED.full_name
RETURNING email, full_name;                                      -- ana@payflow.dev | Ana S. Silva
UPDATE users SET full_name = 'Ana Silva' WHERE email = 'ana@payflow.dev';   -- restaura
```
`EXCLUDED` é a linha que **tentou** entrar.

### 6. `ALTER`, `DROP` e `TRUNCATE` (mensagens reais)
Em um banco de laboratório (não no `payflow`, para não estragar o esquema):
```sql
DROP TABLE users;
```
```
ERROR:  cannot drop table users because other objects depend on it
DETAIL:  constraint fk_accounts_owner on table accounts depends on table users
HINT:  Use DROP ... CASCADE to drop the dependent objects too.
```
```sql
TRUNCATE users;
```
```
ERROR:  cannot truncate a table referenced in a foreign key constraint
DETAIL:  Table "accounts" references "users".
HINT:  Truncate table "accounts" at the same time, or use TRUNCATE ... CASCADE.
```
```sql
-- com uma linha já existente em users:
ALTER TABLE users ADD COLUMN birth_date DATE NOT NULL;
```
```
ERROR:  column "birth_date" of relation "users" contains null values
```
```sql
ALTER TABLE users ADD COLUMN birth_date DATE;                          -- opcional: funciona
ALTER TABLE users ADD COLUMN status VARCHAR(20) NOT NULL DEFAULT 'ACTIVE';  -- NOT NULL com DEFAULT: funciona
ALTER TABLE users RENAME COLUMN status TO state;
ALTER TABLE users DROP COLUMN state;
```
Para uma coluna obrigatória em tabela com dados, o caminho seguro é: adicionar com `DEFAULT`, ou adicionar opcional, preencher e só então impor `NOT NULL`. Em produção isso vira uma sequência de **migrações** (J3.12; migrações sem *downtime* ficam para S3).

### 7. O perigo do `UPDATE` sem `WHERE`
```sql
BEGIN;                                          -- abre uma transação (J3.10)
UPDATE users SET full_name = 'X';               -- sem WHERE
SELECT count(*) AS afetadas FROM users WHERE full_name = 'X';
ROLLBACK;                                       -- desfaz tudo
```
```
UPDATE 1                (em um banco com 1 usuário; no payflow seriam 5)
 afetadas 
----------
        1
```
Com `BEGIN` ... `ROLLBACK` você **ensaia** o comando e confere quantas linhas seriam afetadas antes de valer. Hábito profissional: escreva primeiro o `SELECT ... WHERE`, confira, e só então troque por `UPDATE`/`DELETE`.

## 🧠 Pausa para lógica
**Enunciado:** simule `INSERT ... ON CONFLICT (id) DO NOTHING` em Java com um `Map<String,String>` (a "tabela") e devolva **quantas linhas foram realmente inseridas**. Rode duas vezes o mesmo *seed* e depois altere uma linha: o *seed* deve **não sobrescrever** a alteração.

<details><summary>Dica</summary><code>Map.putIfAbsent</code> devolve <code>null</code> quando insere e o valor antigo quando a chave já existia.</details>
<details><summary>Solução (testada com JDK 25.0.5)</summary>

```java
import java.util.*;

public class SeedIdempotent {
    /** Equivalente a INSERT ... ON CONFLICT (id) DO NOTHING: devolve quantas linhas foram realmente inseridas. */
    static int insertAll(Map<String, String> table, Map<String, String> rows) {
        int inserted = 0;
        for (var row : rows.entrySet()) if (table.putIfAbsent(row.getKey(), row.getValue()) == null) inserted++;
        return inserted;
    }

    public static void main(String[] args) {
        Map<String, String> users = new TreeMap<>();
        Map<String, String> seed = Map.of("u1", "Ana", "u2", "Bruno");
        System.out.println("1ª execução inseriu " + insertAll(users, seed));
        System.out.println("2ª execução inseriu " + insertAll(users, seed));
        users.put("u1", "Ana Maria");                       // alguém editou a linha
        System.out.println("3ª execução inseriu " + insertAll(users, seed) + "; u1 continua '" + users.get("u1") + "' (DO NOTHING não sobrescreve)");
    }
}
```
```
1ª execução inseriu 2
2ª execução inseriu 0
3ª execução inseriu 0; u1 continua 'Ana Maria' (DO NOTHING não sobrescreve)
```
Um *seed* **idempotente** pode ser executado várias vezes sem duplicar nem corromper. É a propriedade que o seed repetível do Flyway (J3.12) precisa.
</details>

## ⚠️ Erros comuns e boas práticas de produção
- **`UPDATE`/`DELETE` sem `WHERE`:** afeta a tabela inteira. Use `BEGIN`/`ROLLBACK` para ensaiar e confira o "`UPDATE n`".
- **Maiúsculas e aspas nos nomes:** o PostgreSQL converte identificadores **sem aspas** para minúsculas. Depois de `CREATE TABLE "Teste"`, o comando `SELECT * FROM Teste` falha com `ERROR:  relation "teste" does not exist` (precisa de `"Teste"`). Por isso o PayFlow usa `snake_case` minúsculo e **nunca** aspas.
- **Aspas duplas no valor:** `WHERE status = "ACTIVE"` falha com `ERROR:  column "ACTIVE" does not exist`. **Aspas simples** são texto; **duplas** são identificador.
- **Ordem de criação/remoção errada** (J3.01): `DROP TABLE users` antes de `accounts` falha.
- **`FLOAT` para dinheiro**, `VARCHAR` sem limite onde há regra, `TIMESTAMP` sem fuso: decisões difíceis de reverter depois.
- **`NOT NULL` sem `DEFAULT` em tabela que já tem dados:** falha (acima).
- **`DROP`/`TRUNCATE` no banco errado:** confira o prompt (`payflow=#`) e o `\conninfo`. Em produção, ninguém roda DDL manual: usa migrações (J3.12) revisadas em pull request.
- **Guardar o esquema só "no banco":** sem versionamento em arquivo, ninguém consegue recriar o ambiente (por isso `db/scratch/*.sql` agora e Flyway depois).

## 🎤 Na entrevista
- **Diferença entre `DELETE`, `TRUNCATE` e `DROP`?** `DELETE` remove linhas (aceita `WHERE`); `TRUNCATE` esvazia a tabela inteira, rápido e sem `WHERE`; `DROP` remove a tabela (estrutura e dados).
- **Por que `NUMERIC` e não `FLOAT` para dinheiro?** `NUMERIC` é exato; `FLOAT` é binário aproximado (`0.1 + 0.2 ≠ 0.3`), o que gera diferenças de centavos.
- **Para que serve `RETURNING`?** Devolve as colunas da linha afetada na mesma instrução, útil para obter `id` e valores padrão gerados pelo banco sem uma segunda consulta.
- **O que é um *upsert* e como o PostgreSQL faz?** Inserir ou atualizar se já existir: `INSERT ... ON CONFLICT (coluna) DO UPDATE ...` (ou `DO NOTHING`).
