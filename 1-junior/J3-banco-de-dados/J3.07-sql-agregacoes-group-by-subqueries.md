# J3.07 — SQL IV: agregações, `GROUP BY` e subqueries

> ⏱️ ~1h30 · 🟢 Júnior · Pré-requisitos: J3.05, J3.06, J1.13 (`Collectors.groupingBy`)

## 🎯 Objetivos
Ao final desta aula você consegue:
- Usar `COUNT`, `SUM`, `AVG`, `MIN` e `MAX`, incluindo `COUNT(*)` vs `COUNT(coluna)` vs `COUNT(DISTINCT ...)` e `FILTER`.
- Agrupar com `GROUP BY` e filtrar grupos com `HAVING`, sabendo a diferença para `WHERE`.
- Escrever subqueries **escalares**, com `IN`, com `EXISTS`, **correlacionadas** e na cláusula `FROM`.
- Escrever a **consulta de conferência** do PayFlow: saldo guardado × soma dos lançamentos (regra 3).
- Interpretar os erros `must appear in the GROUP BY` e `more than one row returned by a subquery`.

## 🤔 Por que isso importa
Relatórios, painéis e conferências são agregações: "quanto cada conta movimentou?", "quais contas têm mais de 3 lançamentos?", "o saldo de cada conta bate com o extrato?". Esta última é a pergunta que um time financeiro faz **todo dia**, e é uma consulta de agregação com `JOIN` e subquery. Escrevê-la corretamente (e saber que o resultado esperado é **zero linhas**) é uma competência de júnior em sistemas de pagamento.

## 💡 Intuição (explicação simples)
Você tem uma **pilha de notas fiscais**. Agregar é **resumir a pilha**: "quantas notas?", "qual o total?". `GROUP BY` é **separar a pilha em montinhos** (um por cliente) e resumir **cada montinho**: "total por cliente". `HAVING` é **descartar montinhos** depois de resumidos ("só os clientes com total acima de 300"). Uma subquery é **uma pergunta dentro de outra**: "contas com saldo maior que a **média das contas**": primeiro calcula-se a média, depois compara-se.

## 🔬 Como funciona por dentro

### Funções de agregação
| Função | Faz | Observação |
|---|---|---|
| `COUNT(*)` | Conta **linhas** | Inclui linhas com nulos |
| `COUNT(coluna)` | Conta valores **não nulos** | Ignora `NULL` |
| `COUNT(DISTINCT coluna)` | Conta valores **distintos** | Útil contra o *fan-out* (J3.06) |
| `SUM`, `AVG`, `MIN`, `MAX` | Soma, média, menor, maior | **Ignoram** `NULL`; em conjunto vazio devolvem `NULL` |
| `... FILTER (WHERE cond)` | Agrega só as linhas que satisfazem `cond` | Alternativa limpa ao `CASE` dentro da soma |

Duas regras de nulo que pegam todo mundo: `SUM` de **nenhuma** linha é `NULL` (não 0), então use `COALESCE(SUM(x), 0)`; e `AVG` de `NUMERIC` devolve muitas casas decimais, então use `ROUND(AVG(x), 2)`.

### `GROUP BY` e `HAVING`
`GROUP BY` forma um grupo para cada combinação de valores das colunas listadas e aplica as funções de agregação a cada grupo. **Regra:** toda coluna no `SELECT` ou está no `GROUP BY` ou está dentro de uma função de agregação. (O banco não sabe qual valor mostrar de um grupo com várias linhas.)

| | `WHERE` | `HAVING` |
|---|---|---|
| Filtra | **Linhas**, antes de agrupar | **Grupos**, depois de agrupar |
| Pode usar agregação? | **Não** | **Sim** |

### Subqueries
Uma subquery é um `SELECT` dentro de outro, entre parênteses. Onde ela pode aparecer decide o que ela precisa devolver:

| Forma | Devolve | Exemplo |
|---|---|---|
| **Escalar** | 1 linha, 1 coluna | `balance > (SELECT avg(balance) FROM accounts)` |
| **`IN (...)`** | 1 coluna, várias linhas | `id IN (SELECT owner_id FROM accounts WHERE ...)` |
| **`EXISTS (...)`** | Só importa se há linha | `EXISTS (SELECT 1 FROM accounts a WHERE a.owner_id = u.id)` |
| **Correlacionada** | Refere-se à linha de fora | A subquery roda "uma vez por linha" (logicamente) |
| **Na `FROM`** (*derived table*) | Uma tabela temporária com apelido obrigatório | `FROM (SELECT ... GROUP BY ...) AS t` |

## 🛠️ Exemplo prático
> Testado em PostgreSQL 18.6 com o seed da J3.04.

### Agregações e `GROUP BY`
```sql
SELECT status, count(*) AS n, sum(amount) AS total, avg(amount) AS media, min(amount), max(amount)
FROM transfers GROUP BY status ORDER BY status;
```
```
  status   | n | total  |        media         |  min   |  max   
-----------+---+--------+----------------------+--------+--------
 COMPLETED | 3 | 245.50 |  81.8333333333333333 |  20.00 | 150.00
 FAILED    | 1 | 500.00 | 500.0000000000000000 | 500.00 | 500.00
```
`AVG` devolveu 16 casas. Para exibir: `round(avg(amount), 2)` dá `81.83`. (Atenção, dinheiro: arredonde **na exibição**; guarde sempre os valores exatos.)

Créditos e débitos por conta, com `FILTER`:
```sql
SELECT account_id,
       count(*) AS lancamentos,
       sum(amount) FILTER (WHERE type = 'CREDIT') AS creditos,
       sum(amount) FILTER (WHERE type = 'DEBIT')  AS debitos
FROM ledger_entries GROUP BY account_id ORDER BY account_id;
```
```
              account_id              | lancamentos | creditos | debitos 
--------------------------------------+-------------+----------+---------
 20000000-0000-0000-0000-000000000001 |           3 |  1000.00 |  170.00
 20000000-0000-0000-0000-000000000002 |           3 |   650.00 |   75.50
 20000000-0000-0000-0000-000000000003 |           3 |   295.50 |        
```
A conta 3 não tem débitos: o `FILTER` encontrou zero linhas e `SUM` devolveu `NULL` (célula em branco). Para mostrar `0.00`, `COALESCE(sum(...) FILTER (...), 0)`.

### `HAVING`
```sql
SELECT account_id, count(*) FROM ledger_entries GROUP BY account_id HAVING count(*) >= 3 ORDER BY account_id;
```
Devolve as três contas com 3 lançamentos. Os dois erros clássicos:
```sql
SELECT account_id, count(*) FROM ledger_entries WHERE count(*) > 2 GROUP BY account_id;
```
```
ERROR:  aggregate functions are not allowed in WHERE
```
```sql
SELECT id, count(*) FROM accounts GROUP BY owner_id;
```
```
ERROR:  column "accounts.id" must appear in the GROUP BY clause or be used in an aggregate function
```
O primeiro: `WHERE` roda **antes** de existirem grupos (J3.05); use `HAVING`. O segundo: o grupo de `owner_id` da Ana tem **duas** contas e o banco não pode escolher qual `id` mostrar.

### Contagens e nulos
```sql
SELECT count(DISTINCT owner_id) AS donos, count(*) AS contas FROM accounts;   -- 3 | 4
SELECT sum(amount) FROM transfers WHERE status = 'NAO_EXISTE';                -- NULL (em branco)
SELECT coalesce(sum(amount), 0) AS total FROM transfers WHERE status = 'NAO_EXISTE';   -- 0
```

### A consulta de conferência da regra 3
**Regra 3:** o saldo de cada conta é igual à soma dos seus lançamentos (créditos menos débitos). Como o saldo é **redundância deliberada** (J3.02), essa consulta é a rede de segurança:
```sql
SELECT a.id, a.balance,
       COALESCE(SUM(CASE l.type WHEN 'CREDIT' THEN l.amount ELSE -l.amount END), 0) AS ledger_sum
FROM accounts a
LEFT JOIN ledger_entries l ON l.account_id = a.id
GROUP BY a.id, a.balance
HAVING a.balance <> COALESCE(SUM(CASE l.type WHEN 'CREDIT' THEN l.amount ELSE -l.amount END), 0);
```
```
 id | balance | ledger_sum 
----+---------+------------
(0 rows)
```
**Zero linhas é o resultado saudável**: nenhuma conta diverge. O `LEFT JOIN` é essencial: a conta 4 (de Ana, sem nenhum lançamento) precisa participar, com `ledger_sum = 0` e `balance = 0`. Para ver o que acontece quando algo está errado, rode dentro de uma transação que você descarta:
```sql
BEGIN;
UPDATE accounts SET balance = balance + 1 WHERE id = '20000000-0000-0000-0000-000000000002';   -- bug: saldo mudou sem lançamento
-- (rode a consulta de conferência: devolve a conta 2 com balance 575.50 e ledger_sum 574.50)
ROLLBACK;
```
Em J7 essa consulta vira um **teste automatizado**; em P2 aparece como *job* de reconciliação.

### Subqueries
```sql
-- escalar: contas com saldo acima da média (a média de 830, 574.50, 295.50 e 0 é 425.00)
SELECT id, balance FROM accounts WHERE balance > (SELECT avg(balance) FROM accounts);

-- IN e EXISTS: donos de alguma conta com mais de 500 (as duas formas dão Ana e Bruno)
SELECT full_name FROM users WHERE id IN (SELECT owner_id FROM accounts WHERE balance > 500);
SELECT full_name FROM users u WHERE EXISTS (SELECT 1 FROM accounts a WHERE a.owner_id = u.id AND a.balance > 500);

-- correlacionada na lista do SELECT: quantas contas por usuário (inclui zero)
SELECT u.full_name, (SELECT count(*) FROM accounts a WHERE a.owner_id = u.id) AS contas
FROM users u ORDER BY 1;
```
```
  full_name  | contas 
-------------+--------
 Ana Silva   |      2
 Bruno Costa |      1
 Carla Dias  |      1
 Diego Alves |      0
 Eva Admin   |      0
```
```sql
-- derived table: total por dono e depois filtra o total
SELECT owner_name, total
FROM (SELECT u.full_name AS owner_name, sum(a.balance) AS total
      FROM users u JOIN accounts a ON a.owner_id = u.id
      GROUP BY u.full_name) AS t
WHERE total > 300 ORDER BY total DESC;
```
```
 owner_name  | total  
-------------+--------
 Ana Silva   | 830.00
 Bruno Costa | 574.50
```
O erro da subquery escalar com mais de uma linha:
```sql
SELECT id FROM accounts
WHERE balance > (SELECT balance FROM accounts WHERE owner_id = '10000000-0000-0000-0000-000000000001');
```
```
ERROR:  more than one row returned by a subquery used as an expression
```
Ana tem duas contas, então a subquery devolve duas linhas onde se esperava uma. Use `max(balance)`, `LIMIT 1` com intenção, ou `ANY`/`ALL`: `amount > ALL (SELECT amount FROM transfers WHERE status = 'COMPLETED')` devolve a transferência de 500,00 (maior que todas as concluídas).

### `JOIN` ou subquery?
Muitas vezes dá o mesmo resultado. Regra prática: **`EXISTS`** para "existe/não existe"; **`JOIN`** quando você precisa de **colunas** da outra tabela; **agregue antes de juntar** quando houver risco de *fan-out* (J3.06). O planejador do PostgreSQL costuma transformar `IN`/`EXISTS` em joins internamente; escolha pela **clareza** e confirme com `EXPLAIN` (J3.09) se houver dúvida de desempenho.

## 🧠 Pausa para lógica
**Enunciado:** a consulta de conferência em Java com Streams (J1.13). Dado o saldo guardado por conta (`Map<String, BigDecimal>`) e a lista de lançamentos, devolva um `Map` `conta → diferença (guardado − soma dos lançamentos)` apenas das contas **divergentes**. Cuidado: (a) conta **sem lançamentos** tem soma 0; (b) compare `BigDecimal` com `compareTo` (e não `equals`, J1.15).

<details><summary>Dica</summary><code>Collectors.groupingBy(Entry::accountId, TreeMap::new, Collectors.reducing(BigDecimal.ZERO, Entry::signed, BigDecimal::add))</code>. Depois percorra as contas **guardadas** (não as dos lançamentos), com <code>getOrDefault(id, ZERO)</code>.</details>
<details><summary>Solução (testada com JDK 25.0.5)</summary>

```java
import java.math.BigDecimal;
import java.util.*;
import java.util.stream.*;

public class Reconcile {
    record Entry(String accountId, String type, BigDecimal amount) {
        BigDecimal signed() { return type.equals("CREDIT") ? amount : amount.negate(); }
    }

    /** Contas cujo saldo guardado difere da soma dos lançamentos (regra 3). */
    static Map<String, BigDecimal> divergences(Map<String, BigDecimal> stored, List<Entry> ledger) {
        Map<String, BigDecimal> sums = ledger.stream().collect(
                Collectors.groupingBy(Entry::accountId, TreeMap::new,
                        Collectors.reducing(BigDecimal.ZERO, Entry::signed, BigDecimal::add)));
        Map<String, BigDecimal> bad = new TreeMap<>();
        stored.forEach((id, balance) -> {
            BigDecimal ledgerSum = sums.getOrDefault(id, BigDecimal.ZERO);
            if (balance.compareTo(ledgerSum) != 0) bad.put(id, balance.subtract(ledgerSum));
        });
        return bad;
    }

    public static void main(String[] args) {
        List<Entry> ledger = List.of(
            new Entry("a1","CREDIT",new BigDecimal("1000.00")), new Entry("a1","DEBIT",new BigDecimal("150.00")), new Entry("a1","DEBIT",new BigDecimal("20.00")),
            new Entry("a2","CREDIT",new BigDecimal("500.00")), new Entry("a2","CREDIT",new BigDecimal("150.00")), new Entry("a2","DEBIT",new BigDecimal("75.50")));
        Map<String, BigDecimal> stored = new TreeMap<>(Map.of("a1", new BigDecimal("830.00"), "a2", new BigDecimal("574.50"), "a3", new BigDecimal("0.00")));
        System.out.println("consistente: " + divergences(stored, ledger));
        stored.put("a2", new BigDecimal("574.00"));      // bug: saldo atualizado sem lançamento
        System.out.println("divergente : " + divergences(stored, ledger));
        stored.put("a3", new BigDecimal("0.01"));        // conta sem lançamento nenhum
        System.out.println("com a3     : " + divergences(stored, ledger));
    }
}
```
```
consistente: {}
divergente : {a2=-0.50}
com a3     : {a2=-0.50, a3=0.01}
```
A conta `a3` (sem lançamentos) só é verificada porque o laço percorre as contas **guardadas**: é o mesmo papel do `LEFT JOIN` no SQL. Se percorresse só as contas que aparecem nos lançamentos, a divergência de `a3` passaria despercebida.
</details>

## ⚠️ Erros comuns e boas práticas de produção
- **`WHERE` com agregação:** `ERROR: aggregate functions are not allowed in WHERE`. Use `HAVING`.
- **Coluna fora do `GROUP BY`:** `must appear in the GROUP BY clause or be used in an aggregate function`. Adicione ao grupo ou agregue.
- **`SUM` de conjunto vazio devolve `NULL`:** o relatório mostra "em branco" e o código Java recebe `null`. `COALESCE(..., 0)`.
- **`COUNT(coluna)` quando queria `COUNT(*)`** (ou o contrário): os nulos mudam o resultado.
- **Agregar depois de um `JOIN` 1:N** sem pensar no *fan-out* (J3.06).
- **`NOT IN` com subquery que pode ter `NULL`:** use `NOT EXISTS` (J3.06).
- **Subquery escalar que devolve mais de uma linha:** `more than one row returned by a subquery used as an expression`: o erro aparece só **quando os dados mudam** (hoje há uma linha, amanhã duas). Garanta a unicidade (`LIMIT 1` com `ORDER BY` consciente, ou agregação).
- **Arredondar antes de somar:** arredonde **no fim**; somar valores já arredondados acumula erro (J1.15).
- **Conferência de saldo ignorada:** uma consulta que ninguém roda não protege nada. Automatize (J7) e alerte (P6).

## 🎤 Na entrevista
- **Diferença entre `WHERE` e `HAVING`?** `WHERE` filtra linhas antes de agrupar e não aceita agregação; `HAVING` filtra grupos depois, e aceita agregação.
- **`COUNT(*)` vs `COUNT(coluna)` vs `COUNT(DISTINCT coluna)`?** Todas as linhas; as linhas em que a coluna não é nula; os valores distintos não nulos.
- **O que é uma subquery correlacionada?** Uma subquery que usa colunas da consulta externa, avaliada (logicamente) para cada linha de fora; `EXISTS` é o uso típico.
- **Como você conferiria que o saldo das contas bate com o extrato?** Agrupar os lançamentos por conta (créditos − débitos), juntar com as contas por `LEFT JOIN` e listar onde o saldo guardado difere; o resultado saudável é vazio. Idealmente automatizado e agendado.
