# J3.08 — SQL V: CTEs e funções de janela básicas

> ⏱️ ~1h30 · 🟢 Júnior · Pré-requisitos: J3.05, J3.06, J3.07, J1.11 (`Deque`, `Map`)

## 🎯 Objetivos
Ao final desta aula você consegue:
- Organizar uma consulta complexa em passos nomeados com **CTEs** (`WITH`).
- Escrever uma **CTE recursiva** com proteção contra ciclos e gerar séries (datas, números) com `generate_series`.
- Usar **funções de janela** (`OVER`, `PARTITION BY`, `ORDER BY`) para totais acumulados, "últimos N por grupo" e comparações com a linha anterior.
- Diferenciar `ROW_NUMBER`, `RANK` e `DENSE_RANK`.
- Montar o **extrato com saldo corrente** do PayFlow.

## 🤔 Por que isso importa
Consultas reais crescem: "para cada conta, calcule isto, depois aquilo, depois compare". Subqueries aninhadas em cinco níveis ninguém lê. A CTE dá **nome a cada passo**, e a função de janela resolve em uma consulta o que antes exigia código Java com laços: o extrato com **saldo após cada lançamento** é exatamente o que um aplicativo de banco mostra. Em entrevistas, "últimas 3 transações por cliente" e "total acumulado" são perguntas clássicas de SQL.

## 💡 Intuição (explicação simples)
- **CTE (`WITH`)** é **separar a receita em etapas com nome**: "primeiro, prepare o molho (`movimentos`); depois, monte o prato com o molho". O resultado final lê-se de cima para baixo, como um texto.
- **Função de janela** é olhar **pela janela do vizinho enquanto percorre a lista**: para cada linha, você enxerga também as linhas ao redor (as anteriores, as do mesmo grupo) **sem juntá-las** em uma só. Diferente do `GROUP BY`, **nenhuma linha some**: cada linha ganha uma coluna extra calculada olhando a "janela".

## 🔬 Como funciona por dentro

### CTE (`WITH`)
```sql
WITH nome_do_passo AS (
    SELECT ...
),
outro_passo AS (
    SELECT ... FROM nome_do_passo ...
)
SELECT ... FROM outro_passo;
```
Cada CTE é como uma "tabela temporária" válida **só durante aquela consulta**. A documentação do PostgreSQL esclarece o comportamento: uma CTE **não recursiva** referenciada **uma única vez** é incorporada à consulta de fora (o otimizador a trata como uma subquery); referenciada **mais de uma vez**, é calculada separadamente. Dá para forçar com `MATERIALIZED` ou `NOT MATERIALIZED`. Em termos práticos: use CTE pela **legibilidade**; não é, por si só, "otimização".

### CTE recursiva
Para dados em árvore ou grafo (cadeia de transferências, hierarquia), ou para gerar séries:
```sql
WITH RECURSIVE nome(colunas) AS (
    SELECT ...                       -- parte "âncora": ponto de partida
    UNION ALL
    SELECT ... FROM nome WHERE ...   -- parte recursiva: usa o resultado anterior; para quando não gera linhas
)
SELECT ... FROM nome;
```
Sem uma **condição de parada**, ou com **ciclos** no grafo, ela nunca termina. Em grafos de transferências, onde dinheiro pode voltar para quem enviou (A → B → C → A), é preciso **guardar o caminho percorrido** e não revisitar contas.

### Funções de janela
`função(...) OVER ([PARTITION BY grupo] [ORDER BY ordem] [moldura])`
- **`PARTITION BY`**: divide as linhas em "grupos" (como o `GROUP BY`, mas **sem colapsar**).
- **`ORDER BY`** dentro do `OVER`: a ordem dentro do grupo (necessária para acumulados, `ROW_NUMBER`, `LAG`).
- **Moldura** (*frame*): por padrão, com `ORDER BY`, a janela vai **do início do grupo até a linha atual, incluindo as linhas "empatadas" no valor de ordenação** (`RANGE`). Esse "empate" é a armadilha desta aula.

| Função | Faz |
|---|---|
| `SUM(x) OVER (ORDER BY ...)` | Total **acumulado** |
| `ROW_NUMBER()` | 1, 2, 3, ... (sem repetir; em empate, ordem arbitrária **a menos que haja desempate**) |
| `RANK()` | Empates recebem a mesma posição e **pula** as seguintes (1, 2, 2, 4) |
| `DENSE_RANK()` | Empates iguais, **sem pular** (1, 2, 2, 3) |
| `LAG(x)` / `LEAD(x)` | Valor da linha **anterior** / **seguinte** |

## 🛠️ Exemplo prático
> Testado em PostgreSQL 18.6 com o seed da J3.04.

### CTE: a conferência da regra 3, em passos
A consulta da J3.07, agora legível:
```sql
WITH movements AS (                         -- 1) cada lançamento com sinal
    SELECT account_id,
           CASE type WHEN 'CREDIT' THEN amount ELSE -amount END AS signed
    FROM ledger_entries
),
totals AS (                                 -- 2) soma por conta
    SELECT account_id, sum(signed) AS ledger_balance
    FROM movements GROUP BY account_id
)
SELECT a.id, a.balance, t.ledger_balance, a.balance = t.ledger_balance AS ok
FROM accounts a
JOIN totals t ON t.account_id = a.id        -- 3) compara
ORDER BY a.id;
```
```
                  id                  | balance | ledger_balance | ok 
--------------------------------------+---------+----------------+----
 20000000-0000-0000-0000-000000000001 |  830.00 |         830.00 | t
 20000000-0000-0000-0000-000000000002 |  574.50 |         574.50 | t
 20000000-0000-0000-0000-000000000003 |  295.50 |         295.50 | t
(3 rows)
```
Repare: com `JOIN` (e não `LEFT JOIN`) a conta 4 (sem lançamentos) **não aparece**. Para uma conferência, o `LEFT JOIN` com `COALESCE` da J3.07 é o correto; aqui a CTE serve para mostrar a **forma**.

### Função de janela: o extrato com saldo corrente
```sql
SELECT created_at, type, amount,
       sum(CASE type WHEN 'CREDIT' THEN amount ELSE -amount END)
           OVER (ORDER BY created_at, id) AS running_balance
FROM ledger_entries
WHERE account_id = '20000000-0000-0000-0000-000000000001'
ORDER BY created_at, id;
```
```
       created_at       |  type  | amount  | running_balance 
------------------------+--------+---------+-----------------
 2026-01-05 09:10:00+00 | CREDIT | 1000.00 |         1000.00
 2026-01-10 11:00:00+00 | DEBIT  |  150.00 |          850.00
 2026-01-15 09:10:00+00 | DEBIT  |   20.00 |          830.00
```
A última linha (830,00) bate com `accounts.balance`: o extrato com saldo corrente **é** a regra 3 vista linha a linha.

**A armadilha do empate.** Se o `ORDER BY` do `OVER` não for único, as linhas "empatadas" entram **juntas** na janela. Abaixo, três pares de lançamentos têm o mesmo `created_at` (os dois lados de cada transferência):
```sql
SELECT id, created_at, amount,
       sum(amount) OVER (ORDER BY created_at)     AS running_ties,
       sum(amount) OVER (ORDER BY created_at, id) AS running_ok
FROM ledger_entries WHERE transfer_id IS NOT NULL ORDER BY created_at, id;
```
```
                  id                  |       created_at       | amount | running_ties | running_ok 
--------------------------------------+------------------------+--------+--------------+------------
 40000000-0000-0000-0000-000000000004 | 2026-01-10 11:00:00+00 | 150.00 |       300.00 |     150.00
 40000000-0000-0000-0000-000000000005 | 2026-01-10 11:00:00+00 | 150.00 |       300.00 |     300.00
 40000000-0000-0000-0000-000000000006 | 2026-01-12 15:30:00+00 |  75.50 |       451.00 |     375.50
 40000000-0000-0000-0000-000000000007 | 2026-01-12 15:30:00+00 |  75.50 |       451.00 |     451.00
 40000000-0000-0000-0000-000000000008 | 2026-01-15 09:10:00+00 |  20.00 |       491.00 |     471.00
 40000000-0000-0000-0000-000000000009 | 2026-01-15 09:10:00+00 |  20.00 |       491.00 |     491.00
```
`running_ties` repete o mesmo total para as duas linhas empatadas (a primeira "já enxerga" a segunda). Com o desempate `id`, cada linha tem seu próprio acumulado. **Sempre inclua um desempate único** no `OVER (ORDER BY ...)`.

### `ROW_NUMBER`: os N últimos lançamentos **por conta**
```sql
SELECT *
FROM (SELECT account_id, id, amount, created_at,
             row_number() OVER (PARTITION BY account_id ORDER BY created_at DESC, id DESC) AS rn
      FROM ledger_entries) x
WHERE rn <= 2
ORDER BY account_id, rn;
```
```
              account_id              |                  id                  | amount |       created_at       | rn 
--------------------------------------+--------------------------------------+--------+------------------------+----
 20000000-0000-0000-0000-000000000001 | 40000000-0000-0000-0000-000000000008 |  20.00 | 2026-01-15 09:10:00+00 |  1
 20000000-0000-0000-0000-000000000001 | 40000000-0000-0000-0000-000000000004 | 150.00 | 2026-01-10 11:00:00+00 |  2
 20000000-0000-0000-0000-000000000002 | 40000000-0000-0000-0000-000000000006 |  75.50 | 2026-01-12 15:30:00+00 |  1
 20000000-0000-0000-0000-000000000002 | 40000000-0000-0000-0000-000000000005 | 150.00 | 2026-01-10 11:00:00+00 |  2
 20000000-0000-0000-0000-000000000003 | 40000000-0000-0000-0000-000000000009 |  20.00 | 2026-01-15 09:10:00+00 |  1
 20000000-0000-0000-0000-000000000003 | 40000000-0000-0000-0000-000000000007 |  75.50 | 2026-01-12 15:30:00+00 |  2
```
Uma função de janela **não pode** aparecer no `WHERE` (ela é calculada depois dele), por isso a consulta é embrulhada em uma subquery (ou CTE) e o `rn <= 2` é filtrado por fora.

### `RANK`, `DENSE_RANK`, `ROW_NUMBER`
```sql
SELECT id, amount,
       rank()       OVER (ORDER BY amount DESC) AS rk,
       dense_rank() OVER (ORDER BY amount DESC) AS drk,
       row_number() OVER (ORDER BY amount DESC, id) AS rn
FROM ledger_entries ORDER BY amount DESC, id;
```
```
                  id                  | amount  | rk | drk | rn 
--------------------------------------+---------+----+-----+----
 40000000-0000-0000-0000-000000000001 | 1000.00 |  1 |   1 |  1
 40000000-0000-0000-0000-000000000002 |  500.00 |  2 |   2 |  2
 40000000-0000-0000-0000-000000000003 |  200.00 |  3 |   3 |  3
 40000000-0000-0000-0000-000000000004 |  150.00 |  4 |   4 |  4
 40000000-0000-0000-0000-000000000005 |  150.00 |  4 |   4 |  5
 40000000-0000-0000-0000-000000000006 |   75.50 |  6 |   5 |  6
 40000000-0000-0000-0000-000000000007 |   75.50 |  6 |   5 |  7
 40000000-0000-0000-0000-000000000008 |   20.00 |  8 |   6 |  8
 40000000-0000-0000-0000-000000000009 |   20.00 |  8 |   6 |  9
```
Nos empates de 150,00: `rank` dá 4 e 4 e **pula** o 5 (próximo é 6); `dense_rank` dá 4 e 4 e segue com 5; `row_number` sempre numera de 1 a 9.

### `LAG`: o intervalo entre transferências
```sql
SELECT created_at, amount,
       lag(created_at) OVER (ORDER BY created_at, id) AS prev,
       created_at - lag(created_at) OVER (ORDER BY created_at, id) AS gap
FROM transfers ORDER BY created_at;
```
```
       created_at       | amount |          prev          |       gap       
------------------------+--------+------------------------+-----------------
 2026-01-10 11:00:00+00 | 150.00 |                        | 
 2026-01-12 15:30:00+00 |  75.50 | 2026-01-10 11:00:00+00 | 2 days 04:30:00
 2026-01-15 09:10:00+00 |  20.00 | 2026-01-12 15:30:00+00 | 2 days 17:40:00
 2026-01-20 18:00:00+00 | 500.00 | 2026-01-15 09:10:00+00 | 5 days 08:50:00
```
A primeira linha não tem anterior, então `prev` e `gap` são `NULL`. Útil para detectar atividade suspeita (transferências muito próximas, P3).

### Séries: `generate_series` e CTE recursiva
Dias **sem movimento** também precisam aparecer em um gráfico. Gerar a série de datas e fazer `LEFT JOIN`:
```sql
SELECT d::date AS day, coalesce(sum(t.amount), 0) AS total
FROM generate_series('2026-01-09'::date, '2026-01-13'::date, interval '1 day') AS d
LEFT JOIN transfers t ON t.created_at::date = d::date AND t.status = 'COMPLETED'
GROUP BY d ORDER BY d;
```
```
    day     | total  
------------+--------
 2026-01-09 |      0
 2026-01-10 | 150.00
 2026-01-11 |      0
 2026-01-12 |  75.50
 2026-01-13 |      0
```
A mesma ideia, sem a função pronta, com **recursão**:
```sql
WITH RECURSIVE n(i) AS (
    SELECT 1                          -- âncora
    UNION ALL
    SELECT i + 1 FROM n WHERE i < 5   -- recursão, com condição de parada
)
SELECT i, i * i AS sq FROM n;         -- 1,1  2,4  3,9  4,16  5,25
```

### CTE recursiva em grafo: para onde o dinheiro de Ana **chegou**?
`transfers` é um grafo (contas são nós; transferências `COMPLETED`, arestas). Partindo da conta 1 de Ana, queremos todas as contas alcançadas, direta ou indiretamente, **sem revisitar** contas (evita ciclos):
```sql
WITH RECURSIVE trail(account_id, depth, path) AS (
    SELECT t.target_account_id, 1, ARRAY[t.source_account_id, t.target_account_id]
    FROM transfers t
    WHERE t.source_account_id = '20000000-0000-0000-0000-000000000001' AND t.status = 'COMPLETED'
  UNION ALL
    SELECT t.target_account_id, tr.depth + 1, tr.path || t.target_account_id
    FROM transfers t
    JOIN trail tr ON t.source_account_id = tr.account_id
    WHERE t.status = 'COMPLETED'
      AND NOT t.target_account_id = ANY (tr.path)        -- não volta a uma conta já visitada
)
SELECT account_id, min(depth) AS min_depth, count(*) AS paths
FROM trail GROUP BY account_id ORDER BY min_depth, account_id;
```
```
              account_id              | min_depth | paths 
--------------------------------------+-----------+-------
 20000000-0000-0000-0000-000000000002 |         1 |     1
 20000000-0000-0000-0000-000000000003 |         1 |     2
```
Carla (conta 3) é alcançada de **dois jeitos**: direto (Ana → Carla) e via Bruno (Ana → Bruno → Carla): 2 caminhos, profundidade mínima 1. O array `path` impede ciclos. Em P3/S1 esse tipo de consulta aparece no antifraude (cadeias de "lavagem" de dinheiro).

## 🧠 Pausa para lógica
**Enunciado:** a CTE recursiva acima é uma **busca em largura** (BFS) em um grafo. Escreva em Java `reachable(start, transfers)` que devolve, para cada conta alcançável, a **profundidade mínima**, sem repetir contas e sem entrar em loop com ciclos (`a3 → a1`).

<details><summary>Dica</summary>Use uma fila (<code>ArrayDeque</code>) e um <code>Map&lt;String,Integer&gt;</code> de profundidade; <code>putIfAbsent</code> devolve <code>null</code> só na primeira vez que a conta é vista (é o seu "marcador de visitado").</details>
<details><summary>Solução (testada com JDK 25.0.5)</summary>

```java
import java.util.*;

public class MoneyTrail {
    record Transfer(String from, String to) { }

    /** BFS: contas alcançáveis a partir de {@code start}, com a profundidade mínima. Ciclos não repetem contas. */
    static Map<String, Integer> reachable(String start, List<Transfer> transfers) {
        Map<String, List<String>> graph = new HashMap<>();
        for (Transfer t : transfers) graph.computeIfAbsent(t.from(), k -> new ArrayList<>()).add(t.to());
        Map<String, Integer> depth = new LinkedHashMap<>();
        Deque<String> queue = new ArrayDeque<>();
        depth.put(start, 0);
        queue.add(start);
        while (!queue.isEmpty()) {
            String current = queue.poll();
            for (String next : graph.getOrDefault(current, List.of())) {
                if (depth.putIfAbsent(next, depth.get(current) + 1) == null) queue.add(next);
            }
        }
        depth.remove(start);
        return depth;
    }

    public static void main(String[] args) {
        List<Transfer> ts = List.of(new Transfer("a1","a2"), new Transfer("a2","a3"), new Transfer("a1","a3"), new Transfer("a3","a1"), new Transfer("a3","a4"));
        System.out.println(reachable("a1", ts));
    }
}
```
```
{a2=1, a3=1, a4=2}
```
Há um ciclo (`a3 → a1`) e o programa termina: `a1` já está no mapa, então `putIfAbsent` não a reenfileira. A **BFS** garante a profundidade **mínima**; a versão SQL com `path` enumera **todos os caminhos sem ciclos**, por isso `count(*)` pode ser maior que 1 e o número de caminhos pode **explodir** em grafos densos (use limite de profundidade em produção).
</details>

**Variação:** limite a busca a no máximo 3 saltos. Como isso muda a BFS? E a CTE (`WHERE tr.depth < 3`)?

## ⚠️ Erros comuns e boas práticas de produção
- **`OVER (ORDER BY coluna_nao_unica)`:** linhas empatadas entram juntas na janela (acima). Desempate sempre.
- **Função de janela no `WHERE`:** não é permitido; embrulhe em subquery/CTE.
- **CTE recursiva sem condição de parada ou sem proteção de ciclo:** consulta infinita que consome o servidor. Ponha limite de profundidade e controle de visitados; configure `statement_timeout` (P2).
- **Achar que CTE é "mais rápida" ou "mais lenta":** em PostgreSQL moderno, é só organização (documentação acima); meça com `EXPLAIN` (J3.09).
- **`UNION` em vez de `UNION ALL` na recursão:** `UNION` remove duplicatas (mais caro) e pode esconder o problema de ciclo; use `UNION ALL` com controle explícito.
- **Saldo corrente calculado na aplicação:** um laço Java sobre milhares de linhas, quando uma janela resolve no banco. Atenção: para **extratos paginados**, o acumulado precisa considerar as linhas **anteriores** à página; calcule a janela sobre o conjunto completo e pagine depois (ou guarde `balance_after` em cada lançamento, decisão de P2).
- **`ROW_NUMBER` sem desempate:** o "primeiro" de um empate é arbitrário e pode mudar.

## 🎤 Na entrevista
- **O que é uma CTE e quando usar?** Uma consulta nomeada (`WITH`) usada dentro de outra, para dividir lógica complexa em passos legíveis. Recursiva, serve para hierarquias e grafos. No PostgreSQL moderno ela não é, por si só, uma otimização.
- **Qual a diferença entre `GROUP BY` e uma função de janela?** `GROUP BY` **colapsa** as linhas em uma por grupo; a função de janela calcula sobre um grupo/janela mas **mantém todas** as linhas.
- **`ROW_NUMBER`, `RANK` e `DENSE_RANK`?** `ROW_NUMBER` numera sem empates; `RANK` dá a mesma posição aos empates e pula as seguintes; `DENSE_RANK` dá a mesma posição e não pula.
- **Como pegar o último pedido de cada cliente?** `ROW_NUMBER() OVER (PARTITION BY cliente ORDER BY data DESC, id DESC)` em uma subquery e filtrar `rn = 1`.
