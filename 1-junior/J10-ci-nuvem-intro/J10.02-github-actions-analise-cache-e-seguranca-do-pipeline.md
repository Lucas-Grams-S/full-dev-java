## 🎯 Objetivos

## 🤔 Por que isso importa
Um CI de 12 minutos é ignorado; um de 3 é respeitado. E um pipeline é **código de terceiros com acesso ao seu repositório e, depois, à sua conta de nuvem**: tratá-lo como alvo de ataque (cadeia de suprimentos, OWASP A03 em 2025) é parte do trabalho de quem escreve o YAML. As promessas das aulas anteriores caem aqui: Dependency-Check e `check-secrets.sh` (J8.07), "testar antes de construir a imagem" (J9.02).

## 💡 Intuição (explicação simples)
- **Cache** é a **despensa abastecida**: em vez de ir ao mercado (Maven Central) a cada receita, você guarda o que já comprou; só repõe quando a lista de compras (`pom.xml`) muda.
- **Fixar por SHA** é conferir a **impressão digital** do entregador, não o crachá: o crachá (a *tag*) pode ser trocado; a impressão digital (o SHA do commit), não.

## 🔬 Como funciona por dentro

### 1. Cache
`actions/setup-java` com `cache: maven` salva e restaura o `~/.m2/repository`. A **chave** do cache é derivada do hash dos `pom.xml` (a v6.2.0 também inclui `.mvn/extensions.xml`, segundo o README da *action*): mudou uma dependência → cache novo; senão, **acerto** e o Maven não baixa nada. Regras do cache do GitHub (documentação de *dependency caching*): restauração por chave exata ou por prefixo (`restore-keys`); a busca é feita primeiro **na branch do workflow** e, sem acerto, **na branch padrão** (a documentação descreve essa ordem); a página de cobrança informa **10 GB de cache incluídos por repositório**. Por isso a `main` precisa rodar o CI (o `on: push` do `ci.yml`) para "aquecer" o cache que as PRs vão encontrar.

O cache **acelera, não garante**: o CI tem de funcionar com cache vazio. Medi o equivalente local: o `./mvnw verify` do laboratório levou **10,9 s** com o `~/.m2` aquecido; o tempo "frio" no runner (JDK + dependências + imagem `postgres:18`) o primeiro run do seu repositório vai mostrar: **anote os dois tempos** (exercício).

### 2. Relatórios e resumo da execução
Dois recursos baratos que poupam "baixar o log e procurar":
- **Artefatos** (`actions/upload-artifact`): `target/surefire-reports/` e `target/site/jacoco/` ficam disponíveis por `retention-days` (aqui 7) na página da execução. Artefatos **contam** na cota de armazenamento (500 MB no plano Free, compartilhada com o GitHub Packages): retenção curta.
- **Resumo do job:** tudo que o passo escrever em `$GITHUB_STEP_SUMMARY` aparece (em Markdown) no topo da execução. O `scripts/ci/coverage-summary.py` lê o `jacoco.csv`:
```python
"""Imprime em Markdown a cobertura de linhas lida do jacoco.csv (usado no resumo do job)."""
import csv
import sys

missed = covered = 0
with open(sys.argv[1], newline="", encoding="utf-8") as f:
    for row in csv.DictReader(f):
        missed += int(row["LINE_MISSED"])
        covered += int(row["LINE_COVERED"])
total = missed + covered
ratio = covered / total if total else 0.0
print("### Coverage")
print(f"Lines: **{covered}/{total}** ({ratio:.1%})")
```
Saída medida: `### Coverage` / `Lines: **26/36** (72.2%)`.

### 4. Segurança do pipeline: o workflow `security.yml`
```yaml
name: Security

on:
  pull_request:
  schedule:
    - cron: '17 6 * * 1'     # segundas, 06:17 UTC (fora da hora cheia, que e disputada)
  workflow_dispatch:

permissions:
  contents: read

jobs:
  secrets:
    name: secrets in the repository
    runs-on: ubuntu-24.04
    timeout-minutes: 5
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          persist-credentials: false
      - run: bash scripts/ci/check-secrets.sh

  dependency-review:
    name: new vulnerable dependencies in the PR
    if: ${{ github.event_name == 'pull_request' }}
    runs-on: ubuntu-24.04
    timeout-minutes: 5
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          persist-credentials: false
      - uses: actions/dependency-review-action@a1d282b36b6f3519aa1f3fc636f609c47dddb294 # v5.0.0
        with:
          fail-on-severity: high

  dependency-check:
    name: OWASP Dependency-Check (weekly)
    if: ${{ github.event_name != 'pull_request' }}
    runs-on: ubuntu-24.04
    timeout-minutes: 30
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          persist-credentials: false
      - uses: actions/setup-java@77dd5b2ce225ea11469928ac317850245a74ae78 # v6.2.0
        with:
          distribution: temurin
          java-version: '25'
          cache: maven
      - uses: actions/cache@55cc8345863c7cc4c66a329aec7e433d2d1c52a9 # v6.1.0
        with:
          path: ~/.m2/repository/org/owasp/dependency-check-data
          key: nvd-${{ github.run_id }}
          restore-keys: nvd-
      - name: Dependency-Check
        env:
          NVD_API_KEY: ${{ secrets.NVD_API_KEY }}
        run: ./mvnw -B -ntp -Psecurity-scan -DskipTests verify
```
| Job | O que pega | Quando | Observação |
|---|---|---|---|
| `secrets` | Segredo no repositório (`scripts/ci/check-secrets.sh`, J8.07) | toda PR | barato: segundos |
| `dependency-review` | Dependência **nova** com vulnerabilidade conhecida **introduzida pela PR** | toda PR | a *action* funciona em repositório **público** ou **privado com GitHub Advanced Security** (README da *action*); sem isso, o job falha: apague-o |
| `dependency-check` | Todas as dependências contra o NVD (perfil `security-scan`, J8.07) | **semanal** + manual | baixa o banco do NVD (lento): chave `NVD_API_KEY` em *Settings → Secrets*; o cache `dependency-check-data` evita baixar tudo de novo |

Por que o `dependency-check` **não** roda em toda PR: leva minutos e depende de um serviço externo com limite de requisições; uma CVE nova aparece **sem você ter mudado nada**, então o agendamento semanal (`cron`) enxerga o que a PR não vê.

**Dependabot** (`.github/dependabot.yml`): abre PRs de atualização para Maven, para as próprias *actions* e para o `Dockerfile`:
```yaml
version: 2
updates:
  - package-ecosystem: maven
    directory: /
    schedule: { interval: weekly }
    open-pull-requests-limit: 5
  - package-ecosystem: github-actions
    directory: /
    schedule: { interval: weekly }
  - package-ecosystem: docker
    directory: /
    schedule: { interval: weekly }
```
Cada PR do Dependabot passa pelo **mesmo CI**: é a razão de a suíte ser confiável. (Para o Dependabot, a página de cobrança lista o uso dos runners como gratuito.)

### 6. `pull_request` × `pull_request_target`
- **`pull_request`** (o que usamos): roda com o código **da PR**, e em PR vinda de **fork** o token é **somente leitura** e **sem segredos**.
- **`pull_request_target`**: roda com o contexto da **base** (com segredos e token com escrita). Se o workflow fizer *checkout* do código da PR e **executá-lo**, um estranho roda código dele com seus segredos. Regra do treinamento: **não use `pull_request_target`**; quando precisar (rotular PRs, por exemplo), nunca execute código da PR. Ver a página de uso seguro.

### 7. Quanto custa?
A página oficial de cobrança (conferida em 2026-11-13): em **repositório público**, os runners padrão são **gratuitos**; em **privado**, o plano GitHub Free inclui **US$ 12 de uso de computação por mês** (e 500 MB de artefatos, 10 GB de cache por repositório), e um minuto de runner Linux padrão custa **US$ 0,006**: o exemplo da própria página, "10 minutos = US$ 0,06". Conta do PayFlow privado: 12 ÷ 0,006 = **2 000 minutos/mês**. Uma execução de 4 minutos × 10 por dia × 22 dias = 880 minutos: cabe, com folga curta. Cada **re-run** de uma execução falha também é cobrado.

## 🧠 Pausa para lógica
**Enunciado:** a suíte leva 4 min; o CI roda a cada `push` em PRs. Você faz 6 `push` por PR e abre 3 PRs por semana, 4 semanas. Quantos minutos/mês **sem** `concurrency` e **com** `concurrency` (suponha que, em média, 2 dos 6 `push` terminam antes do próximo)?
<details><summary>Dica</summary>Sem cancelar, todas as 6 execuções rodam inteiras.</details>
<details><summary>Solução</summary>

PRs/mês = 3 × 4 = 12. **Sem:** 12 × 6 × 4 = **288 min**. **Com:** em média 2 terminam e 4 são canceladas **cedo**; se uma cancelada gasta ~1 min antes de cair, são 12 × (2 × 4 + 4 × 1) = **144 min**. A estimativa depende de quando você dá o `push`: o ponto é que o `concurrency` corta o desperdício **sem custo de configuração**. Variação: some um *re-run* de 30% das execuções.
</details>

## ⚖️ Trade-offs e quando NÃO usar
Cache demais esconde problema (build que só passa com cache); `dependency-check` semanal gera **ruído** de falso positivo (a J8.07 ensinou a suprimir com data e justificativa); fixar por SHA exige o Dependabot para não envelhecer; `upload-artifact` de tudo enche a cota. Em equipe grande, o pipeline vira produto interno (P8).

## ⚠️ Erros comuns e boas práticas de produção
| Sintoma | Causa | Correção |
|---|---|---|
| Cache nunca acerta | a chave muda a cada execução (`github.run_id` em `key` sem `restore-keys`) | chave estável + `restore-keys`; para o NVD o `run_id` na **chave** é intencional, porque o dado muda: o `restore-keys: nvd-` o recupera |
| CI passa só na segunda tentativa | teste instável (*flaky*), geralmente `sleep` ou relógio | corrigir a causa; **nunca** "re-run até passar" |
| `dependency-review` falha com "Dependency review is not supported on this repository" | repositório privado sem GitHub Advanced Security | ⚠️ mensagem de memória: apague o job ou use Dependabot alerts |
| Segredo apareceu no log | `echo $SECRET` | o GitHub mascara **valores de secrets**, mas não derivados (base64, partes): nunca imprima |
| Workflow de PR de fork falha sem `NVD_API_KEY` | fork não recebe segredos | rode o `dependency-check` só no `schedule` (como aqui) |
| `actionlint` acusa `property "x" is not defined` | passo referenciado (`steps.x`) não existe | era o objetivo do linter: corrija o `id` |

O `actionlint` pega erros de sintaxe e de **expressão** que só apareceriam depois do *push*. Pergunta de honestidade: no experimento ele **não** acusou o campo inventado `fetch-deph:` em um `with:`, porque sem acesso aos metadados da *action* ele não conhece os *inputs*: o linter não substitui rodar o workflow.

## 🎤 Na entrevista
1. **Como você deixa um pipeline mais rápido?** *Resposta-modelo:* cache de dependências, jobs em paralelo, `concurrency` para cancelar execuções obsoletas, `paths-ignore`, testes rápidos primeiro; medir antes e depois.
2. **O que é um ataque à cadeia de suprimentos em CI?** *Resposta-modelo:* comprometer algo que o pipeline confia (uma *action*, uma dependência) para rodar código com acesso ao repositório e às credenciais. Defesas: fixar por SHA, token mínimo, revisar atualizações (Dependabot), não executar código de PR com segredos.
3. **Por que `pull_request_target` é perigoso?** *Resposta-modelo:* porque roda com segredos e escrita no contexto da base; se executar código da PR, o autor da PR controla esse código.
