## 🎯 Objetivos
Ao final desta aula você consegue:
1. **Explicar** o que um teste de fatia (*slice*) carrega e o que deixa de fora.
2. **Escrever** um teste `@WebMvcTest` de um controller, com `MockMvc` e `jsonPath`.
3. **Substituir** colaboradores do controller por `@MockitoBean` e **montar** só o que a fatia exige (`@Import`).
4. **Testar** validação, tradução de erros (Problem Details) e autenticação **sem** servidor e **sem** banco.
5. **Ler** o erro de contexto que aparece quando a fatia está incompleta.

## 🤔 Por que isso importa
Os testes da API da J6 (`TransfersApiTest`, `ErrorsApiTest`...) sobem a aplicação **inteira** numa porta aleatória, falam HTTP real e usam o PostgreSQL. Provam muito, mas cada caso de "o JSON de erro está certo?" paga o preço do contexto completo e do banco. A camada web tem responsabilidades **próprias**: roteamento, leitura do corpo, validação, status, serialização do JSON, tradução de exceção em resposta, o interceptor de sessão. Dá para verificar **só isso**, rápido, com o resto trocado por dublês. Em uma vaga júnior, escrever e depurar testes `@WebMvcTest` é rotina.

## 💡 Intuição (explicação simples)
Testar o balcão de um restaurante: você quer saber se o atendente **anota o pedido certo, recusa o que não existe no cardápio e responde com educação**. Não precisa de cozinha funcionando, fogão aceso nem fornecedor: basta um "cozinheiro de mentira" que devolve pratos prontos. O `@WebMvcTest` monta **só o balcão** (a camada web); o cozinheiro de mentira é o `@MockitoBean`.

## 🔬 Como funciona por dentro

### 1. O que a fatia `@WebMvcTest` carrega
O Spring Boot tem uma anotação por fatia ([lista oficial](https://docs.spring.io/spring-boot/appendix/test-auto-configuration/slices.html)). A `@WebMvcTest` (pacote **`org.springframework.boot.webmvc.test.autoconfigure`** no Boot 4, módulo `spring-boot-webmvc-test`) liga a autoconfiguração do Spring MVC e registra **só** estes tipos de bean: `@Controller`/`@RestController` (os que você nomear, ou todos), `@ControllerAdvice`, `Converter`, `Filter`, `HandlerInterceptor`, `WebMvcConfigurer` e afins. **Não** registra `@Component`, `@Service`, `@Repository` nem `@Configuration` comuns; **não** há `DataSource`, JPA, Flyway nem servidor Tomcat (o `MockMvc` chama o `DispatcherServlet` direto, sem rede).

```mermaid
flowchart LR
    T[Teste<br/>MockMvc] --> D[DispatcherServlet]
    D --> I[AuthInterceptor<br/>real]
    I --> C[TransfersController<br/>real]
    C --> M1[TransferSubmitter<br/>@MockitoBean]
    C --> M2[TransferService<br/>@MockitoBean]
    C --> M3[ApiMapper<br/>@MockitoBean]
    D -. erros .-> E[ApiErrors / WebErrors<br/>reais]
```
O PostgreSQL **não aparece** no desenho: está fora da fatia.
Consequência importante: tudo que o controller **injeta** e que a fatia não registra precisa vir de `@MockitoBean` (dublê) ou de `@Import` (classe real). Faltou algum: o contexto não sobe e a mensagem diz qual.

### 2. `@MockitoBean`: o dublê dentro do contexto do Spring
`@MockitoBean` (Spring Framework 7, [documentação](https://docs.spring.io/spring-framework/reference/testing/annotations/integration-spring/annotation-mockitobean.html)) **troca** (ou cria) um bean do `ApplicationContext` por um mock do Mockito e o **zera após cada teste**. É o sucessor do antigo `@MockBean` do Boot. Você o programa como na J7.02 (`given(...)`).

### 3. `MockMvc`: uma requisição sem rede
`MockMvc` monta uma requisição HTTP **em memória** (`post("/api/v1/transfers").header(...).content(...)`) e a entrega ao `DispatcherServlet`; você verifica status, cabeçalhos e corpo com `andExpect(...)` (`status()`, `header()`, `content()`, `jsonPath()`). O Boot oferece também o `MockMvcTester`, a versão com AssertJ (cuja existência a [documentação](https://docs.spring.io/spring-boot/reference/testing/spring-boot-applications.html) confirma); nesta aula usamos o `MockMvc` clássico, o mais comum em bases de código existentes.

### 4. O que esse teste prova, e o que não prova
**Prova:** rota e verbo, `201` × `200`, `Location`, validação (`400`), tradução de exceções de negócio em `422`/`404` com Problem Details, `401` sem sessão, formato do JSON (dinheiro como **string**, decisão 11). **Não prova:** transação, SQL, o `UNIQUE` da idempotência, a conversão **real** feita pelo `ApiMapper` (aqui ele é um dublê). Para isso, a J7.04/J7.05 e os testes de integração da J6.

### 2. O teste do `TransfersController`
`src/test/java/com/payflow/web/api/TransfersControllerWebTest.java`
```java
package com.payflow.web.api;

import static org.mockito.ArgumentMatchers.any;
import static org.mockito.ArgumentMatchers.eq;
import static org.mockito.BDDMockito.given;
import static org.mockito.BDDMockito.then;
import static org.mockito.Mockito.mock;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.get;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.post;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.content;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.header;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.jsonPath;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.status;

import com.payflow.config.PayflowProperties;
import com.payflow.domain.InsufficientFundsException;
import com.payflow.domain.Transfer;
import com.payflow.service.TransferOutcome;
import com.payflow.service.TransferService;
import com.payflow.service.TransferSubmitter;
import com.payflow.web.CurrentUser;
import com.payflow.web.SessionCookies;
import com.payflow.web.Sessions;
import com.payflow.web.api.dto.TransferResponse;
import jakarta.servlet.http.Cookie;
import java.math.BigDecimal;
import java.time.Instant;
import java.util.Optional;
import java.util.UUID;
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.CsvSource;
import org.junit.jupiter.params.provider.ValueSource;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.context.properties.EnableConfigurationProperties;
import org.springframework.boot.webmvc.test.autoconfigure.WebMvcTest;
import org.springframework.context.annotation.Import;
import org.springframework.http.MediaType;
import org.springframework.test.context.ActiveProfiles;
import org.springframework.test.context.bean.override.mockito.MockitoBean;
import org.springframework.test.web.servlet.MockMvc;

/** A camada web do POST/GET /api/v1/transfers: sem servidor, sem banco, com a regra de negócio trocada por dublês. */
@WebMvcTest(TransfersController.class)
@ActiveProfiles("test")
@Import({SessionCookies.class, Sessions.class, ApiProblems.class})   // o que a fatia NÃO registra sozinha
@EnableConfigurationProperties(PayflowProperties.class)              // nem as propriedades (veja abaixo)
class TransfersControllerWebTest {

    static final UUID ANA_ID = UUID.fromString("10000000-0000-0000-0000-000000000001");
    static final UUID SOURCE_ID = UUID.fromString("20000000-0000-0000-0000-000000000001");
    static final UUID TARGET_ID = UUID.fromString("20000000-0000-0000-0000-000000000002");
    static final UUID TRANSFER_ID = UUID.fromString("30000000-0000-0000-0000-000000000001");
    static final String BODY = """
            {"sourceAccountId":"%s","targetAccountId":"%s","amount":25.00}
            """.formatted(SOURCE_ID, TARGET_ID);

    @Autowired MockMvc mvc;
    @Autowired Sessions sessions;                       // o real: assim o interceptor reconhece a sessão
    @MockitoBean TransferSubmitter submitter;
    @MockitoBean TransferService transfers;
    @MockitoBean ApiMapper mapper;

    Cookie session;
    Transfer transfer;

    @BeforeEach
    void logIn() {
        String sessionId = sessions.create(new CurrentUser(ANA_ID, "ana@payflow.dev", "Ana Souza"));
        session = new Cookie("PAYFLOW_SESSION", sessionId);             // nome do cookie: payflow.session.cookie-name
        transfer = mock(Transfer.class);                               // só o id importa ao controller (Location)
        given(transfer.getId()).willReturn(TRANSFER_ID);
        given(mapper.toResponse(transfer)).willReturn(new TransferResponse(
                TRANSFER_ID, SOURCE_ID, TARGET_ID, new BigDecimal("25.00"), "COMPLETED", Instant.parse("2026-11-13T12:00:00Z")));
    }

    @ParameterizedTest
    @CsvSource({"false,201", "true,200"})        // primeira vez = 201 Created; repetição da mesma chave = 200 OK
    void createsOrReplaysATransfer(boolean replayed, int expectedStatus) throws Exception {
        given(submitter.submit(eq(ANA_ID), eq(SOURCE_ID), eq(TARGET_ID), any(BigDecimal.class), eq("k-1")))
                .willReturn(new TransferOutcome(transfer, replayed));

        mvc.perform(post("/api/v1/transfers")
                        .cookie(session)
                        .header("Idempotency-Key", "k-1")
                        .contentType(MediaType.APPLICATION_JSON)
                        .content(BODY))
                .andExpect(status().is(expectedStatus))
                .andExpect(header().string("Location", "/api/v1/transfers/" + TRANSFER_ID))
                .andExpect(jsonPath("$.id").value(TRANSFER_ID.toString()))
                .andExpect(jsonPath("$.amount").value("25.00"))            // dinheiro como STRING (decisão 11)
                .andExpect(jsonPath("$.status").value("COMPLETED"));
    }

    @ParameterizedTest
    @ValueSource(strings = {"-5.00", "0", "10.005"})
    void rejectsInvalidAmountsWithProblemDetails(String amount) throws Exception {
        String body = """
                {"sourceAccountId":"%s","targetAccountId":"%s","amount":%s}
                """.formatted(SOURCE_ID, TARGET_ID, amount);

        mvc.perform(post("/api/v1/transfers")
                        .cookie(session)
                        .header("Idempotency-Key", "k-2")
                        .contentType(MediaType.APPLICATION_JSON)
                        .content(body))
                .andExpect(status().isBadRequest())
                .andExpect(content().contentTypeCompatibleWith(MediaType.APPLICATION_PROBLEM_JSON))
                .andExpect(jsonPath("$.type").value("urn:payflow:problem:validation-failed"))
                .andExpect(jsonPath("$.errors[0].field").value("amount"));

        then(submitter).shouldHaveNoInteractions();         // a validação barrou ANTES da regra de negócio
    }

    @Test
    void missingIdempotencyKeyIsABadRequest() throws Exception {
        mvc.perform(post("/api/v1/transfers")
                        .cookie(session)
                        .contentType(MediaType.APPLICATION_JSON)
                        .content(BODY))
                .andExpect(status().isBadRequest())
                .andExpect(content().contentTypeCompatibleWith(MediaType.APPLICATION_PROBLEM_JSON));

        then(submitter).shouldHaveNoInteractions();
    }

    @Test
    void withoutASessionTheApiAnswers401WithProblemDetails() throws Exception {
        mvc.perform(post("/api/v1/transfers")
                        .header("Idempotency-Key", "k-3")
                        .contentType(MediaType.APPLICATION_JSON)
                        .content(BODY))
                .andExpect(status().isUnauthorized())
                .andExpect(jsonPath("$.type").value("urn:payflow:problem:not-authenticated"));

        then(submitter).shouldHaveNoInteractions();
    }

    @Test
    void insufficientFundsBecomes422() throws Exception {
        given(submitter.submit(eq(ANA_ID), eq(SOURCE_ID), eq(TARGET_ID), any(BigDecimal.class), eq("k-4")))
                .willThrow(new InsufficientFundsException("Insufficient funds in account " + SOURCE_ID));

        mvc.perform(post("/api/v1/transfers")
                        .cookie(session)
                        .header("Idempotency-Key", "k-4")
                        .contentType(MediaType.APPLICATION_JSON)
                        .content(BODY))
                .andExpect(status().isUnprocessableEntity())
                .andExpect(jsonPath("$.type").value("urn:payflow:problem:insufficient-funds"));
    }

    @Test
    void anUnknownOrForeignTransferIs404() throws Exception {
        given(transfers.findVisibleTo(ANA_ID, TRANSFER_ID)).willReturn(Optional.empty());

        mvc.perform(get("/api/v1/transfers/" + TRANSFER_ID).cookie(session))
                .andExpect(status().isNotFound())
                .andExpect(jsonPath("$.type").value("urn:payflow:problem:not-found"));
    }
}
```
Pontos de leitura:
- **`@WebMvcTest(TransfersController.class)`** restringe a fatia a **um** controller (sem o parâmetro, ela carrega todos e você precisaria de dublês para todos os colaboradores).
- **`@Import({SessionCookies.class, Sessions.class, ApiProblems.class})`**: o `AuthInterceptor` é um `HandlerInterceptor` (a fatia o registra), mas as suas dependências são `@Component` comuns (a fatia **não** as registra). Usamos `Sessions` **real** (não dublê) para que a sessão criada no `@BeforeEach` seja reconhecida pelo interceptor: o teste exercita o **fluxo de autenticação de verdade**, só sem a página de login. Se os construtores finais de `AuthInterceptor`/`WebErrors` pedirem outro bean, aparece no erro de contexto (veja abaixo).
- **`@EnableConfigurationProperties(PayflowProperties.class)`**: o `@ConfigurationPropertiesScan` da classe principal (J5.05) **não** vale na fatia (testado com o Boot 4.1.2: sem esta linha o contexto não sobe com `Parameter 0 of constructor in com.payflow.web.SessionCookies required a bean of type 'com.payflow.config.PayflowProperties' that could not be found`). Com ela, `PayflowProperties` existe com os valores do `application.yml` e do perfil `test`. (A [documentação](https://docs.spring.io/spring-boot/reference/testing/spring-boot-applications.html) explica que a fatia só inclui o que a sua autoconfiguração declara.)
- **O mock de `Transfer`** (`mock(Transfer.class)`) serve só para o controller ler `getId()` e montar o `Location`. O `ApiMapper` é dublê: devolvemos o `TransferResponse` pronto. O **mapeamento real** (MapStruct) tem os seus testes na J6.
- **`any(BigDecimal.class)` para o valor:** `BigDecimal.equals` é sensível à escala, e o que o Jackson entrega depende do texto do JSON; o teste não quer discutir isso aqui.
- **`createsOrReplaysATransfer`** junta as duas respostas com `@CsvSource`: o mesmo controller devolve `201` ou `200` conforme `outcome.replayed()` (J6.03). Cada linha é uma execução.
- **Caminho de erro verificado em duas pontas:** o status/`type` **e** `then(submitter).shouldHaveNoInteractions()` (a regra de negócio nem foi chamada).

### 3. A mesma ideia com AssertJ (`MockMvcTester`)
O `MockMvcTester` embrulha o `MockMvc` com afirmações do AssertJ (injeção por `@Autowired MockMvcTester mvc`). Exemplo mínimo, equivalente a `anUnknownOrForeignTransferIs404` (⚠️ detalhes de API a confirmar no Javadoc do Spring Framework 7 ao rodar):
```java
assertThat(mvc.get().uri("/api/v1/transfers/" + TRANSFER_ID).cookie(session))
        .hasStatus(HttpStatus.NOT_FOUND);
```
Escolha um estilo por projeto e mantenha-o. O curso usa `MockMvc` porque é o que você mais encontrará no mercado.

## 🧠 Pausa para lógica
**Enunciado:** um cliente **sem sessão** envia um `POST /api/v1/transfers` com **corpo inválido** (`amount: -5`). A resposta é `401` ou `400`? Justifique pela **ordem em que o Spring MVC executa as etapas** (J5.06): interceptor, resolução de argumentos, validação, controller.

<details><summary>Dica</summary>Desenhe a cadeia: <code>DispatcherServlet → HandlerMapping → <b>interceptors.preHandle</b> → resolução dos argumentos (<code>@RequestBody</code>, <code>@Valid</code>) → método do controller</code>. Em que etapa o <code>false</code> do <code>preHandle</code> encerra tudo?</details>
<details><summary>Solução</summary>

`401`. O `AuthInterceptor.preHandle` roda **antes** de o Spring converter o corpo e validar `@Valid`; ao devolver `false`, a requisição termina ali e o corpo **nunca é lido**. Por isso a ordem dos erros é: autenticação (401) → validação (400) → regra de negócio (422/404/409). É uma propriedade de **segurança** também: não dê feedback de validação a quem nem se identificou.

Teste (para você acrescentar): `POST` sem cookie e com `amount:-5` deve dar `401` e `$.type == "urn:payflow:problem:not-authenticated"`.
</details>

**Variação mais difícil:** o `AuthInterceptor` **não** protege `/api/v1/**` por acidente de configuração (alguém removeu o `addPathPatterns`). Que **um** teste desta classe falha primeiro e por quê? (Dica: qual teste hoje depende de o interceptor barrar?)

## ⚖️ Trade-offs e quando NÃO usar
- **Cada `@MockitoBean` diferente cria um contexto novo** (o cache do Spring usa a configuração como chave, J7.04). Padronize o conjunto de dublês entre classes de teste para reaproveitar o contexto.
- **Dublê demais esconde a integração:** se você mocka `ApiMapper`, um campo faltando no DTO só aparece em outro teste. A suíte precisa de **ambos** (fatia e integração).
- **Não teste o framework:** "o `@RequestBody` desserializa JSON" é do Spring. Teste **as suas regras** (validação, status, tradução de erro, contrato do JSON).

## ⚠️ Erros comuns e boas práticas de produção
Mensagens reais costumam ter este formato (⚠️ texto exato não capturado aqui; o que importa é **aprender a ler**):
```text
java.lang.IllegalStateException: Failed to load ApplicationContext for [WebMergedContextConfiguration ...]
Caused by: org.springframework.beans.factory.UnsatisfiedDependencyException: Error creating bean with name 'authInterceptor'
  ... Unsatisfied dependency expressed through constructor parameter 1: No qualifying bean of type 'com.payflow.web.Sessions' available
```
- **`No qualifying bean of type 'X'`:** a fatia não registra `X`. Duas saídas: `@MockitoBean X` (se for colaborador a substituir) ou `@Import(X.class)` (se for peça real necessária). Siga a cadeia de `Caused by` até o nome do bean que falhou.
- **`Status expected:<201> but was:<401>`:** o interceptor não reconheceu a sessão: cookie com nome errado (`payflow.session.cookie-name`) ou `Sessions` diferente (dublê em vez do real).
- **`Status expected:<400> but was:<500>`:** a exceção não foi traduzida: o `ApiErrors` não está na fatia, ou está fora do pacote `com.payflow.web.api` (o `@RestControllerAdvice(basePackages = ...)` só vale ali).
- **`jsonPath ... No value at JSON path "$.errors[0].field"`:** confira o JSON real: imprima com `.andDo(org.springframework.test.web.servlet.result.MockMvcResultHandlers.print())`.
- **Testar com dados que o `ApiMapper` real trataria de outro jeito:** se o dublê devolve um DTO "bonito demais", o teste não protege contra regressão no mapeamento.
- **`@SpringBootTest` por preguiça:** funciona, mas você perde a velocidade e o isolamento da fatia; só use quando o teste **precisa** do contexto completo.

## 🎤 Na entrevista
1. **Qual a diferença entre `@WebMvcTest` e `@SpringBootTest`?**
   *Resposta-modelo:* `@WebMvcTest` carrega **só a fatia web** (controllers, advices, conversores, interceptors) com `MockMvc`; sem banco e sem servidor real; colaboradores vêm de `@MockitoBean`. `@SpringBootTest` carrega a aplicação **inteira** (com porta real ou `MockMvc`). Uso a fatia para regras da camada web, e o `@SpringBootTest` para provar a integração.
2. **O que é `@MockitoBean` e como difere de um `mock()` comum?**
   *Resposta-modelo:* é uma anotação do Spring que **substitui** um bean no contexto por um mock do Mockito (e o zera entre testes); `mock()` cria um objeto solto, fora do contêiner. Substituir no contexto faz o controller receber o dublê por injeção.
3. **Como você testa que um endpoint exige autenticação?**
   *Resposta-modelo:* faço a requisição sem credencial e espero `401`, confirmo que o colaborador de negócio **não** foi chamado, e faço a mesma requisição autenticada esperando sucesso; também verifico a **ordem** (autenticação antes de validação).
