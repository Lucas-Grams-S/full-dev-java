## 🎯 Objetivos
Ao final desta aula você consegue:
1. **Reconhecer** os *code smells* mais comuns (nomes ruins, método longo, aninhamento, número/texto mágico, *flag argument*, obsessão por tipos primitivos).
2. **Refatorar** em passos pequenos (extrair método, renomear, substituir condicional aninhada por cláusulas de guarda, introduzir `record` e `enum`).
3. **Proteger** uma refatoração com **testes de caracterização**, que registram o comportamento **atual**, certo ou errado.
4. **Separar** refatoração (muda a estrutura) de mudança de comportamento (muda o resultado), em *commits* diferentes.
5. **Explicar** por que `double` não serve para dinheiro mostrando o erro **medido**.

## 🤔 Por que isso importa
A maior parte do tempo de um dev, júnior inclusive, é **ler e alterar código que outra pessoa escreveu** (ou que você mesmo escreveu há seis meses). Código difícil de ler custa caro: cada alteração vira medo de quebrar algo. Um time espera de você duas coisas: escrever código **legível** desde o início e, ao tocar em código ruim, **melhorá-lo sem quebrá-lo**. Esta aula treina o segundo ponto com um caso real de legado, que tem de quebra um bug de dinheiro escondido.

## 💡 Intuição (explicação simples)
Reformar uma casa **com gente morando**: você não derruba paredes sem escoras. Os testes de caracterização são as **escoras**: antes de mexer, você registra como a casa **se comporta hoje** (inclusive as manias estranhas). A cada passo da obra, confere se as escoras seguem de pé. E **reformar** (mudar a estrutura) é diferente de **ampliar** (mudar o que a casa faz): misturar as duas coisas é a receita para não saber qual das duas quebrou o telhado.

## 🔬 Como funciona por dentro

### 1. Refatorar: o que é, e o que **não** é
**Refatorar** é mudar a **estrutura interna** do código **sem mudar o seu comportamento observável** ([catálogo de Martin Fowler](https://refactoring.com/catalog/)). Duas consequências:
- Só dá para afirmar "não mudei o comportamento" **se há testes** que o fixam. Sem testes, você está **editando**, não refatorando.
- Corrigir um bug **muda** o comportamento. É outra atividade, com outro *commit* (os "dois chapéus": ou você refatora, ou você muda o comportamento; nunca os dois ao mesmo tempo).

### 2. Testes de caracterização
Quando o código legado **não tem testes**, você escreve testes que **registram o que ele faz hoje**: rode com entradas representativas, **copie a saída** para o teste como valor esperado e **só então** refatore. Eles não dizem se o comportamento é *correto* (alguns resultados vão parecer errados); dizem se ele **mudou**. A técnica é a de *golden master* (do livro *Working Effectively with Legacy Code*, de Michael Feathers; capítulos não conferidos nesta execução). O que você fixa define **o que pode mudar**: fixar a mensagem exata de uma exceção proíbe melhorá-la; fixar só o tipo permite.

### 3. O catálogo mínimo de *smells*
Um *smell* (cheiro) não é um erro: é um **indício** de que o código vai ficar caro. Catálogo completo em [Refactoring Guru](https://refactoring.guru/refactoring/smells) e no [catálogo do Fowler](https://refactoring.com/catalog/). Os que o júnior mais encontra:

| *Smell* | Sintoma | Refatoração | Exemplo no laboratório |
|---|---|---|---|
| **Nome sem significado** | `c`, `d`, `n`, `v`, `big`, `bigv` | **Renomear** (IntelliJ: `Shift+F6`) | `credits`, `debits`, `entries`, `largest` |
| **Método longo** | faz leitura, validação, conta e formata | **Extrair método** (`Ctrl+Alt+M`) | `parse`, `total`, `render`, `largest` |
| **Aninhamento em seta** | `if` dentro de `if` dentro de `for` | **Cláusulas de guarda** e extração | `Row.parse` devolve cedo |
| **Texto/número mágico** | `"C"`, `"D"`, `3` espalhados | **Enum/constante** | `EntryKind` |
| **Obsessão por primitivos** | `String[]` fazendo papel de objeto | **Introduzir `record`** | `Row(kind, amount, date)` |
| **Argumento *flag*** | `build(rows, true)`: o que é `true`? | **Separar em dois métodos** | `summary` e `summaryWithLargest` |
| **Erro engolido** | linha malformada ignorada em silêncio | **Decidir** e testar (registrar) | `Row.parse` com comentário |
| **Tipo errado para o domínio** | `double` para dinheiro | **Trocar o tipo** (muda comportamento!) | `BigDecimal` (passo 4) |
| **Comentário que explica o "o quê"** | `// soma créditos` sobre `c = c + a` | **Código claro**; comentário só para o "porquê" | comentários do `Report` |

### 4. Regras práticas de legibilidade
- **Nomes dizem a intenção** (`creditsTotal`, não `c`); um nome difícil de escolher indica que o método faz coisa demais.
- **Funções pequenas que fazem uma coisa**, com **um nível de abstração** (ou lê, ou valida, ou calcula, ou formata). Sem fanatismo: "pequeno" é meio, não fim.
- **Cláusulas de guarda** (devolver/lançar cedo) em vez de `if` aninhado: o caminho feliz fica sem recuo.
- **Sem efeitos colaterais surpresa** e **sem *flags*** que mudam o que o método faz.
- **Comentários explicam o porquê** (decisões, armadilhas), nunca o que a linha já diz.
- **Tipos do domínio** (`record`, `enum`, `BigDecimal`) em vez de `String`/`double` soltos: o compilador passa a ajudar.
- *Regra do escoteiro*: deixe o código **um pouco melhor** do que o encontrou, **em passo pequeno e com testes**.

As regras do livro *Clean Code* (Robert C. Martin) são **heurísticas**, e parte delas é contestada (por exemplo, métodos de poucas linhas a qualquer custo fragmentam a leitura). Use o critério da **leitura**: um colega entende isto em um minuto?

## 🛠️ Exemplo prático
O arquivo completo e **testado** está em `1-junior/J7-testes-qualidade/lab/StatementLab.java` (copie para `docs/clean-code-lab/` no repositório `payflow`). É Java puro; rode:

Ele contém três versões do mesmo resumo de extrato (créditos, débitos, saldo e maior lançamento) lado a lado: `Legacy`, `Report` (refatorada) e `MoneyReport` (com o dinheiro corrigido).

### Passo 0: o código herdado
```java
class Legacy {
    // rows: {type, amount, date}; type: "C" credit, "D" debit
    static String build(List<String[]> rows, boolean v) {
        double c = 0;
        double d = 0;
        int n = 0;
        String big = null;
        double bigv = 0;
        for (int i = 0; i < rows.size(); i++) {
            String[] r = rows.get(i);
            if (r != null) {
                if (r.length == 3) {
                    double a = Double.parseDouble(r[1]);
                    if (r[0].equals("C")) {
                        c = c + a;
                    } else {
                        if (r[0].equals("D")) {
                            d = d + a;
                        } else {
                            throw new RuntimeException("bad type");
                        }
                    }
                    n++;
                    if (a > bigv) {
                        bigv = a;
                        big = r[2];
                    }
                }
            }
        }
        String s = "credits=" + c + " debits=" + d + " balance=" + (c - d) + " entries=" + n;
        if (v) {
            s = s + " largest=" + bigv + " on " + big;
        }
        if (n == 0) {
            return "empty";
        }
        return s;
    }
}
```
Conte os *smells*: nomes (`c`, `d`, `n`, `v`, `big`, `bigv`), aninhamento em seta de 4 níveis, textos mágicos (`"C"`, `"D"`), `String[]` como objeto, *flag* `v`, linhas malformadas ignoradas **em silêncio**, `double` para dinheiro, exceção vaga (`"bad type"`), trabalho inútil (monta a `String` e só depois descobre que `n == 0`).

### Passo 1: o *golden master* (antes de mexer em nada)
O `main` do laboratório roda **nove casos** pelo legado e registra o resultado. É o **teste de caracterização**: ele não julga, só registra. Saídas **reais** do legado:

| Caso | Resultado do `Legacy` |
|---|---|
| `sample` (3 linhas) | `credits=105.1 debits=30.05 balance=75.05 entries=3` |
| `sample` com `v = true` | `... entries=3 largest=100.1 on 2026-11-01` |
| lista vazia | `empty` |
| linha `null`, linha com 2 campos, 2 linhas válidas | `credits=10.0 debits=4.5 balance=5.5 entries=2 largest=10.0 on 2026-11-01` (**as linhas malformadas somem em silêncio**) |
| tipo `"X"` | `throws RuntimeException` |
| valor `"abc"` | `throws NumberFormatException` |
| tipo `"X"` **e** valor `"abc"` | `throws NumberFormatException` (o valor é lido **antes** do tipo) |
| valores `0` e `-3` com `v = true` | `credits=0.0 debits=-3.0 balance=3.0 entries=2 largest=0.0 on null` (**uma esquisitice**: ninguém "vence") |
| `0.10 + 0.20` créditos, `0.30` débito | `credits=0.30000000000000004 debits=0.3 balance=5.551115123125783E-17 entries=3` (**o bug do `double`**) |

Repare nas duas últimas linhas: o caso "zero e negativo" e o caso de ponto flutuante parecem **errados**. Não corrija agora: **registre**. Refatorar é manter até as manias.

### Passos 2 e 3: refatorar com o *golden master* verde
Em passos pequenos (no IntelliJ, cada um é uma refatoração automática): **renomear** variáveis; **extrair** `parse`, `total`, `render` e `largest`; trocar `"C"/"D"` por `enum EntryKind`; trocar o `String[]` por `record Row`; **cláusulas de guarda** em `Row.parse`; separar o *flag* em `summary` e `summaryWithLargest`. O resultado:
```java
enum EntryKind {
    CREDIT, DEBIT;

    static EntryKind parse(String code) {
        return switch (code) {
            case "C" -> CREDIT;
            case "D" -> DEBIT;
            default -> throw new IllegalArgumentException("unknown entry type: " + code);
        };
    }
}

final class Report {

    private Report() {
    }

    private record Row(EntryKind kind, double amount, String date) {

        /** Linha nula ou com tamanho diferente de 3 é ignorada, como no legado (decisão a revisar: ver Exercícios). */
        static Optional<Row> parse(String[] raw) {
            if (raw == null || raw.length != 3) {
                return Optional.empty();
            }
            double amount = Double.parseDouble(raw[1]);        // o valor é lido ANTES do tipo, como no legado
            return Optional.of(new Row(EntryKind.parse(raw[0]), amount, raw[2]));
        }
    }

    static String summary(List<String[]> raw) {
        return render(parse(raw), false);
    }

    static String summaryWithLargest(List<String[]> raw) {
        return render(parse(raw), true);
    }

    private static List<Row> parse(List<String[]> raw) {
        List<Row> rows = new ArrayList<>();
        for (String[] fields : raw) {
            Row.parse(fields).ifPresent(rows::add);
        }
        return rows;
    }

    private static String render(List<Row> rows, boolean withLargest) {
        if (rows.isEmpty()) {
            return "empty";
        }
        double credits = total(rows, EntryKind.CREDIT);
        double debits = total(rows, EntryKind.DEBIT);
        String text = "credits=" + credits + " debits=" + debits + " balance=" + (credits - debits) + " entries=" + rows.size();
        return withLargest ? text + largest(rows) : text;
    }

    /** Laço simples, na mesma ordem do legado: DoubleStream.sum() usaria soma compensada e poderia mudar os últimos dígitos. */
    private static double total(List<Row> rows, EntryKind kind) {
        double sum = 0;
        for (Row row : rows) {
            if (row.kind() == kind) {
                sum = sum + row.amount();
            }
        }
        return sum;
    }

    /** Preserva a esquisitice do legado: com valores zero ou negativos, nenhuma linha vence ("largest=0.0 on null"). */
    private static String largest(List<Row> rows) {
        Row best = null;
        double bestAmount = 0;
        for (Row row : rows) {
            if (row.amount() > bestAmount) {
                best = row;
                bestAmount = row.amount();
            }
        }
        return " largest=" + bestAmount + " on " + (best == null ? null : best.date());
    }
}
```
Rodando o laboratório, a comparação **estrita** (texto do resultado ou nome do tipo da exceção) deu, **real**:
```text
sample                                 refactored == legacy
sample verbose                         refactored == legacy
empty                                  refactored == legacy
null and malformed rows are skipped    refactored == legacy
unknown type                           refactored != throws IllegalArgumentException
unparseable amount                     refactored == legacy
bad type AND bad amount                refactored == legacy
zero and negative amounts              refactored == legacy
floating point                         refactored == legacy

refactor differs from legacy in 1 case(s)
```
**Oito de nove iguais e uma diferença honesta.** O legado lançava `RuntimeException` (a classe genérica); o `enum` lança `IllegalArgumentException`, mais específica e com mensagem melhor (`unknown entry type: X`). A comparação estrita enxerga isso. Em um teste de verdade você decide **o que fixar**: se o contrato for "lança `RuntimeException`" (`assertThatThrownBy(...).isInstanceOf(RuntimeException.class)`), a nova exceção **continua válida** (é subclasse); se alguém depende da classe exata, é uma **mudança de comportamento** e merece o seu próprio *commit*.

Três detalhes que a execução protegeu:
- **A ordem de leitura** (valor antes do tipo) foi mantida, e o caso "tipo e valor ruins" confirma (`NumberFormatException` nos dois).
- **O laço de soma** foi mantido: `DoubleStream.sum()` usa soma compensada e **poderia** alterar os últimos dígitos do caso de ponto flutuante (⚠️ não testado aqui; por isso o laço simples).
- **As esquisitices** (linhas malformadas ignoradas, `largest=0.0 on null`) foram **preservadas e comentadas**, não "consertadas": consertar muda comportamento.

### Passo 4: o bug do dinheiro (mudança de comportamento, *commit* separado)
Agora sim, com os testes verdes, troque `double` por `BigDecimal` (decisão 4): leitura com `new BigDecimal(raw[1]).setScale(2, RoundingMode.UNNECESSARY)` (mais de 2 casas lança `ArithmeticException`), somas com `add`/`subtract`, saída com `toPlainString()`. A classe é a `MoneyReport` do arquivo. As saídas **reais**, comparadas ao legado:

| Caso | `Legacy` (`double`) | `MoneyReport` (`BigDecimal`) |
|---|---|---|
| `sample` | `credits=105.1 debits=30.05 balance=75.05` | `credits=105.10 debits=30.05 balance=75.05` |
| ponto flutuante | `credits=0.30000000000000004 debits=0.3 balance=5.551115123125783E-17` | `credits=0.30 debits=0.30 balance=0.00` |
| zero e negativo | `largest=0.0 on null` | `largest=0.00 on null` (a esquisitice continua; é decisão de produto) |

O resultado novo é **diferente de propósito**: o saldo de `0.10 + 0.20 - 0.30` agora é `0.00`, e não `5.551115123125783E-17`. Esse é o motivo de a decisão 4 existir: **dinheiro em `BigDecimal` com 2 casas**.

**Os *commits* deste trabalho**, no padrão Conventional Commits (visto na J0; a J7.09 aprofunda):
```text

refactor: name variables and extract parse/total/render           <- comportamento igual
refactor: replace type codes with EntryKind and rows with Row     <- comportamento igual
refactor: split the verbose flag into summaryWithLargest          <- comportamento igual
fix: use BigDecimal for money in the statement summary            <- comportamento NOVO (de propósito)
```

## 🧠 Pausa para lógica
**Enunciado:** no caso `bad type AND bad amount` (`["X", "abc", "d"]`), tanto o legado quanto a versão refatorada lançam `NumberFormatException`, **não** `RuntimeException` de tipo inválido. Por quê? E o que teria acontecido se, no `Row.parse`, você tivesse escrito `new Row(EntryKind.parse(raw[0]), Double.parseDouble(raw[1]), raw[2])` em uma linha só?

<details><summary>Dica</summary>Em Java os argumentos de um construtor são avaliados da <b>esquerda para a direita</b>, antes de a chamada acontecer. Qual argumento falha primeiro em cada versão?</details>
<details><summary>Solução</summary>

No legado, `Double.parseDouble(r[1])` roda **antes** de qualquer teste do tipo; com `"abc"`, a `NumberFormatException` sai primeiro. Na versão refatorada o valor é lido **antes** de `EntryKind.parse` (por isso a variável `amount` é declarada antes do `return`), preservando a ordem. Com a linha única `new Row(EntryKind.parse(raw[0]), Double.parseDouble(raw[1]), raw[2])`, o primeiro argumento (`EntryKind.parse("X")`) é avaliado **primeiro** e lançaria `IllegalArgumentException`: o resultado do caso "tipo e valor ruins" **mudaria**, e o *golden master* acusaria. É um exemplo de refatoração que "parece inocente" e **não é**: a ordem de avaliação é comportamento.
</details>

**Variação mais difícil:** a esquisitice `largest=0.0 on null` é um bug ou uma regra? Escreva as duas versões do teste (uma que a **fixa**, outra que exige `largest` indefinido quando não há lançamento positivo) e descreva quem decide e como o **processo** deveria registrar a decisão (pense em ADR, J7.09 e a decisão sobre linhas malformadas ignoradas em silêncio).

## ⚖️ Trade-offs e quando NÃO usar
- **Refatorar sem testes** é arriscado: se não dá para escrever o teste de caracterização (acoplamento forte, efeito externo), faça **só** as refatorações automáticas e seguras da IDE (renomear, extrair método) e conte com o compilador.
- **Refatoração oportunista × "grande refatoração":** a regra do escoteiro (melhorar o que você toca) é barata; reescrever um módulo inteiro "para ficar limpo" quase nunca compensa sem um motivo de negócio (o módulo S7, de liderança técnica, volta ao tema com a modernização de legado).
- **Abstração prematura:** extrair interface, fábrica e três camadas para um método de 20 linhas é o *smell* oposto (*over-engineering*). Extraia quando houver **repetição real** ou **mudança prevista**, não "por via das dúvidas".
- **Funções minúsculas demais:** dividir em métodos de 2 linhas obriga o leitor a pular entre eles. Use o teste do colega: ficou mais fácil de entender?

## ⚠️ Erros comuns e boas práticas de produção
- **Refatorar e mudar comportamento no mesmo *commit*:** quando algo quebra, não se sabe qual das duas coisas causou. Dois *commits* (e, idealmente, dois PRs).
- **"Consertar" uma esquisitice durante a refatoração:** muda comportamento sem aviso. Registre, teste, decida depois.
- **Renomear API pública sem perceber os usuários:** a IDE renomeia o projeto inteiro, mas não o código de **outros** repositórios/clientes. Em API HTTP (J6), renomear campo de JSON **quebra clientes**.
- **Comentário que mente:** quando o código muda e o comentário não. Prefira nomes claros.
- **Comentar código antigo "por segurança":** o Git já guarda o histórico (J0.04); apague.
- **`double` para dinheiro:** o caso "floating point" mostra `5.551115123125783E-17` no lugar de `0.00`. Nunca em dinheiro (decisão 4).
- **Testes que fixam detalhes demais:** o *golden master* dos textos exatos é ótimo para o legado, mas em código novo prefira testar **comportamento** (valores, não a formatação).

## 🎤 Na entrevista
1. **O que é refatorar e como você garante que não quebrou nada?**
   *Resposta-modelo:* mudar a estrutura sem mudar o comportamento observável. Garanto com testes; se não há, escrevo testes de caracterização antes (registram o comportamento atual), refatoro em passos pequenos com os testes verdes e deixo qualquer mudança de comportamento para outro *commit*.
2. **Cite três *code smells* e como você os trata.**
   *Resposta-modelo:* método longo → extrair método; condicionais aninhadas → cláusulas de guarda; número/texto mágico → constante/enum; *flag argument* → separar em dois métodos; obsessão por primitivos → introduzir tipo do domínio (`record`).
3. **Por que não usar `double` para dinheiro?**
   *Resposta-modelo:* `double` é binário e não representa `0.1` exatamente; as somas acumulam erro (`0.10 + 0.20` dá `0.30000000000000004`). Uso `BigDecimal` com escala 2 e arredondamento definido (aqui, `HALF_EVEN`).
