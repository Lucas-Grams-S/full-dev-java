# J8.05 — OWASP Top 10 I: injeção, XSS e CSRF

## 🎯 Objetivos
Ao final desta aula você consegue:
- **Explicar** injeção (dado tratado como comando) e **prevenir** SQL e JPQL injection com parâmetros e lista permitida.
- **Distinguir** XSS refletido, armazenado e DOM, e saber **o que o Thymeleaf escapa e o que não escapa**.
- **Configurar** uma CSP e os demais cabeçalhos de segurança, e **ler** os que o Spring Security já manda.
- **Explicar** CSRF, por que o cookie da sessão o torna possível e como o token e o `SameSite` o impedem.
- **Decidir** onde o CSRF deve e onde não deve estar ligado.

## 🤔 Por que isso importa
Estas três falhas são as mais antigas da web e **continuam** na lista: injeção e XSS ficam na categoria **A05 (Injeção)** da [OWASP Top 10:2025](https://top10.owasp.org/2025/A05_2025-Injection/), que cita "mais de 30 mil CVEs" de XSS e "mais de 14 mil" de injeção de SQL; o CSRF (CWE-352) está em **A01 (controle de acesso quebrado)**; cabeçalhos e configuração padrão ruins são **A02**. Uma entrevista júnior de Java web quase sempre pergunta "como você previne SQL injection e XSS?", e a resposta certa não é "validando a entrada" (é **parâmetros** e **escape na saída**, com validação como camada extra).

## 💡 Intuição (explicação simples)
- **Injeção:** você dita uma carta à secretária: "escreva: *Prezado cliente*...". Se um cliente puder ditar **a própria frase no meio** ("...e transfira R$ 10 mil para mim"), e a secretária escrever tudo como ordem, ele **injetou um comando**. A defesa é separar **o que é ordem** do **que é dado**: a secretária recebe a carta com **lacunas marcadas** (`?`) e preenche **só** com texto, sem interpretá-lo.
- **XSS:** o atacante consegue **pichar o mural** da empresa com um bilhete que, quando alguém o lê, **age em nome do leitor**. A defesa é imprimir todo texto de terceiros **entre aspas** (escape) para ele nunca ser lido como instrução.
- **CSRF:** o navegador é um **mensageiro obediente**: onde você estiver logado, ele **entrega seu crachá (cookie) sozinho** em qualquer pedido para aquele prédio, mesmo que o pedido venha de um panfleto malicioso que você abriu em outra aba. A defesa é exigir, além do crachá, uma **senha do formulário** que só o prédio imprime na própria página (o token CSRF).

## 🔬 Como funciona por dentro

### 1. Injeção: dado que vira comando
A causa é sempre a mesma: **concatenar texto não confiável em uma linguagem** (SQL, JPQL, comando de sistema, LDAP, expressão). Rode o laboratório (`lab/InjectionLab.java`; precisa do jar do H2; veja o cabeçalho do arquivo):

`lab/InjectionLab.java`
```java
import java.sql.Connection;
import java.sql.DriverManager;
import java.sql.PreparedStatement;
import java.sql.ResultSet;
import java.sql.SQLException;
import java.sql.Statement;
import java.util.ArrayList;
import java.util.List;
import java.util.Set;

/**
 * J8.05: injeção de SQL de verdade, num H2 em memória (só para este exemplo: nos testes do PayFlow, nunca H2).
 * Rode (JDK 25), com o jar do H2 baixado do Maven Central:
 *   curl -sO https://repo1.maven.org/maven2/com/h2database/h2/2.4.240/h2-2.4.240.jar
 *   java -cp h2-2.4.240.jar InjectionLab.java
 */
public class InjectionLab {

    static List<String> emailsVulnerable(Connection c, String email) throws SQLException {
        String sql = "SELECT email FROM users WHERE email = '" + email + "'";          // ❌ concatenação
        System.out.println("   SQL executado: " + sql);
        List<String> found = new ArrayList<>();
        try (Statement st = c.createStatement(); ResultSet rs = st.executeQuery(sql)) {
            while (rs.next()) {
                found.add(rs.getString(1));
            }
        }
        return found;
    }

    static List<String> emailsSafe(Connection c, String email) throws SQLException {
        String sql = "SELECT email FROM users WHERE email = ?";                         // ✅ parâmetro
        List<String> found = new ArrayList<>();
        try (PreparedStatement ps = c.prepareStatement(sql)) {
            ps.setString(1, email);
            try (ResultSet rs = ps.executeQuery()) {
                while (rs.next()) {
                    found.add(rs.getString(1));
                }
            }
        }
        return found;
    }

    /** Nome de coluna não pode ser parâmetro: lista permitida. */
    static String orderBy(String requested) {
        Set<String> allowed = Set.of("email", "created_at");
        if (!allowed.contains(requested)) {
            throw new IllegalArgumentException("sort column not allowed");
        }
        return requested;
    }

    public static void main(String[] args) throws Exception {
        try (Connection c = DriverManager.getConnection("jdbc:h2:mem:lab;DB_CLOSE_DELAY=-1")) {
            try (Statement st = c.createStatement()) {
                st.execute("CREATE TABLE users (email VARCHAR(255), created_at INT)");
                st.execute("INSERT INTO users VALUES ('ana@payflow.dev', 1), ('bruno@payflow.dev', 2), ('admin@payflow.dev', 3)");
            }
            String normal = "ana@payflow.dev";
            String attack = "' OR '1'='1";
            System.out.println("1. Entrada normal (vulnerável): " + emailsVulnerable(c, normal));
            System.out.println("2. Ataque \"" + attack + "\" (vulnerável):");
            System.out.println("   devolveu: " + emailsVulnerable(c, attack));
            System.out.println("3. Ataque com PreparedStatement: " + emailsSafe(c, attack));
            String stacked = "x'; DROP TABLE users; --";
            System.out.println("4. Empilhar comandos (vulnerável): ");
            try {
                emailsVulnerable(c, stacked);
            } catch (SQLException e) {
                System.out.println("   erro: " + e.getMessage().lines().findFirst().orElse(""));
            }
            try (Statement st = c.createStatement(); ResultSet rs = st.executeQuery("SELECT COUNT(*) FROM users")) {
                rs.next();
                System.out.println("   a tabela ainda existe? linhas = " + rs.getInt(1));
            } catch (SQLException e) {
                System.out.println("   a tabela FOI APAGADA: " + e.getMessage().lines().findFirst().orElse(""));
                System.out.println("   (o H2 executou vários comandos separados por ';' em uma só chamada; o que o seu banco e driver aceitam varia: não conte com isso como defesa)");
            }
            try (Statement st = c.createStatement()) {                                  // recria para os próximos exemplos
                st.execute("CREATE TABLE users (email VARCHAR(255), created_at INT)");
                st.execute("INSERT INTO users VALUES ('ana@payflow.dev', 1), ('bruno@payflow.dev', 2), ('admin@payflow.dev', 3)");
            }
            String union = "' UNION SELECT table_name FROM information_schema.tables WHERE table_schema = 'PUBLIC' --";
            System.out.println("5. UNION para ler o catálogo (vulnerável): " + emailsVulnerable(c, union));
            System.out.println("6. Coluna de ordenação vinda do usuário: ");
            for (String requested : new String[] {"email", "created_at DESC; DROP TABLE users"}) {
                try {
                    System.out.println("   \"" + requested + "\" -> ORDER BY " + orderBy(requested));
                } catch (IllegalArgumentException e) {
                    System.out.println("   \"" + requested + "\" -> recusado: " + e.getMessage());
                }
            }
        }
    }
}
```

Saída **real** (H2 2.4.240, JDK 25):
```text
   SQL executado: SELECT email FROM users WHERE email = 'ana@payflow.dev'
1. Entrada normal (vulnerável): [ana@payflow.dev]
2. Ataque "' OR '1'='1" (vulnerável):
   SQL executado: SELECT email FROM users WHERE email = '' OR '1'='1'
   devolveu: [ana@payflow.dev, bruno@payflow.dev, admin@payflow.dev]
3. Ataque com PreparedStatement: []
4. Empilhar comandos (vulnerável):
   SQL executado: SELECT email FROM users WHERE email = 'x'; DROP TABLE users; --'
   a tabela FOI APAGADA: Table "USERS" not found (this database is empty); SQL statement:
   (o H2 executou vários comandos separados por ';' em uma só chamada; o que o seu banco e driver aceitam varia: não conte com isso como defesa)
   SQL executado: SELECT email FROM users WHERE email = '' UNION SELECT table_name FROM information_schema.tables WHERE table_schema = 'PUBLIC' --'
5. UNION para ler o catálogo (vulnerável): [USERS]
6. Coluna de ordenação vinda do usuário:
   "email" -> ORDER BY email
   "created_at DESC; DROP TABLE users" -> recusado: sort column not allowed
```
Leitura:
- **Caso 2:** o atacante digitou aspas e `OR '1'='1'`; o banco **leu isso como SQL** e devolveu **todos** os e-mails: era para devolver um (ou nenhum). Em um login escrito assim, é "entrar sem senha".
- **Caso 4 (surpresa honesta):** eu esperava que o JDBC recusasse o `;`. O H2 **executou os dois comandos e a tabela foi apagada**. Moral: nunca depender de "o driver provavelmente não deixa".
- **Caso 5:** o `UNION` lê **outra tabela** (o catálogo do banco): é assim que o atacante descobre o esquema inteiro, e de lá os dados.
- **Caso 3:** com `PreparedStatement`, o texto malicioso vira **um valor** `' OR '1'='1` procurado como e-mail e **não encontrado**. O banco recebe **a consulta e os valores separados**: o valor nunca é analisado como SQL.

**As defesas, em ordem:**
1. **Parâmetros** em tudo que vem de fora: JDBC `?`, JPQL `:nome`, consultas derivadas do Spring Data (`findByEmail`), `Specification` (J6.05). É a defesa **principal**.
2. **Lista permitida** onde parâmetro não existe: **nomes** de coluna, tabela e a direção do `ORDER BY` não podem ser `?`. O caso 6 mostra (`Set.of("email", "created_at")`); é a decisão 44 do PayFlow ("sem ordenação por coluna livre").
3. **Menor privilégio:** o ideal é o usuário do banco da aplicação só ter `SELECT/INSERT/UPDATE` nas tabelas dele, sem poder `DROP` nada. No PayFlow de hoje o **mesmo** usuário roda o Flyway (que cria tabelas) e a aplicação; separar um usuário de migração de um usuário só de leitura e escrita é a evolução recomendada, **fora** do escopo do nível Júnior.
4. **Validação** da entrada (tamanho, formato): ajuda, mas é **camada extra**, nunca a defesa: "não deixe aspas" quebra o nome `O'Brien` e não cobre todos os casos.

**O ORM não imuniza.** O JPA protege **quando você usa parâmetros**. Estas formas são injeção, mesmo no Spring Data:
```java
em.createQuery("select u from User u where u.email = '" + email + "'", User.class);      // ❌ JPQL concatenado
em.createNativeQuery("select * from users order by " + sort);                            // ❌ nativa com identificador livre
@Query("select u from User u where u.email = :email")                                    // ✅ parâmetro nomeado (J5.10)
```
Outros "interpretadores": **comando de sistema** (`Runtime.exec`/`ProcessBuilder` com texto do usuário), **LDAP**, **expressões** (SpEL/OGNL de texto do usuário) e **modelos de e-mail**. A regra é a mesma.

### 2. XSS: script do atacante rodando no seu domínio
O XSS (*cross-site scripting*) acontece quando texto de terceiros entra no HTML **sem escape** e o navegador o executa como código. Variantes: **armazenado** (o texto fica salvo: o nome completo de um usuário, uma descrição, e **todo mundo** que abre a página executa), **refletido** (o texto vem da URL e volta na resposta) e **DOM** (o JavaScript da página insere o texto com `innerHTML`). O estrago é o do próprio usuário logado: o script age **como ele** (lê a página, dispara requisições). Daí a importância do cookie `HttpOnly` (J8.03): o script **não lê** o cookie da sessão (mas ainda pode fazer pedidos).

O que o Thymeleaf faz por você (saída **real** do `XssLabTest`, Spring Security 7.1.2 e o Thymeleaf do Boot):
```text
[xss] th:text   corpo   : <p>&lt;img src=x onerror=alert(1)&gt;</p>
[xss] th:utext  corpo   : <p><img src=x onerror=alert(1)></p>
[xss] th:value  atributo: <input value="&quot; onmouseover=&quot;alert(1)">
[xss] th:href   javascript: <a href="javascript:alert(document.cookie)">x</a>
[xss] th:inline js      : <script>var n = "<\/script><script>alert(1)<\/script>";</script>
```
- **`th:text`** escapa (`<` vira `&lt;`): seguro. **`th:utext`** **não** escapa: a tag passa. É por isso que a decisão 23 **proíbe** `th:utext` com dado externo.
- **Atributos** com `th:value`, `th:attr`: as aspas são escapadas (`&quot;`), então o atacante não "sai" do atributo.
- ⚠️ **`th:href` com `javascript:...` NÃO é bloqueado**: o Thymeleaf não sabe que aquele endereço é perigoso. Se um link vier de dado do usuário (um "site pessoal" no perfil), valide o **esquema** (`https://` ou `http://`) no servidor.
- **JavaScript inline** (`th:inline="javascript"` com `[[...]]`) escapa de modo próprio (`<\/script>`). **Mas** a forma `[(...)]` (sem escape) é tão perigosa quanto `th:utext`.

**Escape na saída, não "limpeza" na entrada.** Cada contexto (corpo HTML, atributo, URL, JavaScript, CSS) tem um escape diferente, e só o ponto de **saída** sabe qual é. Por isso o PayFlow guarda o texto **como o usuário digitou** e o escapa **ao exibir** (decisão 23). Se você **precisar** aceitar HTML (um editor de texto rico), use um *sanitizer* de biblioteca (a [OWASP Java HTML Sanitizer](https://owasp.org/www-project-java-html-sanitizer/) é o exemplo), nunca uma regex.

No lado do navegador, o `statement.js` da J4 usa `textContent` (decisão 26): também escapa, pelo mesmo motivo. Em JavaScript, `innerHTML` com texto de terceiros é o equivalente do `th:utext`.

### 3. A segunda camada: CSP e cabeçalhos
Mesmo com todo cuidado, um `th:utext` esquecido acontece. A **CSP** (*Content Security Policy*) é uma **lista do que a página pode carregar e executar**, enviada em um cabeçalho: o navegador **recusa** o resto, inclusive um script injetado. [MDN: CSP](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CSP). Os cabeçalhos **reais** do `/login` do laboratório (`SessionCookieServerTest`):
```text
[cabeçalho] cache-control: no-cache, no-store, max-age=0, must-revalidate
[cabeçalho] content-security-policy: default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; frame-ancestors 'none'; form-action 'self'; base-uri 'self'
[cabeçalho] expires: 0
[cabeçalho] pragma: no-cache
[cabeçalho] referrer-policy: same-origin
[cabeçalho] x-content-type-options: nosniff
[cabeçalho] x-frame-options: DENY
[cabeçalho] x-xss-protection: 0
```
Linha por linha:

| Cabeçalho | O que faz |
|---|---|
| `Content-Security-Policy` | `default-src 'self'`: por padrão, só recursos **do mesmo domínio**. `script-src 'self'`: **só** arquivos `.js` do próprio site (**nada** de `<script>` inline, `onclick=`, `javascript:`). `style-src 'self'`: sem `style=` inline. `img-src 'self' data:`: imagens do site e `data:`. `frame-ancestors 'none'`: **ninguém** pode embutir o PayFlow em um `<iframe>` (*clickjacking*). `form-action 'self'`: formulários só enviam para o próprio site. `base-uri 'self'`: ninguém muda a base de URLs relativas |
| `X-Content-Type-Options: nosniff` | o navegador **não adivinha** o tipo do arquivo: um upload "imagem" com JavaScript dentro não vira script |
| `X-Frame-Options: DENY` | o mesmo do `frame-ancestors`, para navegadores antigos |
| `Referrer-Policy: same-origin` | o endereço da página só vai no cabeçalho `Referer` para o **mesmo** site (URLs não vazam para sites externos) |
| `Cache-Control: no-cache, no-store...` | respostas **não** ficam em cache do navegador ou de intermediários (extrato bancário não pode voltar pelo botão "voltar" depois do logout) |
| `X-XSS-Protection: 0` | **desliga** o antigo "auditor de XSS" dos navegadores, que podia **criar** falhas; é o comportamento padrão do Spring Security ([documentação](https://docs.spring.io/spring-security/reference/servlet/exploits/headers.html)) |

O **`Strict-Transport-Security`** (HSTS: "só fale comigo por HTTPS") **não aparece** na lista acima, que veio de uma requisição **HTTP** do laboratório: o Spring Security o envia por padrão, mas só em requisições HTTPS; você só o verá atrás de HTTPS (J10).

A CSP do PayFlow é possível porque o painel **só tem arquivos em `/static`** (`app.css`, `statement.js`), sem `<script>` nem `style=` inline (conferido por leitura nas aulas J4.04 a J4.08). O `TemplateSafetyTest` abaixo **mantém** isso verdadeiro: se alguém escrever um `onclick=` no futuro, o **teste** acusa, em vez de o navegador ficar "quebrado" só em produção.

### 4. CSRF: o navegador entrega o cookie sozinho
Cenário: a Ana está logada no PayFlow (cookie `PAYFLOW_SESSION`). Em outra aba, ela abre uma página qualquer que contém, escondido:
```html
<form id="f" action="http://localhost:8080/accounts/20000000-0000-0000-0000-000000000001/deposit" method="post">
  <input name="amount" value="1000,00">
</form>
<script>document.getElementById('f').submit()</script>
```
O navegador envia o `POST` para o PayFlow **com o cookie da Ana** (é assim que cookies funcionam: o navegador os anexa a **qualquer** requisição para aquele domínio). O servidor vê uma sessão válida e **executa**. O atacante não leu nada, apenas **forjou uma requisição** (*Cross-Site Request Forgery*). Em um sistema de dinheiro, um depósito é inofensivo; uma **transferência** ou o logout não são.

**Defesa 1: o token CSRF (padrão do Spring Security).** O servidor gera um valor **aleatório por sessão**, o coloca em um campo oculto do **próprio formulário** (`th:action` faz isso, J8.03) e exige que o `POST` o devolva. A página do atacante não consegue **ler** o token (a política de mesma origem do navegador impede), então não consegue forjar um `POST` válido. O Spring guarda o token na sessão (`HttpSessionCsrfTokenRepository`) e o lê do parâmetro `_csrf` ou dos cabeçalhos `X-CSRF-TOKEN`/`X-XSRF-TOKEN` ([documentação](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html)). A cadeia do painel o exige em **todo** método que altera estado (`POST`, `PUT`, `PATCH`, `DELETE`). Provas do laboratório (`WebPanelTest`, `SessionCookieServerTest`):

| Requisição | Resultado |
|---|---|
| `POST /login` **sem** `_csrf` | `403` e a página "Acesso negado" |
| `POST /logout` **sem** `_csrf` (usuário logado) | `403` |
| `POST /logout` **com** `_csrf` | `303` para `/login?logout` |
| `GET /login` | o HTML traz `name="_csrf"` (inserido pelo `th:action`) |

**Defesa 2: `SameSite=Lax` no cookie** (J8.03). O navegador só envia o cookie em requisições **entre sites** quando elas são **navegação de topo e usam método seguro** (`GET`...): um `POST` do formulário do atacante **não leva o cookie** ([MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie)). É uma **segunda** barreira, não a primeira: "site" é domínio registrável, não origem completa (⚠️ `localhost:8080` e `localhost:9000` contam como o **mesmo site**: confira no navegador; para ver o `SameSite` agir em teste manual, use `127.0.0.1` para uma e `localhost` para a outra), e há navegadores e casos (um subdomínio comprometido) em que ele não basta. **Os dois juntos** é o que a OWASP recomenda; a categoria A01:2025 lista até o CWE-1275 ("cookie sensível com `SameSite` impróprio").

**Quando NÃO usar CSRF:** onde **não há credencial automática**. A API `/api/v1/**` autentica por cabeçalho `Authorization: Bearer`, que o navegador **não anexa sozinho**; uma página maliciosa não consegue fazer o navegador mandar esse cabeçalho. Por isso a cadeia da API tem `csrf` **desligado** (J8.03), e a do painel **não**. Desligar o CSRF em uma cadeia que usa **cookie de sessão** é abrir a falha.

**`GET` nunca altera estado.** O CSRF só protege os métodos que mudam coisas porque o contrato HTTP diz que `GET` é **seguro** (J2, J6.01). Um `<img src=".../deposit?amount=100">` faz um `GET` sem pedir permissão a ninguém. Se o seu depósito aceitasse `GET`, nenhum token o salvaria.

## 🛠️ Exemplo prático

### 1. Auditar o PayFlow contra injeção
```bash
# 1. toda construção de consulta que NÃO é parâmetro nomeado ou derivada:
git grep -nE 'createQuery\(|createNativeQuery\(|JdbcTemplate|Statement\b' src/main
# 2. concatenação perto de SQL/JPQL:
git grep -nE '"[^"]*(select|insert|update|delete|where|order by)[^"]*"\s*\+' -i src/main
# 3. ordenação ou filtro que vem do usuário:
git grep -nE 'Sort\.by\(|orderBy|ORDER BY' src/main
```
Resultado **esperado** (não executado; **leitura** das aulas J5.09, J5.10, J6.05): **nenhuma** consulta concatena entrada do usuário; os `@Query` usam `:nome`; a ordenação do extrato é fixa (`created_at`, desempate por `id`, decisão 34/44). Anote em `docs/security-notes.md` o resultado de cada `git grep` **e** a linha que prova cada uma.

Um teste que mostra a falha **só em `src/test`** (decisão 19: código vulnerável nunca em `src/main`), `JpqlInjectionLabTest` (sugestão, **não executado**):
```java
@PayflowTest
class JpqlInjectionLabTest {

    @Autowired EntityManager em;

    @Test
    void concatenatedJpqlLeaksEveryUser() {
        String attack = "' or '1'='1";
        var all = em.createQuery("select u.email from User u where u.email = '" + attack + "'", String.class).getResultList();
        assertThat(all).hasSizeGreaterThan(1);                                     // ❌ vazou todos (o teste existe para MOSTRAR isto)
    }

    @Test
    void namedParameterReturnsNothing() {
        var none = em.createQuery("select u.email from User u where u.email = :email", String.class)
                .setParameter("email", "' or '1'='1").getResultList();
        assertThat(none).isEmpty();                                                // ✅
    }
}
```

### 2. Vigiar os templates
Este teste (executado no laboratório) varre `src/main/resources/templates` e falha se achar saída sem escape ou código inline (que a CSP barraria de qualquer jeito):

`src/test/java/com/payflow/TemplateSafetyTest.java`
```java
package com.payflow;

import static org.assertj.core.api.Assertions.assertThat;

import java.io.IOException;
import java.io.UncheckedIOException;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.List;
import java.util.regex.Pattern;
import java.util.stream.Stream;
import org.junit.jupiter.api.Test;

/** J8.05: vigia os templates. Saída sem escape e código inline também seriam barrados pela CSP (script-src 'self'). */
class TemplateSafetyTest {

    record Rule(String name, Pattern pattern) { }

    static final List<Rule> RULES = List.of(
            new Rule("th:utext (saída SEM escape)", Pattern.compile("th:utext")),
            new Rule("[( ... )] (saída inline SEM escape)", Pattern.compile("\\[\\(")),
            new Rule("javascript: em atributo", Pattern.compile("javascript:", Pattern.CASE_INSENSITIVE)),
            new Rule("manipulador inline (onclick, onerror...)", Pattern.compile("\\son[a-z]+\\s*=", Pattern.CASE_INSENSITIVE)),
            new Rule("<script> inline (sem src)", Pattern.compile("<script(?![^>]*\\bsrc=)[^>]*>", Pattern.CASE_INSENSITIVE)),
            new Rule("atributo style inline", Pattern.compile("\\sstyle\\s*=", Pattern.CASE_INSENSITIVE)));

    static String read(Path p) {
        try {
            return Files.readString(p);
        } catch (IOException e) {
            throw new UncheckedIOException(e);
        }
    }

    @Test
    void noTemplateBreaksTheRules() throws IOException {
        Path dir = Path.of("src/main/resources/templates");
        List<String> offenders;
        try (Stream<Path> files = Files.walk(dir)) {
            offenders = files.filter(p -> p.toString().endsWith(".html"))
                    .flatMap(p -> RULES.stream().filter(r -> r.pattern().matcher(read(p)).find()).map(r -> p.getFileName() + ": " + r.name()))
                    .toList();
        }
        System.out.println("[templates] violações: " + offenders);
        assertThat(offenders).isEmpty();
    }

    @Test
    void theRulesDoCatchBadTemplates() {
        String bad = "<p th:utext=\"${x}\">x</p><p>[(${x})]</p><a href=\"javascript:alert(1)\" onclick=\"f()\" style=\"color:red\">y</a><script>alert(1)</script>";
        List<String> hits = RULES.stream().filter(r -> r.pattern().matcher(bad).find()).map(Rule::name).toList();
        System.out.println("[templates] o template ruim viola " + hits.size() + " de " + RULES.size() + " regras");
        assertThat(hits).hasSize(RULES.size());
        assertThat(RULES.stream().filter(r -> r.pattern().matcher("<script src=\"/static/app.js\" defer></script><p th:text=\"${x}\">x</p>").find())).isEmpty();
    }
}
```
Saída **real**:
```text
[templates] violações: []
[templates] o template ruim viola 6 de 6 regras
```
A segunda linha vem do segundo teste, que **prova que as regras funcionam** (um teste que nunca falhou não prova nada, J7.01): ele alimenta um template propositalmente ruim e confere que **as seis** regras disparam. (Na primeira versão deste teste, a amostra ruim violava só **5** de 6 regras: o próprio teste de teste achou o buraco.) Copie para `src/test/java/com/payflow/web/TemplateSafetyTest.java` (ajuste a linha `package` para `com.payflow.web`).

## 🧠 Pausa para lógica
**Enunciado:** um atacante publica em um fórum `<img src="http://localhost:8080/accounts/ID/deposit?amount=100">`. O `POST /accounts/{id}/deposit` do PayFlow só aceita `POST`. A Ana, logada, abre o fórum. O depósito acontece? E se o PayFlow tivesse, por conveniência, um `@GetMapping("/accounts/{id}/deposit")`?

<details><summary>Dica</summary>

Qual método HTTP uma tag `<img>` usa? O que o token CSRF protege?
</details>

<details><summary>Solução</summary>

Não acontece: a tag `<img>` faz um **`GET`**, e o endpoint só existe para `POST` (a resposta é `405`, J5.06). Com um `@GetMapping` de depósito, **aconteceria**, e **nenhum token CSRF ajudaria**: o filtro de CSRF só confere métodos que alteram estado (`POST`, `PUT`...) porque assume que `GET` é seguro. A regra: **`GET` jamais altera estado.**
</details>

## ⚖️ Trade-offs e quando NÃO usar
- **CSP estrita × conveniência.** Sem `'unsafe-inline'`, você escreve JavaScript e CSS em arquivos (o PayFlow já faz). O ganho é grande: um XSS esquecido deixa de executar. O custo aparece com bibliotecas que injetam estilo inline.
- **Token CSRF × só `SameSite`.** `SameSite=Lax` sozinho é frágil (navegadores antigos, subdomínios, regras de "mesmo site"). O token sozinho é robusto, mas um erro de implementação (esquecer `th:action`) o desliga. **Os dois**.
- **Validar a entrada × escapar a saída.** Validação reduz a superfície (tamanho, formato), mas não substitui o escape: o mesmo texto vai para HTML, URL, JSON e log, cada um com seu escape.
- **CSRF na API.** Desligar é correto **se** a autenticação for por cabeçalho. Se um dia a API aceitar o **cookie** da sessão, o CSRF precisa voltar.
- **Consultas dinâmicas.** Filtros opcionais (J6.05) pedem `Specification` (que usa parâmetros por baixo) em vez de montar texto: um pouco mais de código, **nenhuma** concatenação. "É mais fácil concatenar" não é um trade-off, é o começo da falha.

## ⚠️ Erros comuns e boas práticas de produção
- **`th:utext`, `[(...)]` e `innerHTML` com dado de terceiros.** O `TemplateSafetyTest` barra os dois primeiros.
- **`th:href`/`href` com URL do usuário** sem validar o esquema: `javascript:` passa.
- **`'unsafe-inline'` na CSP** "para o site voltar a funcionar": desfaz a defesa. Mova o código para arquivo.
- **Formulário do painel com `action=` em vez de `th:action=`:** o token não entra e todo `POST` responde `403` (a causa mais comum de "o depósito parou de funcionar").
- **`csrf` desligado em uma cadeia com cookie de sessão** "porque atrapalha os testes": nos testes use `csrf()` (`SecurityMockMvcRequestPostProcessors`) ou pegue o token da página (J8.03).
- **`ignoringRequestMatchers` generoso** ("exceto `/api/**`" quando há rotas do painel sob `/api/`): confira a lista com um teste.
- **`ORDER BY` ou nome de tabela vindo do usuário** sem lista permitida.
- **Confiar no front-end:** a validação do navegador (`required`, `pattern`) é conforto; o servidor valida de novo (decisão 25).
- **Mensagens de erro com detalhes do SQL** na resposta: o atacante lê o esquema. O PayFlow responde Problem Details genérico (J6.04) e loga o detalhe.
- **Cookie sem `HttpOnly`**: um XSS leva a sessão. O PayFlow já tem (J8.03).

## 🎤 Na entrevista
1. **"Como você previne SQL injection?"** *Resposta-modelo:* parâmetros em **toda** consulta com dado externo (`PreparedStatement`, JPQL com `:nome`, métodos derivados do Spring Data); lista permitida para identificadores (coluna de `ORDER BY`); menor privilégio no usuário do banco; validação como camada extra. Nunca concatenar. O ORM só protege se eu usar parâmetros: JPQL ou `nativeQuery` concatenados são injeção do mesmo jeito.
2. **"O que é XSS e como o Thymeleaf ajuda?"** *Resposta-modelo:* é o navegador executar texto de terceiros como script no meu domínio (armazenado, refletido ou DOM). O Thymeleaf escapa por padrão em `th:text`; `th:utext` e `[(...)]` não escapam. Defesa em profundidade: CSP sem inline, cookie `HttpOnly`, validação do esquema de URLs. Escapo **na saída**, no contexto certo.
3. **"O que é CSRF e como o Spring Security o previne?"** *Resposta-modelo:* o atacante faz o navegador da vítima, logada, enviar uma requisição que altera estado, aproveitando que o navegador anexa o cookie sozinho. O Spring exige um token por sessão em todo método não seguro (campo oculto `_csrf`, que o `th:action` insere); o `SameSite=Lax` do cookie é a segunda barreira. Em API com Bearer, que não usa cookie, desligo o CSRF.
4. **"Para que serve a CSP?"** *Resposta-modelo:* é uma lista, em um cabeçalho, do que a página pode carregar e executar. Com `script-src 'self'`, um script injetado por XSS não roda. Introduzo com `Report-Only` e evito `'unsafe-inline'`.
