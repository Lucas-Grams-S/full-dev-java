# J1.12 — Generics

> ⏱️ ~1h30 · 🟢 Júnior · Pré-requisitos: J1.07, J1.10, J1.11

## 🎯 Objetivos
Ao final desta aula você consegue:
- Explicar por que `List<String>` é mais seguro que `List` (sem tipo).
- Escrever uma classe e um método genéricos (`<T>`), com limites (`<T extends Comparable<T>>`).
- Usar *wildcards* (`? extends`, `? super`) e entender a regra PECS.
- Explicar o *type erasure* e suas consequências.
- Ler assinaturas genéricas da API (e dos frameworks).

## 🤔 Por que isso importa
Quase toda API que você usará é genérica: `List<Account>`, `Optional<User>`, `Repository<T, ID>` (Spring Data, J5), `ResponseEntity<T>`. Ler `JpaRepository<Account, UUID>` sem entender `<T, ID>` é ler com o dicionário fechado.

## 💡 Intuição (explicação simples)
Genérico é uma **caixa com etiqueta**: "caixa **de** maçãs". A caixa é a mesma para qualquer fruta, mas a etiqueta impede que alguém guarde um tijolo e faz quem abre saber o que vai achar. Sem etiqueta (tipo cru), tudo é "coisa" e o erro só aparece ao morder.

## 🔬 Como funciona por dentro
- `class Pair<A, B>` declara **parâmetros de tipo**; no uso, `Pair<String, Integer>` os preenche.
- O compilador confere os tipos e insere os *casts* sozinho. Em execução o tipo **é apagado** (*type erasure*): `List<String>` e `List<Integer>` são a mesma classe `List` para a JVM. Consequências: não se faz `new T()`, nem `instanceof List<String>`, nem arrays genéricos.
- **Limite superior:** `<T extends Comparable<T>>` exige que `T` saiba se comparar.
- **Wildcards e PECS (*Producer Extends, Consumer Super*):**
  - `List<? extends Number>`: **lê** `Number`s (produtor), não adiciona.
  - `List<? super Integer>`: **escreve** `Integer`s (consumidor), lê só como `Object`.
- Genéricos são **invariantes**: `List<Integer>` **não** é um `List<Number>`.

## 🛠️ Exemplo prático
> Testado com JDK 25 (o trecho com tipo cru gera *warnings* de compilação, de propósito).

```java
import java.util.*;

public class Genericos {
    record Pair<A, B>(A first, B second) {}                                  // classe genérica (record, J1.14)

    static <T extends Comparable<T>> T max(List<T> l) {                       // método genérico com limite
        T m = l.get(0);
        for (T t : l) if (t.compareTo(m) > 0) m = t;
        return m;
    }
    static double total(List<? extends Number> l) {                           // produtor
        double s = 0; for (Number n : l) s += n.doubleValue(); return s;
    }
    static void fill(List<? super Integer> l) { l.add(1); }                   // consumidor

    interface Repo<T, ID> { void save(T t); Optional<T> findById(ID id); }    // como no Spring Data

    public static void main(String[] args) {
        System.out.println(new Pair<>("a", 1) + " " + max(List.of(3, 9, 2)) + " " + max(List.of("b", "z")));
        System.out.println(total(List.of(1, 2.5)));
        List<Object> lo = new ArrayList<>(); fill(lo); System.out.println(lo);

        List raw = new ArrayList<String>(); raw.add(1);                       // tipo cru: o compilador avisa
        List<String> ls = raw;
        try { String s = ls.get(0); } catch (ClassCastException e) { System.out.println("CCE heap pollution"); }
    }
}
```
Saída real:
```
Pair[first=a, second=1] 9 z
3.5
[1]
CCE heap pollution
```
Com `javac` ou `java Genericos.java` aparecem avisos `[unchecked] unchecked call to add(E) as a member of the raw type List`. Eles apontam exatamente o risco: o `1` entrou numa lista que "diz" ser de `String`, e o erro só estoura **longe**, ao ler (*heap pollution*). Por isso: **nunca use tipos crus**.

`max(List<T>)` funciona com `Integer` e `String` porque ambos implementam `Comparable`. Com `max(List.of(new Object()))` o compilador recusa.

## 🧠 Pausa para lógica
**Enunciado:** escreva `static <T> void swap(T[] a, int i, int j)` e use-o para inverter um `String[]`. Como inverter in-place com dois índices?

<details><summary>Dica</summary>Troque `a[i]` e `a[j]` com uma variável temporária e caminhe `i++`, `j--` até se cruzarem.</details>
<details><summary>Solução</summary>

```java
static <T> void swap(T[] a, int i, int j) { T t = a[i]; a[i] = a[j]; a[j] = t; }
static <T> void reverse(T[] a) { for (int i = 0, j = a.length - 1; i < j; i++, j--) swap(a, i, j); }
```
</details>

**Variação:** por que `static <T> void swap(List<T> l, ...)` também funciona e há `Collections.swap`?

## ⚠️ Erros comuns e boas práticas de produção
- **Tipos crus** (`List`): perdem a checagem; use sempre `List<X>`.
- **Tentar `List<Number> l = new ArrayList<Integer>();`** → erro: `incompatible types: ArrayList<Integer> cannot be converted to List<Number>` (invariância).
- **`new T[]` / `new T()`**: não compila por causa do *erasure*.
- **Complicar demais:** assinaturas com vários *wildcards* ilegíveis. Se ninguém entende, simplifique.
- **Esquecer o diamante** `<>`: `new ArrayList<>()` deixa o compilador inferir.
- Mensagem comum: `incompatible types: inference variable T has incompatible bounds`; leia as *lower/upper bounds* para entender o conflito.

<details><summary>Solução de referência (desafio)</summary>

```java
static <T extends Comparable<T>> List<T> top(List<T> l, int n) {
    List<T> copy = new ArrayList<>(l);
    copy.sort(Comparator.reverseOrder());
    return copy.subList(0, Math.min(n, copy.size()));
}
```
</details>

## 🎤 Na entrevista
- **O que é *type erasure*?** O compilador confere os tipos genéricos e os apaga; em execução, só resta o tipo cru. Por isso não existe `instanceof List<String>`.
- **`List<Object>` é super-tipo de `List<String>`?** Não: genéricos são invariantes; use `List<? extends Object>`.
- **O que é PECS?** *Producer Extends, Consumer Super*: `extends` para ler, `super` para escrever.
