# J6.06 — Versionamento e idempotência

> ⏱️ ~1h30 · 🟢 Júnior · Pré-requisitos: J6.01 (idempotência de métodos), J6.03 (`submit`), J3.10/J3.12 (constraints, `UNIQUE`), J6.04

## 🎯 Objetivos
Ao final desta aula você consegue:
- Comparar as estratégias de **versionamento** (caminho, cabeçalho, parâmetro, tipo de mídia) e configurar o versionamento **nativo do Spring Framework 7**.
- Sinalizar uma versão **obsoleta** com `Deprecation` e `Sunset`.
- Implementar **idempotência** de `POST /transfers` com `Idempotency-Key`: repetição, reuso com corpo diferente e **corrida** entre requisições simultâneas.
- Explicar por que a verificação "existe? então devolva" **sozinha** não basta.

## 🤔 Por que isso importa
Clientes que você não controla demoram meses para atualizar: mudar o contrato sem versão **quebra** quem já integrou. E redes falham: sem idempotência, um *timeout* seguido de repetição pode **transferir duas vezes**.

## 💡 Intuição (explicação simples)
**Versão:** edições de um manual — quem tem a 1ª continua lendo a 1ª enquanto a 2ª circula. **Idempotência:** o **número do protocolo** num guichê: se você volta e diz o número, o atendente não abre outro chamado, mostra o que já abriu.

## 🔬 Como funciona por dentro
### Versionamento
| Estratégia | Exemplo | Prós | Contras |
|---|---|---|---|
| Caminho | `/api/v1/accounts` | visível, fácil de testar e cachear | URI muda |
| Cabeçalho | `X-API-Version: 1` | URI estável | invisível, difícil no navegador |
| Parâmetro | `?version=1` | simples | mistura com filtros |
| Tipo de mídia | `Accept: application/vnd...;version=1` | purista | complexo |

Escolha do PayFlow: **caminho** (decisão), por legibilidade. **Mudança compatível** (campo novo opcional) **não** exige versão nova; **quebra** (renomear/remover, mudar tipo) sim. O Spring Framework 7 tem suporte nativo: `ApiVersionConfigurer` (em `WebMvcConfigurer.configureApiVersioning`) e o atributo `version` em `@RequestMapping`; versões não suportadas são recusadas e há `StandardApiVersionDeprecationHandler` para `Deprecation`/`Sunset`/`Link` ([documentação](https://docs.spring.io/spring-framework/reference/web/webmvc-versioning.html)).

**Armadilha real (testada):** `configurer.usePathSegment(1)` vale para **todas** as requisições; páginas como `/accounts` não têm o 2º segmento e passam a responder **500** (`Invalid API version: 'No path segment at index 1'`). A variante com predicado (`usePathSegment(int, Predicate<RequestPath>)`) aplica só ao que interessa:
```java
    private static final Pattern VERSIONED_PATH = Pattern.compile("^/api/v(\\d+)/");
```

```java
    @Override
    public void configureApiVersioning(ApiVersionConfigurer configurer) {
        configurer.usePathSegment(1, path -> VERSIONED_PATH.matcher(path.value()).find())
                .addSupportedVersions("v1").setVersionRequired(false);
    }
```

O mapeamento usa `version = "v1"` (o analisador aceita o prefixo `v`):
```java
@RequestMapping(path = "/api/v1/accounts", version = "v1", produces = "application/json")
```
(Com `version = "1"` e o segmento `v1`, o springdoc da J6.07 publicou `/api/1/...`: use o **mesmo** texto nos dois lados.) O endpoint **legado** do painel (`/api/accounts/{id}/statement`) fica **sem versão**: o `statement.js` é contrato estável (decisão 22).

Saídas reais do `VersioningApiTest` (v2 de mentira só no teste, v1 marcada obsoleta):
```text

  deprecation=[@1793491200]
  link=[<https://docs.payflow.example/migrate-v2>; rel="deprecation"; type="text/html"]
  sunset=[Sat, 1 May 2027 00:00:00 GMT]
V2 (rota de laboratório): 200 {"hello":"v2"}  (sem Deprecation)
V9 (versão sem mapeamento): 404 application/problem+json {"detail":"No endpoint GET /api/v9/accounts.", ...}
```

### Idempotência
Já vimos o que é e o `submit` (J6.03). Aqui o que falta:
1. **Formato:** o rascunho do IETF (Internet-Draft `draft-ietf-httpapi-idempotency-key-header`, versão 08, ainda **rascunho**) define o valor como *string* entre aspas (`"abc"`). Aceitamos com ou sem aspas, máximo 63 caracteres:
```java
package com.payflow.web.api;

/**
 * Valida a Idempotency-Key. O rascunho do IETF define o valor como string entre aspas ("abc"); aceitamos
 * com ou sem aspas e guardamos sem. Limite de 63 caracteres: a coluna tem 100 e a chave leva o id do usuário (37).
 */
final class IdempotencyKeys {

    private IdempotencyKeys() { }

    static String normalize(String raw) {
        String key = raw.trim();
        if (key.length() >= 2 && key.startsWith("\"") && key.endsWith("\"")) {
            key = key.substring(1, key.length() - 1);
        }
        if (key.isBlank() || key.length() > 63) {
            throw new BadRequestException("Idempotency-Key must have 1 to 63 characters");
        }
        return key;
    }
}
```
2. **Chave ausente → 400; mesma chave com corpo diferente → 422**, segundo o rascunho. Nossos testes cobrem os dois.
3. **Repetição → `200`** com a mesma transferência (a primeira vez é `201`): decisão nossa, para o cliente distinguir; outros provedores repetem o `201`.
4. **Escopo por usuário:** a chave é gravada como `userId:chave` (sem migração; a coluna é `UNIQUE` global).
5. **A corrida.** Duas requisições simultâneas com a mesma chave: ambas veem "não existe" e executam; a segunda falha **no commit** (`UNIQUE`). Esse erro sai do proxy transacional, depois do método. O `TransferSubmitter`, **fora** da transação, captura e relê:
```java
package com.payflow.service;

import java.math.BigDecimal;
import java.util.UUID;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.dao.DataIntegrityViolationException;
import org.springframework.stereotype.Service;

/**
 * Fica FORA da transação de propósito: se duas requisições com a mesma chave correm juntas, a perdedora
 * falha no commit (chave única); aqui, já sem transação, a gente busca a transferência vencedora e a devolve.
 */
@Service
public class TransferSubmitter {

    private static final Logger log = LoggerFactory.getLogger(TransferSubmitter.class);

    private final TransferService transfers;

    public TransferSubmitter(TransferService transfers) {
        this.transfers = transfers;
    }

    public TransferOutcome submit(UUID requesterId, UUID sourceId, UUID targetId, BigDecimal amount, String clientKey) {
        try {
            return transfers.submit(requesterId, sourceId, targetId, amount, clientKey);
        } catch (DataIntegrityViolationException e) {
            // Perdeu a corrida pela chave única: a outra requisição já gravou. Agora é só uma repetição: devolva-a.
            log.info("Lost the race on the idempotency key; returning the stored transfer");
            return transfers.submit(requesterId, sourceId, targetId, amount, clientKey);
        }
    }
}
```

Medido com 8 requisições simultâneas e a mesma chave (`concurrentRequestsWithTheSameKeyTransferOnlyOnce`):
```text
SEM o TransferSubmitter (8 requisições, mesma chave):  [500, 500, 500, 500, 500, 201, 500, 500]   saldo = 820.00
COM o TransferSubmitter:                               [201, 200, 200, 200, 200, 200, 200, 200]   saldo = 820.00   (5 execuções, a ordem varia)
(nos logs: 7 "Lost the race on the idempotency key" por execução e "duplicate key value violates unique constraint")
```
Sem o submitter, 7 das 8 viram **500** (o saldo continua certo graças ao `UNIQUE`, a rede de segurança do banco). Com ele: um `201` e sete `200`.

## 🧠 Pausa para lógica
**Enunciado:** 8 threads, mesma chave; o efeito colateral (a cobrança) só pode ocorrer **uma** vez. Compare "verifica e depois age" com `computeIfAbsent`.
<details><summary>Solução (testada, JDK 25.0.5)</summary>

```java
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.Executors;
import java.util.concurrent.atomic.AtomicInteger;

/** "Efeito exatamente uma vez": 8 threads com a MESMA chave; o efeito colateral só pode acontecer uma vez. */
public class IdempotentOnce {

    static final AtomicInteger charges = new AtomicInteger();
    static final ConcurrentHashMap<String, String> results = new ConcurrentHashMap<>();

    static String charge(String key) {
        // computeIfAbsent é atômico por chave: só UMA thread executa a lambda; as outras esperam e recebem o mesmo resultado
        return results.computeIfAbsent(key, k -> "charge-" + charges.incrementAndGet());
    }

    static String chargeBroken(String key) {
        String existing = results.get(key);                // "verifica e depois age": a janela entre as duas linhas é a corrida
        if (existing != null) return existing;
        String created = "charge-" + charges.incrementAndGet();
        results.put(key, created);
        return created;
    }

    static int run(java.util.function.Function<String, String> f) throws Exception {
        charges.set(0);
        results.clear();
        var pool = Executors.newFixedThreadPool(8);
        var start = new CountDownLatch(1);
        for (int i = 0; i < 8; i++) {
            pool.submit(() -> { start.await(); return f.apply("key-1"); });
        }
        start.countDown();
        pool.shutdown();
        pool.awaitTermination(5, java.util.concurrent.TimeUnit.SECONDS);
        return charges.get();
    }

    public static void main(String[] args) throws Exception {
        int broken = 0;
        for (int i = 0; i < 200 && broken <= 1; i++) broken = run(IdempotentOnce::chargeBroken);
        System.out.println("verifica-e-depois-age: cobranças = " + broken + " (esperado 1)");
        int worst = 0;
        for (int i = 0; i < 200; i++) worst = Math.max(worst, run(IdempotentOnce::charge));
        System.out.println("computeIfAbsent: maior número de cobranças em 200 rodadas = " + worst);
    }
}
```

Saída:
```text
verifica-e-depois-age: cobranças = 6 (esperado 1)
computeIfAbsent: maior número de cobranças em 200 rodadas = 1
```

Verificar-e-agir deixa uma **janela** entre as duas linhas; `computeIfAbsent` é atômico por chave. No PayFlow, o papel da atomicidade é do **`UNIQUE` do banco**, que vale entre processos e servidores.
</details>

## ⚖️ Trade-offs e quando NÃO usar
Versionar cedo demais multiplica código; versione quando quebrar. Guardar a chave **para sempre** cresce a tabela: em produção, chaves expiram (P2/P3). O escopo `userId:chave` evita colisão, mas limita a chave a 63 caracteres.

## ⚠️ Erros comuns e boas práticas de produção
- Versionar por modismo; remover versão sem `Sunset`.
- `usePathSegment` global.
- Idempotência só com "SELECT depois INSERT".
- Chave gerada **no servidor** (inútil: o cliente precisa repeti-la).
- Aceitar a mesma chave com corpo diferente em silêncio.

## 🎤 Na entrevista
- **Como versionar uma API?** Caminho, cabeçalho, parâmetro ou tipo de mídia; só quebras exigem versão; sinalize obsolescência (`Deprecation`, `Sunset`).
- **Como tornar `POST` seguro para repetir?** Chave de idempotência do cliente + armazenamento do resultado + restrição única.
- **E se duas chamadas iguais chegam juntas?** Alguém precisa decidir atomicamente: constraint `UNIQUE` (ou lock); a perdedora relê e devolve o resultado.
