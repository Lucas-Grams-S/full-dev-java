# J6.04 — Tratamento global de erros e Problem Details (RFC 9457)

> ⏱️ ~1h30 · 🟢 Júnior · Pré-requisitos: J5.06 (`@ControllerAdvice`), J5.13 (Bean Validation), J5.14 (logs de erro de negócio × inesperado), J6.01 a J6.03

## 🎯 Objetivos
Ao final desta aula você consegue:
- Explicar o formato **Problem Details** (RFC 9457) e o media type `application/problem+json`.
- Centralizar o tratamento de erros da API em um `@RestControllerAdvice` que **estende** `ResponseEntityExceptionHandler`.
- Mapear cada exceção de negócio para status, `type`, `title` e `detail` **estáveis**, sem vazar detalhes internos.
- Fazer a API responder Problem Details **também** quando não há controller (rota inexistente, método errado, sessão ausente), sem quebrar as páginas HTML do painel.

## 🤔 Por que isso importa
Sem padrão, cada endpoint inventa o seu erro: `{"error":"..."}`, `{"message":...}`, uma página HTML. O cliente precisa de um `if` por endpoint. Pior: o texto da exceção (`could not execute statement ... constraint [uk_transfers_idempotency_key]`) vaza o seu esquema. Um formato único, com um **identificador de tipo estável** (`type`), deixa o cliente decidir por código, não por texto.

## 💡 Intuição (explicação simples)
É o **formulário de ocorrência** de uma empresa: campos fixos (tipo do problema, título, descrição, onde aconteceu) e um espaço para observações extras. Quem lê sabe onde olhar sem aprender um formulário novo a cada departamento.

## 🔬 Como funciona por dentro
Segundo a [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html), o corpo tem membros **opcionais**: `type` (URI que identifica o *tipo*; padrão `about:blank`), `status`, `title` (resumo do tipo), `detail` (explicação **desta** ocorrência) e `instance` (URI desta ocorrência); extensões livres são permitidas. O media type é `application/problem+json`. A RFC adverte: **não exponha internals** (stack traces etc.).

No Spring: `ProblemDetail` (o contêiner), `ErrorResponse`, `ResponseEntityExceptionHandler` (um `@ControllerAdvice` base que já traduz as exceções do Spring MVC: 400, 404, 405, 415...). O Spring escreve `instance` com o caminho da requisição e o Jackson usa `application/problem+json`.

**Duas armadilhas deste projeto** (descobertas ao testar):
1. **O `WebErrors` do painel (J5.06) é global** e devolve HTML. Para rotas **sem controller** (404 de rota, 405) um advice com seletor (`basePackages`) **não se aplica**. Solução: o `ApiProblems` renderiza o Problem Details à mão para caminhos `/api/`, chamado pelo `WebErrors`.
2. O `ApiErrors` precisa de `@Order(HIGHEST_PRECEDENCE)` para ser consultado antes do `WebErrors`.

`type`: usamos URNs (`urn:payflow:problem:insufficient-funds`): URIs válidas que não fingem ser um site. O cliente testa o `type`, não o `title`.

## 🛠️ Exemplo prático
`ApiErrors` final (a parte do `RestClient` é da J6.08):
```java
package com.payflow.web.api;

import com.payflow.client.ExchangeRateUnavailableException;
import com.payflow.client.UnsupportedCurrencyException;
import com.payflow.domain.AccountUnavailableException;
import com.payflow.domain.IdempotencyKeyReuseException;
import com.payflow.domain.InsufficientFundsException;
import com.payflow.domain.InvalidTransferException;
import com.payflow.domain.NotFoundException;
import java.net.URI;
import java.util.Map;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.core.Ordered;
import org.springframework.core.annotation.Order;
import org.springframework.http.HttpHeaders;
import org.springframework.http.HttpStatus;
import org.springframework.http.HttpStatusCode;
import org.springframework.http.ResponseEntity;
import org.springframework.http.ProblemDetail;
import org.springframework.orm.ObjectOptimisticLockingFailureException;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.context.request.WebRequest;
import org.springframework.web.bind.annotation.RestControllerAdvice;
import org.springframework.web.method.annotation.MethodArgumentTypeMismatchException;
import org.springframework.web.servlet.mvc.method.annotation.ResponseEntityExceptionHandler;

/**
 * Erros da API REST como Problem Details (RFC 9457, application/problem+json).
 * Estende a base do Spring, que já trata as exceções do próprio Spring MVC (400, 404, 405, 415, ...).
 */
@RestControllerAdvice(basePackages = "com.payflow.web.api")
@Order(Ordered.HIGHEST_PRECEDENCE)
public class ApiErrors extends ResponseEntityExceptionHandler {

    private static final Logger log = LoggerFactory.getLogger(ApiErrors.class);
    static final String TYPE_PREFIX = "urn:payflow:problem:";

    /** Bean Validation falhou no corpo: devolve QUAIS campos e por quê (extensão "errors" do Problem Details). */
    @Override
    protected ResponseEntity<Object> handleMethodArgumentNotValid(MethodArgumentNotValidException ex,
            HttpHeaders headers, HttpStatusCode status, WebRequest request) {
        ProblemDetail pd = problem(HttpStatus.BAD_REQUEST, "validation-failed", "Validation failed",
                "One or more fields are invalid.");
        pd.setProperty("errors", ex.getBindingResult().getFieldErrors().stream()
                .map(f -> Map.of("field", f.getField(), "message", String.valueOf(f.getDefaultMessage())))
                .toList());
        return handleExceptionInternal(ex, pd, headers, status, request);
    }

    @ExceptionHandler(NotFoundException.class)
    ProblemDetail notFound(NotFoundException e) {
        return problem(HttpStatus.NOT_FOUND, "not-found", "Resource not found", e.getMessage());
    }

    @ExceptionHandler(InsufficientFundsException.class)
    ProblemDetail insufficientFunds(InsufficientFundsException e) {
        log.warn("Business rule refused the request: insufficient funds");        // negócio esperado: WARN, sem stack
        return problem(HttpStatus.UNPROCESSABLE_ENTITY, "insufficient-funds", "Insufficient funds",
                "The source account does not have enough balance for this transfer.");
    }

    @ExceptionHandler(AccountUnavailableException.class)
    ProblemDetail accountUnavailable(AccountUnavailableException e) {
        log.warn("Business rule refused the request: {}", e.getMessage());
        return problem(HttpStatus.UNPROCESSABLE_ENTITY, "account-unavailable", "Account unavailable",
                "One of the accounts does not exist or cannot receive or send money now.");
    }

    @ExceptionHandler(InvalidTransferException.class)
    ProblemDetail invalidTransfer(InvalidTransferException e) {
        return problem(HttpStatus.UNPROCESSABLE_ENTITY, "invalid-transfer", "Invalid transfer", e.getMessage());
    }

    @ExceptionHandler(IdempotencyKeyReuseException.class)
    ProblemDetail keyReuse(IdempotencyKeyReuseException e) {
        return problem(HttpStatus.UNPROCESSABLE_ENTITY, "idempotency-key-reused", "Idempotency-Key reused", e.getMessage());
    }

    @ExceptionHandler(ObjectOptimisticLockingFailureException.class)
    ProblemDetail concurrentUpdate(ObjectOptimisticLockingFailureException e) {
        log.warn("Concurrent update detected on {}", e.getPersistentClassName());
        return problem(HttpStatus.CONFLICT, "concurrent-update", "Concurrent update",
                "The account was changed by another request at the same time. Try again.");
    }

    /** ?size=abc, ?type=XYZ: o cliente mandou um valor que não converte (400). Já {id} que não é UUID = recurso inexistente (404). */
    @ExceptionHandler(MethodArgumentTypeMismatchException.class)
    ProblemDetail typeMismatch(MethodArgumentTypeMismatchException e) {
        if (e.getParameter().hasParameterAnnotation(PathVariable.class)) {       // /accounts/abc: esse recurso não existe (404)
            return problem(HttpStatus.NOT_FOUND, "not-found", "Resource not found", "No resource at this address.");
        }
        return problem(HttpStatus.BAD_REQUEST, "invalid-parameter", "Invalid parameter",
                "The parameter '" + e.getName() + "' has an invalid value.");
    }

    /** API externa lenta = 504 Gateway Timeout; API externa quebrada ou resposta inválida = 502 Bad Gateway. */
    @ExceptionHandler(ExchangeRateUnavailableException.class)
    ProblemDetail upstream(ExchangeRateUnavailableException e) {
        return e.isTimeout()
                ? problem(HttpStatus.GATEWAY_TIMEOUT, "upstream-timeout", "Upstream timeout",
                        "The exchange-rate service took too long to answer. Try again later.")
                : problem(HttpStatus.BAD_GATEWAY, "upstream-failure", "Upstream failure",
                        "The exchange-rate service is not working properly. Try again later.");
    }

    @ExceptionHandler(UnsupportedCurrencyException.class)
    ProblemDetail unsupportedCurrency(UnsupportedCurrencyException e) {
        return problem(HttpStatus.UNPROCESSABLE_ENTITY, "unsupported-currency", "Unsupported currency", e.getMessage());
    }

    @ExceptionHandler(BadRequestException.class)
    ProblemDetail badRequest(BadRequestException e) {
        return problem(HttpStatus.BAD_REQUEST, "invalid-request", "Invalid request", e.getMessage());
    }

    /** Rede de segurança: nada de stack trace nem mensagem interna na resposta (RFC 9457, seção de segurança). */
    @ExceptionHandler(Exception.class)
    ProblemDetail unexpected(Exception e) {
        log.error("Unexpected error in the API", e);
        return problem(HttpStatus.INTERNAL_SERVER_ERROR, "internal-error", "Internal error",
                "Something went wrong. Try again later.");
    }

    static ProblemDetail problem(HttpStatus status, String code, String title, String detail) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(status, detail);
        pd.setType(URI.create(TYPE_PREFIX + code));
        pd.setTitle(title);
        return pd;
    }
}
```

`ApiProblems`, para quando não há controller:
```java
package com.payflow.web.api;

import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import java.io.IOException;
import java.nio.charset.StandardCharsets;
import org.springframework.http.HttpStatus;
import org.springframework.http.MediaType;
import org.springframework.http.ProblemDetail;
import org.springframework.http.ResponseEntity;
import org.springframework.stereotype.Component;
import org.springframework.web.context.request.ServletWebRequest;
import tools.jackson.databind.json.JsonMapper;

/**
 * Escreve Problem Details quando NÃO há controller para a requisição (rota inexistente, método errado,
 * sessão ausente): aí os @RestControllerAdvice com seletor não valem, então escrevemos à mão.
 */
@Component
public class ApiProblems {

    private final ApiErrors errors;
    private final JsonMapper mapper;

    public ApiProblems(ApiErrors errors, JsonMapper mapper) {
        this.errors = errors;
        this.mapper = mapper;
    }

    public static boolean isApi(HttpServletRequest request) {
        return request.getRequestURI().startsWith("/api/");
    }

    /** Uma exceção do Spring MVC (404, 405...) vira a resposta padrão do Spring, escrita na resposta. */
    @SuppressWarnings("unchecked")
    public void render(Exception e, HttpServletRequest request, HttpServletResponse response) {
        try {
            ResponseEntity<Object> entity = errors.handleException(e, new ServletWebRequest(request, response));
            if (entity.getBody() instanceof ProblemDetail pd && pd.getInstance() == null) {
                pd.setInstance(java.net.URI.create(request.getRequestURI()));       // quem ocorreu: o caminho da requisição
            }
            response.setStatus(entity.getStatusCode().value());
            entity.getHeaders().forEach((name, values) -> values.forEach(v -> response.addHeader(name, v)));
            write(response, entity.getBody());
        } catch (Exception ex) {
            throw new IllegalStateException(ex);
        }
    }

    public void write(HttpServletResponse response, HttpStatus status, String code, String title, String detail) {
        response.setStatus(status.value());
        write(response, ApiErrors.problem(status, code, title, detail));
    }

    private void write(HttpServletResponse response, Object body) {
        try {
            response.setContentType(MediaType.APPLICATION_PROBLEM_JSON_VALUE);
            response.setCharacterEncoding(StandardCharsets.UTF_8.name());
            response.getWriter().write(mapper.writeValueAsString(body));
        } catch (IOException e) {
            throw new IllegalStateException(e);
        }
    }
}
```

## 🧠 Pausa para lógica
**Enunciado:** por que o `catch-all` (`Exception.class`) devolve sempre a mesma mensagem genérica e loga a causa? Escreva a tabela exceção → status que o `ApiErrors` implementa e diga qual exceção **não** deveria ser capturada por um `catch-all` (dica: as do Spring MVC).
<details><summary>Solução</summary>A exceção real pode conter dados internos; logar no servidor com o `requestId` (J5.14) permite investigar sem expor. A tabela é a da seção 3 da J6.03 mais: `BadRequestException` → 400, `NotFoundException` → 404, `UnsupportedCurrencyException` → 422, `ExchangeRateUnavailableException` → 502/504. As exceções do Spring MVC já têm tratamento específico na classe-base (400/404/405/415); o `catch-all` só vale para o **inesperado** (500).</details>

## ⚠️ Erros comuns e boas práticas de produção
- Devolver `e.getMessage()` no `detail` de erros inesperados: vaza internals.
- `@ExceptionHandler(Exception.class)` sem `@Order`/seletor: engole erros das páginas.
- Mudar o `type` depois de publicado: é contrato.
- Mensagem diferente para conta inexistente e conta alheia (enumeração).
- Esquecer de logar o 500 (só o inesperado, uma vez, na borda; negócio esperado = `WARN` sem stack, decisão 38).

## 🎤 Na entrevista
- **O que é Problem Details?** Formato padrão (RFC 9457) para erros HTTP: `type`, `title`, `status`, `detail`, `instance` + extensões.
- **Como o Spring ajuda?** `ProblemDetail`, `ErrorResponse` e `ResponseEntityExceptionHandler`.
- **Por que um `type` estável?** O cliente decide por ele; texto muda.
