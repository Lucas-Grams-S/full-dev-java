# J6.05 — Paginação, filtros e ordenação

> ⏱️ ~1h30 · 🟢 Júnior · Pré-requisitos: J3.05 (`ORDER BY`, `LIMIT`/`OFFSET`), J5.10 (`Pageable`, `Slice` × `Page`), J6.01 a J6.04

## 🎯 Objetivos
Ao final desta aula você consegue:
- Desenhar os parâmetros de uma listagem (`page`, `size`, filtros, ordem) com **limites** e validação.
- Decidir **`Slice` × `Page`** para uma API (pendência deixada pela J5.10).
- Montar filtros **opcionais** com `Specification` (e entender por que `(:p is null or ...)` quebra no PostgreSQL).
- Usar intervalos **semiabertos** `[from, to)` e ordenação com **desempate pela chave primária**.

## 🤔 Por que isso importa
Uma listagem sem limite é um ataque a você mesmo: `GET /entries` numa conta com milhões de linhas derruba memória e rede. Filtros e ordem mal desenhados geram resultados repetidos ou faltando entre páginas, e SQL lento.

## 💡 Intuição (explicação simples)
Um **livro de registros**: você pede "as próximas 20 linhas a partir da 40ª, só os créditos, do mais novo ao mais antigo". O bibliotecário precisa de uma **ordem total** (sem empates ambíguos) senão a "página 2" pode repetir linhas da "página 1".

## 🔬 Como funciona por dentro
- **Contrato** de `GET /api/v1/accounts/{id}/entries`: `page` (0..`payflow.statement.max-page`), `size` (1..100, padrão 20), `type` (`CREDIT`|`DEBIT`), `from` (inclusive), `to` (**exclusivo**), `direction` (`asc`|`desc`). Fora do permitido → **400**. Ordenação só por data (**lista permitida**, como na J3.11): nunca aceite um nome de coluna livre.
- **`Slice` × `Page`**: `Page` faz uma consulta `count(*)` extra; num livro-razão grande isso custa. A tela e a API de extrato não precisam do total, só de "há mais?". **Decisão:** a API usa **`Slice`** e devolve `hasNext`; `Page` só onde o total for mostrado (resolve a pendência da J5.10).
- **Envelope**: `PageResponse<T>(items, page, size, hasNext)`.
- **Intervalo semiaberto** `[from, to)`: encadear janelas (`to` de uma = `from` da próxima) não perde nem duplica lançamento na fronteira.
- **Desempate**: `ORDER BY created_at, id`; sem o `id`, lançamentos no mesmo instante podem trocar de lugar entre consultas.
- **Offset tem limites**: se chegam lançamentos entre duas requisições, o offset repete itens (pausa abaixo). O remédio é paginar por **cursor** (keyset, J3.05); fica como evolução (P2).

## 🛠️ Exemplo prático
`PageResponse`:
```java
package com.payflow.web.api.dto;

import java.util.List;
import org.springframework.data.domain.Slice;

/** Envelope das listas paginadas: os itens e o suficiente para pedir a próxima página (sem contar o total). */
public record PageResponse<T>(List<T> items, int page, int size, boolean hasNext) {

    public static <T> PageResponse<T> of(Slice<T> slice) {
        return new PageResponse<>(slice.getContent(), slice.getNumber(), slice.getSize(), slice.hasNext());
    }
}
```

Filtros opcionais com `Specification` (Spring Data JPA 4; `JpaSpecificationExecutor` no `LedgerEntryRepository`):
```java
package com.payflow.repository;

import com.payflow.domain.EntryType;
import com.payflow.domain.LedgerEntry;
import java.time.Instant;
import java.util.UUID;
import org.springframework.data.jpa.domain.Specification;

/** Filtros opcionais do extrato: cada um só entra na consulta se o cliente o pediu. */
public final class EntrySpecifications {

    private EntrySpecifications() { }

    public static Specification<LedgerEntry> ofAccount(UUID accountId) {
        return (root, query, cb) -> cb.equal(root.get("account").get("id"), accountId);
    }

    public static Specification<LedgerEntry> ofType(EntryType type) {
        return type == null ? Specification.unrestricted() : (root, query, cb) -> cb.equal(root.get("type"), type);
    }

    /** A partir de (inclusive). */
    public static Specification<LedgerEntry> from(Instant from) {
        return from == null ? Specification.unrestricted() : (root, query, cb) -> cb.greaterThanOrEqualTo(root.get("createdAt"), from);
    }

    /** Até (exclusivo): intervalos semiabertos [from, to) não deixam lançamento de fora nem contam em dobro. */
    public static Specification<LedgerEntry> before(Instant to) {
        return to == null ? Specification.unrestricted() : (root, query, cb) -> cb.lessThan(root.get("createdAt"), to);
    }
}
```

O endpoint:
```java
    @GetMapping("/{id}/entries")
    public PageResponse<EntryResponse> entries(@RequestAttribute(AuthInterceptor.USER) CurrentUser user,
                                               @PathVariable UUID id,
                                               @RequestParam(defaultValue = "0") int page,
                                               @RequestParam(defaultValue = "" + DEFAULT_SIZE) int size,
                                               @RequestParam(required = false) EntryType type,
                                               @RequestParam(required = false) Instant from,
                                               @RequestParam(required = false) Instant to,
                                               @RequestParam(defaultValue = "desc") String direction) {
        owned(user, id);
        if (page < 0 || page > properties.statement().maxPage()) {
            throw new BadRequestException("page must be between 0 and " + properties.statement().maxPage());
        }
        if (size < 1 || size > MAX_SIZE) {
            throw new BadRequestException("size must be between 1 and " + MAX_SIZE);
        }
        Sort.Direction dir = switch (direction.toLowerCase()) {
            case "asc" -> Sort.Direction.ASC;
            case "desc" -> Sort.Direction.DESC;
            default -> throw new BadRequestException("direction must be asc or desc");
        };
        var spec = Specification.allOf(EntrySpecifications.ofAccount(id), EntrySpecifications.ofType(type),
                EntrySpecifications.from(from), EntrySpecifications.before(to));
        Sort sort = Sort.by(dir, "createdAt").and(Sort.by(dir, "id"));          // desempate pela chave primária
        Slice<LedgerEntry> slice = ledger.findBy(spec, q -> q.slice(PageRequest.of(page, size, sort)));
        return PageResponse.of(slice.map(mapper::toResponse));
    }
```

**Por que `Specification` e não JPQL com parâmetros opcionais?** O jeito "óbvio" é `where (:type is null or e.type = :type) and (:from is null or e.createdAt >= :from)`. Testamos no PostgreSQL 18 (laboratório `OptionalFilterLabTest`): **todas** as combinações falham, porque o driver não consegue inferir o tipo do parâmetro em `:from is null`:
```text
type=CREDIT from=2026-01-01T00:00:00Z -> SQLGrammarException: ERROR: could not determine data type of parameter $3
type=null  from=null                  -> GenericJDBCException: ERROR: could not determine data type of parameter $3
type=CREDIT from=null                 -> GenericJDBCException: ERROR: could not determine data type of parameter $3
type=null  from=2026-01-01T00:00:00Z  -> GenericJDBCException: ERROR: could not determine data type of parameter $3
```

**Duas pegadinhas do Spring Data JPA 4** (testadas): `Specification.and(null)` lança `IllegalArgumentException: Other specification must not be null`, e `allOf(...)` também não aceita `null`; por isso cada filtro ausente devolve `Specification.unrestricted()`. Outra: passar a `Sort` fora do `PageRequest` (`q.sortBy(...)`) **não** ordenou; a ordem precisa estar **dentro** do `Pageable` (`PageRequest.of(page, size, sort)`).

## 🧠 Pausa para lógica
**Enunciado:** entre a página 0 e a 1 chega um lançamento novo. Mostre que a paginação por **offset** repete um item e a por **cursor** não.
<details><summary>Solução (testada, JDK 25.0.5)</summary>

```java
import java.util.ArrayList;
import java.util.Comparator;
import java.util.List;

/** Paginação por OFFSET × por cursor (keyset) quando chegam lançamentos novos entre uma página e outra. */
public class PagingDrift {

    record Entry(long id, String label) { }

    static final List<Entry> ledger = new ArrayList<>();   // do mais novo para o mais antigo (id maior = mais novo)

    static void add(long id) {
        ledger.add(new Entry(id, "e" + id));
        ledger.sort(Comparator.comparingLong(Entry::id).reversed());
    }

    static List<Entry> pageByOffset(int page, int size) {
        return ledger.stream().skip((long) page * size).limit(size).toList();
    }

    /** Cursor: "me dê os `size` itens com id MENOR que o último que eu vi". */
    static List<Entry> pageByCursor(Long lastSeenId, int size) {
        return ledger.stream().filter(e -> lastSeenId == null || e.id() < lastSeenId).limit(size).toList();
    }

    public static void main(String[] args) {
        for (long id = 1; id <= 6; id++) add(id);          // 6 lançamentos: 6,5,4,3,2,1

        System.out.println("== OFFSET ==");
        var p0 = pageByOffset(0, 3);
        System.out.println("página 0: " + p0.stream().map(Entry::id).toList());
        add(7);                                            // chega um lançamento novo ENTRE as duas requisições
        var p1 = pageByOffset(1, 3);
        System.out.println("página 1: " + p1.stream().map(Entry::id).toList() + "  <- o 4 apareceu de novo");

        ledger.clear();
        for (long id = 1; id <= 6; id++) add(id);
        System.out.println("== CURSOR ==");
        var c0 = pageByCursor(null, 3);
        System.out.println("página 0: " + c0.stream().map(Entry::id).toList());
        add(7);
        var c1 = pageByCursor(c0.getLast().id(), 3);
        System.out.println("página 1: " + c1.stream().map(Entry::id).toList() + "  <- sem repetir nem perder");
    }
}
```

Saída:
```text
== OFFSET ==
página 0: [6, 5, 4]
página 1: [4, 3, 2]  <- o 4 apareceu de novo
== CURSOR ==
página 0: [6, 5, 4]
página 1: [3, 2, 1]  <- sem repetir nem perder
```

## ⚖️ Trade-offs e quando NÃO usar
Offset é simples e permite "pular para a página N"; sofre com deriva e com `OFFSET` grande (o banco lê e descarta as linhas). Cursor é estável e rápido, mas só avança/recua. Para extratos (sempre "mais antigo") o cursor é a evolução natural.

## ⚠️ Erros comuns e boas práticas de produção
- Sem limite máximo de `size`.
- Ordenar por coluna escolhida pelo cliente (injeção/colunas sem índice).
- Sem desempate pela PK.
- `Page` onde não se mostra o total.
- `from`/`to` fechados nos dois lados.

## 🎤 Na entrevista
- **Offset × cursor?** Offset é simples e instável sob escrita; cursor é estável e eficiente.
- **Por que limitar `size`?** Proteção de memória/rede.
- **Como filtros opcionais em JPA?** `Specification`/Criteria; JPQL com `is null or` tem problemas de tipo no PostgreSQL.
