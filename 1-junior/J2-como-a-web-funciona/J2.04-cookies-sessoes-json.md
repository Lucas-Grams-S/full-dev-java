# J2.04 — Cookies, sessões e JSON

> ⏱️ ~1h30 · 🟢 Júnior · Pré-requisitos: J1.11, J1.15, J2.02, J2.03

## 🎯 Objetivos
Ao final desta aula você consegue:
- Explicar como cookies e sessões fazem um protocolo sem estado "lembrar" do usuário.
- Ler e criar o header `Set-Cookie` com `HttpOnly`, `Secure`, `SameSite`, `Path` e `Max-Age`.
- Implementar um `SessionStore` simples com expiração testável por `Clock`.
- Ler e escrever JSON válido e conhecer as armadilhas (números, datas, dinheiro, escape).
- Usar um *cookie jar* no `curl` e no `HttpClient`.

## 🤔 Por que isso importa
O login do PayFlow (J8) depende de sessão ou de token; o corpo de toda a API (J6) é JSON. Erros de cookie (`SameSite`, `Secure`) são uma fonte comum de "funciona no Postman e não no navegador", e erros de JSON com número/dinheiro são fonte de bugs financeiros silenciosos.

## 💡 Intuição (explicação simples)
HTTP é o atendente sem memória (J2.02). Para ele reconhecer você, na primeira visita entrega-se uma **pulseira numerada** (cookie). Nas visitas seguintes você mostra a pulseira; **o prontuário fica na recepção** (a sessão, no servidor), e a pulseira só traz o número. **JSON** é o formulário padronizado que os dois lados concordam em preencher: texto simples com campos nomeados.

## 🔬 Como funciona por dentro
```mermaid
sequenceDiagram
    participant B as Navegador/cliente
    participant S as Servidor

    S->>S: cria sessão {id -> usuário, expira em}
    S-->>B: 200 + Set-Cookie: SESSION=<id>; HttpOnly; SameSite=Lax
    B->>S: GET /me  + Cookie: SESSION=<id>
    S->>S: busca id na tabela de sessões
    S-->>B: 200 {"user":"ana"}
```
### Cookies
O servidor envia `Set-Cookie`; o cliente guarda e devolve em **toda** requisição ao mesmo site no header `Cookie`, até expirar.

| Atributo | Efeito |
|---|---|
| `HttpOnly` | JavaScript da página **não** lê o cookie (reduz o roubo por XSS, J8) |
| `Secure` | só é enviado por HTTPS |
| `SameSite=Lax/Strict/None` | controla envio em requisições vindas de **outro site** (defesa contra CSRF, J8). `None` exige `Secure` |
| `Path`, `Domain` | para quais caminhos/hosts o cookie vale |
| `Max-Age` / `Expires` | validade; `Max-Age=0` apaga |

Limites práticos: ~4 KB por cookie; vão em **toda** requisição ao site (cookies grandes pesam). Documentação completa na [MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Cookies).

### Sessão no servidor vs token
- **Sessão (stateful):** o cookie guarda só um **id aleatório**; os dados ficam no servidor (memória, Redis, banco). Dá para invalidar na hora (logout, bloqueio). Com vários servidores, é preciso compartilhar o repositório de sessões (Redis, P2).
- **Token (stateless), ex.: JWT:** os dados vão no próprio token assinado; o servidor não guarda nada, mas revogar é mais difícil. Comparação completa em J8.

### JSON (RFC 8259)
Texto com 6 tipos: **objeto** `{}`, **array** `[]`, **string** `"..."` (aspas duplas, escape `\" \\ \n \uXXXX`), **number**, **boolean**, **null**. Sem comentários, sem vírgula sobrando, sem aspas simples, sem `NaN`. Charset: UTF-8. `Content-Type: application/json`.

Armadilhas:
- **Número sem tipo preciso:** o padrão não fixa precisão. JavaScript lê todo número como `double`: inteiros acima de 2⁵³ perdem dígitos.
- **Datas:** não existe tipo data; usa-se string ISO-8601 (`"2026-11-12T20:49:29Z"`, o `Instant.toString()`).
- **Dinheiro:** como `number`, pode virar `double` no cliente. O PayFlow usa **string** (`"balance":"110.00"`) ou inteiro em centavos. Decisão do projeto: **string com 2 casas** na API.
- **Campos desconhecidos / ausentes / `null`:** definem compatibilidade entre versões da API (J6).

## 🛠️ Exemplo prático
> Testado com JDK 25.0.5 e curl 8.18. Arquivos em `CookieDemo.java` (versão completa abaixo).

### Servidor com login por cookie e sessão com expiração; cliente com cookie jar
```java
import com.sun.net.httpserver.*;
import java.io.IOException;
import java.net.*;
import java.net.http.*;
import java.nio.charset.StandardCharsets;
import java.time.*;
import java.util.*;
import java.util.concurrent.ConcurrentHashMap;

public class CookieDemo {
    /** Sessão no servidor: o cookie leva só um id aleatório; os dados ficam aqui. */
    static class SessionStore {
        private record Session(String user, Instant expiresAt) { }
        private final Map<String, Session> sessions = new ConcurrentHashMap<>();
        private final Clock clock;
        private final Duration ttl;
        SessionStore(Clock clock, Duration ttl) { this.clock = clock; this.ttl = ttl; }

        String create(String user) {
            String id = UUID.randomUUID().toString();         // em produção: aleatório forte e longo (J8)
            sessions.put(id, new Session(user, clock.instant().plus(ttl)));
            return id;
        }
        Optional<String> userOf(String id) {
            Session s = id == null ? null : sessions.get(id);
            if (s == null) return Optional.empty();
            if (!clock.instant().isBefore(s.expiresAt())) { sessions.remove(id); return Optional.empty(); }
            return Optional.of(s.user());
        }
        void destroy(String id) { sessions.remove(id); }
    }

    static String cookie(HttpExchange ex, String name) {
        String h = ex.getRequestHeaders().getFirst("Cookie");
        if (h == null) return null;
        for (String part : h.split(";\\s*")) {
            int eq = part.indexOf('=');
            if (eq > 0 && part.substring(0, eq).equals(name)) {
                String v = part.substring(eq + 1);
                // O CookieManager do JDK pode enviar o valor entre aspas (SESSION="..."): remova-as.
                return v.length() >= 2 && v.startsWith("\"") && v.endsWith("\"") ? v.substring(1, v.length() - 1) : v;
            }
        }
        return null;
    }

    static void reply(HttpExchange ex, int status, String body) throws IOException {
        byte[] b = body.getBytes(StandardCharsets.UTF_8);
        ex.getResponseHeaders().set("Content-Type", "application/json");
        ex.sendResponseHeaders(status, b.length);
        ex.getResponseBody().write(b);
        ex.close();
    }

    public static void main(String[] args) throws Exception {
        SessionStore store = new SessionStore(Clock.systemUTC(), Duration.ofMinutes(30));
        HttpServer server = HttpServer.create(new InetSocketAddress("127.0.0.1", 0), 0);
        server.createContext("/login", ex -> {
            String id = store.create("ana");
            // HttpOnly: JavaScript não lê. SameSite=Lax: não vai em POST de outro site. Secure só faz sentido em HTTPS.
            ex.getResponseHeaders().add("Set-Cookie", "SESSION=" + id + "; Path=/; HttpOnly; SameSite=Lax; Max-Age=1800");
            reply(ex, 200, "{\"ok\":true}");
        });
        server.createContext("/me", ex -> {
            Optional<String> user = store.userOf(cookie(ex, "SESSION"));
            if (user.isPresent()) reply(ex, 200, "{\"user\":\"" + user.get() + "\"}");
            else reply(ex, 401, "{\"error\":\"not authenticated\"}");
        });
        server.createContext("/logout", ex -> {
            store.destroy(cookie(ex, "SESSION"));
            ex.getResponseHeaders().add("Set-Cookie", "SESSION=; Path=/; Max-Age=0");
            reply(ex, 200, "{\"ok\":true}");
        });
        server.start();
        if (args.length > 0) {                                  // modo "serve": fica de pé para testar com curl
            System.out.println("http://127.0.0.1:" + server.getAddress().getPort());
            Thread.sleep(Long.MAX_VALUE);
        }
        String base = "http://127.0.0.1:" + server.getAddress().getPort();

        // Cliente COM jar de cookies (CookieManager) e cliente SEM
        CookieManager jar = new CookieManager();
        HttpClient withJar = HttpClient.newBuilder().cookieHandler(jar).build();
        HttpClient noJar = HttpClient.newHttpClient();
        HttpResponse.BodyHandler<String> s = HttpResponse.BodyHandlers.ofString();

        System.out.println("sem login:   " + noJar.send(HttpRequest.newBuilder(URI.create(base + "/me")).build(), s).statusCode());
        HttpResponse<String> login = withJar.send(HttpRequest.newBuilder(URI.create(base + "/login")).build(), s);
        System.out.println("Set-Cookie:  " + login.headers().firstValue("Set-Cookie").map(v -> v.replaceAll("=[0-9a-f-]{36}", "=<uuid>")).get());
        System.out.println("com jar:     " + withJar.send(HttpRequest.newBuilder(URI.create(base + "/me")).build(), s).body());
        System.out.println("sem jar:     " + noJar.send(HttpRequest.newBuilder(URI.create(base + "/me")).build(), s).statusCode());
        withJar.send(HttpRequest.newBuilder(URI.create(base + "/logout")).build(), s);
        System.out.println("após logout: " + withJar.send(HttpRequest.newBuilder(URI.create(base + "/me")).build(), s).statusCode());

        // Expiração com Clock controlado
        Clock[] now = { Clock.fixed(Instant.parse("2026-11-12T10:00:00Z"), ZoneOffset.UTC) };
        Clock moving = new Clock() {
            public ZoneId getZone() { return ZoneOffset.UTC; }
            public Clock withZone(ZoneId z) { return this; }
            public Instant instant() { return now[0].instant(); }
        };
        SessionStore st = new SessionStore(moving, Duration.ofMinutes(30));
        String id = st.create("ana");
        System.out.println("t+29min: " + st.userOf(id));
        now[0] = Clock.fixed(Instant.parse("2026-11-12T10:30:00Z"), ZoneOffset.UTC);
        System.out.println("t+30min: " + st.userOf(id));
        server.stop(0);
    }
}
```
```bash
java CookieDemo.java
```
Saída real:
```
sem login:   401
Set-Cookie:  SESSION=<uuid>; Path=/; HttpOnly; SameSite=Lax; Max-Age=1800
com jar:     {"user":"ana"}
sem jar:     401
após logout: 401
t+29min: Optional[ana]
t+30min: Optional.empty
```
- **Mesmo servidor, resultados diferentes:** quem guarda o cookie é o cliente. O `HttpClient` sem `cookieHandler` simplesmente não devolve nada.
- **Ponto de atenção real:** na primeira versão deste exemplo, o `/me` respondia `401` mesmo com o jar. O `CookieManager` do JDK devolveu o valor **entre aspas** (`SESSION="..."`), e a comparação com o id guardado falhava. Por isso a função `cookie()` remove aspas. Quando um framework faz isso por você (J5), é por causa de detalhes como este.
- A sessão aqui vive **na memória do processo**: reiniciar o servidor desloga todos e vários servidores não compartilham sessões. A `ConcurrentHashMap` é suficiente porque o `HttpServer` também aceita acessos concorrentes; concorrência é assunto de P1.

### Cookie jar no `curl`
Com `java CookieDemo.java serve` rodando (ele imprime a URL):
```bash
curl -si -c jar.txt $U/login | grep -iE "^(HTTP|set-cookie)"   # -c grava cookies
curl -s -b jar.txt $U/me                                          # -b envia cookies
```
Saída real:
```
HTTP/1.1 200 OK
Set-cookie: SESSION=<uuid>; Path=/; HttpOnly; SameSite=Lax; Max-Age=1800
{"user":"ana"}
```
O `jar.txt` contém uma linha `#HttpOnly_127.0.0.1  FALSE  /  FALSE  <expira>  SESSION  <uuid>`. **Trate esse arquivo como senha.**

### JSON: o que dá errado com números
```java
long big = 9007199254740993L;
System.out.println((long) (double) big + " != " + big);
System.out.println(0.1 + 0.2);
System.out.println(new java.math.BigDecimal("0.1").add(new java.math.BigDecimal("0.2")));
```
Saída real:
```
9007199254740992 != 9007199254740993
0.30000000000000004
0.3
```
Passar por `double` perde o último dígito do `long`; por isso ids grandes e dinheiro vão como **string** (e é o que o `MiniJson` da J2.06 faz).

## 🧠 Pausa para lógica
**Enunciado:** o `SessionStore` acima só remove uma sessão expirada **quando alguém a consulta**. Sessões abandonadas ficam na memória para sempre. Como limpar? Escreva `int purgeExpired()` que remove todas as expiradas e devolve quantas removeu.

<details><summary>Dica</summary><code>ConcurrentHashMap.entrySet().removeIf(...)</code> é seguro para concorrência. Conte quantas foram removidas antes e depois, ou use um contador dentro do <code>removeIf</code>.</details>
<details><summary>Solução</summary>

```java
int purgeExpired() {
    int before = sessions.size();
    Instant now = clock.instant();
    sessions.values().removeIf(s -> !now.isBefore(s.expiresAt()));
    return before - sessions.size();      // aproximação: outras threads podem criar/remover ao mesmo tempo
}
```
Quem chama? Um agendador periódico (`ScheduledExecutorService`; em Spring, `@Scheduled`, P3). Em produção a sessão vive no Redis com TTL nativo (P2), que faz essa limpeza sozinho. *(Esta solução não foi executada nesta execução, só a versão `userOf`.)*
</details>

**Variação:** sessão **deslizante** (renova a expiração a cada uso) vs **absoluta**: qual é mais segura e por quê?

## ⚠️ Erros comuns e boas práticas de produção
- **Cookie de sessão sem `HttpOnly`:** um XSS (J8) lê o id e sequestra a sessão.
- **Sem `Secure` em produção:** o cookie trafega em HTTP puro (J2.03).
- **`SameSite=None` sem `Secure`:** o navegador rejeita. Mensagem típica no console: *"Cookie ... has been rejected because it has the SameSite=None attribute but is missing the Secure attribute"*.
- **Id de sessão previsível** (contador, timestamp): atacante adivinha. Use gerador aleatório forte e longo.
- **Dados sensíveis dentro do cookie** (senha, saldo): o cookie é do usuário; guarde só um id.
- **Não regenerar a sessão após o login** (*session fixation*): crie um id novo ao autenticar (J8).
- **JSON inválido:** em J5/J6 você verá erros de *parse* da biblioteca JSON (a mensagem exata depende da biblioteca e da versão). As causas mais comuns são vírgula sobrando, aspas simples e corpo vazio.
- **Escapar JSON à mão** (como no `MiniJson`) só serve para estudo: use uma biblioteca (J5/J6).

## 🎤 Na entrevista
- **Como o servidor sabe quem é o usuário se HTTP não tem estado?** Por um identificador enviado a cada requisição (cookie de sessão ou token no header); o servidor busca os dados associados.
- **Sessão vs JWT?** Sessão: dados no servidor, revogação imediata, exige armazenamento compartilhado ao escalar. JWT: dados no token assinado, sem armazenamento, revogação mais difícil e payload legível por quem o recebe.
- **Para que servem `HttpOnly`, `Secure` e `SameSite`?** `HttpOnly` bloqueia leitura por JavaScript; `Secure` só envia por HTTPS; `SameSite` limita o envio em requisições entre sites, ajudando contra CSRF.
- **Por que não mandar dinheiro como número em JSON?** O padrão não define precisão; consumidores em JavaScript leem como `double` e perdem exatidão. String decimal (ou centavos inteiros) é seguro.
