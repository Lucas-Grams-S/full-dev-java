# J2.05 — Ferramentas: DevTools, `curl` e Bruno/Postman

> ⏱️ ~1h30 · 🟢 Júnior · Pré-requisitos: J0.01, J2.02, J2.04

## 🎯 Objetivos
Ao final desta aula você consegue:
- Inspecionar requisições e respostas na aba **Network** do DevTools.
- Montar chamadas HTTP com `curl` (método, headers, corpo, cookies, timeout, códigos de saída).
- Formatar e filtrar JSON com `jq`.
- Organizar uma coleção de requisições no Bruno (ou Postman/HTTPie) e saber quando usar cada ferramenta.
- Escrever um *smoke test* em shell que falha quando o status é inesperado.

## 🤔 Por que isso importa
Dois terços da depuração de uma API é responder "o que exatamente foi enviado e o que voltou?". Quem domina `curl` e DevTools reproduz um bug de produção em segundos, cola o comando no ticket e valida a correção sem escrever código.

## 💡 Intuição (explicação simples)
São **lupas e controles remotos** para a conversa HTTP: o **DevTools** é a lupa sobre o que o navegador diz; o **curl** é um controle remoto de texto, que cabe em script; o **Bruno/Postman** é o controle com botões e caderno de anotações, bom para guardar e compartilhar as chamadas.

## 🔬 Como funciona por dentro
Todas fazem o mesmo: montam o texto HTTP (J2.02), abrem TCP/TLS (J2.01, J2.03) e mostram o resultado. A diferença é o contexto.

| Ferramenta | Melhor para | Limite |
|---|---|---|
| **DevTools → Network** | ver o que o navegador **realmente** enviou (cookies, CORS, tempos) | só tráfego do navegador |
| **`curl`** | reproduzir, automatizar, colar em tickets, CI | sem interface; precisa saber as opções |
| **Bruno** | coleções versionadas no Git (arquivos de texto), ambientes (dev/prod), testes simples; open source | exige instalar o app |
| **Postman** | coleções, equipes, mocks (conta e nuvem do fornecedor) | recursos centrais atrelados a conta |
| **HTTPie** | sintaxe amigável no terminal | nem sempre instalado |
| **`jq`** | filtrar/formatar JSON no terminal | só JSON |

### DevTools: onde olhar (Chrome/Edge/Firefox têm equivalentes)
`F12` → aba **Network** → recarregue a página.
- **Linha da requisição:** método, status, tipo, tamanho, tempo.
- **Headers:** *General* (URL, método, status), *Response Headers*, *Request Headers* (inclusive `Cookie`).
- **Payload / Response:** corpo enviado e recebido; **Preview** formata o JSON.
- **Timing:** quanto levou em DNS, conexão, TLS, espera do servidor (TTFB) e download.
- **Application → Cookies:** os cookies do site e seus atributos (J2.04).
- **Console:** erros de CORS aparecem aqui.
- Marque **Preserve log** para não perder requisições em redirecionamentos e **Disable cache** para ver a resposta real.
Guia oficial do Chrome: [Inspect network activity](https://developer.chrome.com/docs/devtools/network).

## 🛠️ Exemplo prático
> Testado com curl 8.18.0 e jq no Linux, contra o servidor do `mini-bank` (J2.06) em `http://127.0.0.1:8080`. **Bruno e DevTools não foram automatizados nesta execução**: o passo a passo de menus vem da documentação, não de captura de tela.

### `curl`: as opções que você vai usar todo dia
```bash
curl http://127.0.0.1:8080/accounts                       # GET simples
curl -i URL                                                # inclui headers da RESPOSTA
curl -v URL                                                # detalha TUDO (> envia, < recebe, * info)
curl -s URL                                                # silencioso (sem barra de progresso)
curl -X POST URL                                           # método
curl -H 'Content-Type: application/json' URL               # header
curl -d '{"amount":"5"}' URL                               # corpo (já vira POST)
curl -o /dev/null -w '%{http_code}\n' URL                  # só o status
curl --max-time 2 URL                                      # timeout total
curl --fail URL                                            # status 4xx/5xx => código de saída 22
curl -L URL                                                # segue redirecionamentos
curl -c jar.txt -b jar.txt URL                             # grava e envia cookies
curl -u usuario:senha URL                                  # Basic auth (J8; só sob HTTPS)
```
Experimentos reais:
```bash
curl -s -o /dev/null -w '%{http_code} %{time_total}s %{content_type}\n' http://127.0.0.1:8080/accounts
```
```
200 0.001084s application/json; charset=utf-8
```
```bash
curl -s --max-time 2 -o /dev/null -w '%{http_code}\n' http://127.0.0.1:9/ ; echo "rc=$?"
```
```
000
rc=7
```
`000` = nenhuma resposta HTTP; código de saída `7` = *failed to connect* (J2.01: *Connection refused*).
```bash
curl --fail -s http://127.0.0.1:8080/accounts/nope; echo "rc=$?"
```
```
rc=22
```
Sem `--fail`, o `curl` retornaria `0` mesmo com 404, e um script não perceberia a falha.

### `jq`: formatar e filtrar
```bash
curl -s http://127.0.0.1:8080/accounts/acc-1/statement | jq .
curl -s http://127.0.0.1:8080/accounts | jq -r '.[] | "\(.id)\t\(.balance)"'
```
```
acc-1	101.00
```
`jq .` formata; `.[]` itera o array; `-r` imprime texto sem aspas.

### Smoke test em shell (`smoke.sh`)
```bash
#!/usr/bin/env bash
# Smoke test do mini-bank: falha (exit 1) se algum status for inesperado.
set -euo pipefail
BASE=${1:-http://127.0.0.1:8080}
check() { # check <esperado> <descrição> <args do curl...>
  local expected=$1 desc=$2; shift 2
  local got; got=$(curl -s -o /dev/null -w '%{http_code}' "$@")
  if [[ "$got" == "$expected" ]]; then echo "OK   $desc ($got)"; else echo "FAIL $desc: esperado $expected, veio $got"; exit 1; fi
}
check 200 "lista contas"        "$BASE/accounts"
check 404 "conta inexistente"   "$BASE/accounts/nope"
check 200 "depósito"            -X POST -d '{"amount":"1.00"}' "$BASE/accounts/acc-1/deposits"
check 422 "saque sem saldo"     -X POST -d '{"amount":"999999"}' "$BASE/accounts/acc-1/withdrawals"
```
```bash
chmod +x smoke.sh && ./smoke.sh
```
Saída real:
```
OK   lista contas (200)
OK   conta inexistente (404)
OK   depósito (200)
OK   saque sem saldo (422)
```
(`set -euo pipefail`: o script para no primeiro erro, em variável não definida ou em falha no meio de um *pipe*.) Esse mesmo script roda no CI em J10.

### Bruno: coleção versionada
1. Instale o Bruno (documentação oficial: [docs.usebruno.com](https://docs.usebruno.com/)).
2. Crie uma **coleção** `payflow` numa pasta do repositório: cada requisição vira um arquivo de texto, então vai para o Git e aparece em *pull requests*.
3. Crie um **ambiente** `local` com a variável `baseUrl = http://127.0.0.1:8080` e use `{{baseUrl}}/accounts`.
4. Crie uma requisição por endpoint do mini-bank (lista, cria, deposita, saca, extrato) e uma aba de **asserts** de status (200/201/404/422).
⚠️ A estrutura exata de menus e a sintaxe dos arquivos do Bruno **não foram verificadas** nesta execução; siga a documentação da versão que você instalar. Postman e HTTPie são equivalentes e válidos (`http POST :8080/accounts/acc-1/deposits amount=5`, ⚠️ não testado).

## 🧠 Pausa para lógica
**Enunciado:** você mediu 10 tempos de resposta (ms): `10 20 30 40 50 60 70 80 90 1000`. A **média** é 135 ms. O que os percentis **p50** e **p95** (método *nearest-rank*) dizem a mais? Implemente `percentile(List<Double>, int p)`.

<details><summary>Dica</summary>Ordene a lista; o rank é <code>ceil(p/100 × n)</code>; o elemento é <code>sorted[rank − 1]</code>.</details>
<details><summary>Solução (testada)</summary>

```java
static double percentile(List<Double> values, int p) {           // nearest-rank
    List<Double> s = new ArrayList<>(values);
    Collections.sort(s);
    int rank = (int) Math.ceil(p / 100.0 * s.size());
    return s.get(Math.max(rank, 1) - 1);
}
// p50 = 50.0 ; p95 = 1000.0 ; média = 135.0
```
A média (135) não descreve ninguém: 9 requisições levaram ≤ 90 ms. O **p50** mostra o caso típico (50 ms) e o **p95/p99** mostra a cauda lenta que o usuário percebe (1000 ms). Por isso SLOs usam percentis (P6, S2, S4).
</details>

**Variação:** meça 100 chamadas reais com `curl -w '%{time_total}\n'` e calcule o p95 com `sort -n | awk` ou com a função acima.

## ⚠️ Erros comuns e boas práticas de produção
- **Aspas no Windows/PowerShell:** `-d '{"a":1}'` costuma quebrar; use `curl.exe` e aspas duplas escapadas, ou WSL. No Linux/macOS, use aspas simples por fora.
- **Esquecer `Content-Type: application/json`** com `-d`: o curl envia `application/x-www-form-urlencoded` e o servidor pode responder `400`/`415`.
- **Segredos no histórico do shell** (`curl -H "Authorization: Bearer ..."`): evite colar tokens reais em comandos que ficam no `~/.bash_history`; use variáveis de ambiente (`-H "Authorization: Bearer $TOKEN"`).
- **Compartilhar coleção com segredo:** Bruno/Postman guardam variáveis; não versione tokens reais (`.gitignore`, ambientes locais).
- **`curl -k` / `--insecure`** desliga a validação do certificado (J2.03). Só para depurar localmente, nunca em script permanente.
- **Cache do navegador** engana: teste com *Disable cache* ou janela anônima.
- **CORS só existe no navegador:** funciona no `curl`/Bruno e falha no navegador? Provavelmente é CORS (olhe o Console). Aprofundado em J4/J6.
- Mensagens comuns do `curl`: `curl: (7) Failed to connect to ... port 8080: Connection refused` (servidor parado); `curl: (28) Operation timed out` (timeout); `curl: (60) SSL certificate problem` (certificado não confiável).

## 🎤 Na entrevista
- **Como você investigaria uma API que "retorna erro às vezes"?** Reproduzo com `curl -v`/Bruno com a mesma requisição, comparo status, headers e corpo, olho tempos (DevTools/`-w`), checo os logs do servidor com o horário e o id da requisição (P6) e só depois mexo no código.
- **Para que serve `-w '%{http_code}'`?** Extrair informação da resposta (status, tempos) para scripts e testes de fumaça.
- **Por que p95 em vez de média?** A média esconde a cauda lenta; p95/p99 mostram a experiência dos piores casos.
- **Funciona no Postman e falha no navegador. Por quê?** Provavelmente CORS, cookies com `SameSite`/`Secure`, ou diferenças de cabeçalhos; o navegador aplica regras de segurança que as ferramentas não aplicam.
