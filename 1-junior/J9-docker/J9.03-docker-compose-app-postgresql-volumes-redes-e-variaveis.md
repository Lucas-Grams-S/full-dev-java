## 🎯 Objetivos
Ao final desta aula você consegue:
- **Descrever** em um `compose.yaml` a aplicação **e** o PostgreSQL, subir tudo com **um comando** e derrubar com outro.
- **Explicar** como os containers se encontram (rede do Compose, DNS pelo **nome do serviço**) e o que **não** é publicado no host.
- **Persistir** dados com volume nomeado e **prever** o que `down` e `down -v` fazem.
- **Passar configuração** por variáveis de ambiente e **segredos** por arquivos montados (`configtree`), sem colocá-los na imagem nem no `inspect`.
- **Ordenar** a subida com `healthcheck` + `depends_on: condition: service_healthy` e **reiniciar** serviços que caem.

## 🤔 Por que isso importa
Na J9.01 você subiu o banco com um `docker run` de cinco linhas. Agora são **dois** serviços, uma rede, um volume, três segredos e uma ordem de subida: ninguém digita isso de cabeça, e ninguém quer que "o jeito certo de subir" viva na memória de uma pessoa do time. O Compose coloca **tudo isso em um arquivo versionado**: o colega novo clona o repositório, roda um comando e tem o PayFlow de pé. É também o **ensaio** para o Kubernetes (P7): os conceitos (serviço, rede, volume, segredo, *probe*) são os mesmos, com outra sintaxe.

## 💡 Intuição (explicação simples)
- **Compose** é o **roteiro de um show**: lista os artistas (serviços), onde cada um fica no palco (rede), o que cada um carrega (volumes e variáveis) e **a ordem de entrada** (o banco entra antes da aplicação, e só depois que ele **está pronto**, não só "chegou").
- **Rede do Compose** é um **condomínio com interfone**: cada serviço atende pelo **nome** (`db`, `app`); a portaria (`ports`) só abre para a rua o que você mandar abrir.
- **Segredo montado como arquivo** é o **cofre da sala**: quem precisa entra e lê; não vai anunciado no quadro de avisos (a variável de ambiente, que **qualquer** processo e o `docker inspect` enxergam).

## 🔬 Como funciona por dentro

### 1. A anatomia do `compose.yaml`
O arquivo padrão se chama **`compose.yaml`** (a [documentação](https://docs.docker.com/compose/intro/compose-application-model/) o chama de **preferido**; `docker-compose.yml`, do tempo do Compose v1, ainda é lido por compatibilidade). *Decisão do treinamento:* `compose.yaml`; o marco `payflow-J9` de `projeto/marcos.md` foi atualizado de acordo. O topo tem blocos:

| Bloco | O que descreve |
|---|---|
| `name:` | nome do **projeto** (prefixo de tudo o que o Compose cria: `payflow_backend`, `payflow_pgdata`, `payflow-app-1`) |
| `services:` | cada **container** (imagem ou `build`, variáveis, portas, volumes, redes, `healthcheck`, `restart`) |
| `volumes:` | volumes **nomeados** |
| `networks:` | redes (o Compose cria uma padrão; declarar `backend` deixa o desenho explícito) |
| `secrets:` | arquivos que viram segredos montados em `/run/secrets` |

**Não** existe mais o campo `version:` no topo (o Compose atual o ignora e avisa: `the attribute `version` is obsolete, it will be ignored, please remove it to avoid potential confusion`, mensagem conferida); você ainda o verá em tutoriais antigos. Comandos que você usará o tempo todo (`docker compose ...`, **com espaço**: o `docker-compose` com hífen é o antigo):

| Comando | Faz |
|---|---|
| `docker compose up -d --build --wait` | constrói o que mudou, sobe em segundo plano e **espera os serviços ficarem saudáveis** |
| `docker compose ps` | estado dos serviços |
| `docker compose logs -f app` | log do serviço (J9.04) |
| `docker compose exec app sh` | comando dentro de um serviço em execução |
| `docker compose down` | para e **remove containers e rede**; **mantém os volumes** |
| `docker compose down -v` | idem, **e apaga os volumes** (os dados!) |
| `docker compose config` | mostra o arquivo **já com as variáveis resolvidas** (ótimo para depurar) |

### 2. Redes e DNS: o nome do serviço é o endereço
O Compose cria uma rede para o projeto e põe os serviços nela. O DNS embutido do Docker resolve **o nome do serviço** para o IP do container. Medido:
```text
$ docker compose exec app getent hosts db
172.20.0.2        db  db
```
Por isso a URL do banco no Compose é `jdbc:postgresql://db:5432/payflow`, e **não** `localhost`: dentro do container da aplicação, `localhost` é **o próprio container** (J2.01). É o erro mais comum desta aula (veja "Erros comuns").

**O que vai para o host.** A aplicação publica a porta (`127.0.0.1:8080:8080`); o **banco não publica nenhuma** (só `5432/tcp` interno, que o `docker compose ps` mostra sem `->`). Medido: do host, uma conexão a `127.0.0.1:5432` dá `Connection refused`. A aplicação alcança o banco pela rede interna; **ninguém de fora** alcança. Para você ver o banco, use o `psql` **dentro** da rede (seção 6). Isso é o **princípio do menor privilégio** aplicado à rede, e é como será em produção (J10: o banco em subrede privada).

### 3. Volumes: o que `down` apaga e o que não apaga
O volume nomeado `pgdata` (montado em `/var/lib/postgresql`, o caminho do PostgreSQL 18, decisão 20) guarda o banco. Medido, com um registro criado pela API antes:
```text
$ docker compose down          # remove containers e rede...
$ docker volume ls | grep payflow
payflow_pgdata                 # ...mas o volume FICA
$ docker compose up -d --wait  # os dados voltam
['ana@payflow.dev', 'bruno@payflow.dev', 'zoe@payflow.dev']      # zoe foi criada ANTES do down
$ docker compose down -v       # com -v o volume é apagado: banco vazio na próxima subida
```
**A pegadinha clássica (medida):** o PostgreSQL só lê `POSTGRES_PASSWORD` **quando cria o banco** (diretório de dados vazio). Troquei o segredo `db_password` com o volume já criado e subi de novo:
```text
app  ... Message    : FATAL: password authentication failed for user "payflow"
```
A aplicação recebeu a **senha nova**; o banco guardou a **antiga**. Soluções: (a) voltar a senha; (b) `ALTER USER payflow PASSWORD '...'` com o banco no ar; (c) `docker compose down -v` (**apaga os dados**: só em desenvolvimento). Em produção, trocar a senha do banco é uma **rotação** com as duas pontas (J8.07, P10).

### 4. Configuração e segredos
**Variáveis de ambiente.** Pelo *relaxed binding* (J5.05), `SPRING_DATASOURCE_URL` vira `spring.datasource.url`, e `SPRING_FLYWAY_LOCATIONS` vira `spring.flyway.locations`. É assim que o **mesmo JAR** (e a mesma imagem) funciona em qualquer ambiente: a imagem **não muda**, o ambiente fornece o que é diferente (decisão 31: *sem perfil = produção*).

**O seed no Compose.** O PayFlow, sem perfil, **não** carrega o seed. O Compose é um ambiente de **desenvolvimento**, então ele o liga **explicitamente**: `SPRING_FLYWAY_LOCATIONS: classpath:db/migration,classpath:db/seed`. Executado: o log mostra `Migrating schema "public" to version "1 - accounts"` e `Migrating schema "public" with repeatable migration "dev seed"`. *Nunca* coloque essa linha no ambiente de produção.

**Segredos como arquivos (`configtree`).** O que **não** pode ficar em variável de ambiente: a senha do banco e o segredo do JWT. O Compose monta cada segredo como **arquivo** em `/run/secrets/<nome>`; a aplicação lê com `spring.config.import=configtree:/run/secrets/` (J8.07): cada arquivo vira uma propriedade **com o nome do arquivo**. Por isso o `compose.yaml` usa `target:` para **dar ao arquivo o nome da propriedade**:
```yaml
    secrets:
      - source: db_password
        target: spring.datasource.password        # /run/secrets/spring.datasource.password
      - source: jwt_secret
        target: payflow.security.jwt.secret       # /run/secrets/payflow.security.jwt.secret
```
Um só arquivo do host (`secrets/db_password`) alimenta **os dois lados**: o `db` o lê por `POSTGRES_PASSWORD_FILE` (suporte da imagem oficial) e o `app` por `configtree`.

O que isso muda, medido:
```text
$ docker inspect payflow-app-1 --format '{{range .Config.Env}}{{println .}}{{end}}' | grep -iE 'secret|password|CONFIG_IMPORT'
SPRING_CONFIG_IMPORT=configtree:/run/secrets/        # só o caminho: o VALOR do segredo não aparece no inspect
```
Com `-e PAYFLOW_SECURITY_JWT_SECRET=...` o valor **apareceria** no `docker inspect`, no `/proc/<pid>/environ` e em qualquer *dump* de ambiente. **Precedência** (testada): se as duas formas existem, a **variável de ambiente vence** o `configtree` (rodei `docker compose run -e PAYFLOW_SECURITY_JWT_SECRET=curto app`: a aplicação usou o valor curto e **recusou subir**).

**A permissão que quebra tudo (erro real, medido).** Primeira tentativa, com `chmod 600` nos arquivos de segredo (o "certo", de quem pensa em segurança):
```text
Caused by: java.nio.file.AccessDeniedException: /run/secrets/spring.datasource.password
$ ls -ln /run/secrets          (no container do banco, que lê como root)  ->  -rw------- 1 1000 1000
```
O Compose monta cada segredo como **bind mount** do arquivo do host (a documentação diz: "Compose delivers each secret by bind-mounting a single file"), e **mantém dono e permissões do host** (uid 1000, modo 600). A aplicação roda como **uid 10001** (J9.02) e **não consegue ler**. Tentei `uid: "10001"` e `mode: 0400` na sintaxe longa: **foram ignorados** (o erro continuou idêntico). A saída, **só para desenvolvimento local**: `chmod 644` nos arquivos (o `scripts/make-secrets.sh` faz isso) e a pasta `secrets/` **fora do Git** e **fora do contexto de build** (`.gitignore` e `.dockerignore`, J9.04). Em plataformas de produção (Swarm, Kubernetes), o `uid` e o `mode` do segredo **funcionam** (P7); e o segredo vem de um cofre (J10, P9, P10).

**Interpolação e `.env`.** O Compose lê um arquivo `.env` ao lado do `compose.yaml` e substitui `${VARIAVEL:-padrão}` no arquivo. Medido: `ports: - "127.0.0.1:${APP_PORT:-8080}:8080"` com `APP_PORT=9090 docker compose config` mostra `published: "9090"`. O `.env` é para **configuração que muda de máquina para máquina** (portas); **segredo não vai no `.env`** (ele é variável de ambiente e geralmente acaba no Git).

### 5. Ordem de subida: `healthcheck` e `depends_on`
Subir "o banco primeiro" **não basta**: o container do PostgreSQL **começa** em um instante, mas só **aceita conexões** segundos depois. Sem espera, a aplicação tenta conectar, falha e cai. O Compose resolve com duas peças:
```yaml
  db:
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U payflow -d payflow"]
      interval: 5s
      timeout: 3s
      retries: 10
      start_period: 10s
  app:
    depends_on:
      db:
        condition: service_healthy
```
- **`healthcheck`** é um comando que o Docker roda **dentro** do container, de tempos em tempos; o estado vai de `starting` a `healthy` ou `unhealthy` (`docker ps` mostra `(healthy)`). `start_period` é a "carência" em que as falhas **não contam**.
- **`depends_on` + `condition: service_healthy`** faz o Compose **esperar** o `healthy` do banco para iniciar a aplicação. Sem a `condition`, `depends_on` só ordena o **início** (`service_started`), que não garante nada.
- **`docker compose up --wait`** só retorna quando **todos** os serviços estão saudáveis (ou falha); é o que usamos nos testes e no CI (J10).
- O *healthcheck* da aplicação usa o **`wget`** do Alpine contra o Actuator (`/actuator/health`, público, J8): `wget -q -O /dev/null http://localhost:8080/actuator/health` termina com erro se a resposta não for `2xx`. *(Na imagem Ubuntu **não há** `curl` nem `wget`: o Actuator só poderia ser consultado com ferramentas que você teria de instalar.)* Medido: `docker inspect ... .State.Health.Status` → `"healthy"`.

> **Cuidado:** `depends_on` só controla a **subida**. Se o banco cair **depois**, a aplicação não é "refeita": ela precisa **tolerar** a falta (o *pool* Hikari reconecta; o *healthcheck* da aplicação reflete o banco, porque o `health` do Actuator inclui o `db`). **A aplicação não pode depender de a ordem ter sido respeitada.**

**`restart`.** `restart: unless-stopped` religa o container se o processo sair (ou o Docker reiniciar), **a não ser** que você o tenha parado. Medido: `docker compose exec app sh -c 'kill 1'` → `restarts=1 status=running`. Os valores: `no` (padrão), `on-failure[:N]`, `always`, `unless-stopped`.

**Evidência (primeira tentativa, antes de arrumar o segredo):** o `up --wait` terminou com `container payflow-app-1 is unhealthy` e o `docker compose ps` mostrou `Restarting (1) Less than a second ago`: **a aplicação caía na subida e o `restart` a levantava em laço**. O `--wait` e o `ps` são o primeiro lugar para olhar; a causa, no `docker compose logs app` (J9.04).

### 6. Profiles: serviços sob demanda
Um serviço com `profiles: ["tools"]` **só sobe quando você pede** (`--profile tools`). Serve para ferramentas de apoio, como um cliente `psql` que **entra na rede** e fala com o banco que não está publicado:
```bash
docker compose --profile tools run --rm psql -c 'select count(*) as contas from accounts'
#  contas
# --------
#       2
# (1 row)
```
A senha vem de um arquivo `.pgpass` montado como segredo (`PGPASSFILE`): nada de senha na linha de comando. O `docker compose exec db psql -U payflow -d payflow` também serve, quando o banco já está de pé.

## 🛠️ Exemplo prático
> **Laboratório executado:** `lab/docker-lab`. Para o **PayFlow**, copie os arquivos e aplique as três marcas `← PayFlow`.

### Passo 1: os segredos de desenvolvimento
`scripts/make-secrets.sh` (`chmod +x`; o laboratório tem o mesmo):
```bash
#!/usr/bin/env bash
# Gera os segredos de DESENVOLVIMENTO do Compose em ./secrets (fora do Git e fora do contexto de build).
set -euo pipefail
cd "$(dirname "$0")/.."
mkdir -p secrets
[ -f secrets/db_password ] || printf 'db-%s' "$(head -c 18 /dev/urandom | base64 | tr -dc 'A-Za-z0-9' | head -c 24)" > secrets/db_password
[ -f secrets/jwt_secret ]  || head -c 48 /dev/urandom | base64 | tr -d '\n' > secrets/jwt_secret
# formato do .pgpass: host:porta:banco:usuario:senha
printf 'db:5432:payflow:payflow:%s\n' "$(cat secrets/db_password)" > secrets/pgpass
# O Compose monta cada arquivo como bind mount (uid e mode do compose.yaml sao ignorados) e o processo da
# aplicacao roda com o uid 10001: o arquivo precisa ser legivel por "outros". So vale para dev local.
chmod 644 secrets/db_password secrets/jwt_secret
chmod 600 secrets/pgpass
echo "segredos de desenvolvimento em ./secrets (ignorados pelo Git e pelo .dockerignore)"
```
`.gitignore` (acrescente): `secrets/` e `.env`. O `jwt_secret` tem 64 caracteres (base64 de 48 bytes): o HS256 exige **pelo menos 32 bytes** (J8.03). O script **não sobrescreve** segredos existentes (rodar duas vezes é seguro).

### Passo 2: o `compose.yaml`
```yaml
name: payflow

services:
  db:
    image: postgres:18
    restart: unless-stopped
    environment:
      POSTGRES_USER: payflow
      POSTGRES_DB: payflow
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    secrets:
      - db_password
    volumes:
      - pgdata:/var/lib/postgresql          # no PostgreSQL 18 o caminho e /var/lib/postgresql (J3.03)
    networks:
      - backend
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U payflow -d payflow"]
      interval: 5s
      timeout: 3s
      retries: 10
      start_period: 10s

  app:
    build: .
    image: payflow:J9                       # ← PayFlow (no laboratório: payflow-lite:dev)
    restart: unless-stopped
    depends_on:
      db:
        condition: service_healthy
    environment:
      SPRING_DATASOURCE_URL: jdbc:postgresql://db:5432/payflow
      SPRING_DATASOURCE_USERNAME: payflow
      SPRING_CONFIG_IMPORT: configtree:/run/secrets/
      SPRING_FLYWAY_LOCATIONS: classpath:db/migration,classpath:db/seed     # seed so em DEV
      SERVER_SERVLET_SESSION_COOKIE_SECURE: "false"                         # ← PayFlow: http://localhost (J8.03)
    secrets:
      - source: db_password
        target: spring.datasource.password
      - source: jwt_secret
        target: payflow.security.jwt.secret
    ports:
      - "127.0.0.1:${APP_PORT:-8080}:8080"
    networks:
      - backend
    healthcheck:
      test: ["CMD", "wget", "-q", "-O", "/dev/null", "http://localhost:8080/actuator/health"]
      interval: 10s
      timeout: 3s
      retries: 5
      start_period: 30s

  # Cliente psql sob demanda: docker compose --profile tools run --rm psql
  psql:
    profiles: ["tools"]
    image: postgres:18
    networks:
      - backend
    depends_on:
      db:
        condition: service_healthy
    environment:
      PGHOST: db
      PGUSER: payflow
      PGDATABASE: payflow
      PGPASSFILE: /run/secrets/pgpass
    secrets:
      - source: db_pgpass
        target: pgpass
    entrypoint: ["psql"]

secrets:
  db_pgpass:
    file: ./secrets/pgpass
  db_password:
    file: ./secrets/db_password
  jwt_secret:
    file: ./secrets/jwt_secret

volumes:
  pgdata:

networks:
  backend:
```
As diferenças do PayFlow (`← PayFlow`) para o laboratório: (1) o nome da imagem; (2) o **`SERVER_SERVLET_SESSION_COOKIE_SECURE: "false"`**: no PayFlow, o cookie de sessão do painel é `Secure` em produção (J8.03) e a aplicação roda aqui **sem perfil** (= produção) mas em `http://localhost`; sem esta linha, o navegador pode não devolver o cookie por HTTP (⚠️ o comportamento varia por navegador e **não foi verificado aqui**; o laboratório não tem sessão); (3) o `Dockerfile` (J9.02, com os dois ajustes dele). Acrescente também o `server.shutdown: graceful` (exercício da J9.02) no `application.yml` do PayFlow.

**Por que a aplicação do Compose roda sem perfil e não com `dev`?** Porque o `dev` traz `localhost:5432` e logs `DEBUG` (J5.05): é para quem roda a aplicação **fora** do container. No Compose a configuração vem do **ambiente** (como será em produção): é o ensaio fiel. O `application-dev.yml` fica para o `scripts/run-dev.sh`.

## 🧠 Pausa para lógica
**Enunciado:** depois de um `docker compose down -v`, o colega roda `docker compose up -d` e, **sem esperar**, abre `http://localhost:8080/accounts` e vê erro. Segundos depois funciona. Quais são **três** causas possíveis (uma por camada: Compose, aplicação e banco) e o que você olha primeiro?

<details><summary>Dica</summary>

`up -d` retorna quando os containers **iniciam**, não quando ficam **prontos**. Em que ordem as coisas acontecem na primeira subida de um banco vazio?
</details>

<details><summary>Solução</summary>

(1) **Compose:** sem `--wait`, o comando devolve o terminal antes do `healthy`; o colega testou **cedo demais**. (2) **Banco:** com o volume apagado, o PostgreSQL **inicializa o diretório de dados** (leva alguns segundos a mais que o normal) antes de aceitar conexões, e o *healthcheck* está em `starting`. (3) **Aplicação:** o Flyway cria o esquema e aplica o seed **antes** do Tomcat aceitar tráfego (`Started ... in N seconds`). Olhe primeiro `docker compose ps` (`(health: starting)` × `(healthy)`) e `docker compose logs app`; o `--wait` evita o problema nos scripts e no CI.
</details>

## ⚖️ Trade-offs e quando NÃO usar
- **Compose × Kubernetes:** o Compose é ótimo para **desenvolvimento, testes e demos** em **uma máquina**. Ele **não** escala em várias máquinas, não faz *rolling update* nem autocura entre nós. Para isso, P7 (Kubernetes) ou serviços como ECS (P9).
- **Aplicação no Compose × aplicação na IDE:** com a aplicação em container você testa **a imagem real** (usuário, variáveis, segredos), mas perde o ciclo rápido do DevTools. Dia a dia: banco no Compose (`docker compose up -d db`) e a aplicação pela IDE (`scripts/run-dev.sh`); antes de abrir a PR e nos testes de fumaça, tudo no Compose.
- **Segredo por arquivo × variável de ambiente:** arquivo evita vazar no `inspect` e no ambiente de **todos** os processos, mas tem o custo de permissão (o erro acima) e exige que a aplicação leia arquivos (`configtree`). Variável é mais simples e é como muitas plataformas entregam; escolha conscientemente, e **nunca** coloque o valor no Git ou na imagem.
- **Banco no Compose em produção:** não. Volume local, sem alta disponibilidade, sem backup gerenciado. Em produção, um banco gerenciado (J10, P9).
- **Um `compose.yaml` para dev e produção:** evite. Dev tem seed, portas abertas em `127.0.0.1` e `chmod 644`; produção tem nada disso. Use **arquivos de sobreposição** (`-f compose.yaml -f compose.prod.yaml`) quando precisar, mas o caminho de produção real é outra ferramenta.

## ⚠️ Erros comuns e boas práticas de produção
- **`localhost` na URL do banco dentro do container:** `Connection to localhost:5432 refused`. Use o **nome do serviço** (`db`).
- **`AccessDeniedException: /run/secrets/...`:** permissão do arquivo do host (a seção 4). `ls -ln secrets` e `chmod 644` (dev).
- **`FATAL: password authentication failed for user "payflow"`:** a senha do ambiente **não é** a que o banco guardou (volume antigo). Veja a seção 3.
- **`Bind for 127.0.0.1:8080 failed: port is already allocated`** (formato conferido com a porta 18099)**:** outro processo na 8080 (a aplicação rodando pela IDE!). Mude o `APP_PORT` ou pare o outro.
- **`container payflow-db-1 is unhealthy`** (o formato da mensagem do `up --wait`, conferido com o `payflow-app-1`): o *healthcheck* do serviço falhou; veja `docker compose logs db`. Causa típica no PostgreSQL 18: volume montado em `/var/lib/postgresql/data` (decisão 20) ou variável faltando.
- **`go-yaml load error in scanner at L5.C11: mapping values are not allowed in this context`** (mensagem do Compose atual, conferida): indentação ou `:` em valor sem aspas. Use `docker compose config -q` para validar.
- **`The "PORTA" variable is not set. Defaulting to a blank string.`** (aviso conferido): você usou `${VAR}` sem definir (nem padrão `${VAR:-x}`) e sem `.env`.
- **`docker compose down -v` por reflexo:** apaga **dados**. Em dev é rotina; em qualquer ambiente com dados que importam, não.
- **Deixar `restart: always` mascarar um bug:** a aplicação cai e volta em laço sem ninguém notar. Olhe `docker compose ps` (e as métricas, P6).
- **Imagem `latest`** (de qualquer serviço): não reproduzível (decisão 50).
- **Publicar o banco** (`5432:5432`) "para olhar com o DBeaver": só se for `127.0.0.1:55432:5432` e **temporário**; prefira o perfil `tools`.
- **Comitar `secrets/` ou `.env`:** o `scripts/check-secrets.sh` e o `.gitignore` (J8.07) existem para isso; confira com `git status` antes de cada commit.

(c) Explique por que o *healthcheck* da aplicação só fica `healthy` depois da migração do Flyway.

<details><summary>Soluções de referência</summary>

1. (a) A rede dá a cada serviço um **nome DNS** e isola o projeto; dentro do container, `localhost` é o **próprio** container, e o banco é **outro** container, alcançável por `db`. (b) `down` remove containers e redes, mantém volumes; `down -v` remove **também os volumes nomeados do projeto** (os dados). (c) Sem a condição, só se ordena o **início** do container; o PostgreSQL ainda não aceita conexões, e a aplicação falha. Com `service_healthy`, o Compose espera o `pg_isready`. (d) Variável de ambiente aparece em `docker inspect`, `/proc/<pid>/environ` e dumps, e é herdada por processos filhos; o arquivo só existe onde é montado. (e) O PostgreSQL só usa `POSTGRES_PASSWORD` ao **criar** o banco; com o volume existente, a senha antiga continua. (f) O serviço só sobe quando o perfil é pedido (`--profile tools` ou `COMPOSE_PROFILES`).
2. Veja o Passo 3 a 5. Os testes de `docker inspect` (`grep -iE 'secret|password'` não deve mostrar valores) e de ausência do `jwt_secret` repetem o que a J8.07 pede com `java -jar` sem o segredo.
3. (b) `ports: ["127.0.0.1:55432:5432"]` no serviço `db` dentro do override; o risco é esquecer o `127.0.0.1` e **expor o banco à rede**, atravessando o firewall do host (J9.01). (c) O Flyway roda na **subida do contexto**, antes de o Tomcat aceitar tráfego; como o `healthcheck` consulta o Actuator (que só responde depois de `Started`), ele só fica saudável **depois** da migração.
</details>

## 🎤 Na entrevista
1. **"Para que serve o Docker Compose e quando você não o usaria?"** *Resposta-modelo:* descrever em um arquivo versionado os serviços de uma aplicação (imagem, variáveis, portas, volumes, redes, ordem) e subir tudo com um comando: desenvolvimento, testes de integração, demos. Não uso em produção com várias máquinas, porque não faz orquestração (escala entre nós, *rolling update*, autocura): aí é Kubernetes ou um serviço gerenciado.
2. **"Como a aplicação encontra o banco dentro do Compose?"** *Resposta-modelo:* pelo **nome do serviço**, resolvido pelo DNS da rede do Compose (`jdbc:postgresql://db:5432/...`). `localhost` seria o próprio container. O banco nem precisa publicar porta no host.
3. **"Como você garante que a aplicação só sobe depois do banco estar pronto?"** *Resposta-modelo:* `healthcheck` no banco (`pg_isready`) e `depends_on` com `condition: service_healthy`; no script, `docker compose up --wait`. E a aplicação precisa tolerar o banco indisponível mesmo assim (reconexão do pool), porque a ordem só vale na subida.
4. **"Como você passa a senha do banco para a aplicação em container?"** *Resposta-modelo:* nunca na imagem nem no Git. Por **segredo montado como arquivo** (`/run/secrets`, lido por `configtree`), ou variável de ambiente injetada pela plataforma, ou um cofre (AWS Secrets Manager, Vault). Arquivo evita vazar no `inspect` e no ambiente de todos os processos; cuido das permissões do arquivo para o usuário não root conseguir ler.
