## 🎯 Objetivos
Ao final desta aula você consegue:
- **Comparar** *cache-aside*, *read-through*, *write-through*, *write-around* e *write-behind*.
- **Explicar** a **corrida do *cache-aside*** (dado velho no cache até o TTL) e **duas** mitigações.
- **Estimar** a **taxa de acerto** pela distribuição de acessos (e por que **cache de 10%** não dá **10%** de acerto).
- **Proteger** contra *stampede* (*single-flight*, TTL com *jitter*) e **decidir** o que **nunca** se coloca em cache.
- **Configurar** HTTP/CDN (`Cache-Control`, `Vary`) **sem vazar dado privado**.

## 🤔 Por que isso importa
Cache é a **otimização mais barata** e a **maior fonte de bugs sutis** (dado velho, dado de **outro usuário**, estouro em cascata quando expira). A P2.09 mostrou que, **para o saldo por chave primária, o cache não ganhou** (0,017 ms × 0,023 ms): o sênior **decide onde cache não vale** e, quando vale, **escreve a regra de invalidação**.

## 💡 Intuição (explicação simples)
Um **post-it** na tela com o telefone do cliente para não abrir a agenda toda vez. É rápido, mas **se o cliente mudar de número**, o post-it **mente** até alguém trocá-lo. E se **200 atendentes** descobrem **ao mesmo tempo** que o post-it sumiu, **os 200 abrem a agenda juntos**: a agenda (o banco) engasga.

## 🔬 Como funciona por dentro

### 1. Os padrões de leitura e escrita
| Padrão | Leitura | Escrita | Quando | Risco |
|---|---|---|---|---|
| ***Cache-aside*** (preguiçoso) | app: cache → **miss** → banco → **preenche** | grava no banco e **invalida** (`DELETE`) | **padrão** (PayFlow, P2.09) | **corrida** (ver 3), dado velho |
| ***Read-through*** | a **camada de cache** busca no banco | idem | biblioteca decide por você | acoplamento ao provedor |
| ***Write-through*** | — | grava **no cache e no banco** juntos | leitura logo após escrita **precisa** do dado novo | escrita **mais lenta**; guarda dado **nunca lido** |
| ***Write-around*** | cache-aside | grava **só** no banco | dado escrito e **pouco lido** | 1ª leitura é *miss* |
| ***Write-behind*** (*write-back*) | — | grava **no cache**; o banco recebe **depois**, em lote | **alta taxa de escrita** tolerante a perda | **perde dados** se o nó cair antes do *flush* |
Descrições de estratégias de cache e seus *trade-offs*: [AWS ElastiCache: Caching strategies](https://docs.aws.amazon.com/AmazonElastiCache/latest/dg/Strategies.html) e [Microsoft: Cache-Aside](https://learn.microsoft.com/en-us/azure/architecture/patterns/cache-aside).

### 2. Quanto o cache acerta? (medido)
A taxa de acerto **depende da distribuição** dos acessos, não do tamanho do cache. LRU com **1 milhão** de leituras de **100 mil** chaves, popularidade **Zipf (s = 1,0)**:
```
cache com   0.1% das chaves (   100): taxa de acerto = 28.9%
cache com   1.0% das chaves (  1000): taxa de acerto = 50.6%
cache com   5.0% das chaves (  5000): taxa de acerto = 66.4%
cache com  10.0% das chaves ( 10000): taxa de acerto = 73.5%
cache com  30.0% das chaves ( 30000): taxa de acerto = 84.8%
MESMO cache de 10% com acesso UNIFORME (sem chaves quentes): taxa de acerto = 9.9%
```
- Com **chaves quentes** (Zipf), **100 entradas** (0,1%) já acertam **29%**; **1%** das chaves acerta **51%**; mas o ganho **desacelera** (de 10% para 30% das chaves: +11 pontos).
- Com acesso **uniforme**, o **mesmo** cache de 10% acerta **9,9%**: **cache só ajuda quando há localidade**. Antes de pôr cache, **meça** a distribuição dos acessos.

### 3. A corrida do *cache-aside* (e como mitigar)
Sequência **real** (intercalada de forma determinística no laboratório):
```
L1  leitor lê o banco: 100.00 (miss no cache)
E1  escritor grava o banco: 40.00
E2  escritor invalida o cache (DELETE)
L2  leitor PREENCHE o cache com o que leu em L1: 100.00   <- velho!
```
```
banco=40.00 cache=100.00  <- cache velho ate o TTL expirar
com preenchimento condicional por versao: preencheu? false cache=vazio (a proxima leitura busca o valor novo)
```
**Mitigações:** (a) **TTL curto** (limita o dano; **não** elimina); (b) **preencher com versão**: o leitor guarda `(versão, valor)` e só preenche se a versão **ainda** for a atual (no Redis: `SET` condicional com script Lua ou `WATCH`); (c) **invalidar depois do commit** *e* tolerar a janela; (d) **não cachear o que decide dinheiro** (decisão 101: a transferência lê do banco, com trava).

### 4. *Stampede* (a "manada")
200 *threads* pedem a **mesma** chave expirada; o carregamento leva 100 ms:
```
sem protecao (cada uma carrega)    consultas ao banco = 200 ; tempo total = 118 ms
single-flight (uma carrega)        consultas ao banco =   1 ; tempo total = 116 ms
```
Os **200** pedidos foram ao banco; com ***single-flight*** (as demais **esperam o mesmo** carregamento, `ConcurrentHashMap.computeIfAbsent` + `CompletableFuture`), **1**. O tempo **quase não muda** (o ganho é a **carga no banco**: **200×** menos). Em produção: *single-flight* **por instância** + **TTL com *jitter*** (`ttl ± 10%`, para não expirar tudo junto) + **renovação antecipada**. `sync = true` no `@Cacheable` do Spring faz o *single-flight* local (P2.09).

### 5. *Write-behind* e a perda
```
apos a queda: write-through tem 1000 registros no banco; write-behind tem 963 (perdeu 37, que estavam so na memoria)
```
Com *write-behind*, o que **está só na fila em memória** quando o nó cai **some**. Para **dinheiro** (regras 2, 3 e 5 do PayFlow): **proibido**. Serve para **métricas**, contadores de visualização, *rascunhos*.

### 6. CDN e cache HTTP
**CDN** (CloudFront, Cloudflare...) = cache **geográfico** de respostas HTTP perto do usuário ([o que é uma CDN](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/Introduction.html)). O que decide **o que** é guardado são os **cabeçalhos** (`Cache-Control`, `Vary`, `ETag`) conforme o **RFC 9111** ([texto](https://www.rfc-editor.org/rfc/rfc9111); resumo em [MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching)):
| Conteúdo | Cabeçalho | Por quê |
|---|---|---|
| Arquivos do painel com *hash* no nome (`app.3f9a.js`) | `public, max-age=31536000, immutable` | nunca mudam; nome novo a cada versão |
| `index.html`, OpenAPI | `no-cache` (revalida com `ETag`) | muda a cada *deploy* |
| **Saldo, extrato, qualquer dado do usuário** | **`no-store`** (e **nunca** `public`) | **dado privado**: um CDN com `public` serve o extrato de **A** para **B** |
| Respostas que variam por idioma/`Authorization` | `Vary: ...` **ou** não cachear | sem `Vary` correto o cache **mistura** usuários |
**Incidente clássico:** o cache compartilhado guardou uma resposta **autenticada** porque a **chave de cache** não incluía a identidade. **Regra do PayFlow:** `/api/**` sai com `Cache-Control: no-store` (já testável por um teste de MockMvc, P6/J6); só **ativos estáticos** passam pelo CDN.

## 🏗️ Estudo de caso: "o extrato de um cliente apareceu para outro"
**Cenário (ilustrativo).** Para "acelerar o painel", alguém põe o `GET /api/v1/accounts/{id}/statement` atrás do CDN com `Cache-Control: public, max-age=60` e **chave de cache = URL**. O `id` na URL isola contas, mas o **papel** (`ADMIN` vê mais campos) **não** está na chave. Um administrador abre o extrato; o CDN guarda a **versão de admin**; o **dono** pede a mesma URL e recebe **campos que não deveria ver** (e o inverso).
**Diagnóstico.** Resposta com `X-Cache: Hit from cloudfront` e conteúdo **de outra visão**; os logs da aplicação **não mostram** a segunda requisição (**não chegou lá**).
**Opções:** (A) `no-store` em `/api/**` (**simples**); (B) `private` (só o navegador do próprio usuário); (C) `Vary: Authorization` (**fragmenta** o cache por usuário: **acerto ≈ 0**); (D) **cachear no servidor** (Redis) com **chave contendo `sub` e visão**.
**Decisão (ADR 0024):** **(A)** para **toda** `/api/**`; ganho de leitura vem do **modelo de leitura** (S1.05) e de **Redis com chave por `sub`** (decisão 101: exibição, **nunca** decisão financeira), **não** do CDN. **Teste:** um teste que falha se **qualquer** resposta de `/api/**` **não** trouxer `no-store`.

## 🧠 Pausa para lógica
Um cache LRU de **1.000** entradas e **10.000** chaves **uniformes** tem taxa de acerto aproximada de **quanto**? E se `TTL` = 60 s e **todas** as chaves foram carregadas no **mesmo** instante (aquecimento), o que acontece **aos 60 s**?

<details><summary>Dica e solução</summary>

**Dica:** com acesso uniforme, cada acesso cai numa das 10.000 chaves com igual probabilidade; o cache guarda 1.000 delas.

**Solução:** `1.000/10.000 =` **10%** (medido com 10% de 100 mil: **9,9%**). Aos 60 s **todas expiram juntas**: **onda de *misses*** (um *stampede* **em massa**, não de uma chave): a carga no banco **salta** para o **máximo** por alguns segundos. **Correção:** **TTL com *jitter*** (`60 s ± 10%`) para espalhar a expiração. **Variação:** pré-aquecimento **escalonado** (não todas as chaves de uma vez).
</details>

## ⚖️ Trade-offs e quando NÃO usar
- **Não** cache **dado que decide dinheiro** (saldo na transferência, limite): leia **do banco com trava** (decisão 101).
- **Não** cache o que o banco devolve em **microssegundos** (P2.09: 0,017 ms contra 0,023 ms do Redis).
- **Invalidação** é o **problema difícil**: cada cache é **uma réplica com atraso** (S1.02). Se a regra de invalidação não cabe numa frase, **não** cache.
- ***Write-behind*** só com **perda aceitável**; ***write-through*** só se o dado **será lido logo**.
- **CDN** para **ativos e dados públicos**; **dado privado → `no-store`**.

## ⚠️ Erros comuns e boas práticas de produção
- **Cache velho "para sempre"**: sem TTL (ou TTL longo) + invalidação que **falha em silêncio**.
- **TTL idêntico** em tudo (expiração em massa); **sem *jitter***.
- **Chave sem o `sub`** (dado de outro usuário) ou **sem versão do formato** (`v2:`), quebrando **no *deploy*** quando o objeto serializado muda.
- **Cachear o erro/`null`**: uma falha momentânea vira **indisponibilidade** pelo TTL.
- **Não medir**: sem a **taxa de acerto** (métrica `cache.gets{result=hit|miss}` do Micrometer, P6.02) você não sabe se o cache **ajuda**.
- **Cache local e Redis juntos** sem política: **duas** camadas de dado velho.

## 🎤 Na entrevista
1. **"Cache-aside ou write-through?"** *Cache-aside* é o **padrão**: simples, o cache é **descartável**; *write-through* quando o dado é **lido logo** após escrito e a escrita **pode** pagar o custo. Em ambos, **o banco é a verdade**.
2. **"O que é *cache stampede* e como evitar?"** Muitos pedidos recarregando a **mesma** chave expirada. **Single-flight**, **TTL com jitter**, renovação antecipada. Medi: **200 → 1** consultas.
3. **"Por que o cache às vezes mostra dado velho mesmo invalidando?"** **Corrida** entre o leitor que leu o valor antigo e o escritor que invalidou antes do preenchimento; mitigação: **preenchimento condicional por versão** e **TTL**.
4. **"Pode pôr o extrato numa CDN?"** **Não** com dado privado: `no-store`; CDN para **estáticos**; o ganho do extrato vem de **modelo de leitura**.
