## 🎯 Objetivos
Ao final desta aula você consegue:
- **Definir** *event sourcing*: o **estado** é a **sequência de eventos**; a **tabela de estado** é **derivada**.
- **Implementar** um agregado que **reidrata** a partir de eventos, com **concorrência otimista** (`expectedVersion`) e *snapshots*.
- **Evoluir** o formato de um evento (*upcasting*) e **corrigir** um erro **sem reescrever o passado**.
- **Listar** os **custos** (consulta, evolução, privacidade) e **decidir** quando **não** adotar.
- **Justificar** por que o PayFlow **não** adota *event sourcing* (e por que o **ledger já entrega** o principal benefício).

## 🤔 Por que isso importa
*Event sourcing* é o padrão que mais **seduz** (auditoria perfeita, "viagem no tempo") e mais **machuca** (evolução de eventos, consultas, privacidade, **curva de aprendizado**). O sênior sabe **o que ele resolve** e **o que o ledger do PayFlow já resolve de graça**.

## 💡 Intuição (explicação simples)
Um **extrato bancário em papel**: você **nunca apaga** uma linha; se errou, **lança um estorno**. O **saldo** é a **soma** das linhas. *Event sourcing* é tratar **toda** a aplicação como esse **caderno**: o que está no caderno **é** a verdade; o "saldo na etiqueta" é só **conveniência** que pode ser refeita.

## 🔬 Como funciona por dentro

### 1. Estado = dobra (*fold*) dos eventos
Em vez de `UPDATE accounts SET balance = ...`, grava-se `Deposited(100)`, `Withdrawn(60)`. O estado atual é `eventos.fold(estado vazio, apply)`. O **fluxo** (*stream*) de **um agregado** é **a unidade de consistência** (como no DDD, P4.06). Descrição do padrão: [Fowler: Event Sourcing](https://martinfowler.com/eaaDev/EventSourcing.html) e [Microsoft: Event Sourcing pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing).

### 2. Concorrência otimista no fluxo (medida)
Cada fluxo tem **versão** (nº de eventos). Gravar exige `expectedVersion`; se outro gravou antes, **conflito**:
```
segundo saque concorrente: conflito: esperava versao 2 mas o fluxo esta na 3
saldo = 4000 centavos (nunca negativo: o segundo saque foi recusado, nao aplicado)
```
É o `@Version` do JPA (P2.02) **na forma de evento**: o **comando** relê o fluxo, **revalida** a regra (saldo) e **tenta de novo**.

### 3. *Snapshots*: encurtar a reidratação
Reler **1 milhão** de eventos para cada comando é caro. Grava-se um *snapshot* do estado a cada N eventos e reidrata-se do *snapshot* + o que veio depois:
```
sem snapshot: 1000001 eventos lidos em 13 ms; com snapshot na posicao 999000: 1001 eventos em 0 ms; mesmo saldo? true
```
**Ressalva honesta:** **em memória**, 1 milhão de eventos custa **13 ms**, então o *snapshot* quase **não** aparece; **num banco**, ler 1 milhão de linhas custa **ordens de grandeza** mais (rede, E/S, desserialização), e é aí que o *snapshot* vale. **Não medido** aqui. Regra: **não** faça *snapshot* antes de **medir** a reidratação.

### 4. Evolução do evento (*upcasting*)
Eventos são **imutáveis** e **vivem para sempre**; o **formato** muda. O *upcaster* converte a versão **antiga** na **nova** **ao ler**:
```
somando os double do v1: 0.6000000000000001 (imprecisao do double); apos o upcast para centavos inteiros: 60 centavos (= 0,60)
```
O evento v1 guardava `double` (um erro de projeto); o v2 guarda **centavos inteiros**; o `upcast` **traduz** na leitura **sem tocar no histórico** (mesmas regras de compatibilidade da P5.04: **nunca** reutilizar o significado de um campo). Alternativas: **migrar** o *store* (reescreve o passado: arriscado) ou **versionar** o tipo (`DepositedV2`).

### 5. Corrigir sem apagar
```
saldo com o deposito duplicado = 10000; apos o evento de correcao = 5000; o historico (4 eventos) ficou inteiro e auditavel
```
Um depósito duplicado por *bug* **não** se apaga: **acrescenta-se** um evento de **correção**. **É exatamente** o que o PayFlow já faz com `ledger_entries` (regra 5: lançamentos **nunca** são alterados) e com o **lançamento de compensação** `reversal_of` (decisão 114).

### 6. Os custos reais
| Custo | Por quê |
|---|---|
| **Consultas** | "todas as contas com saldo > 1000" **não** se faz sobre eventos: exige **projeção** (S1.05) **sempre** |
| **Evolução** | eventos **eternos** + *upcasters* **acumulados** (cada versão antiga vira código) |
| **Privacidade** | LGPD (J8.07): **eliminar** dado pessoal de um log **imutável**? Soluções: **não** pôr dado pessoal no evento (só ids), ou **criptografar por titular** e **descartar a chave** (*crypto-shredding*); **a decisão jurídica de retenção é do jurídico**, não do desenvolvedor |
| **Consistência da projeção** | tudo é **eventual** (S1.05) |
| **Curva de aprendizado** | o time inteiro pensa em eventos; **depurar** exige ferramentas |

## 🛠️ Exemplo prático
```bash
cd 3-senior/S1-sistemas-distribuidos/lab
JAVA_HOME=/usr/lib/jvm/java-25-openjdk-amd64 $JAVA_HOME/bin/java EventSourcingLab.java
```
O núcleo (Java 25: `sealed` + `switch` por padrões, decisão 93):
```java
sealed interface Ev permits Opened, Deposited, Withdrawn, DepositedV1 {}
record Deposited(String id, long cents) implements Ev {}          // v2: centavos
record DepositedV1(String id, double amount) implements Ev {}     // v1 legado

static Ev upcast(Ev e) { return e instanceof DepositedV1 v ? new Deposited(v.id(), Math.round(v.amount() * 100)) : e; }
static long apply(long bal, Ev e) {
    return switch (upcast(e)) {
        case Deposited d -> bal + d.cents();
        case Withdrawn w -> bal - w.cents();
        case Opened o    -> bal;
        case DepositedV1 v -> throw new AssertionError();   // nunca chega: o upcast o converteu
    };
}
// fluxo: saldo = eventos.stream().reduce(0L, EventSourcingLab::apply, Long::sum)
```
O `switch` **sem `default`** **falha na compilação** se alguém acrescentar um evento novo e esquecer de tratá-lo (decisão 93): é a **rede de segurança** do padrão.

## 🏗️ Estudo de caso: "adotamos event sourcing?" (ADR 0024)
**Contexto.** Depois do CQRS (S1.05), alguém propõe: "e se o `Account` virar *event sourced*? Teríamos auditoria perfeita."
**O que o PayFlow já tem:** `ledger_entries` é **imutável** (regra 5), `balance = Σ lançamentos` (regra 3), correção por **lançamento de compensação** (decisão 114): é, na prática, um **log de eventos do dinheiro**, com `accounts.balance` como **projeção transacional** (e `@Version`, P2.02).
**Opções:**
| Opção | Ganho | Custo |
|---|---|---|
| **A. Manter o ledger** (relacional, imutável) | auditoria **do dinheiro**, SQL, transações ACID, *joins* | `User`, `PaymentRequest`, preferências continuam **estado mutável** (e tudo bem) |
| **B. *Event sourcing* só no `Account`** | histórico **de tudo** que mudou a conta (bloqueio, limite) | **duas** formas de persistir; *upcasting*; projeções **para toda consulta**; Hibernate/Flyway **fora** do caminho do dinheiro (**reescreve** P2) |
| **C. *Event sourcing* em tudo** | uniformidade | **reescrita** do PayFlow; **privacidade**; **time** novo no padrão |
**Decisão (ADR 0024, decisão 189):** **A**. **Não** adotar *event sourcing*. **Gatilhos para reabrir:** (1) **exigência regulatória** de reconstruir o **estado de qualquer entidade** em qualquer instante (não só o dinheiro); (2) **vários** modelos de leitura que **hoje** exigem *joins* proibitivos **e** já estão em CQRS; (3) um **time** que já opera o padrão. **O que adotamos dele:** **eventos imutáveis com versão** (P5.04), **correção por evento** (decisão 114), **reconstrução de projeções** (S1.05).

## 🧠 Pausa para lógica
Um fluxo tem `Deposited(100), Withdrawn(30), Withdrawn(50), Deposited(10)`. (a) Qual o saldo? (b) Se a regra é "saldo nunca negativo" e chegam **dois** `Withdrawn(60)` **concorrentes** sobre a versão que tem saldo 100, o que acontece com o `expectedVersion`? (c) Que evento **corrige** um `Withdrawn(50)` feito por engano?

<details><summary>Dica e solução</summary>

**Dica:** fold; depois a ordem de chegada ao *store*.

**Solução:** (a) `100 − 30 − 50 + 10 =` **30**. (b) Ambos leram a **mesma versão** (saldo 100); o **primeiro** grava (saldo 40); o **segundo** recebe **conflito** (versão mudou), **relê** (saldo 40), **revalida** (`60 > 40`) e **recusa** por saldo insuficiente: **sem** saldo negativo e **sem** lock. (c) **`Deposited(50)`** com **referência** ao evento original (`correctionOf`), **nunca** `DELETE` do `Withdrawn(50)` (decisão 114).
</details>

## ⚖️ Trade-offs e quando NÃO usar
- **Não** use se o que você quer é **auditoria**: uma tabela **imutável** (ledger, *audit log*) dá 90% disso **sem** os custos.
- **Não** use onde há **muita consulta ad hoc** e **pouca** lógica de domínio (CRUD).
- **Não** use **sem** CQRS: o padrão **exige** projeções.
- **Não** ponha **dado pessoal** no evento (LGPD): **ids**, não nomes.
- **Use** quando o **histórico é o negócio** (livro-razão, reservas, *workflow*), há **regra de negócio rica** e o time **aceita** o custo.

## ⚠️ Erros comuns e boas práticas de produção
- **"CRUD disfarçado de evento"** (`AccountUpdated` com o objeto inteiro): perde a **intenção** (por que mudou?).
- **Eventos com nomes do presente** (`Deposit`): são **fatos**, no **passado** (decisão 120).
- **Mudar o significado** de um campo (quebra o histórico): **nunca**.
- **Reprocessar** projeções sem **parar** consumidores/efeitos colaterais: o *replay* **reenvia e-mails** se o projetor **notifica** (separe projeção de **efeito**).
- **Snapshot como verdade**: ele é **cache**; a verdade são os eventos.

## 🎤 Na entrevista
1. **"O que é *event sourcing*?"** O **estado** é a **sequência de eventos** imutáveis; o estado atual é a **dobra** deles. Dá **auditoria** e **reconstrução**; custa **consultas** (projeções), **evolução** (*upcasting*) e **privacidade**.
2. **"Quando você **não** usaria?"** **CRUD**, necessidade só de **auditoria** (uma tabela imutável basta), **muita consulta ad hoc**, **dado pessoal** em eventos, time **sem** experiência. No PayFlow o **ledger imutável** já entrega o principal.
3. **"Como evoluir um evento?"** **Nunca** mudar o significado; **adicionar** campos opcionais, **versionar** o tipo e **upcast** ao ler. Medi: `double` v1 → centavos v2 sem tocar no histórico.
4. **"Como corrigir um erro no histórico?"** Com um **evento de correção**; **nunca** `DELETE`/`UPDATE`.
