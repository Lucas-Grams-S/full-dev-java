## 🤔 Por que isso importa
Para quem nunca trabalhou como dev (o perfil deste treinamento), o PayFlow é **a** evidência: é o único lugar onde quem contrata pode ver como você pensa, testa e decide. A documentação do GitHub diz que o README "é muitas vezes o primeiro item que um visitante vê" e lista o que ele costuma ter: o que o projeto faz, por que é útil, como começar, onde pedir ajuda e quem mantém. Um entrevistador técnico vai além: abre um teste, uma ADR, o histórico. Um repositório bom não garante a vaga; um repositório **com uma senha no histórico** ou que **afirma "em produção"** sem estar pode tirá-la.

## 💡 Intuição (explicação simples)
Restaurante com **cozinha aberta**: o cliente não vê só o prato, vê **como** a equipe trabalha (limpeza, ordem, quem faz o quê). O portfólio é a sua cozinha aberta. O cardápio na porta (README) diz o que se serve e como pedir; a cozinha (código, testes, ADRs) prova que o cardápio é verdadeiro. E ninguém deixa a chave do cofre pendurada na parede da cozinha, nem "só por um dia".

## 🔬 Como funciona por dentro

### 1. O que o GitHub mostra (e onde)
| Peça | Regra (documentação do GitHub) | Uso no portfólio |
|---|---|---|
| **README** | reconhecido na **raiz**, em `.github/` ou em `docs/` | a porta de entrada do PayFlow |
| **Diagramas** | Markdown aceita **Mermaid** (e GeoJSON, TopoJSON, STL) em arquivos, *issues* e PRs | o diagrama de arquitetura do `projeto-central.md`, vivo no repositório |
| ***Badge* de CI** | `https://github.com/OWNER/REPOSITORY/actions/workflows/WORKFLOW-FILE/badge.svg` | o `ci.yml` da J10 mostrando verde (ou vermelho: não esconda) |
| ***Topics*** | minúsculas, números e hífens; **até 50 caracteres**; **no máximo 20**; sempre **públicos** | `java`, `spring-boot`, `postgresql`, `kafka`, `outbox-pattern`… |
| **Fixados** (*pinned*) | **até seis** repositórios e *gists*, combinados | o PayFlow primeiro; nada de seis tutoriais |
| **README de perfil** | repositório **com o nome do seu usuário**, **público**, com `README.md` na raiz | três linhas: quem você é, o que está construindo, onde ver |
| **Licença** | **sem licença valem as leis de direito autoral**: ninguém pode reproduzir, distribuir ou criar obra derivada | MIT ou Apache-2.0 se quiser que leiam **e** reusem |
| **E-mail dos *commits*** | dá para usar o endereço *no-reply*; *commits* antigos **continuam** com o e-mail anterior | decida **antes** do primeiro *push* público |

### 2. Anatomia do README de portfólio
Oito seções, nesta ordem (a ordem é a do leitor: o que é → por que ler → como ver funcionando → como confiar):
1. **O que é** (duas frases; diga que é **de estudo**).
2. **O que este projeto demonstra**: tabela **competência → onde ver → evidência**. É a matriz de competências (`00-guia/matriz-de-competencias.md`) virada para fora: cada linha aponta um arquivo, um teste ou uma ADR.
3. **Arquitetura**: um diagrama Mermaid (o do seu nível atual) e, no máximo, um parágrafo.
4. **Como rodar**: um bloco `bash` com **poucos** comandos que funcionam num **clone limpo** (o checkpoint Júnior pedia 3).
5. **Como testar**: `./mvnw verify` e o que precisa estar no ar (Docker para Testcontainers).
6. **Decisões**: link para as ADRs, a RFC e o design doc (S7).
7. **Limitações**: o que **não** está pronto ou **não** foi executado (sem produção, AWS não aplicada, números de laboratório). É o que separa portfólio de propaganda.
8. **Licença**.

**Português e inglês:** `README.md` em português e `README.en.md` em inglês, com **as mesmas seções**, o mesmo diagrama e um link de um para o outro. Vagas internacionais leem o inglês; avaliadores brasileiros leem o português; um README pela metade em uma das línguas diz "deixei para depois".

### 3. O histórico é público, inteiro
Um repositório público publica **todos os *commits***, não só o último. Apagar um arquivo num *commit* novo **não** apaga o arquivo dos *commits* antigos. A documentação do GitHub sobre remover dados sensíveis é direta: se o dado é um **segredo**, o **primeiro passo** é **revogar ou trocar** o segredo; reescrever o histórico vem depois e tem efeitos colaterais (alto risco de **recontaminação** por quem tem um clone antigo, PRs fechados sem *diff*, assinaturas perdidas, proteção de *branch* desligada temporariamente). A ferramenta recomendada é o `git-filter-repo`; o próprio manual do `git filter-branch` avisa que ele tem "uma infinidade de armadilhas".

Para usuários, o GitHub tem ***push protection*** **ligada por padrão**, que **impede enviar segredos a repositórios públicos**. Ela reconhece **tipos conhecidos** de segredo; não confie nela para a senha do seu banco de laboratório. A defesa continua a da J8.07: segredo **fora** do repositório, `.gitignore`, varredura no CI (S5.04).

### 4. O que um repositório mostra sobre senioridade
| Sinal | Onde aparece | Módulo |
|---|---|---|
| Decisões com alternativas e consequências | `projeto/adrs/`, RFC, design doc | S7.01, S7.02 |
| Testes que **falham** sem a regra | mutantes mortos, testes de arquitetura com *fixture* ruim | S7.05, P4 |
| Mudança pequena e explicada | *commits* convencionais, PRs com "como testei" e "como reverter" | J0.05, S7.05 |
| Operação pensada | SLOs, *runbooks*, alertas testados | S4 |
| Honestidade técnica | seção de limitações; "premissa" × "medido" | todo o curso |

**Como ler (e o que eu conferi à mão):**
1. **Não há `LICENSE`** no repositório público do treinamento. Pela documentação do GitHub, isso quer dizer que, legalmente, ninguém pode copiar nem adaptar o material. Pode ser exatamente o que você quer, ou não: é uma **decisão sua** (registrada em Correções pendentes do `progresso.md`, **não** corrigida aqui).

```text
   (commit, file) pairs with the secret, counting refs/original: 1

   objects still in the repository with the secret: 0

4) the clone made before the rewrite:
   (commit, file) pairs with the secret: 1

=> rewriting fixes YOUR copy; the secret already left. Revoke/rotate it first (GitHub docs), then clean the history.
```
1. A página do repositório (o `HEAD`) mostra **0**; quem clona recebe o *commit* `7078019` com o segredo. `git log -S <texto>` acha **onde** ele entrou e saiu: use antes de publicar.
2. A reescrita **muda todos os *ids*** (`36c4461` → `f7b807d`): quem tinha clone precisa recomeçar (efeito colateral citado pelo GitHub).
3. Logo depois da reescrita, o segredo **ainda** estava alcançável por `refs/original` (o *backup* do `filter-branch`); só sumiu depois de apagar essas referências, expirar o *reflog* e rodar o `gc`.
4. O clone feito **antes** continua com o segredo. Por isso a ordem é: **trocar o segredo primeiro**.

## 🏗️ Estudo de caso: publicar o PayFlow com o histórico inteiro?
**Contexto.** Você vai tornar o `payflow` público para começar a se candidatar. São ~60 semanas de *commits*: muitos bons (pequenos, convencionais), alguns constrangedores ("wip", "agora vai"), e você não lembra se algum arquivo `.env` passou pela J8 ou pela J9.

**Opções.** (A) Publicar como está. (B) Apagar o histórico: um *commit* único "initial commit" com tudo. (C) Varrer o histórico (`hygiene` no `HEAD`, `git log -p -S` e uma ferramenta de segredos por **todos** os *commits*), **trocar** o que for achado, limpar com `git-filter-repo` **antes** do primeiro *push* público, acrescentar `LICENSE` e o README de portfólio, e publicar **com** o histórico.

<details><summary>Decisão (proposta) e por quê</summary>

**(C).** (A) arrisca publicar um segredo que vira incidente (e pergunta na entrevista). (B) é seguro, mas joga fora a **melhor evidência** que um júnior tem: a evolução do projeto, *commit* a *commit*, com testes e ADRs aparecendo ao longo do tempo. Mensagens feias de *commit* **não** são problema grave; um segredo real é. Limpar o histórico **antes** do primeiro *push* público é barato (ninguém tem clone); depois, é caro (a seção 4 do laboratório). Registre a decisão numa ADR curta (S7.01) e deixe a varredura de segredos no CI (S5.04) para o futuro.
</details>

## ⚖️ Trade-offs e quando NÃO usar
- **Um projeto profundo × muitos rasos:** seis tutoriais fixados dizem "sigo instruções"; um PayFlow com decisões diz "decido". Repositórios de estudo antigos podem ficar, **arquivados** e não fixados.
- **README longo × curto:** o README é **porta**, não manual. Detalhes vão para `docs/`; o README aponta.
- **Bilíngue custa manutenção:** cada mudança vira duas. Se não for manter o inglês, prefira um README em inglês **curto e correto** a um longo desatualizado; o *linter* de paridade ajuda a não esquecer.
- **Licença aberta × nenhuma:** MIT/Apache permitem reuso (inclusive comercial); sem licença o código fica **visível**, mas não reutilizável. Para portfólio, a escolha é sua: o erro é **não escolher sabendo**.
- **Diagramas envelhecem:** um diagrama errado é pior que nenhum. Um só, no nível de contêiner, revisto a cada marco.
- **Quando NÃO usar o *linter*:** para decidir conteúdo. Ele garante forma (seções, links, paridade), não que a tabela de evidências seja verdadeira.

## ⚠️ Erros comuns e boas práticas de produção
- **"Como rodar" que não roda:** teste num **clone limpo** (outra pasta, sem `~/.m2` aquecido se possível). Os erros que o leitor verá são os da J9 e da J7.05, por exemplo:
  ```text
  java.lang.IllegalStateException: Could not find a valid Docker environment. Please see logs and check configuration
  ```
  (a mensagem do Testcontainers sem Docker, J7.05): diga no README que os testes **precisam de Docker**.
- **Afirmar o que não é verdade:** "em produção", "milhares de usuários", "*production-ready*". O entrevistador vai perguntar; a seção de limitações protege você.
- **Segredo apagado num *commit* novo:** continua no histórico (laboratório). Troque o segredo; depois limpe.
- **Link relativo quebrado** depois de renomear um arquivo (mutante 2): rode o *linter* no CI.
- **E-mail pessoal nos *commits*:** decida antes de publicar; *commits* antigos não mudam de e-mail sozinhos.
- **Fork de tutorial sem mudança** fixado no perfil: conta contra.
- ***Badge* mentiroso** (aponta para outro *workflow* ou está sempre vermelho): ou conserte o CI, ou tire o *badge*.

## 🎤 Na entrevista
1. **"Me apresente um projeto do seu GitHub."** *Resposta-modelo:* em dois minutos: o problema (carteira com transferências que não podem duplicar nem perder dinheiro), duas decisões com o *trade-off* (travas em ordem fixa × otimista; Outbox × publicar direto), uma coisa medida (o teste que falhava antes da correção) e o que eu faria diferente. Termino apontando a seção de limitações.
2. **"Você publicou uma senha no GitHub. O que faz?"** *Resposta-modelo:* trato como incidente: **troco/revogo** a credencial primeiro (o histórico já foi copiado por quem clonou), confiro se ela foi usada (logs), depois limpo o histórico com `git-filter-repo` coordenando com quem tem clone, e fecho a causa: segredo fora do repositório, `.gitignore` e varredura no CI.
3. **"Por que eu deveria confiar nesse número do seu README?"** *Resposta-modelo:* porque ele diz **onde** foi medido e com que premissas; os números de desempenho são de laboratório, não de produção, e o README diz isso.
