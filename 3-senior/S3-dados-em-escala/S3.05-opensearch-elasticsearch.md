## 🤔 Por que isso importa
Alguém sempre pede "uma busca": **"ache a transferência para o *Joao* na padaria"** (sem acento, com erro de digitação, em qualquer ordem). `WHERE memo ILIKE '%joao%'` **não usa índice B-tree** (curinga no início) e **varre tudo**. O reflexo "vamos pôr o Elasticsearch" **cria um sistema novo** (cluster a operar, dados duplicados, **consistência eventual**, custo, segurança). O sênior **mede primeiro** o que o banco que **já existe** consegue, e **só adiciona** o motor quando o **gatilho** diz.

## 💡 Intuição (explicação simples)
O **índice remissivo** no fim de um livro: em vez de ler as 400 páginas procurando "padaria", você vai à lista alfabética (**termo → páginas**). O motor de busca **monta esse índice** para **todas** as palavras e ainda **normaliza** (minúsculas, sem acento, singular/plural) e **ordena por relevância**. `LIKE '%padaria%'` é **folhear o livro inteiro**.

## 🔬 Como funciona por dentro

### 1. O índice invertido e a **análise**
Cada texto passa por um **analisador**: **tokenização** (separa palavras), **normalização** (minúsculas, **remover acentos**), **remoção de *stopwords*** ("de", "para"), ***stemming*** (reduz "pagamentos" e "pagamento" ao mesmo radical). O resultado alimenta um **índice invertido**: `termo → lista de documentos`. A consulta passa **pelo mesmo analisador** e o índice devolve os documentos **sem varrer**. A **relevância** (BM25 no Lucene) pondera **frequência do termo** e **raridade** (palavra rara pesa mais). Vale para **PostgreSQL** (`tsvector` + GIN) **e** para o **Lucene** (OpenSearch/Elasticsearch): é a **mesma ideia**; muda **o que** vem pronto.

**D) O custo de manter os índices** — inserir 100 mil linhas com **0**, **1** e **2** índices GIN:

no index:

Sem índice: **~0,1 a 0,2 s**; com o de trigramas: **~1,4 a 2 s** (**~8 a 17×**); com trigramas **+** *full-text*: **~2 a 3 s**. **Cada índice de busca encarece a escrita** (o GIN tem **fila de pendências** e atualização mais pesada). Para o PayFlow, o **caminho de escrita é o dinheiro** (o ledger): **índice de busca não vai na tabela do ledger**; vai em **tabela de leitura** (o `statement_entries` da S1.05), **fora** do caminho crítico.

**E) O ESCOPO muda tudo:**

```text
## E) the SCOPE of the search: one account (1,000 rows per account here) x the whole table

                                      QUERY PLAN

         Sort Key: id DESC
         Sort Method: top-N heapsort  Memory: 28kB

               Recheck Cond: (account_id = 424)
               Filter: (memo ~~* '%mercado%'::text)
               Rows Removed by Filter: 955
               Heap Blocks: exact=1000
               ->  Bitmap Index Scan on idx_memo_account (actual rows=1000.00 loops=1)
                     Index Cond: (account_id = 424)
                     Index Searches: 1
 Planning Time: 1.715 ms
 Execution Time: 4.783 ms
```

A busca **dentro de uma conta** (~1.000 lançamentos) usa o **índice B-tree por `account_id`** e **filtra o texto nessas linhas**: **~5 ms** (1.000 páginas lidas, porque cada conta está **espalhada** pela tabela; um índice de **cobertura** ou a tabela agrupada por conta baixaria isso), **sem** trigrama, **sem** motor de busca. **A pergunta que decide a arquitetura é "buscar onde?"**: no **extrato do próprio usuário** (poucas linhas por conta) o **PostgreSQL basta**; a busca **global** (suporte/*back-office* procurando em **todas** as contas, ou "ache o comerciante X") é a que **precisa** de índice de texto.

### 3. Quando o PostgreSQL **não** basta
| Necessidade | PostgreSQL (`tsvector` + `pg_trgm`) | OpenSearch/Elasticsearch |
|---|---|---|
| Palavras, sem acento, plural, ordem livre | **sim** (medido) | sim |
| Relevância **ajustável** (peso por campo, sinônimos, *boost*) | básico (`setweight`, `ts_rank`) | **rico** (BM25, `multi_match`, *function score*) |
| Tolerância a erro de digitação **barata** | **cara** para palavra comum (medido: ~460 ms) | `fuzziness: AUTO` (índice de Levenshtein) |
| **Facetas/agregações** sobre resultados (contagens por tipo/mês) | `GROUP BY` (lento em volume) | **agregações** nativas |
| **Autocompletar** | `LIKE 'pre%'` + índice, limitado | analisadores de *n-gram*/sugestores |
| Busca em **várias entidades** juntas | UNION/visões, complexo | **um índice** (ou vários com alias) |
| Volume (centenas de milhões de documentos), **latência** estável | limita pelo primário | **escala horizontal** (shards) |
| **Operação** | **nenhuma extra** | **cluster** (JVM, shards, *snapshots*, versões) |
| **Consistência** com a fonte | **transacional** (mesmo banco) | **eventual** (cópia assíncrona: S3.06) |

### 4. Parte 2 (leitura): o desenho no OpenSearch
> **Não executado.** **Release mais recente** do repositório `opensearch-project/OpenSearch` (API do GitHub, lida em 2026-11-14): **3.9.0** (publicada em 2026-09-29); a **sintaxe** abaixo vem da **documentação** (`docs.opensearch.org`) e **precisa ser validada** num cluster antes de ser adotada. **Elasticsearch** tem API **muito parecida** (por **licenciamento** e ritmo de evolução, as duas **divergem** a cada versão: confira a da sua escolha).

**Mapeamento** (esquema) com **analisador customizado** (acento + *stemming* + *stopwords* do português) e `dynamic: strict` (campo inesperado **falha**, em vez de virar mapeamento por acidente):
```json
PUT /statement-entries-v1
{
  "settings": {
    "number_of_shards": 1,
    "number_of_replicas": 1,
    "analysis": {
      "filter": {
        "pt_stop": { "type": "stop", "stopwords": "_portuguese_" },
        "pt_stem": { "type": "stemmer", "language": "portuguese" }
      },
      "analyzer": {
        "pt_search": {
          "type": "custom",
          "tokenizer": "standard",
          "filter": ["lowercase", "asciifolding", "pt_stop", "pt_stem"]
        }
      }
    }
  },
  "mappings": {
    "dynamic": "strict",
    "properties": {
      "account_id":   { "type": "keyword" },
      "entry_id":     { "type": "keyword" },
      "occurred_at":  { "type": "date" },
      "type":         { "type": "keyword" },
      "amount_cents": { "type": "long" },
      "counterparty": { "type": "text", "analyzer": "pt_search" }
    }
  }
}
```
Notas: **dinheiro em `long` (centavos)**, nunca `float` (decisão 4; o valor **exibido** vem do banco); `keyword` = valor **exato** (filtro/ordenação/agregação), `text` = **analisado** (busca); **sem** dado pessoal além do necessário (**LGPD**: o índice é **outra cópia** de dado pessoal, com **retenção e eliminação** próprias).

**Consulta** (filtro **obrigatório** pelo dono, texto com **tolerância a erro**, relevância depois recência):
```json
GET /statement-entries/_search
{
  "query": {
    "bool": {
      "filter": [
        { "term":  { "account_id": "<id da conta do usuário autenticado>" } },
        { "range": { "occurred_at": { "gte": "2026-01-01" } } }
      ],
      "must": [
        { "match": { "counterparty": { "query": "joao padaria", "operator": "and", "fuzziness": "AUTO" } } }
      ]
    }
  },
  "sort": [ { "_score": "desc" }, { "occurred_at": "desc" } ],
  "size": 20
}
```
**Autorização:** **o `account_id` vem do token** (`sub` → contas do usuário, P10.03), **nunca** do corpo ou da URL (senão a busca vira **IDOR**: ler lançamentos de outro). O filtro **sempre** no **servidor** (um *alias* filtrado por conta é uma defesa em profundidade; **não** substitui o filtro).

**Indexação em lote** (`_bulk`, NDJSON: uma linha de ação, uma de documento; `index` com `_id = entry_id` é **idempotente**: reenviar **sobrescreve**, não duplica):
```text
POST /_bulk
{ "index": { "_index": "statement-entries-v1", "_id": "01a1dcc5-..." } }
{ "account_id": "...", "entry_id": "01a1dcc5-...", "occurred_at": "2026-09-10T12:00:00Z", "type": "DEBIT", "amount_cents": 1500, "counterparty": "Padaria São João" }
```
**Reindexar sem parar** (mudou o analisador? **não dá para alterar** o de um campo existente): criar `statement-entries-v2`, **copiar** (API `_reindex`), **trocar o *alias*** `statement-entries` de `v1` para `v2` **atomicamente**, e remover o `v1` depois. É o **expand/contract** da S3.01 **no mundo da busca**.

**Visibilidade:** o documento indexado **não aparece na hora**: aparece no próximo *refresh* do índice (configurável por índice). **A busca é eventual**: um lançamento recém-feito pode **faltar** nela alguns segundos. **Por isso o extrato "oficial" e o saldo NUNCA saem do motor de busca** (decisão 211).

### 5. A decisão do PayFlow (**ADR 0026**, decisão 211)
1. **Busca no extrato do usuário:** **PostgreSQL**: filtro por **conta + período** (índice B-tree, S3.02) e texto sobre as linhas **dessa conta** (medido: ~5 ms para ~1.000 linhas). **Sem OpenSearch.** Se for preciso busca por palavra com acento/plural: coluna `tsvector` **gerada** na **tabela de leitura** (`statement_entries`), **nunca** no ledger.
2. **Busca global** (suporte, *back-office*, conciliação por contraparte): **começa** com `pg_trgm`/*full-text* **na réplica de relatórios** (S3.03); **OpenSearch** só se **um gatilho** disparar:
   - **G1** a busca global precisa de **relevância/sinônimos/autocompletar** que o banco não entrega; **ou**
   - **G2** o p99 da busca no banco, medido **sob carga** (S2.06), **passa do orçamento** (a definir) **depois** de índices e réplica; **ou**
   - **G3** **facetas/agregações** sobre resultados viram requisito de produto; **ou**
   - **G4** há **várias fontes** a buscar juntas.
3. **Se adotado:** **índice** alimentado **por CDC** (S3.06), **idempotente**, **`dynamic: strict`**, **alias**, **filtro por dono no servidor**, **retenção** do índice, e o motor **fora** de qualquer decisão de dinheiro.

## 🏗️ Estudo de caso: "o endpoint de busca que derrubou o primário"
**Sintoma.** Depois de um *release*, o p99 do checkout sobe de 90 para 700 ms; a CPU do **primário** passa de 40% para **95%**; o novo endpoint `GET /transfers/search?q=` (back-office) faz `memo ILIKE '%' || :q || '%'` **sobre `transfers`** (milhões de linhas).

**Diagnóstico.** `EXPLAIN` mostra **varredura paralela** da tabela (a seção 2-A: ~220 ms e **3 processos** por chamada). Cinco analistas pesquisando por minuto ocupam **vários núcleos o tempo todo**, **competindo** com o checkout. (**Cenário construído**: números **inventados**; o **mecanismo** — o custo da varredura — foi **medido**.)

**Opções.**
1. **`pg_trgm` + GIN** em `transfers`: **2 a 3,5×** mais rápido (medido), mas **a escrita das transferências paga o índice** (**~8 a 17×** no laboratório): **no caminho do dinheiro**.
2. **Mover a busca para a réplica de relatórios** (S3.03): o primário **sai da linha de fogo**; o índice (se houver) fica **só lá**? Réplica **física** herda os **mesmos** índices do primário; então o **índice** precisaria existir no primário também. **Alternativa:** a busca roda **sem** índice na réplica, **com `statement_timeout`**, limitada.
3. **Tabela de busca separada** (`transfer_search`, alimentada **depois** da transação): índice de texto **fora** do caminho do dinheiro. **Custo:** consistência eventual e um *job*.
4. **OpenSearch** (por CDC): **resolve**, mas é **o maior custo operacional**; só se um gatilho (G1–G4) disparar.

**Decisão.** (3) **no PostgreSQL**, na **tabela de leitura**, **atualizada pelo evento** (Outbox, P3.09), com `statement_timeout` de 5 s e **limite de linhas**; (4) **só** com gatilho. **Consequência:** a busca pode estar **segundos atrás** do ledger (aceito: **não** é o extrato oficial).

## ⚖️ Trade-offs e quando NÃO usar
- **Um motor de busca é um segundo banco** (e nunca a **fonte da verdade**): **cópia derivada**, que **pode divergir**: precisa de **reconstrução** (reindexar do banco) e de **monitoramento de defasagem** (S3.06).
- **Custo operacional:** JVM, **shards** (número de *shards* **não se altera** depois sem reindexar), versões e *upgrades*, *snapshots*, segurança do cluster (autenticação e TLS), **memória**. Serviço gerenciado (**Amazon OpenSearch Service**, equivalentes Azure/GCP) **reduz** o trabalho, não o custo.
- **Não usar** quando: a busca é **dentro de um escopo pequeno** (uma conta), o **volume** é moderado e o **banco** responde no orçamento; o time **não tem** quem opere; os dados são **sensíveis** e a **eliminação** (LGPD) numa segunda cópia é **difícil** de garantir.
- **Usar** quando: **relevância** e **facetas** são o **produto**, o **volume** exige escala horizontal, ou **muitas fontes** são buscadas juntas.
- **Elasticsearch × OpenSearch:** mesma origem (Lucene); **diferem** em licença, recursos e ritmo; confira **versão** e **cliente Java** (o cliente oficial de cada um **é distinto**; **não** verificado aqui).

## ⚠️ Erros comuns e boas práticas de produção
**Mensagens e problemas típicos** (**da documentação/uso**; não reproduzidos aqui): `mapper_parsing_exception` (campo de tipo diferente do mapeado), *cluster* `yellow` (réplicas não alocadas), `circuit_breaking_exception`, `too_many_requests` (fila de escrita cheia), `index_not_found_exception` (alias errado).
- **Busca no caminho crítico de escrita:** índice de texto na tabela do ledger (medido: escrita **~8 a 17×** mais lenta).
- **`LIKE '%x%'` em tabela grande** (medido: varredura): **sempre** passe por `EXPLAIN`.
- **Autorização no cliente:** `account_id` vindo do corpo/URL.
- **Mapeamento dinâmico** em produção (`dynamic: true`): um campo estranho **cria** mapeamento e **explode** o número de campos.
- **Float para dinheiro** no índice.
- **Sem plano de reindexação:** o analisador **mudou** e você não pode alterar o campo (use `v2` + *alias*).
- **Tratar a busca como fonte da verdade** (saldo, extrato oficial).

Tabela: **extrato do usuário** → B-tree `(account_id, occurred_at DESC)` + filtro de texto (medido ~5 ms para ~1.000 linhas); **back-office** → `tsvector`/`pg_trgm` na **réplica de relatórios**; **OpenSearch** só pelos gatilhos. Gatilhos: G2 "p99 da busca global sob carga > X ms (a definir com S2.06)"; G3/G4 por **requisito de produto**. Teste: usuário A busca com `account_id` de B → **vazio/404** (como a decisão 25/43). ## 🎤 Na entrevista
1. **"Quando você usaria Elasticsearch/OpenSearch?"** Quando **relevância**, **facetas** ou **volume** da busca excedem o que o banco entrega **no orçamento de latência**, **medido**. Antes, meço o PostgreSQL (`tsvector`, `pg_trgm`): no meu laboratório o *full-text* em português respondeu em **~45 ms** em 1 milhão de linhas e a busca **por conta** em **~5 ms**.
2. **"Por que `LIKE '%x%'` é lento?"** Não há prefixo para o B-tree: **varredura** (medi ~220 ms em 1 milhão, com 3 processos). Soluções: **trigrama + GIN** (aceita curinga), **full-text** (palavras) ou um **motor** de busca.
3. **"Como manter o índice de busca consistente com o banco?"** É **cópia derivada**, **eventual**: alimento **por CDC/Outbox** com `_id` do documento = chave de negócio (**idempotente**), **reconstruo** do banco quando divergir, **monitoro a defasagem** e **nunca** uso a busca para decisão de dinheiro.
4. **"Como mudar o analisador de um campo em produção?"** **Não dá** no mesmo índice: crio `v2`, **reindexo** e **troco o alias** atomicamente (expand/contract).
