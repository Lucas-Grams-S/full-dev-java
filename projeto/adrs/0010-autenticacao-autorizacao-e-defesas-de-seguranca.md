# ADR 0010 — Autenticação, autorização e defesas de segurança do PayFlow

- **Status:** aceita (J8, 2026-11-13). Os laboratórios da J8 (Spring Boot 4.1.2, Spring Security 7.1.2, JDK 25) foram **executados**; a aplicação no repositório do aluno foi **revisada por leitura** e a validação prática fica para o fim do treinamento.
- **Contexto:** o PayFlow tinha login provisório **sem senha** (decisão 24), sessão própria em memória, um `AuthInterceptor` que protegia só os caminhos listados (permitido por padrão), nenhum token CSRF, nenhuma defesa de navegador, papéis no banco sem uso, segredos e logs sem política. Há dois tipos de cliente: o navegador do painel (cookies, formulários) e programas que consomem a API REST `/api/v1`.
- **Opções:** (1) manter o interceptor e acrescentar senha; (2) Spring Security com **uma** cadeia e sessão para tudo; (3) Spring Security com JWT para tudo, inclusive o painel; (4) **duas cadeias**: sessão e CSRF para o painel, JWT *stateless* para a API; (5) delegar a um servidor de autorização (Keycloak, OAuth2/OIDC) já agora.
- **Decisão:** a opção **4**. Spring Security 7 com **negar por padrão** (`anyRequest().authenticated()`), duas `SecurityFilterChain` (`/api/v1/**` primeiro, o resto depois). **Painel:** `formLogin` com e-mail e senha, sessão do contêiner (`PAYFLOW_SESSION`, `HttpOnly`, `SameSite=Lax`, `Secure` em produção, 30 min, troca de id no login), CSRF obrigatório (`th:action`), CSP e cabeçalhos, redirecionamentos `303`. **API:** `oauth2ResourceServer` com JWT **HS256** emitido pelo próprio PayFlow (`POST /api/v1/auth/token`, 15 min, claims mínimas), sem CSRF, com CORS, erros 401/403 em Problem Details. Senhas com `DelegatingPasswordEncoder` (`{bcrypt}`). Papéis `USER`/`ADMIN` aplicados na cadeia **e** com `@PreAuthorize`; autorização **por objeto** nos casos de uso (`404` para recurso alheio). Limite de tentativas (`429`), auditoria sem dado pessoal, política de senha do NIST, segredos só por ambiente (a aplicação não sobe sem o do JWT), varredura de dependências em perfil separado, mapa de dados da LGPD.
- **Consequências:**
  - (+) Cada cliente usa o mecanismo certo: o navegador mantém sessão revogável e `HttpOnly`; a API fica sem estado e imune a CSRF.
  - (+) *Negar por padrão* acaba com a classe de falha "rota esquecida"; a regra vale para estáticos e para o `/error`.
  - (+) As barreiras de URL e de método são independentes (defesa em profundidade), e há testes que derrubam uma de cada vez e uma matriz de IDOR.
  - (−) **Dois mecanismos** de autenticação para manter e testar; o `CurrentUser` precisa de um resolvedor que aceita os dois.
  - (−) **JWT não se revoga**: um token roubado vale até 15 minutos; **não há refresh token** (o cliente loga de novo). A evolução é um servidor de autorização (P10) com *refresh* revogável e RS256.
  - (−) HS256 usa um segredo compartilhado: quem valida poderia assinar; serve enquanto emissor e validador são a mesma aplicação. Trocar o segredo derruba todos os tokens (a rotação com duas chaves é um desafio da J8.07).
  - (−) O limitador de tentativas é **em memória e por e-mail** (uma instância; permite trancar a conta de outra pessoa de propósito): evolui para e-mail+IP em Redis (P2) e MFA (P10).
  - (−) Sessão em memória do Tomcat: some a cada reinício e não é compartilhada entre instâncias (Redis, P2/P7).
  - (−) Os testes antigos (`ApiClient`, `PayflowWebTest`, `TransfersControllerWebTest`) precisam de migração (documentada na J8.03 e na J8.04).
