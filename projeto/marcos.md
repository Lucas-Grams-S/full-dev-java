# Marcos do projeto PayFlow

Cada marco é uma tag no Git criada ao fim do módulo. O texto descreve o que o projeto deve ter nesse ponto.

| Tag | Módulo | O que o projeto tem |
|---|---|---|
| `payflow-J0` | J0 — Ambiente e ferramentas do dev | Repositório `payflow` criado no GitHub, com `.gitignore`, README e primeiro commit. |
| `payflow-J1` | J1 — Java e lógica de programação | Mini-projeto `mini-bank` em console (contas, depósito, saque, extrato), com testes JUnit, reaproveitado como domínio do PayFlow. |
| `payflow-J2` | J2 — Como a web funciona | Servidor HTTP mínimo (`com.sun.net.httpserver`) expondo contas do `mini-bank` em JSON, mais um cliente com `HttpClient`. |
| `payflow-J3` | J3 — Bancos de dados relacionais | O repositório `payflow` vira um projeto Maven (`com.payflow`): esquema do PayFlow (`users`, `accounts`, `transfers`, `ledger_entries`) em migrações Flyway (`db/migration`, V1 a V4) com seed repetível de dev, acesso JDBC (`com.payflow.db`: repositórios e transferência transacional) e 11 testes contra PostgreSQL real. |
| `payflow-J4` | J4 — Front-end essencial para dev backend | Painel web do PayFlow (`com.payflow.web`): login provisório sem senha, contas, extrato com depósito (Post/Redirect/Get) e "Mais antigos" por `fetch`, renderizado com Thymeleaf sobre o servidor JDK e o JDBC da J3; endpoint JSON do extrato; `app.css` responsivo e acessível (axe sem violações); protótipos em `web-prototype/`; 21 testes (11 da J3 + 10 do painel). |
| `payflow-J5` | J5 — Spring Framework e Spring Boot | Monólito Spring Boot 4.1.2 (`com.payflow`): entidades JPA (`User`, `Account`, `LedgerEntry`, `Transfer`, `@ManyToOne(LAZY)`, `@Version`) com `ddl-auto: validate`, repositórios Spring Data, regras no domínio e serviços `@Transactional` (depósito, transferência, histórico sem N+1), painel em Spring MVC com os templates da J4, extrato com `Slice`, depósito validado (Bean Validation, `Locale` fixo), perfis `dev`/`test` (sem perfil = produção), logs com `requestId`, Actuator (`health`,`info`), e 87 testes contra PostgreSQL real. O JDBC da J3 e o servidor manual da J4 foram removidos. |
| `payflow-J6` | J6 — APIs REST | API REST `/api/v1` do PayFlow (contas, depósitos, extrato paginado e filtrável, transferências atômicas e idempotentes, saldo convertido via `RestClient`), DTOs com MapStruct, erros em Problem Details, versionamento, CORS, OpenAPI (springdoc) e 43 testes novos. |
| `payflow-J7` | J7 — Testes e qualidade | Suíte em camadas sobre os 130 testes da J5/J6: unidade (`AmountsTest`, `AccountTest`, `TransferServiceUnitTest` com Mockito), fatia web (`TransfersControllerWebTest`), fatia JPA (`RepositoriesJpaTest`) e fumaça do contexto; **banco PostgreSQL 18 por Testcontainers** (`@PayflowTest`, sem `payflow_test` local, sem H2); JaCoCo com piso medido; Checkstyle e SpotBugs no `mvn verify`; `Masking` (TDD); modelo de PR, lista de revisão e *hook* de Conventional Commits. 43 métodos de teste novos (esperado, revisado por leitura). |
| `payflow-J8` | J8 — Segurança essencial | Login com senha (BCrypt, `{bcrypt}`) e **duas cadeias** do Spring Security 7: painel com sessão, CSRF e CSP; API `/api/v1` com JWT (HS256, 15 min). Papéis `USER`/`ADMIN` (bloquear/desbloquear contas), defesas contra injeção, XSS, CSRF e IDOR (matriz de testes), limite de tentativas (`429`), `SecurityAudit`, política de senha, segredos por ambiente, perfil `security-scan` (Dependency-Check) e mapa de dados da LGPD. 64 métodos de teste novos (esperado, revisado por leitura; os laboratórios foram executados). |

| `payflow-P3` | P3 — Comunicação síncrona e assíncrona | Dinheiro **síncrono**, reações **assíncronas**: **Outbox** (`outbox_events`, relé com `SKIP LOCKED`, *at-least-once*), eventos de transferência no **Kafka** (`payflow.transfers.v1`, chave = conta) e tarefas de notificação no **RabbitMQ** (DLQ), **consumidores idempotentes** (`processed_messages`, `ON CONFLICT` na mesma transação; `UNIQUE (request_id)`), **retry com *backoff* + DLT/DLQ** e runbook, **pagamento por QR code** (`payment_requests`, `PENDING→PAID\|EXPIRED`) confirmado por **webhook assinado** (HMAC dos bytes, janela de tempo, `eventId` único) em uma 3ª cadeia de segurança, **SSE** autenticado por conta com `Last-Event-ID`, *jobs* com **ShedLock**, executor `@Async` limitado, conciliação pedido × débitos e ADR 0015. **Escrito por leitura; não compilado nem executado no PayFlow** (laboratório `messaging-lab`, 47 testes, executado). |

> **Fim do nível Pleno:** o checkpoint de nível (`2-pleno/checkpoint-pleno.md`) **não cria tag nova**: ele avalia o repositório na tag **`payflow-P10`** (e as anteriores `payflow-P1` … `payflow-P9`). O item obrigatório dele que atravessa os módulos é a **conta de conexões** (checklist 2.9).

> **Depois da S1:** as migrações **V13–V17** estão **reservadas** (por leitura; a próxima livre é a **V18**). O contrato HTTP `/api/v1` **não muda** (novos *endpoints* aditivos: `GET /accounts/{id}/statement` com `X-Min-Seq`, `POST /payments`, `GET /p/{code}`).

> **Depois da S2:** a **V18** continua **livre** (a S2 não usou migração) e o contrato HTTP `/api/v1` **não muda**. Os **alvos de p99** em `docs/perf/orcamento.md` são **propostas** até o primeiro teste de carga real (S2.06; o SLO formal é da S4).

> **Depois da S3:** as migrações **V18–V24** (`V18`, `V19`, `V19_1`, `V20`–`V24`) estão **reservadas** (por leitura; a próxima livre é a **V25**) e o contrato HTTP `/api/v1` **não muda** (o extrato ganha **limite de data no SQL**). A **retenção de 5 anos é premissa** a validar com o jurídico; **todo número do PayFlow é "a medir"** (os do laboratório são de modelos).

> **Depois da S4:** **nenhuma migração** (a **V25** continua **livre**; V18–V24 seguem reservadas pela S3) e o contrato HTTP `/api/v1` **não muda**. A tag `payflow-S4` reúne **artefatos de operação** (SLOs e regras testadas, *runbooks*, processo de incidente, postmortem, catálogo de caos, continuidade, modelo de capacidade). **SLOs, RPO/RTO e severidades são propostas** a assinar com produto; **todo número do PayFlow é "a medir"** (os do laboratório são de modelos).

> **Depois da S5:** **uma migração: V25** (`audit_events`, **por leitura**; o DDL **foi executado** num PostgreSQL 18 descartável); a **V26** fica **livre** (V18–V24 seguem reservadas pela S3). O contrato HTTP `/api/v1` **não muda**. A tag `payflow-S5` reúne **controles e artefatos de segurança** (política, papéis, trilha, alertas, decisões de mTLS e de criptografia, pipeline, LGPD/PCI, revisão). **Papéis, políticas, SLAs e retenções são propostas** a validar com o jurídico/DPO, o adquirente (PCI) e produto; **o PAN não deve tocar o PayFlow**; **todo número do PayFlow é "a medir"** (os do laboratório são de modelos).

> **Depois da S6:** **nenhuma migração** (a **V26** continua **livre**; V18–V24 reservadas pela S3; V25 usada pela S5) e o contrato HTTP `/api/v1` **não muda**. A tag `payflow-S6` reúne **artefatos de arquitetura e custo** (revisão, estimativa, tags, orçamentos, *landing zone*, *runbook*); **nada foi aplicado em conta AWS**: os módulos Terraform passaram só no `validate`.
